CLASS: broken access control / AUTHORIZATION BYPASS BY REPRESENTATION SWITCHING — the same resource endpoint returns HTML (authorization-checked) or JSON (authorization NOT checked) depending on the `Accept` header; the JSON branch has no ACL at all, so a PRIVATE asset is returned in full to a caller who cannot read it in the HTML branch (CWE-863 / CWE-639).

  3. CHAIN: any authenticated low-privilege user (primitive: a normal account with a valid session cookie) -> request a private asset by its id with `Accept: application/json` instead of the browser's `text/html` (primitive: the representation is chosen by the request header, and the JSON branch has no authorization check) -> the full private picture/video/post is returned (escalation: authorization bypass — the ACL exists only on the HTML path) -> enumerate or guess asset ids for any user (impact: cross-user private media/content disclosure; program rated Medium 6.5). Per doctrine §8: preconditions = any authenticated account plus a private asset id; gain = the private asset's content.
TRANSFERABLE TEST: for every resource endpoint that returns HTML to a browser, replay the SAME request with `Accept: application/json` (then `application/xml`, `text/plain`, plus a `.json` / `?_format=json` suffix) using a session that does NOT own the object; a 200 carrying the full record where the HTML path 403s or redirects = the authorization check is bound to the representation, not the object. Rule: **the authorization check is often implemented in the view/template layer, not the object layer — toggle the representation (`Accept: application/json`, `.json`, `?_format=`) on a private resource and the ACL disappears.**

  4. THE CACHE RULE, verbatim: "Sadly the pages under https://www.glassdoor.com/Job were not being cached, but all the pages under https://www.glassdoor.com/Award/ were." (Discovered by testing a real `/Award/...` URL and observing it cached.)
  5. THE PARSER DISAGREEMENT, verbatim: "path traversal characters `/../`, also known as dot segments, were being normalized by the caching frontend server but not being normalized by the backend web application (Dissagreement of RFC 3986 5.2.4). This means for the path https://www.glassdoor.com/Job/../Award/blah?xss=</script it would be seen as https://www.glassdoor.com/Award/blah?xss=</script by the caching server and cached, but the contents for https://www.glassdoor.com/Job/../Award/blah would be returned by the webserver due to lack of normalization." The control test, verbatim: "The Award payload was NOT cached, meaning the frontend server's URL parser does normalize the dot segment before matching with the cache rule. The Job path, however, returned a 200, which means that the web server did NOT normalize the dot segment."
  6. THE POISON REQUEST, verbatim:
     GET /Job/../Award/RANDOMPATHTATDOESNOTEXIST?cachebuster=046&attack=VULN%3C/script%20 HTTP/2
     Host: www.glassdoor.com
     Cookie: optimizelyEndUserId=BRUH><svg/onload=a=self['aler'%2B't']%3Ba(document.domain)>
     (the `>` that closes `</script` arrives from the COOKIE, not the URL — the WAF only ever sees `</script%20`)
  7. THE STORED RESULT, verbatim: "when the victim will visit https://glassdoor.com/Award/RANDOMPATHTATDOESNOTEXIST?cachebuster=046&attack=VULN%3C/script%20, they will get the stored response with the XSS from the CDN."
  8. THE HEADER-ONLY VARIANT, verbatim: "Achieving a stored XSS was also possible using https://glassdoor.com/mz-survey/interview/collectQuestions_input.htm, which behaved very similarly to `/Job`, but the XSS was all in the headers and cookies, so sending a parameter in the URL was not necessary. Sending https://www.glassdoor.com/mz-survey/interview/collectQuestions_input.htm/../../../Award/blah with the XSS in the headers and cookies will result in a stored xss under https://www.glassdoor.com/Award/blah."
DETECTION SIGNAL: a page that reflects a URL parameter inside a `<script>` block AND reflects a cookie/header value adjacent to it; a WAF that blocks `</script>` only when followed by `>` (test `</script%20` and `</scriptx`); a path rule where one branch is cacheable and another is not (`X-Cache: hit` / `Cf-Cache-Status` on `/Award/*` but MISS on `/Job/*`); a front-end that normalises `/../` before matching a cache rule while the origin does not (or vice versa); a reflected cookie value that is attacker-settable (analytics/optimizely-style cookies).
CHAIN: any unauthenticated attacker -> the WAF blocks `</script>` in the URL (primitive) -> the payload is SPLIT: `</script%20` in the URL parameter and the closing `>` in a reflected cookie value (escalation: the WAF never sees the assembled payload) -> the self-XSS is real but needs the victim's cookie (primitive) -> the dot-segment path `/Job/../Award/<random>` is normalised by the FRONT-END (so it matches the `/Award/*` cache rule and is stored) but NOT by the ORIGIN (so the origin serves the `/Job/` reflection page with the payload) (escalation: the attacker chooses both the body and the cache key) -> the poisoned response is served to every visitor of the clean `/Award/<random>` URL (impact: stored XSS, no click, site-wide; program rated High). Per doctrine §8: preconditions = none (the victim only has to visit the poisoned URL); gain = script execution in the glassdoor.com origin for arbitrary visitors.
