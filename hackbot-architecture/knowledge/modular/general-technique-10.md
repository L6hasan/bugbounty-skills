§17.252 — A CACHE AND AN ORIGIN THAT DISAGREE ABOUT A DELIMITER OR ABOUT NORMALISATION HAND AN ATTACKER BOTH "WHAT IS STORED" AND "UNDER WHICH KEY": ENUMERATE THE ORIGIN'S DELIMITERS (`;` SPRING MATRIX VARIABLES, `.` RAILS FORMATTER EXTENSIONS, `%00` OPENLITESPEED TRUNCATION, ENCODED NEWLINE AFTER AN NGINX PREFIX REWRITE), LEARN WHO NORMALISES DOT-SEGMENTS AND ENCODINGS FIRST, THEN AIM THE DISCREPANCY AT A STATIC EXTENSION/DIRECTORY/FILE RULE (DECEPTION: THE CACHE STORES SOMEONE ELSE'S AUTHENTICATED RESPONSE AND YOU FETCH IT) OR AT THE CACHE KEY (POISONING: YOUR BODY ENDS UP ON A HOT URL) — AND "CACHE-WHAT-WHERE" TURNS A NON-BROWSER-EXPLOITABLE OPEN REDIRECT INTO CROSS-DOMAIN JAVASCRIPT ON `/main.js` (PortSwigger, "Gotta cache 'em all: bending the rules of web cache exploitation", Martin Doyhenard @PortSwiggerRes, published 8 August 2024, UPDATED 8 January 2026; read in full this pass — `curl` + desktop UA + local strip, 30,812 chars; the two technique names "Static Path Deception" and "Cache Key Confusion" come from the pass's sixth source, the DEF CON/BH preview, which was also opened; the diagram/table payloads are IMAGES in the published page and are NOT reproduced here). DETECTION, three request controls: (1) DELIMITER — take a non-cacheable request as R0 (`POST`, or `Cache-Control: no-store`/`private`), confirm `/homeabcd` == R0, then test `/home<CANDIDATE>abcd` == R0 (fuzz all ASCII, raw and encoded; cache side: `GET /static-endpoint<DELIMITER><Random>` against a proven cache hit). (2) DECODING — `/%68%6f%6d%65%2f%69%6e%64%65%78` vs `/home/index`: same body, not from cache ⇒ origin decodes before mapping; same cache headers ⇒ the KEY was decoded. (3) NORMALISATION — `/aaa/../home/index` (and `aaa\..\home/index`) vs `/home/index?cacheBuster`: identical ⇒ normalised before mapping; repeat on a cacheable resource and inspect `X-Cache`. EXPLOITS: static-extension rule `GET /<Dynamic_Resource><Delimiter><suffix>.css` (encoded `#` works where the raw one is dropped; stack encodings to target a specific proxy in a rewriting chain); static-DIRECTORY rule in both directions — front-end normalises, backend does not ⇒ `GET /<Dynamic_Resource><Delimiter><Encoded_Dot_Segment><Static_Directory>` (CloudFront/Azure/Imperva normalise before evaluating rules by default), backend normalises, front-end does not ⇒ `GET /<Static_Directory><Encoded_Dot_Segment><Dynamic_Resource>` (Cloudflare/Google Cloud/Fastly do not; Nginx/IIS/OpenLiteSpeed normalise before mapping; IIS + a cache that does not convert backslashes is a variant); static-FILE rule `GET /<Dynamic_Resource><Delimiter><Encoded_Dot_Segment><Static_File>`; KEY NORMALISATION (default on Azure and Imperva) ⇒ store a self-reflected XSS/404 body on a hot path with `GET /<Backend_Path><Path_Traversal><Poisoned_Path>`, or `<Backend_Path><Delimiter><...>` where the origin has a delimiter, or `<Poisoned_Path><Front-End_Delimiter><Path_Traversal><Backend_Path>` where the CACHE has one (the hash on Azure). CACHE-WHAT-WHERE: an `X-Forwarded-Host`-driven open redirect (`302 Location: http://evil.com/index.html`) is key-confused onto `/main.js` so every homepage visitor loads attacker JS; if the redirect carries `Cache-Control: public, max-age=3600` no extension is needed and it is arbitrary poisoning/defacement. DEFENCE a target may have: `no-store, private` on dynamic responses with cache rules NOT overriding it, un-normalised keys, and the post-delimiter suffix not forwarded. WHY IT IS A NEW GENERAL METHOD: `matrix variab`, `OpenLiteSpeed`, `formatter extension`, `static directory`, `Cache-What-Where`, `cache key confusion`, `Static Path Deception`, `hybrid caching`, `cache buster`, `rewrite /user` = 0 hits; the recorded `dot-segment` material is an OAuth `redirect_uri` prefix-check traversal (§17.195) and an nginx `alias` filesystem join, and the recorded `cache deception` entries (§8.8 wildcard `/share/*`+`%2F..%2F`; §12.4 cache deception + CSPT with a static extension rule) record neither the delimiter matrix, the normalisation-ORDER test, static directory/file rules, key normalisation nor Cache-What-Where. TRANSFERABLE TEST: fingerprint front-end vs origin → run the three controls → for each delimiter append a static-looking suffix and check whether an authenticated response is served to you out of the cache → if the key normalises, append `<dot-segment><payload>` and check whether the reflection is stored on the clean hot path. §17.253 — AN E-MAIL ADDRESS IS A STRING SEVERAL PARSERS DISAGREE ABOUT: THE APPLICATION VALIDATES ONE PARSE, THE MAILER DELIVERS BY ANOTHER, DISPLAY CODE MAY DECODE A THIRD — SO A VERIFIED ADDRESS ON A DOMAIN YOU DO NOT OWN DEFEATS EVERY "DOMAIN = AUTHORISATION" CHECK (IdP / Cloudflare Zero Trust / registration allow-lists / support-centre domains), AND MALFORMED PUNYCODE CAN TURN THE DISPLAYED ADDRESS INTO MARKUP (PortSwigger, "Splitting the email atom: exploiting parsers to bypass access controls", Gareth Heyes @garethheyes, published 7 August 2024, updated 27 June 2025; read in full this pass — `curl` + desktop UA + local strip, 44,827 chars; MANY payload strings (GitHub/GitLab splits, the Joomla `<style>` tag, the punycode subdomain chains) are IMAGES in the published page and are NOT reproduced — only the strings printed as text are quoted; the paper's UNICODE-OVERFLOW section is §17.247 and is deliberately not re-recorded). MAILER-SIDE REROUTING (Postfix/Sendmail): Sendmail 8.15.2 with UUCP syntax whose separator runs backwards and where a trailing backslash escapes the `@` — `oastify.com!collab\@example.com` is delivered to oastify.com (the author's first hit was the same shape with every local-part special `!#$%&'*+\/=?^_`{|}~-collab\@psres.net`); Postfix 3.6.4 source route + "percent hack" with a comment that removes the real domain — `collab%psres.net(@example.com` goes to psres.net; also `"psres.net!collab"(\"@example.com` (sent regardless of quoting) and `collab%psres.net@[127.0.0.1]` both deliver to collab@psres.net; ORCPT smuggling `"foo\\"@psres.net> ORCPT=test;admin"@example.com`. GROUND TRUTH: quoted local-parts and comments are RFC-valid — `"@"@example.com`, `"\\""@example.com`, `(foo)user@(bar)example.com`. ENCODED-WORD (RFC 2047) IS A DECODER STACK IN THE ADDRESS: `=?<charset>?q?=41=42=43?=` / `=?<charset>?b?<base64>?=`, Ruby's `Mail` gem (>508M downloads) decodes it in BOTH the local-part and the domain and also decodes UTF-7, layers compose (base64 whose charset is UTF-7 decodes twice), and in Q-encoding `_` is a space (`=20` too). PROBES: place an encoded `@` + collaborator domain inside an encoded-word local-part (short `x` charset where accepted, but prefer widely-accepted charsets) and watch the Collaborator `RCPT TO:` — a DECODED address proves the feature (common on Ruby sites). THE SPLIT: encode `@` (`=40`) and `>` (`=3e`) so the SMTP RCPT TO command ENDS at your `>`, then `=00` (NUL) plus a trailing valid local-part (`foo`) so the mailer discards the tail while the app's validation still accepts the whole string (GitHub, charset irrelevant) — the author verified microsoft.com, mozilla.com and github.com addresses from a GitHub account, and because GitHub is an IdP for Cloudflare Zero Trust (domain decides access) reached an internal network; where the stack needs it, use an encoded SPACE (`=20`, or `_`) with a real charset (`iso-8859-1`) — that shape opened GitLab Enterprise registration and, per a documented case study, GitLab web; Zendesk was cracked with DOUBLED encoded quotes plus `=3c22`, whose decoded `<` is REMOVED by the app, removing it completes the quote and satisfies validation, with `=3e=00` finishing RCPT TO (observed input `=?x?q?=41=42=43collab=40psres.net=3e=20?=@psres.net` → `RCPT TO:<"ABCcollab@psres.net> "@psres.net>`). MALFORMED PUNYCODE (PHP IDN/IdnaConvert) DECODES TO ARBITRARY ASCII: `psres.net.com.xn--0049.com.psres.net` → `psres.net.com.,.com.psres.net`, `foo@xn--0117.example.com` → `foo@@.example.com`, `x@xn--42` → `x@,`, `x@xn--694` → `x@;`, `x@xn--svg/-9x6` → `x@<svg/`; Joomla escaped the stored address and then a display path punycode-decoded it, so the `<` became live → single-subdomain constraint limits the opening tag to `<style>` → persistent style injection on the users page with NO activated account → two accounts (`{}` so the remainder parses as an invalid CSS selector; `@import` chaining to exfiltrate the super-admin CSRF token) → token replayed to edit a backend template with PHP = RCE (CVE-2024-21725, fixed 20 Feb 2024; library fixed 14 Feb 2024). METHODOLOGY: "Probe, Observe, Encode and Exploit" with Collaborator; Hackvertor tags `_unicode_overflow(0x100,…)`, `_unicode_overflow_variations(0xfff,…)`, `_encoded_word_encode/_decode`, `_email_utf7/_decode`, `_encode_word_meta('iso-8859-1',…)`; a Turbo Intruder script replaying every known splitter with a configurable sleep; a punycode fuzzer. DEFENCE: disable encoded-word or block `=[?].+[?]=`, validate even SSO-provided addresses, never authorise on the e-mail domain alone. TRANSFERABLE TEST: two encoded-word probes → SMTP `RCPT TO:` decode check; build the local split (`=40`+`=3e`+`=00`+`foo`, or `_`/`=20` + `iso-8859-1`) and see whether a verification mail for the target domain lands in your collaborator while the app still accepts the address; throw `xn--` fuzz labels at any display path; treat a successful domain spoof as access-control bypass, not "e-mail spoofing". §17.254 — THE SINGLE-PACKET ATTACK PLUS BOTTOM-QUARTILE SAMPLING TURNS "DID THE SERVER RESOLVE/CONNECT TO THAT HOSTNAME?" INTO A YES/NO ANSWER (DNS-CACHE DIFFERENTIAL, OR AN OVER-LONG 63-OCTET DNS LABEL) — THAT IS HOW SCOPED SSRF IS PROVEN WHEN OAST NEVER FIRES, AND THE PROVEN PROXY THEN YIELDS FIREWALL BYPASS, HIDDEN INTERNAL ROUTES AND FRONT-END IMPERSONATION (PortSwigger, "Listen to the whispers: web timing attacks that actually work", James Kettle @albinowax, published 7 August 2024, updated 18 November 2024; read in full this pass — `curl` + desktop UA + local strip, 44,578 chars; the response-time tables/diagrams are images, so only the millisecond values written in the text are quoted; validated on a 30,000-site corpus). MEASUREMENT: single-packet attack — `disable TCP_NODELAY`, send a ping frame per request, send the headers, withhold the final data frame, wait 100ms, send a ping frame, send the final frames — then compare the ORDER responses arrive in (the sacrificial ping makes the OS coalesce header frames and removes HTTP/2's sticky request-order bias with no per-target tuning; the Timeless Timing idea of padding dummy parameters is explicitly rejected as target-specific). SAMPLING: 30 measurements per variant, compare the BOTTOM QUARTILES (least noise) — distinct sets = a real difference, overlapping = noise; shorten the code path and reuse caches/objects/connections; raise signal with random inputs (defeat caching), slow resources and workload multiplication (`X-Uaa: a`/`X-Ubb: a`/`X-Ucc: a` …{256} amplifies a fixed-prefix header lookup), plus ReDoS/nested entities/hashtable collisions. FINDINGS THIS YIELDS: a header that costs time only when its value is INVALID (`commonconfig: {}` 50ms vs `commonconfig: x` 55ms vs `foo: x` 50ms); a header that leaks through a connection-resetting server (`authorization: x` 50ms vs `foo: x` 30ms before the reset); `GET /?id=random` 310ms vs `GET /?foo=random` 22ms ⇒ `id` is in the CACHE KEY (parameter-based cache-poisoning exposure, site-wide); SCOPED SSRF — `foo.example.com` 404/25ms vs `foo.bar.com` 403/20ms shows validation, then the PROOF is DNS caching (`abc.example.com` 25ms then 20ms) or, where failures are not cached, an over-long label that makes the DNS client refuse (`aaa{62}.example.com` 25ms vs `aaa{63}.example.com` 20ms); IP-spoofing headers (`True-Client-IP: xyz.example.com` → in-band DNS lookup, faster on repeat; an INVALID IP such as `x.psres.net` short-circuits a slow third-party geo-lookup = exceptions cut code paths, so timing detects them), `?objectId=57%23` 180ms vs `57%21` 430ms (blind server-side parameter pollution — most prolific probe), blind SQLi (`mic='` 162ms vs `mic=''` 170ms; 50 pairs per probe, report at ≥80% order bias) — but for SQLi/command/code injection timing only matters when a WAF blocks classic detection, so timing's home is the "injection underclass" (JSON/XML/CSV/params/headers). EXPLOITATION: after 'Detect scoped SSRF', compile hostnames (generic list + Project Sonar `fdns` reversed/sorted/`look`-searched + columbus.elmasy.com), request each directly and through the proxy and diff status/header names/`Location` ⇒ firewall bypass on the same host (`sonarqube.redacted.com` resets from outside but 200 through `app.redacted.com` with that `Host`), invisible internal/pre-prod systems and admin consoles, front-end rule bypass, and FRONT-END IMPERSONATION — the back-end trusts headers the front-end overwrites (`X-Forwarded-For`, custom auth headers; the author fully compromised New Relic's core internal API with `Service-Gateway-Is-Newrelic-Admin`), and a misconfigured proxy is the route that dodges the overwrite; upgrade scoped→full SSRF by taking over a subdomain and pointing its DNS at an arbitrary IP. WHY IT IS A NEW GENERAL METHOD: `timing attack`, `scoped SSRF`, `front-end impersonation`, `True-Client-IP`, `64-octet`, `DNS caching`, `nowafpls`, `bottom quartile`, `h2spacex` = 0 hits; recorded `single-packet`/`Timeless` hits are the race-condition/smuggling and HEIST cross-site search material, recorded `timing oracle` hits are generic blind-SQLi and the `%<N>c` format-string oracle (§17.206), and recorded `reverse proxy`/`vhost` hits are smuggling, GlobalProtect and nginx mTLS — none is the proxy-as-route or the timing oracle above. TRANSFERABLE TEST: build the single-packet pair and compare ORDER, 30 samples, bottom quartile → ask the `Host` question of every candidate (`<random>` twice; 63-octet label) and treat "second request faster"/"long label faster" as proof of a scoped SSRF → enumerate the proxy's reachable hosts by diffing direct vs proxied responses → replay the front-end's trust headers on each alternate route to become the front-end. §17.258 — A SIGNED TOKEN IS ONLY AS STRONG AS THE SECRET YOU CAN GUESS WITH THE FRAMEWORK'S OWN DERIVATION: RE-SIGN YOUR OWN TOKEN WITH A DEFAULT KEY *BEFORE* YOU OWN THE SECRET (ACCEPTANCE IS THE FINDING), THEN AIM THE IDENTITY CLAIM AT USER 1 AND MINT A SAME-KEY OIDC `access_token` WHOSE `picture` CLAIM THE SERVER FETCHES (PortSwigger, "Introducing SignSaboteur: forge signed web tokens with ease", Zakhar Fedotkin @zakfedotkin, published 22 May 2024, updated 4 June 2024; read in full this pass — `curl` + desktop UA + local strip, 13,759 chars; the tool is the open-source Burp BApp `SignSaboteur` with a self-hosted lab in the linked repo; the demo GIF is an image and is not reproduced). THE POST'S OWN METHODOLOGY, in order: "Observe request/response cookie, url, body parameters for potential signed tokens: base64 encoded or hex strings of known length common for HMAC"; if the token "contains a timestamp, observe whether the signature changes when the token expires"; "Try to identify any frameworks the target is using"; search "for common secret keys and salts, for example hardcoded values or configuration files, including docker environment variables"; "Update your wordlists with found information"; "Try to brute force the token with different derivation techniques". THE DERIVATION LADDER IS THE METHOD (SignSaboteur's brute-force strategies, quoted): `Known keys` (previously found secrets only), `Fast` ("the default hashing algorithm and key derivation"), `Balanced` ("all known key derivation techniques, except slow PBKDF2 Hmac with a big number of iterations"), `Deep` ("all key derivation techniques, including different types supported by Ruby on Rails framework") — and "JSON encoded strings are supported too, so you can include even non ASCII secrets keys". ### [Bugbountyskills.md] 17.277 A MITIGATION's own bound check is off by one against the SCALED index it guards — the single admitted boundary value indexes one past the fixed-size match vector, and the leaked slot becomes a string LENGTH field (Adobe Flash Player RegExp `ovector[99]`, CVE-2015-0330 / apsb15-04, HackerOne #47012) — extends 17.107

SOURCE: https://hackerone.com/reports/47012  2026-11-08
STATUS: UNVERIFIED (not reproduced — Flash Player EOL 2020-12-31; PoC a private attachment; the public body states the trigger, the arithmetic and the escalation)
CLASS: off-by-one in a mitigation's own bounds check over a FIXED-SIZE match vector → stack out-of-bounds read → the leaked slot is used as a string LENGTH field → fake-length string = arbitrary memory read → ASLR defeat / code execution in the host process (memory-corruption depth LAB-ONLY; the reusable part is the audit rule, not the CVE)
CORE METHOD:
  1. The engine stores match results in a FIXED-SIZE array on the STACK — `int ovector[99]` in Flash's RegExp matcher.
  2. A NAMED capture group is resolved through an index derived from the pattern itself: `nameIndex` = the number of left brackets in the regex, i.e. fully attacker-controlled; the substring is built as `start = target + ovector[nameIndex*2]` and `length = ovector[nameIndex*2+1] - ovector[nameIndex*2]`.
  3. The mitigation added for exactly this containment is the bug: "Flash took mitigations where it checks if the nameIndex is larger than 49, ignoring the fact that nameIndex can be 49 itself" → the guard is written against the RAW index while the dereference uses the DOUBLED index, so the one admitted boundary value gives `49*2+1 = 99`, one element past a 99-element array.
  4. The leaked slot is not random: it "points to the saved EIP under windows and it is a very large value for length field" → "returning a string with a fake length field with enormous value to the AS3 interface".
  5. Escalation (reporter): that string is an arbitrary-read primitive — "Advanced Heap Fengshui techniques may even allow an attacker build workable exploit via such string to access arbitrary memory"; summary-level impact "defeat ASLR protection or even execute arbitrary code in the context of affected application".
DETECTION SIGNAL: a fixed-size match/result vector of length `N` whose bound check compares the RAW loop index while the dereference is SCALED (`i*2`, `i*2+1`, `i*stride`) — do the arithmetic (guard constant × scale vs `N`) instead of just confirming a check exists; a count or index taken from attacker-controlled SYNTAX (capture groups, numbered back-references, nesting/recursion depth, `%`-specifiers, column counts) used to index that vector; an engine returning a string/array whose reported LENGTH is implausible for the input — the info-leak tell, no crash required.
CHAIN: attacker pattern with the maximum capture count the guard ADMITS (primitive: `> 49` admits 49) → `ovector[99]`, one past the on-stack vector (primitive: stack OOB read; on Windows the saved return address) → that value becomes a string's LENGTH field (primitive: fake-length string surfaced to script) → arbitrary memory READ (impact: ASLR defeat / address disclosure in the host application) → heap grooming steers the string at chosen memory → code execution (reporter's escalation; recorded as primitive + documented escalation, same bar as §17.107).
TRANSFERABLE TEST: for any reachable pattern/query engine (regex in a WAF · IDS · log parser · JS engine · email or search filter · template expression · format-string parser): (1) find the fixed-size match vector and its size `N`; (2) read the guard and check its ARITHMETIC against the indexed expression — `i*2`, `i*2+1` or `i*stride` versus a constant compared to `i`; (3) submit input that fills exactly the MAXIMUM number of counted elements the guard admits (the boundary value, not max+1) and look for one element read past the vector. ## [Bugbountyskills.md] V-19: Guard-layer bypass by path shape, judged by the error-code LAYER

**Also known as:** matrix-parameter guard bypass; security-layer skip; captcha-filter bypass by path suffix.
**Mechanism:** a captcha / bot / WAF / ACL layer that matches the request PATH literally is not applied when
the path carries a servlet matrix-parameter suffix (or another equivalent shape) — the request still routes
to the same handler, so the guarded lookup executes unfiltered. The proof is not the status code but the
ERROR-CODE LAYER: the canonical path answers with the guard's own code (`OB_SEC_*`, "captcha validation
failed", "true client IP required"); the suffixed path answers with the business layer's code ("missing or
incorrect parameters"). Violated assumption: "the guard protects the handler."
**Preconditions:** any endpoint behind a path-matched captcha/WAF/ACL/IP-allowlist layer; highest value on
lookup/eligibility/dedupe/PII endpoints.
**Detect:** send the CANONICAL request first (control) and record the guard's code; then re-send with each
of `;` `%3B` `;.json` `;%20` `/;` `..;/` `;foo=bar` `%23` `;.css`; diff the code VALUE and the code FAMILY.
Then supply real values and read the response.
**Proof of concept:** `guard_suffix_bypass.sh <URL> [METHOD] [BODY]` (canonical row = control; per-suffix
HTTP/bytes/code layer). Corpus: DBS SG onboarding `…/byob/onboarding/dedupe;` → NRIC + DOB returned the
applicant's address, mobile and email, unauthenticated, one record (minimum extraction).
**Chain it with:** `info-disclosure-testing` (the guarded lookup is usually a PII oracle), `bac-idor-testing`
(guard-skipped routes often skip ownership too).
**Do not report:** a code-family change with no data or state change proves a filter-design weakness only —
land the data read first.

## [Bugbountyskills.md] V-20: `/public/` unauthenticated API surface + two-step identifier chaining

**Also known as:** declared no-auth API contract; metadata→identifier→document chain.
**Mechanism:** routes under `/public/`, `/open/`, `/external/`, `/pub/`, `/unauth/`, `/api/v1/public/` are
designed to be called without a session; the first endpoint's response then leaks the identifier the second
endpoint requires, so metadata disclosure escalates to a document/PII read. Two paid reports: an order
address reader (`/public/api/order/{uuid}/address`) and a chain where `…/my-mailings/get/{uuid}` returned the
`userUuid` that `…/mailing/{userUuid}/{mailingUuid}/preview.pdf` needed.
**Preconditions:** an app with such markers; an id-bearing object model.
**Detect:** enumerate the markers before authenticated testing; mine every 2xx body for `uuid`, `userUuid`,
`applicationId`, `customerNo`, `custNo`, `valGenID`; feed each to the reader endpoints.
**Proof of concept:** `curl` the marker route → capture the identifier → call the dependent reader; state
where the identifier came from (a UUID is not guessable — "needs an id" is not a finding).
**Chain it with:** `bac-idor-testing` (ownership on the reader), `info-disclosure-testing`.
