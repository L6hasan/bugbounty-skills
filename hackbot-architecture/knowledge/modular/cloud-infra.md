**Confirm:** A fresh server-side read shows the terminal/advanced state while step 2's
own record (audit row, sub-resource, downstream precondition) shows it never ran — plus
a downstream gated action now succeeds (withdraw without KYC, ship without payment).

**False positives:** Endpoints that no-op when unready (re-read state — it did *not*
advance); flows where step 2 is genuinely optional; async pipelines that revert the
status you "skipped to" on the next queue drain (poll before claiming); test tenants
with checks disabled; soft-200 error bodies (`200 {"error":"state invalid"}` is a
rejection, not a skip).

**Impact:** "The `<flow>` state machine is enforced only in the UI; a user can reach
`<terminal state / gated action>` without completing `<prerequisite step>`." Name the
gated action — the skip matters only for what it unlocks.

**Remediation:** Encode allowed transitions in one server-side table
(`from_state → to_state` + precondition checks) applied at every mutating endpoint,
default-denying any transition whose precondition row is absent.

**CWE / OWASP:** CWE-841 (Improper Enforcement of Behavioral Workflow) / CWE-372

## [Bugbountyskills.md] V-03: Cloud infrastructure takeover via metadata API instance extraction

**Mechanism:** Cloud instances expose a link-local metadata service (AWS
`169.254.169.254`, GCP `metadata.google.internal`/`169.254.169.254` +
`Metadata-Flavor: Google` header, Azure `169.254.169.254/metadata` +

to use. IMDSv2 adds a PUT-token session (`X-aws-ec2-metadata-token-ttl-seconds`)

(gopher-style, V-05) or to environments where IMDSv2 is still optional.

**Preconditions:**
- App runs on AWS/GCP/Azure/Alibaba/etc. (or Kubernetes with cluster IP)
- Egress to link-local/metadata not blocked (no `169.254.169.254` deny rule)
- IMDSv1 allowed (AWS) *or* SSRF supports PUT + custom headers for the v2 token
- Required headers reachable: GCP/Azure need `Metadata-Flavor`/`Metadata`
  (absence still yields 400/403 = reachability signal)

1. **Guardrail first: prove by identifying the role/instance — never dump

### [Bugbountyskills.md] 17.194 An ATOMIC FILE REPLACE installs the TEMP file's permissions instead of the DESTINATION's — the object is correct but its metadata is not, so a secret store widens to the umask default and becomes readable by another local principal (curl cookie/alt-svc/HSTS jars, CVE-2022-32207, HackerOne #1614331)

SOURCE: https://hackerone.com/reports/1614331 — Internet Bug Bounty, "CVE-2022-32207: Unpreserved file permissions" (Medium, fixed in curl 7.84.0)  read 2026-11-08 (`visibility: full`, whole body via `curl .../1614331.json`).
CLASS: metadata loss on an atomic write (permission widening on a secret file -> local information disclosure -> session/credential theft chain).
CORE METHOD: (1) "When curl saves cookies, alt-svc and hsts data to local files, it makes the operation atomic by finalizing the operation with a rename from a temporary name to the final target file name." (2) "In that rename operation, it might accidentally widen the permissions for the target file, leaving the updated file accessible to more users than intended." (3) The write is therefore correct in CONTENT and wrong in MODE: the temp file was created at umask-default permissions and the rename installs them over a store that used to be 0600. Impact as stated: "Information disclosure (cookie file in specific)."
DETECTION SIGNAL: any save/update path pairing a PRE-EXISTING secret file (cookie jar, `--hsts`/`--alt-svc` store, token/credential cache, `known_hosts`, kube config, `.pgpass`, config holding an API key) with a temp-file+`rename()` finaliser; on a server, an export/backup/config writer that atomically replaces a 0600 file. Probe: `stat -c '%a'` the file before and after the app rewrites it — the tell is the mode becoming the umask default (0644 under 022). Owner/group can be lost the same way.
CHAIN: a second, lower-privileged principal on the same host (another service account, a shared group directory, a co-tenant) (primitive: read access as a different user) -> the atomic replace widens the secret store to world-readable (primitive: destination metadata not carried across the rename) -> live session cookies / tokens are read and replayed (session hijack / account takeover; sensitive info disclosure with PoC).
TRANSFERABLE TEST: create the secret file at the tightest expected mode (`chmod 600 cj.txt`), let the application rewrite that SAME path, then `stat -c '%a' cj.txt`; repeat under `umask 000` and with a root-owned target to expose owner/group loss. Rule: **an atomic-replace save must carry over the DESTINATION's mode and owner — a rename silently installs the temp file's metadata.**
REPRO/METER: MEASURED NEGATIVE on this host's curl 8.5.0 (post-fix) — 0600 cookie/alt-svc/HSTS files stayed 0600 after curl rewrote them, including under `umask 000` (details in /root/bugbountyhuntingskills.md).
WHY IT IS A NEW GENERAL METHOD: §17.191(a) is the case where the cleanup acts on the wrong OBJECT (identity wrong); here the object is the right one and its METADATA is wrong — a distinct failure of the same "state captured before finalisation" family, and one that turns a *correct* write into a disclosure. Reusable rule: **on every atomic write, verify which file's METADATA survives the rename; a secret file's mode and owner are part of its contents.** Slot 17.194.
