STATUS: UNVERIFIED (not reproduced)
CLASS: config/code injection → INTERNAL FILE READ SERVED OVER THE SAME PROXY → cluster-credential theft → privilege escalation. The injected directive is a FILE-SERVING directive (`alias`), not a code directive (`content_by_lua_block`) and not a log-write (`access_log`): the `path` field breaks out of the generated `location` and mounts the pod's `serviceaccount/` directory as web content (CWE-94 → CWE-22 → CWE-522).
CORE METHOD (reporter's steps, verbatim structure):
  1. Precondition: a user with `get, create, update` on `networking.k8s.io/ingresses` in ONE namespace — the report ships the `ingress-creator` Role + RoleBinding YAML verbatim; the reporter states "this user cannot list secrets at all" (no cluster role, no secret read).

  3. Why it works — reporter, verbatim: "When a user creates an ingress resource, the new configuration is updated in the /etc/nginx/nginx.conf file in the ingress-nginx-controller pod … I caused a 'config file injection' using the following payload as path". `{`/`}` break out of the generated `location`; `alias` maps a URL prefix onto the pod's filesystem; the trailing `location ~* ^/aaa` keeps the generated config syntactically valid so nginx loads it.
  4.   5. Decode the token to confirm it belongs to `ingress-nginx`; that ServiceAccount is bound to a ClusterRole that can "list secrets is all namespaces (cluster wide)".
  6. Reporter's impact statement, verbatim: "A user with the permissions to create an ingress resource can obtain the ingress-nginx service account token which can list secrets is all namespaces (cluster wide)."
DETECTION SIGNAL: any generated-config proxy/ingress where a user-settable string (`path`, `host`, `server_name`, annotation, CRD field) reaches the rendered config — the tell is that `{`, `}` and newlines SURVIVE into `/etc/nginx/nginx.conf` (`kubectl exec <controller> -- cat /etc/nginx/nginx.conf` after a probe object). Bootstrap probe: submit a path (or host/annotation) containing `{return 200 "MARKER";}` and request it — MARKER in the response proves the field is unfiltered.
CHAIN: namespaced Ingress write with NO cluster role (primitive: create one object) → the `path` value is spliced raw into `nginx.conf`, so `}` + `alias /var/run/secrets/kubernetes.io/serviceaccount/;` defines a location that STATICALLY SERVES that directory (primitive: config injection → internal file read) → one GET `/gaf/token` returns the controller's ServiceAccount JWT (High 7.6) → that SA is ClusterRole-bound to list Secrets in ALL namespaces (primitive: cluster-wide credential) → every namespace's Secrets/ConfigMaps. The escalation needs NO code execution and NO file write: the injected directive serves ONE attacker-chosen file, and that file happens to be a cluster credential.
TRANSFERABLE TEST: on ingress-nginx (pre-2021-10, before the 25745 path fix) or any templated reverse proxy you can create objects on, push the block-breakout into the PATH/host/annotation surface — `/probe{alias /etc/;}` for the read, `{return 200 "MARKER";}` first to prove breakout — then `curl https://<host>/probe/passwd` and `…/probe/var/run/secrets/kubernetes.io/serviceaccount/token`. A file body or directory index served out of the pod's filesystem is the finding; the operator's own token is the impact. Rule: **`alias`/`root`/`autoindex` turn config injection into arbitrary internal file read — you do not need code injection, you need the pod's credential files to be servable.** Where the vendor has already patched `alias` in the SNIPPET annotation (§17.172/§17.178/§17.179), test the PATH field and every other user-settable string that lands in the same config file.
