§17.279 — Cloud-storage enumeration is an EXTRACTION problem first, and tool fidelity decides whether an H2 desync probe is a test or a no-op (LIVE-VERIFIED 2026-11-13, norma pass97)
SOURCE: live hunt (NORMA) — 438-file corpus storage extraction + raw-h2 desync indicators against www.norma24.de (Akamai), kvmmaap.norma24.de (origin ELB), www.norma-connect.de (Varnish).
CORE METHOD (live-verified):
  1. Bucket hunting without a corpus is name-guessing and mostly touches assets outside the program's scope. Extract the storage references from what the TARGET ITSELF loads (all shipped JS + every page), then test the posture of exactly those. On a mature estate this collapses to almost nothing — here: 438 files -> ONE endpoint, a third-party widget bucket. State that plainly instead of padding the class.
  2. Posture test that stays read-only: bucket root in BOTH path-style and virtual-host style (403 AccessDenied = no listing; ListBucketResult = world-listable, an immediate finding), a known-good object (must 200, else your key shape is wrong), and a non-existent object (403 vs 404 tells you whether the bucket leaks an existence oracle). Writability CANNOT be proven without a write — say "unproven", never "writable".
  3. H2 desync probes: H2.CL (declared Content-Length != DATA length) and H2.TE (a `transfer-encoding` header inside an HTTP/2 request, illegal per RFC 9113 8.2.2) are the two single-request indicators. A compliant front rejects both (400 / RST_STREAM PROTOCOL_ERROR); accepting-and-processing them is a PRECONDITION, not a desync.
  4. TOOL FIDELITY IS PART OF THE RESULT: libcurl SILENTLY DROPS `Transfer-Encoding` on h2 — a run using `curl --http2 -H 'Transfer-Encoding: chunked'` produces ZERO requests containing the header and its "200 OK" rows are VOID, not clean. Always dump the headers actually SENT (`curl -v` and read the `>` lines, or `conn.send_headers` in a raw client) before interpreting any H2 header-level probe — same standard as the earlier lesson that a WAF 403 is a blocked probe, not a negative.
  5. Run a CONTROL POST on every host before trusting the probe rows: if the well-formed request itself GOAWAYs or times out, that host's illegal-header row is INCONCLUSIVE (never write it down as a negative). Here the control POST passed on the origin ELB (302) and failed on Akamai/Varnish — which is exactly why only one host's H2.TE row is citable.
  6. Raw client setup when the interpreters are locked: `python3 -m venv <scratch>/h2env && <venv>/bin/pip install h2` (PEP 668 refuses the system install), then ALPN `["h2"]` + h2.connection; `nghttp/h2load/h2spec` are usually absent.
TRANSFERABLE TEST: for any "is this front desync-prone" question — (a) extract storage refs from the target's own bundles before bucket-guessing; (b) prove the client actually transmits the header under test; (c) require a passing CONTROL POST on each host; (d) treat illegal-header tolerance as a PRECONDITION, and never run the two-request poisoning sequence on a production shared cache (hazardous; forbidden by non-destructive scopes).

§17.280 — Browser-extension cookie-exposure pattern, and how an API's ORIGIN GATE doubles as its CSRF defence (LIVE-READ 2026-11-14, phantombuster)
SOURCE: PhantomBuster staging (Yogosha) — extension CRX v1.3.10 + api-staging.phantombuster.io, read-only.
CORE METHOD:
  1. An MV3 extension that carries the `cookies` permission and injects a content script on WILDCARD host matches is a cookie-exposure primitive when the page->extension channel is a same-page event the page can forge: here the content script listens for a custom DOM event (`PB_APP_MESSAGE`) on window, `FETCH_COOKIES` is forwarded to the background, the background calls `chrome.cookies.getAll({})`, and the content script posts the cookies back with `window.postMessage(e, "*")`. Custom DOM events carry NO origin, so any script in the page (including a third-party tag or an XSS payload) can ask for and receive the user's platform session cookies.
  2. GRADE IT BY THE HOST MATCHES, not by the primitive: the impact exists only where an attacker can run script. If the content script matches only hosts the program EXCLUDES (here `*.phantombuster.com`, explicitly out of scope), the finding is a CHAIN PRIMITIVE needing a same-domain XSS/HTML-injection — and if that same-domain injection is already on the program's known list, the whole chain is dead. Read `manifest.json` content_scripts/host_permissions BEFORE writing anything.
  3. Also read the BACKGROUND's message handler: `chrome.runtime.onMessage` is only reachable from the extension's own contexts (no `externally_connectable` = no web-page access), so "no sender validation" is a weak observation by itself. Check for `onMessageExternal` and for privileged actions (cookie harvest, API proxying with the user's session, tab navigation) before calling it exploitable.
  4. API ORIGIN GATE = CSRF DEFENCE: probe the same endpoint with NO Origin and with a foreign Origin. `403 Access Forbidden` for both + `200` for the app's own Origin proves the API rejects cross-site callers -> cross-site CSRF/state-changing attacks are blocked, and any same-origin-only primitive (XSS) becomes the requirement for abuse. Record it as a measured defence, not as a misconfiguration.
  5. ANONYMOUS SESSION MINTING is not a bypass: an endpoint that returns a fresh `{"sessionId":"..."}` per unauthenticated call (visitor tracking) must be tested as a CREDENTIAL before it means anything — send it back in every plausible carrier (?key=, the vendor's API-key header, and the cookie names the bundle references) and compare against a protected endpoint. All 401 = harmless; a 200 on any protected route = auth bypass (P1). Keep it as a FIXATION primitive if login may adopt a client-supplied session id.

§17.778 — Path-shape suffix skips a PATH-matched security layer while the handler still runs (error-code LAYER as the proof)

SOURCE: operator corpus — DBS SG card onboarding, `POST /personal/hoapgw/oc/gateway/api/sg/v1/byob/onboarding/dedupe` (paid). Canonical path → `OB_SEC_20003` "True client IP address is required for captcha validation" (400) / with a dummy token → `OB_SEC_20001` "Captcha validation failed" (422); the identical request with a trailing `;` (servlet matrix parameter) → `OB-KYC-10001` "Missing or incorrect parameters" (400) — i.e. the captcha filter never fired and the BUSINESS handler ran. With a real NRIC + DOB that bypassed endpoint returned the applicant's full residential address, mobile and email (200).
CLASS: filter/guard bypass (Improper Access Control / CWE-284) — a SECURITY LAYER that matches the request path literally is skipped by a path-shape suffix, proved by the error code moving from the security layer to the business layer.
CORE METHOD: (1) issue the CANONICAL request first and record the guard's own error code (a security-layer code); (2) re-issue with each path suffix in order — `;`, `%3B`, `;.json`, `;%20`, `/;`, `..;/`, `;foo=bar`, `%23`, `;.css`; (3) read the CODE LAYER, not the status: a business-layer code (validation/parameter error) means the request reached the handler with the filter skipped; (4) then supply real values.
DETECTION SIGNAL: two DIFFERENT error-code families on the same route — one name-spaced for captcha/WAF/rate/security (`OB_SEC_*`, "captcha validation failed", "true client IP required") and one for business validation (`OB-KYC-*`, "missing or incorrect parameters"). That divergence alone is the bypass proof; the PII read is the impact proof.
CHAIN: guard-skipped lookups (dedupe / existence / eligibility / pre-check / quote) are exactly where PII oracles live → the bypass converts a protected lookup into an anonymous PII oracle keyed on widely-shared identifiers (NRIC + DOB; mobile; last-4).
TRANSFERABLE TEST: for EVERY route protected by a captcha/bot/WAF/ACL layer, run the suffix ladder and diff the error CODE, before any payload work. Rule: **a guard that matches the PATH is not a guard on the HANDLER — the handler is reachable by any path shape that still routes, and the error-code layer tells you which one you reached.** (Corpus report also states the extraction discipline: one third-party record, read-only.)
AUTOMATE: `web-vulnerability-hunting/scripts/guard_suffix_bypass.sh <URL> [METHOD] [BODY]` — canonical row = control; prints HTTP/bytes/code-layer per suffix.

§17.779 — Pattern-query (LIKE) oracle on an identity field: one non-secret key returns MANY records

SOURCE: operator corpus — DBS India card-servicing portal `validate-card-details` (paid). ### [bugbountyhuntingskills.md] §17.789 — TEMPLATE POISONING BY AN ACCEPTED WRITE PRIMITIVE INTO THE COMPILED-TEMPLATE DIRECTORY: THE FILTER GUARDS THE CREATE PATH, THE COMPILER READS THE DISK — SO ANY ALLOWED FILE-WRITE (a document API that saves, an archive extraction, an asset upload) OVERWRITES ANOTHER PAGE'S TEMPLATE AND THE VICTIM'S FIRST RENDER COMPILES YOUR CODE (the record survives deletion)
