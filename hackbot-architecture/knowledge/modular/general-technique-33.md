SOURCE: https://hackerone.com/reports/4129950 (curl, "IDN decoding inserts authority delimiters and can redirect proxy CONNECT to a different host"; reporter zefanxu; submitted 2026-10-20, High 7~8.9, Weakness: SSRF, disclosed 2026-10-21)  2026-11-12

STATUS: UNVERIFIED (not reproduced — no curl/libidn2 build exercised this pass; the code locations and quotes are verbatim from the report body).
CLASS: SSRF via URL/authority parser differential — IDN decode output is never re-validated, so a pre-decode-safe character decodes INTO a structural delimiter and the proxy connects to a different host than the one checked.
CORE METHOD:
  1. THE PAYLOAD CHARACTER (report verbatim): "libcurl's IDN decoder accepts a hostname containing U+FF20 FULLWIDTH COMMERCIAL AT (`＠`). libidn2's TR46 transitional fallback converts it to ASCII `@`. `Curl_idn_decode()` only checks that the result is non-empty" — a check that runs BEFORE decode sees no `@`, so the name passes every authority check.
  2. THE DECAY (verbatim): "`curl_url_get(..., CURLU_PUNYCODE)` returns a URL that reparses to a different host and userinfo" — "This is an internal round-trip inconsistency in libcurl, not merely a browser-versus-curl disagreement."
  3. THE SSRF LEG (verbatim): "Through an HTTP proxy, curl sends the decoded host in the request target. A proxy using generic URL/authority parsing sees a different host than the URL's apparent host." (the non-tunneling proxy path fails with `CURLE_OUT_OF_MEMORY` because the decoded host cannot be stored with `CURLUPART_HOST`).
  4. ROOT CAUSE (verbatim locations): `lib/idn.c:314` `Curl_idn_decode()` only rejects an empty result at `lib/idn.c:329`; `lib/peer.c:215` stores the decoded host directly; `lib/urlapi.c:1638` concatenates the decoded host into the serialized URL; `lib/http_proxy.c:213` builds the CONNECT authority from the decoded host. "The URL parser already has an `invalid_host_char` table at `lib/urlapi.c:446` that rejects `@`, `/`, `:`, `?`, `#`, `[`, `]`, and other delimiters. The decoder does not apply that validation to its output."
  5. TESTED VERSIONS (verbatim): curl 8.23.0, curl master `eb2b201a2` (8.23.1-DEV), and system curl 7.68.0 — all with libidn2 2.2.0.
DETECTION SIGNAL: any URL/hostname consumer that normalizes (IDN/TR46/NFKC) AFTER its delimiter/authority validation; a proxy/forward layer that parses the request authority independently of the client's URL parser; the cheap oracle: round-trip failure — serialize the normalized form, re-parse it, and diff host/userinfo/path.
CHAIN: attacker supplies a hostname containing compatibility characters (primitive: input accepted pre-decode) -> TR46 transitional decode turns `＠` into `@` -> the serialized authority reparses to attacker-controlled host + userinfo -> the allowlist/validator judged the pre-decode name -> the proxy's CONNECT goes to the decoded host (SSRF / proxy-level reach past the intended host check).
TRANSFERABLE TEST: for every URL/hostname consumer on the target: (1) fuzz with compatibility characters that map to structural delimiters — U+FF20 `＠`→`@`, U+FF1A `：`→`:`, U+FF0F `／`→`/`, U+FF1F `？`→`?`, U+FF03 `＃`→`#`, U+FF0E `．`→`.`, U+3002 `。`→`.` — in host, userinfo and path positions; (2) enforce a ROUND-TRIP invariant everywhere: normalize/decode -> serialize -> re-parse -> compare components; any difference is a live parser differential; (3) re-run the delimiter table (`invalid_host_char`-style) against the DECODED output, not the input. Rule: **validation must run on the decoded form — a check before normalization is a check of a different string than the one that connects; and anything that fails a round-trip is lying to one of its parsers.**
WHY IT IS A NEW GENERAL METHOD (A/B + §17.690): 0 hits across the three write targets for `4129950`, `FF20`, `U+FF20`, `CURLU_PUNYCODE`, `TR46`, `libidn2`. Recorded IDN/punycode and authority-confusion material REVIEWED and delta'd: ledger ~7740-7742 (malformed `xn--` PUNYCODE mis-decoded by a PHP IdnaConvert library INTO arbitrary ASCII -> HTML/CSS injection — a wrong-decode bug in a different library, mail/CSS carrier); ~2442 (`<allowed>@<evil>` userinfo confusion in ASCII — no decode step); §17.213 (NAT64 embedded-IPv4 byte-offset differential — different encoding family, same "two parsers disagree" spirit).
