CLASS: cross-user stored/reflected XSS delivered through a realtime JSONP push channel — broken access control on the caller-supplied channel name (authorization failure) + unescaped reflection into an executable JS string.
CORE METHOD:
  1. CLASS: SQL injection (ORM annotation-alias injection) — INCOMPLETE-FILTER BYPASS via PostgreSQL dollar-quoting.
CORE METHOD:
  1. The sink is the same one as §7.5: a user-controlled FILTERED-RELATION ALIAS passed as `annotate(**{user_data: FilteredRelation("editor")})` and then re-referenced by `.select_related(user_data)`. CLASS: unauthenticated FULL-READ SSRF via an inbound third-party webhook attachment fetch.
CORE METHOD:
  1. THE ENTRY POINT: `POST /api/v1/livechat/sms-incoming/:service` (only `twilio` is accepted), registered in `apps/meteor/app/livechat/imports/server/rest/sms.ts` as `API.v1.addRoute('livechat/sms-incoming/:service', { async post() {...} })` — the route options contain NO `authRequired`, so the endpoint is UNAUTHENTICATED (matching the report title).
  2. Twilio's inbound-MMS webhook POSTs a form body whose media fields are `MediaUrl0`, `MediaUrl1`, … (Twilio's own docs). The handler does `const sms = SMSService.parse(this.bodyParams)` then `const [media] = sms?.media || []` -> `const { url: smsUrl, contentType } = media`.
  3. THE SINK, verbatim (pre-fix): `const getUploadFile = async (details, fileUrl) => { const response = await fetch(fileUrl); const content = Buffer.from(await response.arrayBuffer()); … return fileStore.insert({ ...details, size: contentSize }, content); }` — `fileUrl` is the attacker's `MediaUrl0` and there is NO validation of it at all.
  4. THE READ-BACK (why it is FULL-READ, not blind): the fetched bytes are stored with `FileUpload.getStore('Uploads').insert(...)`, and the stored path is returned into the chat as the attachment (`const fileUrl = FileUpload.getPath(`${file._id}/${encodeURI(file.name || 'file')}`)` -> `title_link` / `image_url`). The attacker therefore receives the CONTENT of whatever internal URL he named.
  5. THE FIX, verbatim: `const isSsrfSafe = await checkUrlForSsrf(fileUrl); if (!isSsrfSafe) { throw new Meteor.Error('error-invalid-url', 'Invalid URL'); } const response = await fetch(fileUrl, { redirect: 'error' });` — a URL guard plus `redirect: 'error'` so a public URL cannot 302 into the internal network. The same `checkUrlForSsrf` + `redirect: 'error'` pair was added to `setUserAvatar` (the `service === 'url'` avatar-from-URL path) in the same hotfix.
  6. `checkUrlForSsrf` resolves the hostname with `dns.lookup` and rejects a denylist of ranges (`0.0.0.0/8`, `10/8`, `100.64/10`, `127/8`, `169.254/16`, `172.16/12`, `192.168/16`, `224/4`, `240/4`, `100.100.100.200/32`, …) plus `metadata.google.internal` — the DNS-resolve step is what leaves DNS-rebinding as the residual risk that `redirect: 'error'` also has to cover.
