CORE METHOD:
  1. THE FLOW — phpBB's "login-link" feature (`ucp.php?mode=login_link`) links an OAuth account to an existing phpBB account. The callback `ucp_login_link.php` first reads `login_link_*` query parameters via `get_login_link_data_array()`; if they are empty it errors with `LOGIN_LINK_NO_DATA_PROVIDED`.

     `Content-Type: application/x-www-form-urlencoded`
     `Authorization: Basic YWRtaW46eA==`   (base64 of `admin:x`)
     (empty line)
     `login_username=admin&login_password=x&login=Login`
     -> HTTP 302 with a `phpbb_sid` cookie -> the caller is logged in as `admin`.
  5. THE DEFAULT-INSTALL REACHABILITY — the vulnerable OAuth/login-link code paths are active even when NO OAuth provider has been configured; a stock phpBB install using only database authentication still exposes the endpoint. Disabling OAuth providers in the ACP does not eliminate it.
  6. THE FIX (3.3.17) — `ucp.php?mode=login_link` now issues a 301 redirect to an OAuth controller and the auth provider is sourced from server-side configuration; the `auth_provider` query parameter is no longer accepted.

STATUS: UNVERIFIED (not reproduced — no Cloudflare/Netlify/S3 endpoint was driven this pass; the payloads, the header behaviour and the chain are verbatim from the article).
CLASS: XSS with impact (cache-mediated, same-origin) via an SVG sanitizer serialization differential + a `Cache-Control: no-cache="<field-name>"` trick that strips CSP in Chromium + signed-URL response-header overrides (CWE-79 / CWE-116 / CWE-346).
CORE METHOD:
  1. THE ENDPOINT — Cloudflare's `/cdn-cgi/image/` fetches a source image, sanitizes SVG via `svg-hush` (Rust/`xml-rs`), and serves the transformed body from the customer's own hostname. The response carries `Content-Security-Policy: default-src 'none'; navigate-to 'none'; form-action 'none'; img-src data:; style-src 'unsafe-inline';` — JavaScript is blocked.
  2. THE SANITIZER DIFFERENTIAL — `xml-rs` stores namespace declarations as namespace METADATA, separate from the ordinary attribute list. During serialization, `emit_current_namespace_attributes` writes the namespace URI into `xmlns:prefix="{uri}"` WITHOUT escaping, while ordinary attribute values ARE escaped via `Escaped<AttributeEscapes>`. A namespace URI containing `">` and markup therefore breaks out of the quoted `xmlns` value AFTER the sanitizer validated the document. Payload: `<s:svg xmlns:s="http://www.w3.org/2000/svg" xmlns="&quot;&gt;&lt;a:script xmlns:a=&quot;http://www.w3.org/1999/xhtml&quot;&gt;alert(location.href)&lt;/a:script&gt;&lt;svg">` — the `s:` prefix keeps the root in the legitimate SVG namespace (passes the sanitizer), while the default namespace is serialized unescaped, producing `<svg xmlns=""><a:script xmlns:a="http://www.w3.org/1999/xhtml">alert(location.href)</a:script><svg"/>`.
  3. THE CSP STRIP — `/cdn-cgi/image/` forwards the source response's `Cache-Control` header (and `X-*`). Chromium implements RFC 7234's selective `no-cache="<field-name>"` directive (`HttpResponseHeaders::AddNonCacheableHeaders`): the argument names response headers to EXCLUDE from the cached representation. Setting `Cache-Control: no-cache="Content-Security-Policy"` makes Chromium store the body in its HTTP disk cache WITHOUT the CSP header. The first response still has the CSP (script blocked); the cached copy does not. Firefox and Safari do not implement the selective form.
  4. FORCING THE CACHED COPY — open the target page in a NEW window (so it retains a `window.opener` and is ineligible for BFCache), navigate that window to the attacker's domain, then call `history.back()` — Chromium falls back to the HTTP cache and renders the body with no CSP. (Known CTF technique since 2022 — SECCON 2022 spanote.)
  5. THE SOURCE-RESTRICTION BYPASS — with the default "This zone only" source config, the image fetcher follows HTTP redirects WITHOUT re-checking the source allowlist, so an open redirect on any allowed origin loads an attacker image; with Cloudflare Access enabled on any hostname in the zone, `/cdn-cgi/access/logout?returnTo=<cloudflare.com open redirect>` chains to an arbitrary domain. The chain achieved XSS through `/cdn-cgi/image/` on `https://www.cloudflare.com/`.
  6. THE EXTENSIONS — Netlify Image CDN also forwards/permits the `Cache-Control` value, and the same `no-cache` trick can strip BOTH `Content-Security-Policy` and `Content-Type`, turning an SVG/HTML polyglot (a processing instruction that is inert as SVG but active as HTML: `<?a ><script>alert(location.href)</script> a?>`) into HTML execution. On S3-backed origins, presigned URLs with `response-content-type=text/html` and `response-cache-control=no-cache="Content-Security-Policy"` (signed with your OWN AWS credentials against a publicly readable object) override both headers, extending the technique to custom domains / CNAMEs / reverse proxies that preserve query parameters; GCS V4 signed URLs support the same `response-content-type` override.
DETECTION SIGNAL: an image-optimization/transformation endpoint (`/cdn-cgi/image/`, `/_next/image`, an image CDN) that reflects an attacker-controlled source body and forwards or lets you set response headers (`Cache-Control`, `X-*`, signed-URL `response-*` params); a transformed response carrying `default-src 'none'`; a sanitizer that parses and reserializes XML/SVG (look for a serializer that escapes attributes but not namespace declarations); a Chromium-only `Cache-Control: no-cache="<field-name>"` implementation; a source-fetch that follows redirects without re-validating the allowlist.
CHAIN: an attacker who can control (or inject) an image body the endpoint fetches (primitive: an image source the endpoint will process — an open redirect or an allowed origin) -> the SVG sanitizer's serialization differential lets markup survive as an XSS payload in the transformed body (escalation: a sanitized image becomes an HTML/JS carrier) -> the endpoint forwards the source's `Cache-Control` header (primitive: attacker-controlled response header) -> `Cache-Control: no-cache="Content-Security-Policy"` makes Chromium cache the body without the CSP (escalation: the only remaining defence is removed from the cached copy) -> the attacker forces a `history.back()` from an opener window to load the cached copy (escalation: the CSP-less body is rendered) -> the script executes in the target origin (impact: XSS). HONESTY: the Cloudflare chain is demonstrated by the researchers; the Netlify/S3/GCS extensions are described in the same article with PoCs.
