§17.690 — VALIDATION BEFORE NORMALIZATION VALIDATES A DIFFERENT STRING: a compatibility character that survives the authority check decodes INTO a structural delimiter — libcurl's IDN decoder accepts U+FF20 FULLWIDTH COMMERCIAL AT (`＠`), libidn2's TR46 transitional fallback turns it into ASCII `@`, and `Curl_idn_decode()` "only checks that the result is non-empty", so the serialized authority reparses to a different host + userinfo and `lib/http_proxy.c:213` builds the CONNECT from the DECODED host — "A proxy using generic URL/authority parsing sees a different host than the URL's apparent host" (HackerOne #4129950, curl, reporter zefanxu, High 7~8.9, SSRF, disclosed 2026-10-21; read in full this pass 2026-11-12 via live `web_extract`; UNVERIFIED — not reproduced; the wider compatibility-character table beyond `＠` is an UNVERIFIED extension of the transferable test). §17.693 — A BLIND BOOLEAN ORACLE ANSWERED BY A LOAD-BALANCED POOL NEEDS POSITIVE/NEGATIVE PROBE PAIRS AND REGEX-CLASS BINARY SEARCH, NOT A LINEAR WALK: when consecutive guesses can be answered by DIFFERENT backends, ship every guess as a matched pair `foo[a-n]` + `foo[^a-n]` and repeat until one lands on the right instance — the complement guarantees coverage of both branches; regex character classes probe several positions in parallel (`foo.[a-n]`, `foo..[a-n]`) and overlapping prefixes converge to a unique string in ~10 characters (David Nechuta, "31k$ SSRF in Google Cloud Monitoring led to metadata exposure", nechudav.blogspot.com/2020/11/31k-ssrf-in-google-cloud-monitoring.html, 2020-11; VRP report June 2020; the extraction trick is the Google engineers' own comment, "Update 25.01.2021"; read 2026-11-12 via curl of the live page after web_extract/r.jina.ai truncation; UNVERIFIED — not reproduced, gist not run). CARRIER CONTEXT (recorded, not re-taught): Google Cloud Monitoring uptime check -> Hostname `169.254.169.254`, Path `/computeMetadata/v1/project/project-id`, "Custom Headers: Metadata-Flavor: Google" ("there was an option to add custom headers to the request") -> the Response-validation content-match = the §17.685 boolean read oracle -> GCP metadata + service-account access token. THE PROBLEM, verbatim: the check service "is running on multiple instances across the world (there were about 54 running instances) and the requests made to the service are load-balanced. So there was no assurance that multiple requests would be sent to the same instance" — a linear prefix walk diverges when the answering instance changes. THE MATH, verbatim: "The two main tricks were binary search for each character (to send fewer requests) and probing both positive and negative matches (to get reliably results). For example: foo[a-n] foo[^a-n]. One of those requests must eventually return a success response when we hit the correct backend. We'd repeat queries (up to some limit) until we get any OK response and then adjust the search space based on that." Parallel probes: "( foo[a-n] , foo.[a-n] , foo..[a-n] ) ... after ~10 characters or so we usually had a unique prefix." Budget: "Access tokens are valid for 60 minutes, so on average you have 30 minutes ... the exploit took ~15 minutes to get a full access token, including rate limiting." DETECTION SIGNAL: a boolean contains/match oracle whose answers are UNSTABLE across identical repeats; a rate limit that forbids linear extraction; regex accepted in the probed position; data with a lifetime shorter than a walk. TRANSFERABLE TEST: on any blind boolean oracle with unstable answers: (1) binary-search the character domain with the oracle's pattern syntax; (2) pair every positive guess with its negative complement and repeat the pair until one returns OK; (3) probe k positions in parallel and intersect overlapping prefixes; (4) budget against the data lifetime and the rate limit first.
