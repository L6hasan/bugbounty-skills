CLASS: COOKIE-PREFIX BYPASS (`__Host-` / `__Secure-`) via a browser↔server PARSER DISCREPANCY, escalating to session fixation / reflected-cookie XSS / privilege escalation — i.e. session-integrity forgery from a subdomain or an insecure origin. Chain-only: the disguised cookie is the first link; the XSS / session fixation / priv-esc it reaches is the finding.
CORE METHOD:
  1. THE TWO PROGRAMS DISAGREE ABOUT THE NAME: the browser enforces the prefix on the name it is handed; the server DECODES and normalises the bytes it receives ("the Cookie header is defined as a sequence of octets, not characters ... it's the server's responsibility to decode those bytes into a string").
  2. DISGUISE THE NAME WITH UNICODE WHITESPACE: `document.cookie = `${String.fromCodePoint(0x2000)}__Host-name=injected; Domain=.example.com; Path=/;`` — to the browser this is an unprefixed, unrestricted cookie, so it is accepted and sent to ALL subdomains (and over an insecure origin), while a trimming server sees the name as `__Host-name`.
  3. WHICH SERVERS TRIM: Django processes cookie keys/values with Python's `.strip()`, which removes a wide range of Unicode whitespace — `[133, 160, 5760, 8192–8202, 8232, 8233, 8239, 8287, 12288]` (U+2000 included); ASP.NET applies the same normalisation/trim. Safari is the exception: it refuses MULTIBYTE Unicode whitespace in a cookie name, but still permits the single-byte U+0085 (NEL) and U+00A0 (non-breaking space).
  4. LEGACY-PARSING VARIANT (Java): "if a Cookie header begins with `$Version=1`, some Java-based web servers, such as Apache Tomcat and Jetty, switch into a legacy parsing" mode where a single cookie string is read as SEVERAL cookies — `document.cookie = "$Version=1,__Host-name=injected; Path=/somethingreallylong/; Domain=.example.com;"` therefore forges a `__Host-` pair from a subdomain or an insecure origin, bypassing the browser's prefix check entirely.
  5. FULL CHAIN: from an XSS (or any unescaped cookie reflection) inject the forged protected cookie — `document.cookie = `${String.fromCodePoint(0x2000)}__Host-name=<img src=x onerror=alert(1)>;Domain=example.com;Path=/;`` — and the browser puts BOTH on the wire: `Cookie: __Host-name=Carlos; â€€__Host-name=<img src=x onerror=alert(1)>;`. Many frameworks (Django named explicitly) resolve a duplicate-cookie conflict by accepting only ONE value, "typically the last occurrence", so the attacker-controlled value takes precedence: a reflected XSS if the value is re-rendered unencoded, or session fixation / privilege escalation if the same cookie feeds CSRF protection or session identification. (A lightweight Burp Custom Action accompanies the post for detecting backends vulnerable to the prefix bypass; the "cookie sandwich" post is the earlier article in the same series.)
DETECTION SIGNAL: `__Host-`/`__Secure-` cookies in use (they are only meaningful if the server RELIES on the prefix, which is the bug); a backend that TRIMS/normalises cookie names — Django, ASP.NET — or a Java server (Tomcat, Jetty) that honours `$Version=1` legacy parsing; a duplicate-cookie resolution that silently picks one value; any sink that re-renders a cookie value or derives CSRF/session identity from it.
CHAIN: JS execution on a sibling subdomain or an insecure origin (primitive: normally blocked from writing a `__Host-` cookie) -> the U+2000-prefixed (or `$Version=1,`-prefixed) twin is accepted by the browser and NORMALISED into the protected name by the server (escalation: the cookie-prefix protection is gone) -> the server keeps the attacker's duplicate (last-wins) -> a reflected cookie value becomes XSS on the main origin, or the session/CSRF cookie becomes attacker-chosen giving session fixation and privilege escalation (escalation: account takeover / priv-esc). Doctrine note: cookie prefixes are a HARDENING control, so the finding is the escalation (XSS, session fixation, priv-esc), never the bypass on its own.
TRANSFERABLE TEST: when a target ships `__Host-`/`__Secure-` cookies and you have any JS execution on a sibling subdomain or an insecure origin (or a cookie value you can influence): (a) set the twin — `document.cookie = String.fromCodePoint(0x2000) + "__Host-<name>=x; Domain=.example.com; Path=/;"` — then confirm the value reaches the target origin and that the app treats it as the protected cookie; (b) try `$Version=1,__Host-<name>=x; Path=/a-very-long-path/; Domain=…` against Tomcat/Jetty; (c) on Safari use U+0085 or U+00A0 (multibyte whitespace is refused there); (d) check WHICH duplicate the server honours (last-wins is the exploitable case). Rule: **`__Host-`/`__Secure-` are enforced by the BROWSER on the raw name and by the SERVER after decoding — hide the prefix behind Unicode whitespace (U+2000, U+0085, U+00A0) or a `$Version=1,` legacy list, and a subdomain or insecure origin can plant a cookie whose NAME the server normalises into the protected one.**

CLASS: REQUEST-SMUGGLING FALSE-POSITIVE DISCRIMINATION / connection-reuse semantics — a METHODOLOGY for deciding whether a connection-reuse-requiring desync PoC is real, and the escalation ladder that turns a real one into impact. In-class: request smuggling / desync → cross-user response capture, cache poisoning, ACL bypass, auth bypass.
CORE METHOD:
  1. ALWAYS DISABLE CONNECTION REUSE WHEN TESTING SMUGGLING: "when creating a request smuggling proof of concept, always disable connection reuse where possible. If this breaks your attack, you have a choice — give up, or dive deeper." The usual false positive is a desync between YOUR HTTP CLIENT and the target, not between the front-end and the back-end — the article's CL.0 example (`POST / HTTP/1.1` / `Content_Length: 47` (malformed) / `GET /robots.txt`) only produced two responses because the author's own client appended the next request's bytes to the first request's body; the underlying stream shows `X: YPOST / HTTP/1.1` — "This is useless. In fact, hackxor doesn't even have a back-end so it's immune to request smuggling."
  2. THREE VALID CLASSES DO REQUIRE CONNECTION REUSE (so "breaks when reuse is off" is not proof of a false positive): (a) CONNECTION-LOCKED request smuggling — some front-ends only reuse the upstream connection if the client connection was reused, so the bug is only triggerable with client-side reuse; (b) CONNECTION-STATE attacks — not technically smuggling: some servers treat the FIRST request on each connection differently from subsequent ones (first-request routing), and they can occur even with no front-end; (c) CLIENT-SIDE DESYNC — restricted to a request the victim's browser can be made to send cross-domain, which rules out header-obfuscation techniques.
  3. PROVE A CONNECTION-LOCKED SMUGGLING IS REAL (not a client artefact): "see if you can send a request over HTTP/2 that triggers a response containing a separate HTTP/1 response nested inside it" — a nested HTTP/1 response proves the disagreement is in the server chain; alternatively "you can often distinguish connection-locked request smuggling using partial requests".
  4. REQUIRE EVIDENCE OF IMPACT: "to prove a vulnerability is really present, you need to obtain evidence of real impact beyond 'an attacker can make themselves receive a surprising response'". Connection-locked smuggling cannot be used for direct cross-user attacks, so escalate instead by: (i) poisoning the server CACHE if one exists — "an easy high-impact attack"; (ii) "look for an input reflection gadget and use it to reveal any headers the front-end is injecting. Sometimes internal headers enable complete authentication bypass!"; (iii) bypassing "any security controls applied by the front-end server" (paths it blocks) — "This is your pathway to a valid report!"; (iv) host-header tampering both directly and inside smuggled requests "to gain access to some previously off-limits internal systems, or launch other host-header attacks".
  5. TOOLING/ROUTE: explore with Turbo Intruder `requestsPerConnection=2`, or a Repeater tab group using 'Send group in sequence (single connection)'; HTTP Request Smuggler has a 'connection-state probe' that finds first-request routing automatically; use HTTP Hacker to see the raw request stream beneath Burp's abstraction.
DETECTION SIGNAL: a smuggling PoC that only works with connection reuse (Turbo Intruder `requestsPerConnection > 1`, Burp Intruder HTTP/1 Connection Reuse, Repeater 'Send group in sequence (single connection)' / 'Enable connection reuse', or "two HTTP/1 responses in one"); a front-end whose upstream reuse is keyed to client reuse (connection-locked); a server that treats the first request on a connection differently (first-request routing / connection-state); an open input-reflection gadget next to the desync (internal-header disclosure); a cache in front; front-end rules that block specific paths.
CHAIN: a smuggling PoC that only fires with connection reuse (primitive: ambiguous — most such PoCs are client-artefacts) -> confirm it belongs to one of the three valid reuse-requiring classes (HTTP/2 request yielding a nested HTTP/1 response, or a partial request, or a first-request-routing probe) (escalation: a REAL desync) -> then convert to impact: cache poisoning (site-wide), an input-reflection gadget that discloses front-end-injected internal headers (sometimes a COMPLETE AUTHENTICATION BYPASS), bypass of front-end security controls, or host-header tampering into internal systems (escalation: P1/P2 desync impact). If no impact path is found, the finding stays a lead.
TRANSFERABLE TEST: before ever reporting a desync that needs connection reuse — (a) re-run the PoC with reuse DISABLED; if it still works it is a normal desync, done; (b) if it breaks, test whether it is connection-locked / connection-state: send the same request over HTTP/2 and look for a nested HTTP/1 response in the reply, try partial requests, and run a connection-state probe for first-request routing; (c) for a confirmed connection-locked bug, spend the effort on IMPACT ONLY — poison the cache, use an input-reflection gadget to leak front-end-injected headers (→ possible auth bypass), bypass front-end path controls, and test host-header tampering toward internal systems. Rule: **"only works with connection reuse" is usually a client-side artefact, so disable reuse first; if it still fires, classify it as connection-locked smuggling / a connection-state attack / a client-side desync, and pay for it with cache poisoning, a reflection gadget that discloses internal headers (auth bypass), control bypass or host tampering — a desync that yields only "a surprising response to myself" is not a report.**

CORE METHOD:
  1. DETECT THE DISCREPANCY, NOT THE EXPLOIT (HTTP Request Smuggler v3, extending Daniel Thacher's 2021 header-smuggling idea): send a request with a PARTIALLY HIDDEN header — a leading space before the header NAME (` Content-Length: 23`, ` Host: x`) or a masked duplicate (`Xost: x`) — and compare the response against four references: the normal header, the header omitted, and an arbitrary other masked header. If the masked variant produces a response that CANNOT be triggered any other way, there is a parser discrepancy in the server chain. "Note that the specific status codes are not relevant, and can sometimes be confusing. All that matters is that they're different."
  2. CLASSIFY V-H vs H-V: VISIBLE-HIDDEN = the masked header is visible to the front-end but hidden from the back-end; HIDDEN-VISIBLE = hidden from the front-end but visible to the back-end. Distinguish by inspecting the responses and guessing which tier produced them (the paper's IIS/ALB example is unambiguous from the banners: unmasked `Host: foo/bar` → `400, Server: awselb/2.0` (front-end), masked `Xost: foo/bar` → `200, -no server header-` (back-end)).
  3. V-H → CL.0 BY HIDING `Content-Length` (hidden from the back-end, so the back-end treats the next request's bytes as this request's body): `GET /style.css HTTP/1.1` / `Host: <redacted-food-corp>` / `Foo: bar` / ` Content-Length: 23` (LEADING SPACE) / blank / `GET /404 HTTP/1.1` / `X: y` → the smuggled request is answered separately. CL.0 is preferred over TE.CL "as it's much less likely to get blocked by a WAF". BARRIER WORKAROUND: when the front-end rejects GET requests carrying a body, "I was able to work around this simply by switching the method to OPTIONS".

H-V ON IIS BEHIND AWS ALB (a mass-vulnerable, DELIBERATELY UNPATCHED case): the malformed/masked `Host` is hidden from ALB and passed to IIS, so the classic exploit is CL.TE; AWS' Desync Guardian blocks it, and Thomas Stacey bypassed that with an H2.TE desync. Even with the H2.TE bypass fixed, the same discrepancy still allows smuggling HEADERS, "enabling IP-spoofing and sometimes complete authentication bypass". AWS will not patch it (compatibility with ancient HTTP/1 clients); self-mitigate with `routing.http.drop_invalid_header_fields.enabled` and `routing.http.desync_mitigation_mode = strictest`.
  5. 0.CL DESYNC AND ITS DEADLOCK: exploit an H-V discrepancy to hide `Content-Length` from the FRONT-END while the back-end sees it — `GET /Logon HTTP/1.1` / `Host: <redacted>` / `Content-Length:` / ` 7` / blank / `GET /404 HTTP/1.1` / `X: Y`. This normally DEADLOCKS (the front-end buffers the second request and forwards only the header block; the back-end waits for the 7-byte body; the front-end waits for the back-end; one times out and resets → `504 Gateway Timeout`).
  6. BREAK THE 0.CL DEADLOCK WITH AN EARLY-RESPONSE GADGET — a way to make the back-end respond WITHOUT waiting for the body: on nginx a STATIC FILE does it (nginx answered before the request was complete and broke the author's timing tests); on IIS, which ignored the static-file trick, use the WINDOWS RESERVED DEVICE NAME — request `/con` inside any filesystem-mapped folder and IIS "respond[s] without waiting for the body to arrive, and helpfully leave[s] the connection open" (the reserved list is `CON, PRN, AUX, NUL, COM1, COM2 …`; "I've known about the /con quirk for over ten years but this was the first time I've been able to actually make use of it"). SERVER-LEVEL REDIRECTS also act as early-response gadgets on other servers; the author never found one for Apache ("too studious about closing the connection when they hit an error condition"). This is why the tool's "Mystery 400" responses are in fact usually exploitable.
  7. PROVE 0.CL, THEN CONVERT IT TO CL.0 WITH A DOUBLE-DESYNC: proof = give the first request a correct `Content-Length: 20` and put a second path inside the victim request's header block — the sliced request line is processed (`302 Found Location: /Logon?ReturnUrl=%2fwrtz`). A realistic attack needs the payload in the VICTIM's request, i.e. 0.CL → CL.0, which requires a DOUBLE-DESYNC: request 1 poisons the connection with a 0.CL; the poisoned connection weaponises request 2 into a CL.0 which re-poisons the connection with a malicious prefix; the prefix poisons the VICTIM's request. The clean form (`POST /nul` + `Content-length:` + ` 163` + a second `POST /`) is fragile because you must know the exact size of the front-end's injected headers ("virtually all front-end servers append extra headers ... often contain things like the client IP, which means the attack works for you but breaks when someone else tries to replicate it"). THE FIX: "Most servers insert headers at the END of the header block, not at the start. So, if our smuggled request starts before that, the attack will work reliably!" — reveal the inserted header with an input reflection (`Foo: GET /y HTTP/1.1` then `???: ???? // front-end header lands here`), measure its length with the `0cl-find-offset` Turbo Intruder script, and from there use traditional CL.0 techniques (the paper's `HEAD` technique served malicious JavaScript to random users). CORE METHOD:
  1. `location` AND `document.URL` DISAGREE: `https://foo:bar@portswigger-labs.net` gives `alert(location)` = `https://portswigger-labs.net/` but `alert(document.URL)` = `https://foo:bar@portswigger-labs.net/` — "document.URL contains the credentials part of the URL whereas location doesn't". Chrome and Firefox hide the credentials in the address bar and it "even persists through same origin navigations".
  2. A SINK THAT READS `URL`/`document.URL` READS YOUR CONCEALED PAYLOAD: `https://***@portswigger-labs.net` plus `<img src onerror=alert(URL.slice(8,16))>` — "you can use just URL inside an event [handler to] grab the payload from the credentials".

THE BYPASS THAT REVIVES A DEAD DOM XSS: after fuzzing which characters are encoded in the credentials segment (Shazzer vector linked in the post), "Firefox doesn't URL-encode single quotes" — so against `function getBase(url){ return url.split(/[?#]/)[0]; } document.write(\`<script>const url='${getBase(document.URL)}';<\/script>\`)` the credentials segment closes the single-quoted string: "useful in DOM XSS scenarios, if the site removes the query string and hash". Delivery: "redirection or user navigation".
  4. ANCHOR PROPERTIES CARRY THE SAME DATA: every `<a>` has `username`/`password` properties holding the URL credentials, and "if it's a relative link, it inherits the parent credentials, allowing you to clobber these values" — `https://***@example.com` + `<a href=# onclick=alert(username)>test</a>`.
