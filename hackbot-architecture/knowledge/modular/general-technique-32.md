CORE METHOD:
  1. ENTRY (verbatim): "When `IPT_SO_SET_REPLACE` or `IP6T_SO_SET_REPLACE` is called in compatibility mode, which requires the `CAP_NET_ADMIN` capability that can however be obtained in a user+network namespace, structures need to be converted from user to kernel as well as 32bit to 64bit… Our vulnerability is in `xt_compat_target_from_user()` where `memset()` is called with an offset `target->targetsize` that is not accounted for during the allocation - leading to a few bytes written out-of-bounds".
  2. PRIMITIVE SHAPING (verbatim): "The `targetsize` is not controllable by the user, but one can choose different targets with different structure sizes by name (like `TCPMSS`, `TTL` or `NFQUEUE`)… the target size must _not_ be 8 bytes aligned in order to fulfill `pad > 0`. The biggest possible I found is `NFLOG` for which we can choose an offset up to 0x4C bytes out-of-bounds (one can influence the offset by adding padding between `struct xt_entry_match` and `struct xt_entry_target`)". "the minimum size is > 0x100 which means that the smallest slab this object can be allocated in is kmalloc-512".
  3. SLAB DISCIPLINE (verbatim): "it had something to do with the `GFP_KERNEL_ACCOUNT` flag… Jann Horn confirmed that before 5.9, separate slabs were used to implement accounting. Therefore, every heap primitive we use in the exploit chain should also use `GFP_KERNEL_ACCOUNT`."
  4. OOB -> UAF via `msg_msg` (verbatim design): spray `msgsnd()` PRIMARY messages + SECONDARY segments of 1024 bytes ("its structure `msg_msg` has surprisingly never been abused"); "we create some holes (in our case every 1024th) in the primary messages, and trigger the vulnerable `setsockopt(IPT_SO_SET_REPLACE)`"; overwrite two zero bytes of the adjacent primary's secondary-message pointer — "Since we allocate them with a size of 1024 bytes, we therefore have a 1 - (1024 / 65536) chance to redirect the pointer"; two primaries now share ONE secondary -> "we namely fetch the secondary message from the real message queue using `msgrcv()` and as such free it" = use-after-free.
  5. SMAP BYPASS + LEAK (verbatim): reclaim with `socketpair()` unix-socket sk_buff sprays "and imitate the `struct msg_msg` header"; `mlist.next` stays `41414141` ("not having a kernel address is crucial as it actually prevents us from freeing the block again"); inflate `m_ts` "to `DATALEN_MSG=4096-sizeof(struct msg_msg)`" to read past the message and "leak the `struct msg_msg` header of the adjacent message"; the circular list makes `mlist.next` point back to the primary -> re-craft `next` -> leak the secondary's address.
  6. BETTER UAF (verbatim): "This stale `struct sk_buff` data buffer is a better use-after-free scenario to exploit, because it does not contain header information, meaning that we can now use it to free _any_ kind of object on the slab."
  7. VICTIM + KASLR (verbatim): `struct pipe_buffer` ("allocated in kmalloc-1024", `alloc_pipe_info()` uses `GFP_KERNEL_ACCOUNT`) holds `const struct pipe_buf_operations *ops`; writing to pipes sets `ops` to the static `anon_pipe_buf_ops` in .data — leak it through the stale buffer ("anon_pipe_buf_ops: ffffffffa1e78380 / kbase_addr: ffffffffa0e00000") because "the difference between the .data segment and the .text segment is always the same".
  8. CODE EXEC (verbatim): reclaim the pipe_buffer with a fake one whose `ops` points at a planted fake `pipe_buf_operations` with a malicious `release`; "close all pipes in order to trigger the release which in turn will kick off the JOP chain… achieve a kernel stack pivot as soon as possible in order to execute a kernel ROP chain"; ROP = "call `commit_creds(prepare_kernel_cred(NULL))`… then call `switch_task_namespaces(find_task_by_vpid(1), init_nsproxy)`".
  9. CONTAINER ESCAPE (verbatim): "Arriving back in userland, we now have root permissions to change mnt, pid and net namespaces to escape the container and break out of the kubernetes pod": `setns(open("/proc/1/ns/mnt", O_RDONLY), 0); setns(open("/proc/1/ns/pid", O_RDONLY), 0); setns(open("/proc/1/ns/net", O_RDONLY), 0);` then `execve("/bin/bash", ...)`.
