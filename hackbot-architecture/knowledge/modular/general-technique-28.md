THE IMPACT (report verbatim): "An attacker who has an account on Roundcube, and can find any XSS vulnerability on a same-site service next to Roundcube, can prepare an attack that takes over the victim's Roundcube account. With this they can read all emails (eg. take over accounts through password resets), send emails from the victim's account, and make any changes to the settings."
DETECTION SIGNAL: a mail/app endpoint that renders user-uploaded HTML inline with no CSP (attachment preview/display, file viewer, "open in browser") while sibling endpoints (get.php, download) DO set CSP; a per-path session gate (a `$SESSION` key set only when a compose/view action starts) that the attacker cannot satisfy for the victim; any same-site (same registrable domain) service with an XSS primitive; a session cookie scoped to the parent domain (`Domain=.site`) so a sibling can write it.
CHAIN: any XSS on a same-site service (primitive: a P4 same-site XSS) -> cookie tossing: `document.cookie` writes the ATTACKER's session cookies with `Domain=.site` and a NARROW `Path=` (bypass: the per-path session gate is satisfied by the attacker's session, while the victim's own session cookies still apply to every other path) -> the victim is redirected to the stored-XSS attachment-preview URL (primitive: the endpoint renders uploaded HTML with no CSP) -> the payload executes in the Roundcube origin (escalation: stored XSS in the victim's mail session) -> the attacker's JS reads the victim's mail / performs actions as the victim (final: account takeover — read all emails, send mail, password resets, settings changes).
TRANSFERABLE TEST: on any multi-app site where a session cookie is scoped to the parent domain and a sensitive endpoint has a per-path session gate — (1) find any XSS on a same-site subdomain (even self-XSS); (2) from it, set `document.cookie = '<session-cookie-name>=<your-value>; Domain=<parent>; Path=<the-gated-path>'` for every session cookie the app uses; (3) redirect the victim to the gated sensitive URL under that path; (4) if your JS executes there, the cookie-tossing session override worked — then check whether the app's other paths still carry the victim's cookies (the Path-scope trick) and exfiltrate the victim's data. Rule: **cookie tossing from any same-site XSS is a session-override primitive — scope the tossed cookies to the one gated path so the victim's session survives everywhere else, and target an endpoint whose only gate is a per-path session key.**
