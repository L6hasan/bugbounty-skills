CLASS: HTTP request smuggling — CLIENT-SIDE desync (CSD, CWE-444) reached through mishandled `Content-Length` on an INCOMPLETE POST, with a cross-user information-disclosure consequence
CORE METHOD:
  1. Affected range: Apache Tomcat 8.5.7–8.5.63 and 9.0.0-M11–9.0.43 (fixed in 8.5.64 / 9.0.44).
  2. Internet Bug Bounty, "Request Smuggling in Apache Tomcat (Important, CVE-2023-45648)" — HTTP Request Smuggling; High (8.2); $4,660; 51 votes; reporter mukeran (Keran Mu & Jianjun Chen, Tsinghua University / Zhongguancun Laboratory); submitted 2023-12-30; disclosed 2024-02-07; asset github.com/apache/tomcat.
STATUS: UNVERIFIED (not reproduced — the report's own docker reproduce recipe was not run this pass)
CLASS: HTTP request smuggling via TRAILER-SECTION parsing (CWE-444) — a trailer header LINE WITHOUT A COLON makes the parser keep consuming FOLLOWING lines as trailers until it finds a valid colon-separated pair, so the next request's headers are eaten while its body is parsed as a NEW request
CORE METHOD (verbatim payload + reproduce steps from the body):
  1. Affected: Tomcat 11.0.0-M1–M11, 10.1.0-M1–10.1.13, 9.0.0-M1–9.0.80, 8.5.0–8.5.93 (fixed in M12/10.1.14/9.0.81/8.5.94).
  2. Payload: `POST /benign_path HTTP/1.1` / `Host: a.com` / `Connection: keep-alive` / `Transfer-Encoding: chunked` / blank / `5` / `12345` / `0` / `Content: hello` ← the trailer line, followed by chunk-size `a` (10 bytes) / blank / `POST /benign_path HTTP/1.1` / `Host: a.com` / `Connection: keep-alive` / `Content-Length: 37` / blank / `GET /evil_path HTTP/1.1` / `Any: any` / `Host: b.com` / blank.
  3. Root cause stated by the reporter: Tomcat "cannot properly parse the trailer section if there's no colon in the trailer header's line. It will skip the following lines until the last line with a valid colon-separated key-value header pair".
  4. Consequence: lines 12-15 (the second request's HEADERS) are taken as TRAILER section of the first request, while lines 17-19 (the second request's CONTENT — a complete `GET /evil_path` with `Host: b.com`) are processed as a SECOND request. NGINX and other implementations treat lines 12-21 as one second request → the front-end and the back-end disagree on the message boundary.
  5. Reproduce (verbatim): `docker run -d --name hrs_tomcat_11 -p 43022:8080 tomcat:10.1.13`; `printf`/`echo -n` the payload with CRLF into `nc 127.0.0.1 43022`; then `docker exec -it hrs_tomcat_11 /bin/sh -c "cat /usr/local/tomcat/logs/localhost*"` → the access log shows BOTH `POST /benign_path` and `GET /evil_path` from one client message.
DETECTION SIGNAL: Tomcat ≤ this range behind a reverse proxy/CDN; chunked requests that include a Trailer section (`Trailer:` header or a trailer block); a trailer line that lacks a colon (or a malformed one); front-end request count ≠ back-end access-log count; a smuggled prefix whose `Host:` differs from the front-end's routing (vhost bypass).
CHAIN: malformed trailer line (primitive) → trailer parser swallows the next request's headers → the following body becomes a fresh request with an ATTACKER-CHOSEN `Host:` → smuggling behind the proxy → request-queue poisoning / capture of the next user's request → auth bypass, cache poisoning, ATO/stored-XSS downstream. Framing desync alone; the finding is what the smuggled prefix reaches (report's own impact statement: "bypass security mechanisms when Apache Tomcat is deployed behind a reverse proxy").
TRANSFERABLE TEST: send the payload verbatim at a proxied Tomcat (`nc`/socket, CRLF-exact, chunked with a trailer line that has no colon and a chunk-size line that swallows the intent), then read the back-end access log and compare with the front-end's view: TWO back-end requests (`/benign_path` + `/evil_path` with `Host: b.com`) from ONE front-end request = smuggling. RELATED-BUT-DISTINCT: this is the TRAILER-LINE-SKIPPING root cause (malformed line without a colon), not the trailer SIZE-LIMIT `IOException` path (HackerOne #2280391, already recorded above), not TE-header obfuscation (§17.20), not H2→H1.1 (§17.56), not CRLF-via-rule-engine (§17.77).

CLASS: HTTP request smuggling by TIMEOUT rather than by parsing ambiguity — a "pause-based" desync: a server that answers a PARTIAL request itself (server-level rule) times out and leaves the half-read connection reusable, so the remaining bytes are parsed as a NEW request
CORE METHOD:
  1. Root cause: the server generates the RESPONSE ITSELF instead of letting the application handle the request (so it never reads the body), hits its request timeout, and — the bug — leaves the connection OPEN FOR REUSE although it has only read half the request off the socket. When the client then sends the rest, it is interpreted as a fresh request.
  2. Find a server-level responder. Varnish: a `synth()` rule, e.g. `if (req.url ~ "^/admin") { return (synth(403, "Forbidden")); }` — on a partial request matching a synth rule Varnish times out after 15 s and leaves the connection reusable. Because the front-end will not hand you the timeout response until it has seen a COMPLETE request, the sequence must be "send headers → pause → continue unprompted"; Kettle had to add `pauseBefore` / `pauseMarker` / `pauseTime` to Turbo Intruder's queue interface to do it.

If the server RESPONDS during the read, the front-end considered the message complete and therefore parsed it as chunked (secure). If the read HANGS, the front-end is still waiting for the body and is therefore using `Content-Length` ⇒ vulnerable. This is the resolution of the pipelining ambiguity and adapts directly to TE.CL.
