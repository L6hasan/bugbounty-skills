**Source:** HackerOne #489146 (Jan 2019), **$20,000**, Critical.

**Core method**
- A new GraphQL feature shipped without access controls on the `User` type.

  `facebook_user_id`, `account_recovery_phone_number_verified_at`, `totp_enabled`.

(`Did you mean "email"?`), and field-name fuzzing.

**Transferable test.** `__schema { types { fields { name } } }` → build a query for every scalar on
`User`/`Account`/`Organization` → run with a second account's ID → compare against the same query
on your own ID.

### [bugbountyhuntingskills.md] 13.5 Arbitrary file write → `authorized_keys` → command execution

**Source:** HackerOne #298873 — GitLab project import, **$2,000**, by @jobert.

**Core method**
- `Projects::GitlabProjectsImportService` builds `import_upload_path` from the unsanitized
  `params[:path]` and copies the uploaded archive there:
  ```ruby
  mkdir_p(File.dirname(import_upload_path))
  FileUtils.copy_entry(file.path, import_upload_path)
  ```
- Traversal in `path` writes arbitrary files as the `git` user; file contents are not validated.
- Direct write to the Rails views dir failed on permissions, so the target became
  `/var/opt/gitlab/.ssh/authorized_keys`, which *is* writable by `git`:
  ```
  command="ls -lash",no-port-forwarding,no-X11-forwarding,no-agent-forwarding ssh-rsa AAAA... attacker@host
  ```
- The request returns `302` (validation error on the project name) but the file is **not cleaned
  up**, so the exploit persists.

**Lesson.** Arbitrary file write is RCE once you find a file the service user can write that is
later *executed* or *trusted*: `authorized_keys`, cron files, `.bashrc`/`.profile`, systemd units,
`config.json` for a supervisor, Python `.pth` files, PHP session files, Jenkins `config.xml`.
Enumerate writable paths **as the service account** (`find / -writable -user git`), not as root.
