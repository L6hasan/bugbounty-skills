### [Bugbountyskills.md] 17.65 Length-prefixed decoder: bounds checks hoisted OUT of the `do/while` that advances both cursors; continuation path guarded only by a DEBUG `Assert` → buffer overrun (Valve Steam SILK voice decoder #1180252)

SOURCE: https://hackerone.com/reports/1180252 — Valve, "Buffer overrun in Steam SILK voice decoder" (Classic Buffer Overflow; Critical 9.1; reporter slidybat)  read 2026-11-07 (full body, 6,311 bytes, via the HackerOne `.json` endpoint)
CLASS: parser/decompressor where input and output bounds are checked once before an inner loop that advances both cursors, with a release-compiled `Assert` as the only continuation guard · CWE-787 / CWE-617
CORE METHOD:
  1. Frame format studied: `8 bytes steamid | 1 byte type | 2 bytes size | <payload> | 4 bytes CRC`; type SILK loops over `nSize` frames.
  2. The loop checks `pPayloadCurr + nSize > pPayloadEnd` (input) and `pDestCurr + 2*nBytesInFrame > pDestEnd` (output) BEFORE the inner `do { SKP_Silk_SDK_Decode(...); pPayloadCurr += nSize; pDestCurr += 2*nDecodedSamples; Assert(moreInternalDecoderFrames == 0); } while (m_decControl.moreInternalDecoderFrames);` — the checks are NOT repeated inside.
  3. Reporter's finding verbatim: with `moreInternalDecoderFrames == true`, "we can increment `pDestCurr` past the end of the destination buffer, and overwrite stack data"; the `Assert` is "ignored" without a debugger attached.
  4. Payload under a 512-byte cap: repeat `nSize = 0` frames to walk `pDestCurr` to just over one frame from the end → one frame that sets `moreInternalDecoderFrames` → one more frame writes past the buffer.
  5. Impact: crash/DoS for every client that hears the attacker; return-address overwrite with a decoded ROP chain = RCE. Affects every SteamWorks `DecompressVoice` consumer, including official matchmaking servers.
DETECTION SIGNAL: a length-prefix loop parser (codecs, archivers, protobuf/AVRO/Thrift, HTTP multipart, ZIP/TAR) where a bounds check precedes a loop body that mutates the cursor more than once per check, and where the safety condition lives in `assert`/`Assert`/`debug_assert` (compiled out in release) rather than a runtime `break`.
CHAIN: one crafted compressed payload → single-frame reservation + multi-frame continuation → second iteration writes past `pDestBuffer` → stack/heap corruption → crash (DoS for all listeners) → decoded-to-ROP output overwrites the return address → RCE (Critical 9.1).
TRANSFERABLE TEST (LAB; the shape is testable on any API we own): for every length-prefix loop parser, send input that (a) leaves the output reservation exactly one frame short of the buffer end and (b) triggers the continuation path ("more frames" flags, `Continue`/`Partial` states, multi-member gzip/zip, chunked encodings), then check whether a second iteration advances the write cursor past the reservation. Grep the target's source for `assert` around the safety condition — an assert-only guard is a live missing check in production; on web surfaces the same rule applies to streaming parsers (chunked transfer, multipart parts, SSE, gRPC frames, decompression bombs).

### [Bugbountyskills.md] 17.109 Hostname validation/resolution DIFFERENTIAL — a fixed 256-byte truncation makes the string the validator checks differ from the string the resolver resolves → allowlist bypass → internal IP (libuv CVE-2024-24806 / HackerOne #2429894)

DETECTION SIGNAL: (a) any write path pairing an overwrite-protection flag with a cleanup-on-error step, where the cleanup tracks a path captured BEFORE the rename/clobber suffix is applied — upload/import/export/download endpoints, temp-file workflows that rename before the error handler runs; (b) any client/proxy that REUSES one request handle and sets the method globally (`CURLOPT_UPLOAD`/`CURLOPT_POST`/`setMethod`) with the body source attached to the handle rather than passed per request.
CHAIN: attacker makes the operation FAIL after the destination path is reserved (primitive: stall the transfer / break the parse / hit the size limit) -> the cleanup deletes the path it recorded, not the file it created (primitive: error-path cleanup acts on the wrong object) -> a protected — or another tenant's — file is REMOVED while the partial artifact remains (integrity/data destruction). Separately: one handle reused across hosts (primitive: method + body-source state persist) -> the next request goes as the previous method with the previous buffer -> another principal's data or stdin bytes reach an unintended recipient (sensitive information disclosure; UAF crash path).
TRANSFERABLE TEST: (a) for each flag, ask whether it re-derives its target or reuses one captured earlier — then compose an overwrite guard with a failure-triggered cleanup and check WHICH object disappeared and which was left; (b) issue a full-body method (PUT/PATCH) then a POST/DELETE on the SAME handle to a DIFFERENT host, with the body supplied per request, and capture what the second request actually sent and where. Rule: **state that belongs to a REQUEST must not live on the pooled handle or be captured before the object is finalised — otherwise a later action lands on the wrong object.**
WHY IT IS A NEW GENERAL METHOD: this file records request SMUGGLING connection-reuse ("connection reused → remainder re-parsed") and file-write primitives, but not the pattern where a client's OWN bookkeeping — not an attacker's message — selects the wrong victim object. Reusable rule: **audit every composition of a safety feature with a cleanup or with pooled state: if the target is captured before the object is finalised, the safety feature itself becomes the destructive action.** Slot 17.191.
