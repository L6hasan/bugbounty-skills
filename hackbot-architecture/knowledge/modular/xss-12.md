CLASS: stored XSS via a SANITIZER-WHITELIST BYPASS — an XML DTD entity inside an uploaded SVG stops the element/attribute whitelist from being enforced, so an event handler is accepted on the root element and later executes inside a privileged admin origin (the app-developer dashboard AND every authorizing merchant's `$shop$.myshopify.com/admin/`).
CORE METHOD:
  1. Target an asset slot whose content is validated against an SVG ELEMENT+ATTRIBUTE WHITELIST: Shopify lets a developer upload a 16x16 SVG "Navigation icon" for a Sales Channel app, and the design-guidelines checklist limits the allowed elements and attributes.
  2. Upload an SVG whose only unusual feature is an XML DTD entity declaration, then reference the entity in the document body:
     `<?xml version="1.0" encoding="ISO-8859-1"?>`
     `<!DOCTYPE svg [ <!ENTITY elem ""> ]>`
     `<svg onload="alert(document.domain);" height="16" width="16">&elem;</svg>`
     Reporter's finding, verbatim: "when the SVG contains an XML entity this whitelist is no longer enforced allowing the developer to include malicious attributes such as `onload`". The DTD/entity is the bypass; the dangerous attribute rides in on the same document.
  3. The icon is rendered on `partners.shopify.com` (the partner/developer dashboard) → the handler fires as soon as the icon loads.
  4. To reach a MERCHANT's admin, publish the app and get the shop owner to authorize it through the ordinary OAuth screen:
     `https://$shop$.myshopify.com/admin/oauth/authorize?client_id=<app_client_id>&scope=read_products&redirect_uri=https://attacker/<nonce>.html&state=<nonce>`
     After authorization — and on every subsequent admin-panel load — the icon is rendered inside `/admin` on the shop's own myshopify origin, so the payload fires there as the merchant admin.
  5. Exploitability note from the report, worth copying as a habit: the app required NO special permissions to trigger, so an admin is more willing to authorize it; and the same stored icon may surface in OTHER sinks (app-store listing, internal admin panels) — enumerate every render location of the asset before writing the report.
DETECTION SIGNAL: any upload/preview path that advertises a whitelist for SVG/XML (a documented "allowed elements and attributes" list, a sanitizer that walks the parsed tree) — the tell is that enforcement can be disturbed by a DOCUMENT-LEVEL construct: a DTD/`<!ENTITY>`, an XML prolog, a namespace prefix, a second processing instruction. Also: one stored asset rendered on more than one origin (partner/dev dashboard + merchant/admin console) turns a single upload into an admin-context stored XSS; app-install/OAuth flows that render developer-supplied branding inside the victim's privileged UI.
CHAIN: developer (or any account able to create an app) → upload an SVG icon carrying `<!DOCTYPE svg [<!ENTITY …>]>` plus `onload` on the root `<svg>` → the whitelist validator stops enforcing → the handler is stored → rendered on `partners.shopify.com` AND, after an OAuth app authorization, inside `https://$shop$.myshopify.com/admin/` → script executes as the merchant admin on every admin load with no further interaction → admin session theft / privileged store actions (Stored XSS, $5,000.00; disclosed 2017-06-27; reporter bored-engineer).

GitLab, "Stored XSS in markdown when redacting references" (Cross-site Scripting (XSS) - Stored; High 7~8.9; $5,000; reporter vakzz; asset `gitlab.com`; disclosed 2020-09-09).
CLASS: stored XSS via a MARKDOWN REFERENCE-REDACTION pass that reads a stored html-encoded attribute back out and re-emits it as raw HTML (sanitize-on-render / decode-on-redact), escalated past `script-src 'self'` with a same-origin attacker-uploaded `.js`
CORE METHOD:
  1. Entry point = a markdown surface that links to a REFERENCE OBJECT under the app's autolink/mention/reference filter. Create your own PRIVATE project plus one issue in it, then from a SECOND account that has NO permission on that project post a comment (on any public issue) linking to it. The link points at an object the reader may not read, so the app's reference-REDACTION replace pass runs. The permission-crossing link is the trigger — no payload-bearing field is needed.
  2. Payload shape: use the raw-HTML anchor that markdown passes through, and ENTITY-ENCODE the dangerous markup so the sanitizer sees text:
     `link: <a href="https://gitlab.com/<you>/private-project/-/issues/1" title="title">xss &lt;img onerror=alert(1) src=x></a>`
  3. The redaction stores the html-encoded content in `data-original` and builds the output by string interpolation from that value with NO re-escape. The report's own code: `redacted_node_content` -> `original_content = node.attr('data-original')` ... `%(<a href="#{href}">#{content}</a>)` (Ruby, GitLab 12.9.2-ee). Because the value was encoded on the way IN and is decoded on the way OUT, the encoded tag becomes live: rendered output is `<div class="md"><p ...>link: <a href="https://gitlab.com/wbowling/private-project/-/issues/1">xss <img onerror="alert(1)" src="x"></a></p></div>`.
  4. CSP blocks the inline handler, so arm the injected markup with the app's OWN JS-framework attributes and make the click target full-viewport (report's second payload, "requires clicking anywhere on the page, but the link is full screen"):
     `link: <a href="https://gitlab.com/<you>/private-project/-/issues/1" title="title">csp` / `&lt;a data-remote=&quot;true&quot; data-method=&quot;get&quot; data-type=&quot;script&quot; href=/<you>/<proj>/wiki/raw/master/test.js class='atwho-view select2-drop-mask pika-select'>` / `&lt;img height=10000 width=10000>` / `&lt;/a>` / `</a>`
     The generated HTML is an `<a data-remote="true" data-method="get" data-type="script" href="/<you>/<proj>/wiki/raw/master/test.js">` wrapping a 10000x10000 `<img>` (a rails-ujs remote-script anchor: one click anywhere loads the href AS A SCRIPT).
  5. `script-src 'self'` defeat (reporter's comment in the same report, verified with `curl -I`): a `.js` file committed through **git-lfs** is served from the app's own origin with a JavaScript content type, so the UJS anchor loads ATTACKER code under a `'self'`-only policy — `$ curl -I 'https://gitlab.com/<you>/<proj>/-/raw/master/test.js'` -> `HTTP/2 200` / `content-type: application/javascript`. A later comment on the report says issue #3 carries a variant with a "full csp bypass not requiring user interaction".
  6. Impact per the report: "Anywhere the `ReferenceRedactor` is run arbitrary html can be injected. A user can setup their own private project, then post a comment or an issue on a public project linking to it and injecting the xss."
DETECTION SIGNAL: a filter PAIR where the first render escapes but a later REDACT/RE-RENDER/REPLACE pass reads a STORED raw value back out (`data-original`, `data-raw`, `data-text`, a serialized `title`, a tooltip/copy buffer) and interpolates it into the page — especially when that pass runs only for a viewer who LACKS permission on the linked object (so proving it needs a second account); the redaction feature itself is the bug surface ("redacting references", "restricted", "confidential", "you don't have access to this object" renderers); rails-ujs / framework helpers that turn an ATTRIBUTE into a script or request load (`data-type="script"`, `data-remote="true"`, `data-method`, htmx/`x-on`/Alpine `@`/`ng-`attributes) — a sanitizer that allows generic attributes lets the app's own JS library pull the trigger; `script-src 'self'`/`'strict-dynamic'` where the app stores user files (git-lfs, wikis, attachments, raw endpoints, S3/asset hosts) — fetch a user-uploaded `.js` and read its `Content-Type`.
CHAIN: low-privileged account -> post a markdown comment whose raw `<a>` links to a private/unauthorized object and whose inner HTML is ENTITY-ENCODED -> the redaction pass decodes the stored `data-original` and re-emits it as HTML -> live markup plus a `data-type="script"` remote anchor is stored in the comment -> CSP `script-src 'self'` is defeated by a same-origin `.js` stored through git-lfs and served as `application/javascript` -> script executes in every victim's authenticated session on every markdown surface (issues, comments, merge requests) -> API-token/session theft -> account takeover (Stored XSS; High 7~8.9; $5,000).
TRANSFERABLE TEST: post a markdown comment that (a) LINKS to a private/unauthorized object you own so the redaction pass runs for the reader and (b) wraps the markup in a raw `<a>` with the payload ENTITY-ENCODED (`&lt;img onerror=alert(1) src=x>`); re-read the rendered HTML as the OTHER account — a live `<img onerror>` proves the decode-on-redact bug. STATUS: UNVERIFIED (not reproduced — Flash Player reached EOL 2020-12-31 and the PoC `crash.swf` is a private HackerOne attachment; the body nevertheless states entry point, root cause and escalation concretely)
CLASS: use-after-free of a NATIVE SDK object that untrusted script can free through an EXPLICITLY EXPOSED `release()` member → stale-reference VIRTUAL CALL → attacker object reclaiming the freed slot → code execution (RCE class; memory-corruption depth LAB-ONLY)
CORE METHOD (verbatim `crash.swf` from the body):
  1. Take the native media-SDK singleton and hold TWO live references to the SAME instance: `var ps:PSDK = PSDK.pSDK; var ps_:PSDK = PSDK.pSDK;` (`com.adobe.tvsdk.mediacore.PSDK`).
  2. Call the object's own `ps.release();` — it frees the inner native memory of `PSDK.pSDK`, but the report's root cause is that "Not all of PSDK's AS3 references are cleaned", so `ps_` still points into the freed block.
  3. Touch any member through the stale reference (`ps_.currentTime;`) → a virtual function is invoked on released memory → UAF at a site the reporter calls "highly controllable".
  4. Escalation stated by the reporter: "it is feasible to build a fully working exploit for shellcode execution with proper AS3 object occupied the original PSDK memory" — reclaim the freed allocation with a same-size attacker-controlled AS3 object so the virtual call dispatches through attacker data.
DETECTION SIGNAL: any API that exposes an explicit free/destroy/release/close/dispose member to untrusted script while other references to the same native object stay live (singletons/global handles of native objects: media SDK, file/camera/USB/socket handles, workers, plugin handles); a deterministic crash on a getter or virtual method called immediately after the release; a fault address inside memory the script can influence.
CHAIN: script holds two references to a native singleton → `release()` frees native memory but leaves the AS3 reference → a virtual call through the stale reference → an attacker-shaped AS3 object reclaims the freed block → controlled virtual dispatch → shellcode execution in the plugin process (memory-corruption depth stays LAB-ONLY per doctrine; on a web surface the reportable form is a client crash/DoS or the first link of a sandbox-escape chain).
TRANSFERABLE TEST: for any runtime/plugin/desktop API that lets script call an explicit free/destroy/release/dispose (media object, file handle, camera/USB/socket handle, plugin/extension object), hold a SECOND reference, free through the first, then immediately call a method/getter through the second. A deterministic crash whose fault address you influence is the primitive; the exploit step is grooming a same-size attacker object into the freed slot so the virtual call lands in attacker data. LAB-ONLY.

Internet Bug Bounty, "Adobe Flash Player Out-of-Bound Read/Write Vulnerability" (Memory Corruption - Generic; CVE-2014-0564; $5,000; reporter hhj4ck; submitted 2014-10-15; disclosed 2015-03-11; 2 votes).
STATUS: UNVERIFIED (not reproduced — Flash EOL; PoC `OBRW.rar` is a private attachment and was hosted off-site)
CLASS: out-of-bounds read/write from a STALE RECURSION-LOCAL POINTER while a parser's fixed-size workspace is relocated to the heap → OOB copy → typed-array LENGTH-FIELD overwrite → arbitrary read/write (RCE class; memory-corruption depth LAB-ONLY)
CORE METHOD (everything the public body states):
  1. Trigger by compiling a malformed regex with repeated FORWARD references: `var exp:RegExp = new RegExp("(?:(VenusTech)(?2){0,1020}(b))?")` — normally a crash from an out-of-bounds read of stack memory.
  2. Root cause: the compiler keeps a FIXED-SIZE stack workspace `cworkspace`; repetitions of forward references fill it, so an "expanding" mechanism replaces it with a large heap block and updates the cworkspace pointers — but "the updating of cworkspace pointers happens inside a recursively called function", and "a local variable of cworkspace pointer is not synchronizing upon different calls".
  3. A later copy of the workspace content therefore runs from the stale (stack) pointer to the new heap pointer — reading/writing below the frame, out of bounds, stack→heap.
  4. Escalation: with heap feng shui (an attacker-controlled heap block placed adjacent), the same copy "may allow the modification to the length field of Vector.<int>, gaining attacker the ability to read and write arbitrary memory address"; failing that, the OOB READ alone leaks ActionScript object / OS struct addresses to bypass ASLR.
DETECTION SIGNAL: a parser/compiler whose workspace or lookaside buffer starts on the STACK and is relocated to the HEAP when it grows (`realloc`/"expanding"/"grow" path) — especially when the relocation runs inside recursion or a callback and the base pointer is cached in a LOCAL variable; input shapes that are self-referential (regex back/forward references, recursive includes, cyclic graph nodes, nested templates) and can force the buffer to grow repeatedly; a crash where the copy bounds come from two different allocations.
CHAIN: attacker-controlled pattern (regex/rule/template/config input) → workspace growth during recursion leaves a stale local pointer → OOB stack read/write → attacker-shaped object placed adjacent → `Vector.<int>` length-field overwrite → arbitrary memory read/write → with an info leak, arbitrary code execution (LAB-ONLY; bare memory corruption is not a §1 class — what is recorded here is the primitive plus its documented escalation).
TRANSFERABLE TEST: feed any recursive parser you can reach (regex fields, search/filter/sort expressions, template/expression languages, XML/JSON/YAML parsers, image/archive decoders) a SELF-REFERENTIAL input that makes its growable workspace relocate many times (deep nesting + repetition of a back-reference), then look for a crash or a corrupted length/size field. The exploitable step is controlling what sits next to the relocated buffer — target a length field of a typed array/string/vector to convert OOB into arbitrary R/W. LAB-ONLY.

STATUS: UNVERIFIED (not reproduced — Flash EOL; PoC `crash.swf` is a private attachment; the public body is three sentences)
CLASS: TYPE CONFUSION through an INTERNAL, undocumented native dispatch entry callable from script (`ASnative(101,10)`) → invalid EIP → instruction-pointer hijack → shellcode (RCE class; memory-corruption depth LAB-ONLY)
CORE METHOD (all the body states):

Internet Bug Bounty, "Adobe Flash Player TimedEvent.parent Memory Corruption Vulnerability" (Memory Corruption - Generic; CVE-2016-4182; $5,000; reporter hhj4ck; submitted 2016-07-13; disclosed 2019-11-12; 1 vote).
STATUS: UNVERIFIED (not reproduced — Flash EOL; PoC `poc.swf` is a private attachment)
CLASS: UNINITIALIZED pointer field + deliberate heap grooming → the victim object is built over a released block the attacker filled with a known pattern → fake object / type-confused class pointer → code execution (RCE class; memory-corruption depth LAB-ONLY)
CORE METHOD (verbatim `poc.swf` from the body):
  1. Spray a recognisable pattern into a ByteArray: `bytes.endian = Endian.LITTLE_ENDIAN; for(var i:int=0;i<0x100/4;i++) bytes.writeUnsignedInt(0x13371337);`

CHAIN: attacker script grooms the heap with a known 4-byte pattern held by a runtime metadata object → the victim object is allocated over that memory → its uninitialized field yields a fake object → type-confused class pointer → code execution in the runtime process (LAB-ONLY).
TRANSFERABLE TEST: for any runtime with partially initialized object layouts (native SDK/extension objects, FFI structs, C++/Rust extension types, JIT objects, deserialized records), find a field set only on some paths; groom the same size class with a recognisable pattern, free it, then cause the victim allocation and call a method that dereferences the unset field. CORE METHOD:
  1.
