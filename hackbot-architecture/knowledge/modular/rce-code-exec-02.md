SOURCE: https://hackerone.com/reports/861744 — Elastic, "Remote Code Execution in coming Kibana 7.7.0" (Privilege Escalation; bounty; reporter alexbrasetvik; created 2020-04-28; disclosed 2021-04-19)  read 2026-11-07 (route: full 3,414-B reporter body from the LOCAL dataset mirror `/tmp/h1_train.parquet`, `visibility: full`; corroborated the same day by `https://api.osv.dev/v1/vulns/CVE-2024-37287` — "Kibana arbitrary code execution via prototype pollution … attacker with access to ML and Alerting connector features, as well as write access to internal ML indices", introduced 7.7.0, fixed 7.17.23 / 8.14.2 — and by the Metasploit module `kibana_upgrade_assistant_telemetry_rce.rb`, which credits alexbrasetvik and uses `'constructor.prototype.sourceURL' => "\u2028\u2029\nglobal.process.mainModule.require('child_process').exec(...)"`)

CHAIN: any authenticated user with write access to internal data indices ("like any Cloud user would have") -> anomaly document keyed `foo.__proto__.sourceURL` with a `\u2028\u2029\n;`-prefixed value -> signal builder folds the key => prototype pollution -> generated source context broken out of -> `child_process.exec` -> RCE as the Kibana process (critical scope; CVE-2024-37287 stayed exploitable from 7.7.0 until 7.17.23 / 8.14.2).
TRANSFERABLE TEST: send `{"a":{"__proto__":{"zzprobe":"1"}}}` (also `constructor.prototype`) through every document/object/rule/dashboard/connector write API and confirm the write in the server's own JS context; then target a property name the code SYNTHESIZES rather than reads (`sourceURL`, `env`, `shell`, `NODE_OPTIONS`, `input`, `code`) and put `\u2028\u2029\n;<statement>` in the value. WHY IT IS A NEW GENERAL METHOD: this ledger only had CLIENT-side prototype pollution into a DOM sink (#998398, §1.3). Here the pollution is SERVER-side inside an index-driven pipeline and the escalation is a code-generation gadget — the two halves to hunt are the merge sink and the property name the generated code reads.

### [Bugbountyskills.md] 17.121 DNS rebinding via `0.0.0.0` + macOS `.local` DNS to read the Node inspector's `webSocketDebuggerUrl` and drive it over the SOP-exempt WebSocket → RCE (Node.js CVE-2022-32212 / HackerOne #1714979, orig. #1632921)

Generalise: any loopback management/debug interface guarded only by a Host/Origin check that accepts unusual literals is rebindable.
WHY IT IS A NEW GENERAL METHOD: the file already has the generic SSRF DNS-rebinding bypass and a desktop-app loopback WebSocket-without-`Origin` note; §17.121 adds the SPECIFIC `0.0.0.0`+macOS-`.local` bypass of a HOST check and aims it at a local DEBUG port to reach RCE — a new entry surface (developer debugger/agent ports), not another SSRF rebinding.

### [Bugbountyskills.md] 17.151 A server-side JS engine given LIVE serializer objects: coerce its OVERLOAD RESOLUTION into constructing a serializer with attacker `TypeNameHandling` → deserialization RCE (8x8 Connect Automation Builder / Jint→Newtonsoft)

SOURCE: https://hackerone.com/reports/3861550 — 8x8, *"connect.8x8.com: Deserialization Vulnerability in Automation Builder via Jint→Newtonsoft serializer coercion (TypeNameHandling)"* (Deserialization of Untrusted Data; **Critical 9.9**; $3,000; reporter **kyotozzx**; created 2026-07-13, disclosed 2026-09-01; asset connect.8x8.com)  read 2026-11-07 (only the VENDOR summary/timeline/JSON metadata render — `visibility: no-content`; the researcher's body and PoC are not public, so no payload or parameter is asserted here)
CLASS: insecure deserialization reached through TEMPLATE EVALUATION — a .NET JavaScript interpreter handed raw Newtonsoft JSON objects rather than plain values can be steered, by attacker-controlled DATA, into building a serializer with attacker-chosen settings.
CORE METHOD (vendor's own wording):
  1. Entry point: the Automation Builder's HTTP request step — an AUTHENTICATED user's automation makes an outbound request, and the RESPONSE is fed to server-side template evaluation.
  2. The evaluator runs that response through Jint, and the response arrived as raw Newtonsoft objects, not plain JS values: "server-side template evaluation exposed Newtonsoft JSON objects directly to the Jint JavaScript engine".
  3. Because the template scope can call methods on those live host objects, a "specially crafted JSON response" steers overload resolution: the attacker "could coerce Jint's overload resolution to construct a `JsonSerializer` with attacker-controlled `TypeNameHandling` settings".
  4. `TypeNameHandling != None` means `$type` in JSON is honoured → "deserialization of arbitrary .NET types including `System.Diagnostics.Process`" → command execution in the worker (rated Critical 9.9, $3,000).
  5. Fix names the defect precisely: "projecting HTTP responses to plain JavaScript values (`System.Dynamic.ExpandoObject`) before template evaluation, removing all Newtonsoft object exposure from the template scope".
DETECTION SIGNAL: an expression/template/no-code step evaluated IN-PROCESS over data you influence (a .NET engine — Jint/ClearScript/Jurassic/Razor/NCalc — fed an HTTP response, upload or webhook body); host objects visible to the script (the template can name `JObject`/`JToken`/`JsonConvert`/`JsonSerializer`); `TypeNameHandling` anywhere but `None` with a null `SerializationBinder`; JSON accepted with `$type`/`$values`/`$ref` (test key ORDER — `$type` must lead the object); no `System.Dynamic.ExpandoObject` projection in the render path (its absence is the tell, its presence the fix).
CHAIN: authenticated user builds an automation with an HTTP step → their endpoint returns JSON crafted for the evaluator → template evaluation exposes a live Newtonsoft object to the JS scope → the template call binds, via overload resolution, to a serializer constructor that accepts settings → serializer built with attacker `TypeNameHandling` → `$type` instantiates `System.Diagnostics.Process` → command execution in the worker. Shape: "attacker influences a string the template evaluates" (P4-grade primitive) + "the template scope owns a serializer" = P1.
TRANSFERABLE TEST: point every automation/template HTTP step at a listener you control and return JSON whose FIRST key is `$type` naming a type (the vendor names `System.Diagnostics.Process`), then, in the same expression language, try to reach a serializer factory taking a settings/config object (`JsonSerializer.Create`, `CreateDefault`, `DeserializeObject`) and echo the result into the rendered output to learn whether it is a live host object or a plain value; confirm execution by DNS/HTTP callback only. The probes are generic TypeNameHandling tests, not the reporter's PoC (not public).
WHY IT IS A NEW GENERAL METHOD: §17.3 reaches RCE through the Node `$where`/`new Function` sink, §17.63 through AngularJS CSTI, §17.98 through an attacker-named JAAS module — none needs the injection of template SOURCE or a script sink. This records the pure OBJECT-path escalation: no code injected into the template at all; the attacker's DATA makes the engine's own overload resolution construct the dangerous serializer.

### [Bugbountyskills.md] 17.193 TLS SESSION-TICKET RESUMPTION state is not isolated per virtual host — a ticket minted by the mTLS vhost the attacker MAY use resumes against the vhost it may NOT, so the second vhost's client-authentication policy is never evaluated (nginx multi-vhost mTLS, Internet Bug Bounty #2978267)

SOURCE: https://hackerone.com/reports/2978267 — Internet Bug Bounty, "TLS client authentication can be bypassed due to ticket resumption" (Medium; no CVE in the record; PoC withheld by the reporter)  read 2026-11-08 (`visibility: full`, whole body via `curl .../2978267.json`).
CLASS: authentication bypass / privilege escalation via shared TLS resumption state (mTLS context confusion; the resume path skips the vhost's client-auth check).
CORE METHOD: one server hosts virtual hosts A and B, BOTH requiring client certificates but with DIFFERENT configurations; the attacker is entitled to A and not to B. (1) "TLS session tickets are not properly isolated for multiple virtual hosts in one server. That is, a ticket issued for one virtual host, may be resumed at a different virtual host"; "tickets are always resumed". (2) Connect to A, complete the mTLS handshake, receive the session ticket. (3) Connect to B presenting that ticket — the handshake RESUMES instead of re-authenticating, so B's client-auth rule is never evaluated. (4) The SNI detail that makes it work: "If the HTTP host header and TLS SNI value diverge, the server correctly returns a 421 (if client authentication is used). However, if the SNI is chosen appropriately (changed to resumption host, or omitted), nginx allows the Host header to specify the second site" — i.e. keep SNI at the vhost that issued the ticket (or omit it) and put the TARGET host only in `Host:`. (5) Secondary: nginx "uses the wrong key material on the second virtual host to encrypt the tickets" (no extra impact claimed).
DETECTION SIGNAL: TLS termination with session tickets at the default across multiple vhosts/server blocks/SNI names, where at least one vhost requires CLIENT CERTIFICATES and the mTLS policy lives in the vhost config rather than in the ticket/resumption key; a second handshake that is RESUMED (`ssl_session_reused=1`, abbreviated handshake) against a vhost whose client certificate would fail a fresh handshake; the SNI≠Host → 421 behaviour as a probe oracle.
CHAIN: attacker holds a client-certificate identity for vhost A only (primitive: one legitimate mTLS identity) -> captures/keeps the session ticket from A (primitive: ticket not bound to the issuing vhost) -> resumes it against vhost B with SNI pinned to A or omitted and `Host:` set to B (primitive: the SNI/Host cross-check that would return 421 is bypassed) -> B's client-authentication requirement is never evaluated and B's content/API is reachable (privilege escalation / authentication bypass).
TRANSFERABLE TEST: on any multi-vhost TLS endpoint, (1) map which SNI names require client certificates; (2) open a session to a vhost you ARE authorised for and keep its ticket/session, then connect to the OTHER vhost reusing it while (a) overriding `Host:`, (b) omitting SNI, (c) leaving SNI at the first vhost; (3) confirm via `ssl_session_reused` in the server log or a handshake diff — content served without re-validating your certificate means the resumption context is not isolated. Rule: **TLS resumption state IS an authentication decision — tickets and the session cache must be keyed/bound to the SNI or vhost whose policy issued them, because a resumed handshake skips the policy check.**
WHY IT IS A NEW GENERAL METHOD: this file's connection-reuse material is CLIENT-side (§17.190 a pool's reuse key; §17.188 credentials re-sent across host+scheme) and the request-smuggling entries reuse a TCP/request stream. Neither records the SERVER-side case where the confused state is the TLS session-ticket cache and the consequence is an AUTHENTICATION BYPASS: the same class of mistake (reuse state keyed on something narrower than the policy that produced it) sitting in the TLS layer instead of the HTTP layer. Slot 17.193.
