CORE METHOD:
  1. THE ENCODING (verbatim): the block's "Data hash" is NOT the commented Merkle tree ("// The hash of the BlockData, by MerkleTree" — "actually it is far from being the case"); instead "the transactions in the block are concatenated to one another, creating a big long byte array and then this big long byte array is hashed" — no delimiters, no length prefixes: `$$$$$$$$$$$$*************@@@@@@@@@@@@%%%%%%%%%`.
  2. THE BYPASS (verbatim): "An adversary can't change the bytes of the concatenation, however what it can do, is to modify how transactions are encoded in the block" — MERGE two adjacent transactions into one record: `|$$$$$$$$$$$$*************|@@@@@@@@@@@@|%%%%%%%%%|` ("a block with the above transactions has the same concatenation of bytes as the original block, but the block has one less transaction — the first transaction is a concatenation of the first and second transactions in the original block").
  3. WHY THE MERGE PARSES (verbatim): "When the peer receives this block, it looks at the first transaction and when it parses it, it completely ignores the `***` bytes" — the record parser tolerates TRAILING BYTES inside an element, so the surplus bytes vanish at parse time while staying in the hashed string.
  4. THE PROOF (verbatim): Raft orderer "Created block [10] with 2 transactions"; after "I just modified only its transaction content (without modifying the block hash)" the peer logs "[testchannel] Committed block [10] with 1 transaction(s)" at the SAME commitHash — "the peer does not detect any tempering was done to the block.
