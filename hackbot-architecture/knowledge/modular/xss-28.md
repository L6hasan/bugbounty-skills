Metadata: #1524692 Node.js team (assigned re-submission sits in Internet Bug Bounty), "HTTP Request Smuggling Due To Improper Delimiting of Header Fields", weakness HTTP Request Smuggling, medium, reporter `zeyu2001`, created 2022-03-28, disclosed 2022-07-07; CVE-2022-32214; llhttp in the `http` module of Node v17.8.0.
STATUS: UNVERIFIED (not reproduced as an exploit — see MEASURED NEGATIVE in the pass note: the exact payload is REJECTED by the Node on this host)
CLASS: HTTP request smuggling (CVE-2022-32214) — the FIELD DELIMITER is lenient: a lone LF (no CR) ends a header line whose value is NON-EMPTY, so the next line becomes a genuine header on the lenient side while a CRLF-strict peer keeps both lines inside ONE header value.
CORE METHOD (the report's own text and payload):
  1. The defect: "The LF character (without CR) is sufficient to delimit HTTP header fields in the `lihttp` parser. According to RFC7230 section 3, only the CRLF sequence should delimit each `header-field`."
  2. State the PAIR of upstream properties the chain needs, because they are the whole point: the proxy "Correctly delimits lines by the CRLF sequence instead of only LF" AND "Incorrectly allows the LF character in header values". With that pair, the proxy reads the smuggled line as part of a value (so its `Content-Length` for request 1 is 0) while Node reads it as a header.
  3. The payload (all lines CRLF except the marked `[\n]`):
     `GET / HTTP/1.1` / `Host: localhost` / `Dummy: x[\n]Content-Length: 23` / blank / `GET / HTTP/1.1` / `Dummy: GET /admin HTTP/1.1` / `Host: localhost` / blank
     — i.e. one `\n` (0x0A, no 0x0D) between a harmless header's value (`Dummy: x`) and the header you want the back-end to honour (`Content-Length: 23`).
  4. Raw sender: `(printf "GET / HTTP/1.1\r\n" "Host: localhost\r\n" "Dummy: x\nContent-Length: 23\r\n" "\r\n" "GET / HTTP/1.1\r\n" "Dummy: GET /admin HTTP/1.1\r\n" "Host: localhost\r\n" "\r\n" "\r\n") | nc localhost 80`. The bytes after the injected length are the attacker's OWN pipelined request, and its first line becomes the body of request 1 (23 bytes = `GET / HTTP/1.1\r\nDummy: `).
  5. Read the differential, not the status: "Expected result: Sees two requests, both to `/`. Actual result: Sees one request to `/` and another to `/admin`." Observed on Node: request 1 = `{"URL":"/","Headers":{"host":"localhost","dummy":"x","content-length":"23"},"Length":23,"Body":"GET / HTTP/1.1\r\nDummy: "}` and request 2 = `{"URL":"/admin","Headers":{"host":"localhost"},"Length":0,"Body":""}` — the second request reaches the application with a path the front-end never saw as a separate request.
  6. Because the injected header is `Content-Length` (not `Transfer-Encoding`), no framing header is obfuscated at all: the desync is manufactured by the DELIMITER ALONE, and the smuggled unit is a complete request with an attacker-chosen path.
DETECTION SIGNAL: an HTTP/1 hop whose parser accepts a bare LF as a field terminator while its peer requires CRLF; the fingerprinting probe is a request carrying `Dummy: x\nContent-Length: <n>` (bare LF) plus a pipelined second request — one side answers two requests, the other one. Same family tell: any WAF/proxy rule set that validates header VALUES by regex over the raw text (it sees one value `x\nContent-Length: 23`) sitting in front of an engine that splits on LF.
CHAIN: an attacker-written request with a lone-LF line break inside a header VALUE (primitive: no credentials, any client) → the lenient back-end promotes the next line to a real `Content-Length` header (primitive: parser differential — the front-end keeps it inside a value, so its view of request 1 is body-length 0) → the attacker's second request rides as the FIRST request's body and is processed as an independent request by the back-end (escalation) → the smuggled request reaches endpoints/paths the edge would never have authorised for the attacker's connection, and its response is delivered to the next user on the shared connection (impact: access-control bypass, cache poisoning, credential/response theft — the report's own impact wording: "cache poisoning, bypassing of security layers, stealing of credentials and so on") — P2, P1 where the poisoned resource is site-wide. RELATED-BUT-DISTINCT from the recorded leniency pair (CVE-2022-35256's EMPTY-valued header + lone LF *for TE obfuscation*, and §17.236's single-LF BLOCK-termination detector): here the header HAS a value, the injected header is `Content-Length`, and the smuggled bytes are the attacker's own pipelined request rather than a hijacked victim request.
TRANSFERABLE TEST: on any front-end→back-end HTTP/1 pair, send one clean control (proper CRLF, `Content-Length: 1`, body `A`) and confirm both ends agree, then replace ONE CRLF inside a header region with a bare LF: `Dummy: x` + `\n` + `Content-Length: <len-of-your-next-request>` + `\r\n` + blank + your second request. Declare it found when the back-end reports TWO requests (second one at your chosen path, reported body length 0) while the front-end reports ONE with body length 0 — and keep the empty-value variant (`x:\n`) and the bare-CR variant in the same probe set, since a parser may be lenient on one and strict on the other. RULE: a delimiter is as attacker-controlled as a value — never test header VALUES alone; test the byte BETWEEN lines, and prefer the variant that injects `Content-Length` (no framing header to obfuscate, and the smuggled unit is a whole request with your path in it).

STATUS: UNVERIFIED (not reproduced as an exploit — MEASURED NEGATIVE in the pass note: rejected with 400 by the Node on this host)
CLASS: HTTP request smuggling (CVE-2022-32215) — CODING PRECEDENCE inside an obs-folded `Transfer-Encoding`: the parser stitches continuation lines with SP for the VALUE it exposes to the application, but decides the FRAMING from a coding it saw before/independently of that normalisation, so it frames as `chunked` while the value it hands the app — and any peer that reads the value correctly — ends in a non-chunked coding.
CORE METHOD (the report's own text and payloads):
  1. The payload is a `Transfer-Encoding` header with an obs-fold continuation line that adds a SECOND coding, and it is only valid because the parser accepts multi-line header values: `GET / HTTP/1.1` / `Transfer-Encoding: chunked` / ` , identity` / blank / `1` / `a` / `0` / blank (raw: `printf "GET / HTTP/1.1\r\nTransfer-Encoding: chunked\r\n , identity\r\n\r\n1\r\na\r\n0\r\n\r\n"`).
  2. Observed: `{"Headers":{"transfer-encoding":"chunked , identity"},"Length":1,"Body":"a"}` — "it processes the final encoding as `chunked`" even though the folded value's final coding is `identity`. The application receives the UNNORMALISED, invalid value `chunked , identity`.
  3. The differential is the point: "An upstream proxy that correctly implements multi-line header values will therefore process the final encoding as `identity` instead. This could lead to request smuggling as an `identity` header indicates that the body length is 0 — the upstream proxy and Node will disagree on where a request ends."
  4. Why it survived the fix: the report names the lineage — "This could be seen as an incomplete fix to #1002188, though it is a slightly different issue. The fix for #1002188 processed subsequent `Transfer-Encoding` headers, only setting the `chunked` encoding if the last `Transfer-Encoding` header is `chunked`. This should be extended to check for subsequent LINES of the same `Transfer-Encoding` header." So the guard counts HEADERS, not the folded VALUE.
  5. The report's own variant shows the smuggled-request form (duplicate-TE replaced by a multi-line one): `POST / HTTP/1.1` / `Host: 127.0.0.1` / `Transfer-Encoding: chunked` / ` , chunked-false` / blank / `1` / `A` / `0` / blank / `GET /flag HTTP/1.1` / `Host: 127.0.0.1` / `foo: x` / blank.
  6. RFC context the report cites for why a strict peer is allowed to disagree: RFC7230 §3.2.4 requires an obs-fold to be replaced by SP "prior to interpreting the field value" — "While Node correctly replaces each received `obs-fold` with SP octets, in the case of the `Transfer-Encoding` header it does not do so prior to interpreting the field value."
DETECTION SIGNAL: any engine in the chain that accepts an obs-fold / continuation line (leading SP or TAB) INSIDE `Transfer-Encoding`, and whose value is exposed un-normalised (`chunked , identity`, `yeet, , chunked`, `chunked , chunked-false`); the probe oracle is a three-way set — plain `Transfer-Encoding: chunked` (both sides chunked), `Transfer-Encoding: chunked` + folded ` , identity` (lenient side chunked, strict side CL 0), and a duplicate/multi-line `chunked`, `chunked-false`. The tell is framing that follows one coding while the value's LAST coding disagrees.
CHAIN: an attacker-written `Transfer-Encoding` with a folded continuation coding (primitive: any request to a front-end→back-end HTTP/1 hop, no credentials) → the lenient back-end frames it as `chunked` while a correct reader of the same value derives `identity`/length 0 (primitive: obs-fold normalisation applied to the exposed value but not to the interpretation) → the two disagree on where request 1 ends = TE.CL / CL.TE desync (escalation) → the smuggled prefix executes against the next request on the shared connection ⇒ access-control bypass, cache poisoning, credential theft (the report's own impact wording) — P2, P1 where the poisoned resource is site-wide. RELATED-BUT-DISTINCT from the recorded obs-fold material (CVE-2022-32213's `Transfer-Encoding: chunked` + folded ` abc` patch bypass; #1675191's triple-folded `yeet` / empty / `chunked`): those rely on the fold making the token UNRECOGNISABLE or repeating it, whereas here the fold adds a NON-CHUNKED coding that the lenient side ignores and the strict side honours — the exploitable axis is WHICH CODING WINS, not whether the token is seen.
TRANSFERABLE TEST: keep one clean chunked request as the control, then attach a continuation coding to `Transfer-Encoding`: ` , identity`, ` , chunked-false`, ` , gzip` (leading SP, then a comma and a second token) and watch framing — if the body is de-chunked while the exposed value's last coding is not `chunked`, the hop is desynced; send a victim-shaped request on the same connection and see whose response comes back. RULE: when a parser normalises a folded value for the APPLICATION but interprets the value BEFORE normalising, the differential is "which coding wins" — test every coding you can put after the fold, not just a repeat of `chunked`; and when a fix guards "the last HEADER", re-test with the same token moved into a folded LINE of the same header.

CLASS: broken access control / missing SCOPE enforcement — an OAuth access token carrying only a READ scope is accepted by an UNDOCUMENTED, internal-use WRITE route, because that route was never annotated with the scope it requires (and never restricted to first-party apps).
CORE METHOD (verbatim from the two summaries in the archived report JSON):
  1. Researcher summary (`category: "researcher"`, user `cybxis`): "By using the endpoint `/2/account/change_name` to change the user's full name, I found out that it accepts OAuth requests but does not validate scope limitation. Newly-scoped platforms are the best hunting ground: the migration covers the documented surface and leaves the internal routes unannotated.
CHAIN: any OAuth integration registered by the attacker, even one asking for a single read scope the users happily grant (primitive: no privileged role, no user interaction beyond the ordinary consent screen) → the token is accepted by an undocumented internal write route whose scope annotation was never added during the platform's transition to scoped access (primitive: missing function-level authorization / scope check) → the attacker rewrites the account name of ANY user who authorized the app (escalation: authenticated identity modification, reversible and repeatable, not a read) → and because the token is per-user and app-wide, the same one request is a bulk modification of the whole user base (impact: integrity of account identity at scale; rated medium / $1,728 upstream because no data or funds moved). Chain-only note: the reaction is to treat EVERY minimal-scope token as a probe credential, not just as a read token.
TRANSFERABLE TEST: take the least-privileged token the platform will give you (a read-only scope on an OAuth app you register yourself) and enumerate the API's WRITE-shaped and internal routes against it — from the docs, from the JS/mobile bundle, and from versioned prefixes the docs omit (`/2/…`, `/v3/…`, `/internal/…`) — sending the same minimal `Authorization: Bearer <read-token>`. A 200/domain error where you expected `missing_scope`/`insufficient_scope` IS the finding; then check whether the token is per-user (i.e. the impact multiplies over every user of the integration). RULE: when a platform migrates to scopes, the enforcement lives in per-route annotations — hunt the routes that are not in the SDK, and judge the response by its ERROR VOCABULARY, not by the documented permission list.
