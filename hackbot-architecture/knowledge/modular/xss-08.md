### [Bugbountyskills.md] 17.683 A SIGNATURE CHECK WHOSE SIGNER NAME, SIGNER CERT AND REVOCATION DATA ALL RIDE THE CHANNEL BEING MITM'D VERIFIES NOTHING: FROM A HOSTNETWORK+CAP_NET_RAW WORKLOAD, FORGE THE NODE'S PLAINTEXT METADATA DIALOGUE AND SUPPLY YOUR OWN CHAIN — ON EKS THE EC2-INSTANCE-CONNECT VERIFIER DERIVES `expected_signer="managed-ssh-signer.${region}.${domain}"` FROM METADATA-SUPPLIED VALUES AND FETCHES THE SIGNER CERT + OCSP OVER THE SAME HTTP CHANNEL, SO A LET'S ENCRYPT CERT FOR THE DERIVED NAME PLUS A SELF-SIGNED KEY LIST BECOMES ROOT (champtar, "Metadata service MITM allows root privilege escalation (EKS / GKE)", https://github.com/champtar/blog/tree/main/Metadata_MITM_root_EKS_GKE, writeup 2021-02-28, events 2020-06-15 → 2021-02-10; Google bounty, AWS fix commit c15b99fa "verify the domain", GKE fix `iptables -w -t mangle -I OUTPUT -s 169.254.169.254 -j DROP`; read 2026-11-12; UNVERIFIED — not reproduced). PRIMITIVE (verbatim): "`CAP_NET_RAW` ... is enabled by default in Docker/Containerd, but not in cri-o since 1.18" + `hostNetwork: true` (alternate MITM vector: K8S CVE-2020-8554 ExternalIPs). GKE leg (same family as §17.580, not re-taught): the host long-polls `http://169.254.169.254/` for authorized ssh keys ("HTTP long pooling ... 1min+"), and from a raw socket you forge the response with correct TCP seq ("it's pretty easy using Scapy to forge TCP packets"; the author's Go/gopacket PoC because "scapy was often slower to inject packets than the metadata service to respond"); L2-on-lo is blocked by `rp_filter=1`, L3 was blocked later by the OUTPUT drop above. EKS leg — the method: the AMI runs `AuthorizedKeysCommand /opt/aws/bin/eic_run_authorized_keys %u %f`, whose `eic_curl_authorized_keys` pulls over HTTP: a metadata-v2 token, instance-id (checked against `/sys/devices/virtual/dmi/id/board_asset_tag`), `placement/availability-zone` -> region, `services/domain` -> TLD, and "With 5 and 6 we deduce the expected CN of the signer certificate: expected_signer=\"managed-ssh-signer.${region}.${domain}\"", then `managed-ssh-keys/signer-cert/` (+chain), `signer-ocsp/` responses, and the signed `active-keys/USER/` list; `eic_parse_authorized_keys` "checks that the certificates match expected_signer, is trusted and with valid OCSP responses" — but "an attacker able to perform a MITM ... can inject responses for 4/6/8/9/10/11 and then SSH as root": "managed-ssh-signer.us-east-2.amazonaws.com signed by Amazon is trusted; managed-ssh-signer.us-east-2.champetier.net signed by Let's Encrypt can also be trusted with the right responses". Serve: LE cert for `managed-ssh-signer.us-east-2.<your-domain>` + chain + self-generated OCSP (`openssl ocsp -no_nonce -issuer ... -respout`, base64 per SHA1) + a key list (`#Timestamp=2147483647 / #Instance=$(curl http://169.254.169.254/latest/meta-data/instance-id/ -s) / #Caller=wedontcare / #Request=wedontcare` + your `ssh-ed25519` pub) signed by your key (`openssl dgst -sha256 -sigopt rsa_padding_mode:pss -sigopt rsa_pss_saltlen:32 -sign privkey.pem`), then `ssh root@127.0.0.1`. DETECTION SIGNAL: a workload with `hostNetwork` + `CAP_NET_RAW` (Docker/Containerd default); a node-side agent that pulls TRUST DECISIONS (signer identity, cert, OCSP, key lists) over link-local HTTP at run time; an expected-identity string computed from values that arrive on the same channel. TRANSFERABLE TEST: from inside a pod, `capsh --print` + `tcpdump -i any 'host 169.254.169.254'` (Azure: `168.63.129.16`); catalogue every periodic node-side metadata fetch and what its responses decide; wherever a response carries signature/cert/OCSP/keys, check if the EXPECTED identity derives from same-channel data — if yes, mint a publicly-trusted cert for the derived name and sign your own payload (L3 raw socket to race the reply). Rule: **a signature check whose signer name, signer cert and revocation data all ride the channel being MITM'd verifies nothing — supply your own chain and sign your own keys; and any hostNetwork+CAP_NET_RAW workload is one forged metadata response away from node root.**

### [Bugbountyskills.md] 17.689 WHEN VALIDATION AND FETCH PARSE THE SAME STRING DIFFERENTLY, THE HOST THE FILTER SEES IS NOT THE HOST THE REQUEST HITS — FUZZ FOR THE DISAGREEMENT INSTEAD OF ENUMERATING PAYLOADS: A TAB (`\x09`) INSIDE THE HOSTNAME IS *STRIPPED* BY WHATWG `new URL().hostname` (concatenating `yourdomain.co<TAB>m` -> `yourdomain.com`) BUT *TRUNCATES* LEGACY `require('url').parse().hostname` (`yourdomain.co`), SO THE ALLOWLIST PASSES AND AXIOS CONNECTS TO THE ATTACKER'S REGISTERED DOMAIN — FOUND BY RADAMSA DIFFERENTIAL FUZZING: MUTATE A SEED URL, PARSE EVERY OUTPUT WITH BOTH PARSERS, KEEP THOSE WHOSE VALID HOSTNAMES DIFFER (blog.deesee.xyz, "SSRF: Bypassing hostname restrictions with fuzzing", https://blog.deesee.xyz/fuzzing/security/2021/02/26/ssrf-bypassing-hostname-restrictions-fuzzing.html, 2021-02-26, disclosed with permission; Kibana alerting webhooks `xpack.actions.allowedHosts`; read 2026-11-12; UNVERIFIED — not reproduced). METHOD: (1) the two parsers: the check `isHostnameAllowedInUri` runs `new URL(uri).hostname`; the sender (axios `lib/adapters/http.js`) runs `require('url').parse(fullPath).hostname`; (2) blind discovery: radamsa over `user:pass@domain.com:23/?ab=12#`, prefix `http://`, keep inputs where both hostnames are valid and DIFFERENT — the find: `http://user:pass@domain.com%094294967298/...` parsed "as domain.com4294967298 with URL constructor and domain.com with url.parse"; (3) exploit: allowlist wants `yourdomain.com` -> register `yourdomain.co` -> A-record to `127.0.0.1`/internal -> webhook action with url `http://yourdomain.co<TAB>m` (`POST /api/actions/action`, `kbn-xsrf`) -> `POST /api/actions/action/<id>/_execute` -> 3 response classes (live / live-HTTP / dead) = internal port scan; (4) stated limit (preserved): the truncated tail is pushed into the path (`pathname: '%09m/path'`), so the URL is mangled — scan-level impact, not full path/body control (inverted parser roles would give that). DETECTION SIGNAL: a host allowlist on a user-supplied URL in a Node stack; control/whitespace bytes accepted inside a hostname; the generic tell = one input, N parsers, differing `.hostname`. TRANSFERABLE TEST: on every validated-then-fetched URL, (a) radamsa-differential the parsers (the loop is ~20 lines), (b) hand-try `host<TAB>suffix`, `host<LF>suffix`, `host<space>suffix`, `host\x00suffix` and register the truncated prefix pointing at `127.0.0.1`, (c) prove SSRF via response-class differences across internal ports. WHY NEW: the validator-vs-fetcher class is recorded (Dropbox #1406938; §17.109 libuv 256-byte validator-vs-RESOLVER truncation) but not the TAB truncation-vs-strip byte, the WHATWG-vs-legacy-Node pair, the register-the-truncated-domain escalation, or differential fuzzing as the discovery method. SOURCE: https://blog.deesee.xyz/fuzzing/security/2021/02/26/ssrf-bypassing-hostname-restrictions-fuzzing.html read 2026-11-12. CLASS: SSRF (hostname-allowlist bypass, parser differential).
