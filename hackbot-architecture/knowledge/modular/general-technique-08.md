### [Bugbountyskills.md] 17.201 A SPLIT CREDENTIAL whose missing half parses to `nil` matches every record whose credential COLUMN IS NULL — `<victim_id>-` authenticates as that user (Basecamp Campfire bot keys, HackerOne #3329310)

SOURCE: https://hackerone.com/reports/3329310 — Basecamp, "Improper bot-authentication allows to impersonate any user when sending messages in a room" (Improper Authentication - Generic; **High**, rated by the team; $2,000; 128 votes; reporter `stackered`; submitted 2025-09-06, disclosed 2025-11-21, asset `ONCE: Campfire`)  read 2026-11-08 (`visibility: "full"` — whole body via `curl .../3329310.json`, HTTP 200, 7,518 B, body 1,992 B).
CLASS: authentication bypass / user impersonation — a credential is a single string split into `id` + `secret`; an empty secret half becomes `nil`, and the ORM lookup then matches rows whose secret column is NULL (which is exactly the human users).
CORE METHOD: (1) the server's bot auth, verbatim: `def authenticate_bot(bot_key)` / `  bot_id, bot_token = bot_key.split("-")` / `  active.find_by(id: bot_id, bot_token: bot_token)` / `end`. (2) Send a key with an empty right-hand side: "if `bot_key` has no right-hand side (ex: `1-`), `bot_token` will be `nil`, and the query will match a `User` record if `bot_id` matches a valid ID." (3) Pick the id: "IDs are incremental, as can be seen in the rails console, so they can be guessed easily. They are also visible in some URLs." — the report's console dump shows the human rows with `bot_token: nil` (`id: 1` role `administrator`; `id: 2` role `member`), so `find_by(id: <victim>, bot_token: nil)` is satisfied by every non-bot account. (4) The unauthenticated request, verbatim: `POST /rooms/2/2-/messages HTTP/1.1` / `Host: localhost:8000` / `Accept: text/vnd.turbo-stream.html, text/html, application/xhtml+xml` / `Content-Type: application/x-www-form-urlencoded;charset=UTF-8` / body `Hello ! I'm the test user, even though I'm not authenticated` — note the credential is the MIDDLE PATH SEGMENT of `/rooms/<room_id>/<bot_key>/messages`. (5) Impact as stated: "An unauthenticated user can send arbitrary messages as any user, in rooms the impersonated user have access to."
DETECTION SIGNAL: a credential of the form `<identifier><separator><secret>` parsed by `split`/`substring`/`partition` where a missing or empty component is not rejected — the tell is an AUTH CHECK rather than an auth failure when the secret half is absent; a query comparing against a column that is NULL for the accounts you want (`bot_token`, `api_token`, `service_token`, `invite_code`, `sso_id`, `password_hash`); sequential, URL-visible ids; the credential carried in a URL PATH segment (`/rooms/<id>/<key>/messages`, `/webhooks/<id>/<token>`, `https://<id>-<token>@host`); first-match lookup semantics (`find_by`, `first`, `WHERE … LIMIT 1`).
CHAIN: attacker with NO account (the bot route requires no session) -> supplies `<victim_id>-`, so the parsed token is `nil` (primitive: empty credential component) -> the lookup matches the NULL-token rows, i.e. the human users (primitive: NULL-equality match in the credential query) -> the request is processed as that user, so arbitrary messages are posted under their identity in every room they can reach (authentication bypass / impersonation; on a chat that also drives sensitive rooms/actions this is the ATO-adjacent leg). Rated High by the team, $2,000.
TRANSFERABLE TEST: for EVERY credential shaped `<id><sep><secret>`, submit the degenerate forms — `<id>-`, `<id>`, `-<secret>`, `<id>-` with a trailing space/newline, `<id>-""` — and observe whether the request AUTHENTICATES as `<id>`'s owner instead of being rejected; always run a CONTROL id whose column is non-NULL (it must fail). Rule: **a missing credential half must FAIL CLOSED — if the parsed secret is `nil`/blank it can still match rows whose column IS NULL, and the NULL-credential rows are the human users you want to impersonate (never store a bot/service credential as NULL — use an empty sentinel or a NOT NULL constraint).**
WHY IT IS A NEW GENERAL METHOD: V-07 records a VERIFY step accepting `code=null`/a manipulated response (fail-open on a one-time code), and the file records identity resolution from trusted internal headers (`Geo-GL-Id`, `X-User-Id`) plus mass-assignment. None records a CREDENTIAL PARSER whose degenerate input produces a `nil` comparison that the database satisfies for a whole class of accounts: the bug is the interaction of string splitting with SQL/ORM NULL semantics, not a missing check on one field. Reusable rule: **when a credential is composed of parts, test the parser with each part absent — `nil` is not "no credential", it is a value that matches every NULL in the column.** Slot 17.201. §17.219 — A SIGNED-NOT-ENCRYPTED CLIENT COOKIE THAT CARRIES THE VERY SECRET WHICH SIGNS IT, FEEDING `pickle.loads`: RECOVER THE KEY FROM THE COOKIE, FORGE THE SESSION AND REACH UNAUTHENTICATED RCE — AND PROVE IT BLIND WITH `__reduce__ -> time.sleep` (Google DevSite; simonkoeck.com, "How I Found a $90,000 Remote Code Execution Vulnerability in Google", published October 12, 2026; report submitted 2026-08-06, accepted within ~24 h, hotfixed, reward $90,000 = Google T2 S0 RCE $75,000 x 1.2 for report quality, fixed 2026-10-07). Read in full this pass by `curl` + script/style strip (41,660 B HTML -> 6,476 chars), reached from the assigned Intigriti Bug Bytes #241 feed; every command and payload below is the author's own. CHAIN OF FACTS: the OAuth entry point `GET https://developers.google.com/oauth2authorize?return_url=%2F` sets a Flask `session=<payload>.<timestamp>.<signature>` cookie with NO account; "Flask cookies are signed, not encrypted, so the contents are right there for anyone holding one" — split `cookie.rsplit(".", 2)`, base64url-decode (pad with `=` so `-len(v) % 4`), `zlib.decompress` if the payload starts with a dot, `json.loads`; the size was the first clue ("about 1,200 bytes it seemed large for a CSRF token and a return URL"). The decoded session was `{"_permanent":true,"google_oauth2_csrf_token":"…","google_oauth2_flow_<csrf>":{" b":"…"}}` — the `" b"` key is Flask tagging a BYTES value; base64-decoding it and running `pickletools.dis` printed an `oauth2client.client.OAuth2WebServerFlow` with `client_id` and `client_secret = b"<redacted>"` IN PLAINTEXT. THE TWO-JOB CHECK (do not guess — prove): Flask signs via itsdangerous with the `cookie-session` derivation, so recompute offline — `derived_key = hmac.digest(client_secret, b"cookie-session", "sha1")`, `expected = hmac.digest(derived_key, f"{payload}.{timestamp}".encode(), "sha1")` — and compare with the cookie's signature; it came out "byte-for-byte identical", with controls (one flipped signature character rejected; the original payload re-signed with the recovered secret accepted). "The signing key was stored inside the object it signs." FORGE AND SINK: the OAuth callback does `verify Flask signature -> read google_oauth2_flow_<csrf> -> base64-decode the bytes -> pickle.loads(...)`, so post a session of your own with a made-up CSRF token and your pickle under the MATCHING flow key: `{"_permanent":True,"google_oauth2_csrf_token":"attacker-chosen","google_oauth2_flow_attacker-chosen":{" b": base64(attacker_blob)}}` — the `state` is attacker-chosen too, so nothing must line up server-side; the broken assumption is that "that `pickle.loads` is only 'safe' as long as nobody else can forge a valid cookie". BLIND PROOF (the transferable trick): pickle's `REDUCE` opcode "names a callable and its arguments, and unpickling just calls it", so a class whose `__reduce__` returns `(time.sleep, (self.seconds,))` turns the response time into the oracle — same forged session, only the number changed: `sleep(0) -> 0.207 s`, `sleep(3) -> 3.193 s`, `sleep(5) -> 5.194 s`, `sleep(8) -> 8.283 s`, with the controls that kill the "slow endpoint" objection: no cookie = "Invalid request"; one flipped signature byte = "Invalid request"; valid signature without a flow entry = "Invalid request state"; valid signature with the real flow = Google's token exchange reached and failed later with `invalid_grant`. SCOPE: the same key validated sessions on firebase.google.com, developer.android.com, source.android.com and docs.partner.android.com. FIXES the author lists: rotate both exposed OAuth secrets and kill every session signed with them; per-deployment high-entropy `SECRET_KEY` from a server-side store unrelated to any OAuth credential; keep the flow object server-side with only an opaque reference in the cookie; drop pickle for anything crossing a client boundary. DETECTION SIGNAL: a Flask/Werkzeug-signed cookie that decodes to STRUCTURED data rather than a scalar id — a `" b"`-tagged bytes value that pickles, `oauth2client`/SDK objects, or any secret material (`client_secret`, API key, signing key) — plus any path that unpickles data arriving from the session/cookie; a session cookie that is large relative to what the UI claims to store; an OAuth entry point that mints a session for an unauthenticated visitor. TRANSFERABLE TEST: decode every signed session cookie you receive (base64url; `zlib` after a leading dot) and read the plaintext; if it contains pickled objects or secrets, run the two-job check above, then re-sign a payload of your choosing and probe the sink with a `__reduce__ -> time.sleep(N)` payload, timing N=0,3,5,8 and ruling out jitter with the no-cookie / bad-signature / no-flow-entry controls. WHY IT IS A NEW GENERAL METHOD: `pickle`'s only hits (3) are the generic deserialization FINGERPRINT table (`__destruct`, `unserialize`, "pickled `__reduce__`", "Python `gASV…`"), the `Flask` hits are Jinja2 SSTI and Django/Werkzeug debug-page lines, and `itsdangerous`, `cookie-session`, `oauth2client`, `oauth2authorize` = 0 hits — nothing records a signing key recoverable FROM the object it signs, nor the time-based pickle oracle. Rule: **a signed-not-encrypted client cookie is a confidentiality bug the moment it carries a secret, and if the secret inside the signed object is the key that signs the object, the cookie is forgeable end-to-end — always test whether a recovered secret validates its own cookie's HMAC before assuming it is only an API credential, and prove a blind deserialization sink by timing `__reduce__`.** Slot 17.219. §17.226 — AN ARCHIVE EXTRACTOR THAT SELECTS ITS PARSER BY MAGIC BYTES LEAVES ONE FORMAT UNVALIDATED: THE MINIMAL-INTEGRITY CONFIG PLUS AN EMPTY VALIDATOR MEANS THE ATTACKER SUPPLIES THE CONFIG, AND A TRAVERSAL EXPLOIT MUST BE PACKAGED WITH A STRUCTURALLY VALID BUNDLE SO THE EXTRACTOR'S OWN SUCCESS CHECK LETS IT THROUGH (Apple Private Cloud Compute, `darwin-init`; CVE-2026-20685, fixed in PCC 5E290.3+, $150,000 award, Apple-rated CVSS 6.5 info disclosure `AV:A/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`; Sentry Applied Research Center, Drinor Selmanaj, "Beyond Prompt Injection: Hacking Apple's Private Cloud Compute", images 2026/07; read in full this pass via `web_extract`, 17,363 chars; reached from the assigned Bug Bytes #239 feed). THE CHAIN: `darwin-init` is PID 1, root, and unpacks cryptex archives before any steady-state service exists; it reads the FIRST FOUR BYTES to choose an extractor (`AEA1`/`AA01` take Apple's safe extractors; anything else falls through to a generic `extract(to:)`), and a tar's `ustar` signature sits at offset 257 — outside the window — so a tar ALWAYS takes the unvalidated route. The sink appends the archive entry name to the output directory with no sanitisation (`let str = String(cString: archive_entry_pathname(entry)); let pathname = path.appending(str); archive_entry_set_pathname(entry, pathname.description)`) while the options set only `ARCHIVE_EXTRACT_TIME|PERM|ACL|FFLAGS` — none of libarchive's security flags — so it writes wherever the entry points. Two controls are absent: `PrivateCloudOSValidator.validate(cryptexConfig:)` is an empty function body and the per-cryptex `sha256` is OPTIONAL, so an attacker-supplied config skips integrity. DEPTH: base `/var/tmp/darwin-init/cryptex/<UUID>/`, so `..`×3 → `/var/tmp` (wiped by the userspace reboot) and `..`×4 → `/var/db` on the persistent data volume — pick the persistent one. THE TRICK: a traversal-only tar writes the files and then FAILS the `fullyApplied` check, hanging the boot with no services; so the tar holds BOTH (a) traversal entries prefixed `../../../../db/` and (b) a complete, valid cryptex bundle (Restore/BuildManifest.plist plus Restore/Cryptex/POC_DEMO/{gdmg,ginf,gtcd,gtgv} produced with Apple's own `pccvre cryptex create`), so personalization/install succeed, `fullyApplied` passes and the node boots clean. IMPACT: the second traversal writes `/var/db/prcos/splunkloggingd/config-main.plist`, whose `launchd` `PathState` KeepAlive starts `splunkloggingd` against the attacker's server the moment the file exists — ~785 KB of CloudBoard/node telemetry within seconds, plus per-request `PlaintextMetadata` (`bundleID`, `workloadType`, `requestID`, `automatedDeviceGroup`, fields marked "must not be logged publicly") and inference token/latency side channels; and a clean-vs-poisoned attestation comparison showed every relevant field identical, because attestation measures INSTALLED software, not writable-volume config. DETECTION SIGNAL: any boot/provisioning process that unpacks a supplyable archive (cryptex, app bundle, OS update, container layer); extractor selection by magic bytes where one format falls to a generic path; extraction options missing libarchive's security flags or a hand-rolled `path.appending(entry_name)` without a `..` filter; an empty validator; an OPTIONAL integrity digest; a depth where one level is tmp and the next persists; a `launchd`/systemd watcher on a writable config read at runtime. TRANSFERABLE TEST: tar with `../`×N to prove the escape; package it WITH a valid bundle so the post-extraction success check passes; choose the persistent level; aim at a file a daemon re-reads. WHY IT IS A NEW GENERAL METHOD: `libarchive`, `archive_entry`, `ARCHIVE_EXTRACT`, `darwin-init`, `cryptex`, `splunkloggingd`, `CloudBoard`, `PlaintextMetadata`, `attestation`, `Drinor`, `20685`, `Private Cloud Compute` = 0 hits across all three write targets; the Zip Slip class IS recorded (V-10, table row "Archive import/extract feature; entry names containing `../` or absolute paths") and is deliberately NOT re-recorded here — the new rule is the extractor-selection/validation-evasion pair. Rule: **an extractor that picks its parser by magic bytes guarantees one archive format skips validation; an optional digest plus an empty validator means the attacker supplies the configuration; and a traversal must be packaged together with a structurally valid bundle so the extractor's own success check lets it through — then aim the write at a file a service watches.** Slot 17.226.
