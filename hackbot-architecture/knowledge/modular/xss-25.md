Syntax `=?<charset>?q?<Q-encoding>?=` (Q-encoding is hex with `=` prefixes, e.g. `=41=42=43` -> `ABC`) or `=?<charset>?b?<base64>?=`. Ruby's `Mail` gem (>508M downloads) decodes UTF-7 and base64, IN THE LOCAL-PART AND IN THE DOMAIN; the layers compose — base64 whose charset is UTF-7 is decoded twice; in Q-encoding `_` is a space (`=20` also works). The consequence: blocked characters (`@`, `>`, `"`, `<`, whitespace, NUL) can be assembled from allowed ones after validation.

ENTRY POINT — the author's case was an HTTP/2 desync reached through a header-value line-break injection: "it was possible to inject a line break character in a header's value, letting me smuggle transfer-encoding header which would eventually split the request at backend." The point of the article is what to do when that is ALL you have: the program's answer was "Being able to smuggle a request is not a vulnerability in itself.   2. TRACE is default-on in "Apache and many Microsoft IIS and Tomcat versions" and must be disabled explicitly.
  3. RESPONSE CONCATENATION REFRESHER: smuggle a `HEAD` (a headers-only response whose `Content-Length` must equal what the GET body would be, and which a proxy would ignore) so that "as the HEAD message was smuggled and the proxy never noticed this, the content-length will not be ignored, causing a concatenation with the next available response". The TRACE response body — the reflected header — is glued onto the forwarded response: "The response will be forwarded to the next request that arrives through the same connection, taking control of the browser with a malicious JavaScript!"
  5. BYPASS THE TRACE FIREWALL RULE: proxies commonly forbid TRACE, but "as smuggling can be used to bypass firewall rules, it is possible to hide a TRACE message from the proxy and deliver it directly to the backend. WHEN BACKEND CONNECTIONS ARE PER-USER (why the naive attack dies): the malicious response reaches only you, so escalate with `Web Cache Poisoning` or `Client-Side Desync` — in this case client-side desync was out (HTTP/2 injection was required) and the app "was storing static responses in the cache".   7. THE STRONGER FORM — FULL RESPONSE SPLITTING: instead of relying on a static resource, inject a COMPLETE response so the cache stores arbitrary headers and body for a URL you choose: a body-reflecting `POST /reflect` returns padding plus injected CRLFs, `HTTP/1.1 200 Ok\r\n` / `Cache-Control: max-age=1000000\r\n` / `Content-Type: text/html\r\n` / `Content-Length: 44\r\n` / `\r\n` / `<script>alert("arbitrary response")</script>`; the first 78 bytes complete the HEAD and, because the remaining bytes ARE a valid HTTP response, "the message will be forwarded as the response of the next available request" and stored in the cache for that URL.   8. WHEN TRACE REFUSES A BODY: "depending on the configuration, TRACE requests cannot contain a content-length header bigger than 0" — then build the payload from several responses: "the message length header can be added using a smuggled transfer-encoding or with an extra response which will be appended right after the last header of the TRACE message" (the post's listing writes `A: HTTP/1.1 200 Ok` / `A: Cache-Control: max-age=1000000` as TRACE header values, then a second smuggled `TRACE /` carrying `A: <script>alert("XSS")</script>`). CI CACHE (source 5) = precondition is the ability to create a project/pipeline that names its own cache `key` on a runner whose cache service is shared and does not sanitise the key; no interaction beyond the victim's own pipeline run; gain = another project's cache ZIP read (cross-tenant data), then arbitrary file write into that cache so the victim's build executes attacker code on its own runner (P1 as cross-tenant RCE / supply-chain injection). OAUTH CODE REPLAY (source 6) = precondition is a single leaked authorization code (Referer, redirect-page logs, a TLS-inspecting proxy, browser history on the redirect page — the report's own list) plus a token endpoint that neither consumes the code nor checks the code row's expiry; no user interaction during the attack; gain = unlimited re-minting of bridge tokens in the victim's identity, convertible to real credentials carrying the victim's scopes (here Firefox-CI roles, i.e. build integrity) — the program rated it medium because the leak itself is narrow, but the chain is an account takeover inside the provider and the doctrine floor keeps it because the impact is identity + CI integrity, not the disclosure.
