Uber, "password reset token leaking allowed for ATO of an Uber account", weakness Improper Authentication - Generic, Critical, $10,000, reporter procode701, submitted 2016-10-02, disclosed 2017-05-17, 100 upvotes.
CLASS: authentication bypass → account takeover — the password-RESET SESSION TOKEN is returned in the HTTP RESPONSE of the reset-initiate request, so initiating the reset is equivalent to completing it (CWE-200 → CWE-287)
CORE METHOD (from the reporter's published detail):
  1. Send the normal "email me a reset link" request: `POST /login/handleanswer HTTP/1.1` to `auth.uber.com` with body `{ "init": false, "answer": { "type": "PASSWORD_RESET_WITH_EMAIL", "userIdentifier": { "email": "<victim email>" } } }`.
  2. The `200 OK` RESPONSE BODY hands back the reset session token that should only have gone by email: `{ "inAuthSessionID": "cdc1a741-0a8b-4356-8995-8388ab4bbf28", "stage": { "question": { "signinToken": "", "type": "VERIFY_PASSWORD_RESET", "tripChallenges": [] }, "alternatives": [] } }`.
  3. Use that token to reach the reset-completion stage and set a new password: `https://auth.uber.com/login/stage/<inAuthSessionID>/<tokenID>` — the reporter notes the `tokenID` had no expiration date.
  4. Result: any victim account is taken over with nothing but the victim's email address — no mailbox access, no interaction (Critical, $10,000).
DETECTION SIGNAL: a "forgot password"/reset-INITIATE endpoint whose RESPONSE (body, a JSON field, a header, or a redirect URL) carries the token / OTP / verification id / "stage" object the flow expects to be delivered out-of-band; response fields named like `sessionToken`, `resetToken`, `inAuthSessionID`, `signinToken`, `verificationId`, `stage`, or a stage type `VERIFY_*`. Tell: initiating the flow returns the material needed to COMPLETE the flow.
CHAIN: known victim email → POST the reset-initiate request → read the reset/session token from the response body → navigate to the completion stage URL with that token → set a new password → full account takeover (Critical, $10,000), reachable with the email address alone.
TRANSFERABLE TEST: for EVERY password-reset / magic-link / OTP-initiate endpoint, capture the complete RESPONSE (body + headers + redirects) and check the DevTools/network copy for a reset/verification token or a stage/step id. If the response carries it, the reset is self-completing. Confirm the completion step accepts the response-supplied token without any value that was really delivered out-of-band.

Uber, "OneLogin authentication bypass on WordPress sites", weakness Improper Authentication - Generic, reporter jouko, submitted/disclosed 2016-06-06.
CLASS: authentication bypass via SAML assertion forgery — the SP's SAML response validator only verifies the XML signature when a `<ds:Signature/>` element is PRESENT, so a signature-less assertion is trusted and can be minted with an attacker-chosen identity + role (admin) (CWE-347 → CWE-287)
CORE METHOD (the reporter's exact steps and payload):
  1. The `*.uber.com` WordPress sites used the OneLogin SAML-SSO plugin in place of normal login. That plugin's `wp-content/plugins/onelogin-saml-sso/php/lib/Saml2/Response.php :: isValid()` performs the cryptographic signature check INSIDE `if (!empty($signedElements)) { ... }` — so a response XML that contains NO `<ds:Signature />` tag is never signature-verified.
  2. Take a VALID OneLogin SAML response and DELETE the `<ds:Signature />` element (plus other unnecessary nodes) → an unsigned assertion the plugin accepts.
  3. Control identity and role through the assertion attributes: `User.Username`, `User.email`, `User.FirstName`/`User.LastName`, and crucially `memberOf = Administrator`. With provisioning ON the plugin CREATES the user if the username is unknown, so you can also target an existing admin by guessing their username/email.
  4. POST it to the SP ACS endpoint: `curl 'https://newsroom.uber.com/wp-content/plugins/onelogin-saml-sso/onelogin_saml.php?acs' --data "RelayState=/wp-login.php" --data-urlencode "SAMLResponse=$(base64 response.xml)"`.
  5. The SP replies `302 Found` with `Set-Cookie: wordpress_logged_in_<hash>=...` and `saml_login=1`, then redirects to the front page — you are authenticated. On `newsroom.uber.com` the role name was simply "administrator", so admin was granted; on `eng.uber.com` the role name could not be guessed, so only a "subscriber" account was minted.
DETECTION SIGNAL: an SP that consumes SAML/OAuth assertions and whose validator wraps the signature check in an "if a signature element exists" branch (or otherwise treats a missing/empty signature as valid); an ACS endpoint path (`...?acs`, `/saml/consume`, `/Shibboleth.sso/SAML2/POST`, `/wp-content/plugins/*-saml-sso/*.php?acs`) accepting a `SAMLResponse` POST; SAML attributes that carry role/group directly (`memberOf`, `Role`, `groups`) and are mapped to authorization; "just-in-time provisioning" enabled so an unknown user is created.
CHAIN: attacker with no credential → strip `<ds:Signature/>` from a valid SAML response and set `memberOf=Administrator` → POST to the ACS endpoint → plugin accepts the unsigned, unverified assertion → WordPress sets auth cookies → authenticated as admin → full control of the site and its customer data.
TRANSFERABLE TEST: capture one legitimate SAML response, remove the entire `<ds:Signature>` element (then try empty-signature / signature-wrapper variants) and re-POST it to the ACS endpoint. If it authenticates, the signature is OPTIONAL. Then flip the role/group attribute (`memberOf`, `Role`, `groups`) to the admin value and confirm the role is granted. General rule: whenever a security control sits inside an `if (something exists)` block, DELETE the something and retry.

GitLab, "Exposure of a valid Gitlab-Workhorse JWT leading to various bad things", weakness Improper Authentication - Generic, High, reporter ledz1996, submitted 2020-11, disclosed 2022-07-05.
CLASS: authentication/authorization bypass — a valid internal "Gitlab-Workhorse" JWT is EXPOSED through a path traversal in the Terraform State API, and the internal identity header that JWT unlocks (`Geo-GL-Id`) is trusted to name ANY ssh key → push to a repository you only have read access to (CWE-22 + CWE-287/CWE-863)
CORE METHOD (the reporter's exact steps):
  1. EXPOSE the JWT: POST to the Terraform State API with a URL-encoded traversal in the state name so Workhorse's normalized URL and the file written by the State API disagree (`data = request.body.read` is appended as a FILE): `POST /api/v4/projects/<id>/terraform/state/%2e%2e%2f%2e%2e%2fwikis%2fattachments?serial=1` with a `multipart/form-data` body (fields `import_url`, `mirror`, …), header `Private-Token: <PAT>`.
  2. READ the JWT back: `GET /api/v4/projects/<id>/terraform/state/%2e%2e%2f%2e%2e` → the response is a multipart body whose `mirror.gitlab-workhorse-upload` field carries a signed JWT (`eyJhbG...`) — a VALID Workhorse API-request token (this is what lets `Gitlab::Workhorse.verify_api_request!` pass).
  3. On EE the git-http controller picks the acting user from an INTERNAL header: `def user; super || geo_push_user&.user; end`, `geo_push_user = ::Geo::PushUser.new_from_headers(request.headers)`, `new_from_headers` builds it from `headers['Geo-GL-Id']`, and `identify_using_ssh_key(gl_id)` runs `User.find_by_ssh_key_id(key_id.gsub("key-",""))`. So sending `Geo-GL-Id: key-<n>` authenticates you as the owner of ssh-key `<n>` — and key ids are a small incremental integer (brute-forceable from 1).
  4. Turn read into write on a repo you can read but not push to: fork it, clone the fork over HTTP, and intercept the push (`POST <fork>.git/git-receive-pack`). Rewrite the target path using both the traversal AND the internal push route: `/-/push_from_secondary/2/<victim-project>.git/git-upload-pack.t%2f%2e%2e%2fgit-receive-pack`.
  5. Add the two headers: `Gitlab-Workhorse-Api-Request: <the JWT from step 2>` (so the Workhorse API-request check passes) and `Geo-GL-Id: key-<id>` with the id of ANY ssh key whose owner has push access to the victim project. The request body is the normal `git-receive-pack` pack.
  6. Result: the push is accepted and written to a repository you were only authorized to read — unauthorized write, with the JWT exposure as its gate.
DETECTION SIGNAL: (a) an upload/import/state endpoint whose stored "filename"/name comes from `request.body` or a user path and is then written AFTER URL normalization (the traversal escapes a directory the app then serves back); (b) a signed INTERNAL token (Workhorse JWT, an `X-*-Api-Request` header) landing in a RESPONSE you can read — grep responses for `eyJ`/`*-upload` multipart fields; (c) any service that resolves the ACTING USER from an internal header (`Geo-GL-Id`, `X-User-Id`, `X-Pid`, `X-Gitlab-*`) instead of the session, especially a `find_by_<key>_id(<int>)` with a small/sequential int; (d) an alternate write route (`/-/push_from_secondary/`, an "internal"/`/-/` admin route, a mobile BFF) that honours the internal header while skipping the primary authorization gate.
CHAIN: attacker with any account + a PAT → expose a valid Workhorse JWT via traversal in the Terraform State API → forge an internal API-request and add `Geo-GL-Id: key-<victim-id>` → authenticate as any ssh-key owner → bypass the pre-receive push check via `push_from_secondary` + `%2f%2e%2e%2f` path trick → unauthorized push to any readable repository (High).
TRANSFERABLE TEST: (1) hunt any "read a file into a response" where a user-controlled name/param is written to a path after normalization, and grep the response for a signed token (`eyJ`…). (2) If you obtain an internal signed token, replay it in its native header AND pair it with each internal identity header the stack consumes (`Geo-GL-Id`, `X-User-Id`, `X-Pid`, `X-Gitlab-*`), cycling small sequential ids to see whose identity you inherit. (3) Look for a second route (`push_from_secondary`, an "internal" route, a mobile BFF) that performs the same write without the primary authorization gate.

ROUTE: full report body via the HackerOne `.json` endpoint (`vulnerability_information`, 17,456 bytes — PoC, sandbox + gdb backtraces). shopify-scripts, "Crash: Overwriting NoMethodError with a builtin class crashes/corrupts memory", weakness Memory Corruption - Generic, High, reporter brakhane, submitted/disclosed 2017-03-01.
CLASS: memory corruption in a code sandbox (interpreter-engine DoS → corruption) — reassigning a BUILT-IN EXCEPTION CLASS constant makes the runtime's own error-construction path recurse on itself; the recursion overflows the VM stack and incremental GC then walks a corrupted context stack → SIGSEGV (CWE-787/CWE-248). shopify-scripts ran UNTRUSTED merchant Ruby in-process, so a crash in the engine is the first step of a sandbox-escape chain.
CORE METHOD (the reporter's exact PoC):
  1. Inside the sandboxed script, OVERWRITE the exception class the runtime itself uses with a builtin class: `NoMethodError = Fixnum` (Fixnum/Integer both work), then trigger it: `boom!`.
  2. Root cause (reporter's wording): "triggering the `NoMethodError` triggers another `NoMethodError` when `mrb_no_method_error` in error.c tries to call `new` on the new `NoMethodError`, which has no new." The constant mruby uses to CONSTRUCT its own error has been replaced by a class that cannot be constructed → each attempt to raise `NoMethodError` raises another (`mrb_no_method_error` → `mrb_method_missing` → `mrb_funcall ... "new"` → `mrb_no_method_error` …).
  3. The recursion (the gdb trace shows ~1,800 frames) blows the VM stack; the incremental GC then runs on the inconsistent VM context stack: `mark_context_stack` (gc.c:532) dereferences garbage → SIGSEGV at `0x0000000000000a`.
  4. Hosted engine surfaced as `Application Error` / `MRubyEngine::EngineTimeQuotaError` followed by a crash; the reporter also broke `https://mruby.science` while testing.
DETECTION SIGNAL: a product that executes untrusted code in an in-process interpreter sandbox (mruby, Lua, JS, a WASM/WASI runtime, a template DSL) and lets the script REDEFINE/overwrite core runtime constants or classes — the exception/error classes first, then `Object`/`Class`/core modules — that the runtime's OWN error/GC paths use. Also: no per-script memory isolation, an error path that calls `new` on a class the script can replace, and a GC running concurrently with the script.
CHAIN: attacker submits a script (snippet, formula, macro, template) → reassigns a builtin exception class (`NoMethodError = Fixnum`) → raises it → the engine's error path recurses on itself → VM stack overflow → incremental GC walks a corrupted context stack → SIGSEGV / memory corruption in the sandbox host process (DoS now; a corruption primitive toward sandbox escape). Reported as Memory Corruption (High).
TRANSFERABLE TEST: on any in-process interpreter sandbox, try to reassign the runtime's OWN core constants/classes — exception classes first (`NoMethodError`, `StandardError`, `TypeError` = a builtin), then `Object`/`Class`/`Module` — and trigger the matching error. A crash, a hang, or a quota-error-then-crash says the engine's error/GC path is reachable with attacker-controlled core state; on a multi-tenant target that is a DoS/corruption finding and the head of an escape chain. (LAB ONLY — same doctrine as the PlayStation UAF entries above: memory-corruption depth stays out of live targets; the reportable unit on a live target is "untrusted script can corrupt/crash the shared engine".)

ROUTE: full report body is NOT public (`visibility: no-content`); the verbatim team SUMMARY (summary id 56475, credited @chaynik) was retrieved from the HackerOne `.json` endpoint and contains the protobuf schema, the handler pseudocode, the exploitation steps and the PoC description — that (not the private body) is the text used here. Valve, "RCE on CS:GO client using unsanitized entity ID in EntityMsg message", weakness Out-of-bounds Read, Critical 9.6, $9,000, disclosed 2021-05-27.
CLASS: RCE on a networked native client — an untrusted network message carries an index used, UNVALIDATED, to resolve an object from a fixed table, then a virtual function is called on the resolved object → out-of-bounds access + control-flow hijack (CWE-125 → CWE-94)
CORE METHOD (from the team summary):
  1. The server notifies the client about entity actions with `CSVCMsg_EntityMsg` (protobuf: `ent_index int32 = 1`, `class_id int32 = 2`, `ent_data bytes = 3`).
  2. The handler runs: `IClientNetworkable *entity = entitylist->GetClientNetworkable(msg->ent_index); if (entity) { … entity->ReceiveMessage(...); … }` — NEITHER the handler NOR `GetClientNetworkable` validates `ent_index`, so ANY integer indexes outside the entity list → out-of-bounds object-pointer read → a virtual call on an attacker-influenced object → control-flow diversion.
  3. To make it reliable you need a controllable buffer at a KNOWN address: `client_panorama.dll`'s base was assumed known (obtainable via a separate memory-disclosure bug, e.g. #581774, or guessed — 32-bit ASLR has low entropy). The attacker uses a global the server can write: the MAP NAME is copied into a global inside `client_panorama.dll`.
  4. Payload = a ROP chain + a fake `IClientNetworkable` object, delivered as the map name (a string, so no NUL bytes — worked around by overwriting it in several passes).
  5. The entity list is a STATICALLY allocated array in `client_panorama.dll`, so the offset from the list base to the payload is CONSTANT → compute the `ent_index` that lands on the fake object and send the `CSVCMsg_EntityMsg`.
  6. The ROP chain launches `calc.exe`, using the `IProcessUtils` interface that `client_panorama.dll` imports from `tier0.dll` (start-a-process) to shorten it. Delivery: a malicious game server the victim joins, or auto-connect via the `steam://` browser protocol from a web page (no confirmation).
DETECTION SIGNAL: a networked/native client (or any service parsing a binary/RPC/WS message) where a message FIELD is an index/id into an array or object table and is used with NO bounds/existence check, in the shape `obj = table->Get(id); if (obj) obj->Virtual(...)` with attacker-controlled `id`; a statically allocated object table at a fixed image offset; a global buffer the remote party can write whose address is known; a low-entropy address space (32-bit, no PIE/ASLR).
CHAIN: attacker controls the server (or lures the victim via `steam://` from a web page) → sends `CSVCMsg_EntityMsg` with an out-of-range `ent_index` → the OOB lookup returns a pointer into an attacker-writable global (the map-name buffer) → the virtual call dispatches through a fake vtable → the ROP chain runs arbitrary code on the victim's machine → full client compromise (Critical 9.6, $9,000).
TRANSFERABLE TEST (our equivalent surface): for every message field that is an index/id into a server-side array or object table (`ent_index`, `entity_id`, `object_id`, `slot`, `channel`, `player_id`, `index`), send an out-of-range value (`-1`, `0x7fffffff`, `len+N`) and watch the dereference — the reportable pattern is "untrusted index → unvalidated table lookup → indirect/virtual call". Then check whether a neighbouring global you can influence (a name/string you supply) sits at a computable offset from the table base; if so the primitive is a control-flow hijack.
