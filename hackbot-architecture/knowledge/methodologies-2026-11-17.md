STATUS: UNVERIFIED (not reproduced this pass; no Basecamp tenant was touched).
CLASS: cross-account stored XSS (CWE-79) → same-origin JS execution → CSRF-token read → persistent administrator takeover (CWE-269). The mechanism is a SANITIZATION/parsing bug, not an authorization bug.
CORE METHOD (as the report states it):
  1. Mint a legitimate embed first, to obtain a real server-generated `sgid`: `POST /<attacker-acct>/embeds.json` with `X-CSRF-Token` and `{"url":"https://www.youtube.com/watch?v=dQw4w9WgXcQ"}`.

  6. That response contains `<turbo-frame id="h1proofframe" src="https://attacker.example/frame">`; the `/frame` response is CORS-enabled HTML with an inline script; Turbo loads it and SUPPLIES THE CURRENT PAGE NONCE when activating the script → script executes on `https://app.basecamp.com`.
  7. The script reads the victim's CSRF token from page metadata and grants the attacker admin: `POST /<acct>/account/administratorships` with `Content-Type: application/x-www-form-urlencoded`, `X-CSRF-Token: <victim>`, body `person_id=53489491` → `302 /<acct>/account/administrators`; the grant persists after the victim browser closes (`{"id":53489491,"admin":true,"owner":false}`), and the attacker then promotes another member as an admin write proof.

No password, cookie, token or second click needed by the attacker.
TRANSFERABLE TEST: on any app with attachments/embeds/rich text — (1) store markup inside the attachment's client-controlled content while keeping a VALID server id (the id is what buys the storage); (2) open the item in the EDIT view as a different role and diff the DOM against the reader view: any attribute that was inert and is now live is the primitive; (3) list every `data-*` attribute the sanitizer allows and grep the JS for behaviours that consume them (data-behavior/data-url/data-action/data-controller); (4) if innerHTML is reachable, insert a cross-origin frame element and check whether the executed script carries the page nonce (log `document.currentScript.nonce` / observe a nonce-authorized fetch). SOURCE: https://hackerone.com/reports/4062639 (Shopify — "Unauthenticated UCP/MCP catalog access on a password-protected dev store", weakness Improper Access Control, disclosed 2026-11-12, RESOLUTION: Informative)  read 2026-11-17

### §INTAKE-2026-11-17/7 — A SHARED CACHE STORES A SESSION-BEARING RESPONSE BECAUSE `Vary: Cookie` IS ABSENT: THE `csp-nonce` IS THE SECRET THAT MATTERS (A NONCE SERVED TO EVERY VISITOR STOPS BEING UNPREDICTABLE, AND ANY HTML INJECTION ON THAT PAGE BECOMES SCRIPTABLE)

SOURCE: https://hackerone.com/reports/4151790 (Basecamp, app.fizzy.do — "Public board pages are served Cache-Control: public with no Vary: Cookie, so a signed-in visitor's response is cached at the edge and returned to everyone", Low CVSS 3.1, reported 2026-10-27, disclosed 2026-11-12)  read 2026-11-17
ROUTE: https://hackerone.com/reports/4151790 read IN FULL on hackerone.com (report body, the poc.sh output, the diff, the fix commit discussion and the severity negotiation all present).
STATUS: UNVERIFIED (not reproduced this pass; the reporter used their own account and public board).
CLASS: information disclosure via shared-cache keying (CWE-524/CWE-200) — cache-primitive that escalates to a CSP bypass when combined with any HTML injection.
CORE METHOD (as the report states it):
  1. Find a "public" surface that still renders SESSION-BOUND values: the controller opts out of authentication only for the redirect (`allow_unauthenticated_access` skips `require_authentication` while `resume_session` still runs) and marks responses cacheable — Rails `expires_in 30.seconds, public: true` → `Cache-Control: public, max-age=30`.
  2. Run the test with TWO unrelated cache keys so each starts cold: a CONTROL key requested ONLY without cookies, and a second key requested first WHILE SIGNED IN and then twice with NO cookies at all (script needs only curl + grep: `url.txt` with the public board URL, `cookie.txt` with the full Cookie header).
  3. Read the four/three-way diff: the control has NO `current-user-id`, a DIFFERENT `csp-nonce` and `timezone: UTC`; the signed-in response carries `csp-nonce`, `csrf-token`, `current-user-id`, `timezone`; the cookieless re-requests come back `cf-cache-status: HIT` with a rising `age` and bodies BYTE-IDENTICAL to the signed-in response (same nonce, same user id).
  4. Read the cache key from the response: `vary` listed `Accept, Sec-Fetch-Site;accept-encoding` — NOT `Cookie`; so the cookie-carrying response was stored under the URL alone.
  5. State the exposure by weight, not by volume: the **CSP nonce** is the headline (it stops being a per-response secret for the cache window, so any HTML injection reachable on that same page becomes scriptable against the policy); `current-user-id` identifies which user opened the link (it also leaks in the `user_css` block); `timezone` and any `flash[:notice]`/`flash[:alert]` from that session ride along; the CSRF token is listed as a session value that should not be shared but is bound to the cookie, so it is not a CSRF path on its own.
DETECTION SIGNAL: `Cache-Control: public` (or any max-age) on a route that ALSO emits per-response secrets — a CSP nonce meta tag, CSRF token meta, current-user/tz meta, flash messages, user CSS; a `vary` header that omits `Cookie`; a framework pattern where "allow unauthenticated" only skips the auth redirect while session loading stays on; a cache status header (`cf-cache-status`, `x-cache`) plus `age` on an authenticated response.
CHAIN: any signed-in user opens a public link (normal team sharing — the only precondition) → the edge caches their session-bearing response under the URL alone for the window → any visitor requesting the URL in that window receives their CSP nonce, user id and timezone (+ session flash) → combined with ANY HTML injection on that page (stored or reflected), the leaked nonce makes the injection executable for the window → CSP bypass; the user id feeds identification/enumeration. STANDALONE the report was scored Low 3.1 (CVSS AV:N/AC:H/PR:N/UI:R/S:U/C:L/I:N/A:N) and is a chain primitive — record it as such, never as a standalone finding.
TRANSFERABLE TEST: pick any publicly cacheable page and (1) request it cold WITHOUT cookies; (2) request it WITH a session; (3) request it again WITHOUT cookies — diff the bodies and look for `HIT` + rising `age` carrying the session's meta values; (4) grep the `Vary` header for `Cookie`; (5) if a shared nonce or user id survives, hunt an injection on the SAME page and present the combination as the finding. Rule: **a per-response secret that survives a cookieless request is a cache leak, a shared CSP nonce is a CSP-bypass enabler, and "public" on a template is a statement about who may see it — verify it in the response, not in the intent.**
DEDUPE/DELTA: `4151790`, `Vary: Cookie`, `current-user-id`, `resume_session` = 0 hits pre-append. Existing cache material REVIEWED and NOT re-recorded: the ledger's cache-poisoning/unkeyed-header entries (header-list bruteforce, cache deception) and the Active Storage `Set-Cookie`-in-a-public-response leak — NEW atoms: (a) the MISSING `Vary: Cookie` KEY on a response that is authenticated, (b) the leaked secret being the CSP NONCE, with the explicit CSP-bypass consequence, (c) the two-cache-key control design (one clean key, one key warmed while signed in).
HONESTY: not reproduced this pass; the report ships `poc.sh` and its output (CONTROL / STEP 1 signed in / STEP 2-3 cookieless HIT), the body diff, and the vendor triage→Low-3.1→Resolved exchange; the nonce exploitability is stated by the reporter as NOT claimed without an injection and is recorded here the same way.
