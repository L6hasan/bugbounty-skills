### §INTAKE-2026-11-27/01 — THE PUBLICATION FLAG IS COMPUTED FROM THE OBJECT'S **OWN** STATUS AND NEVER FROM ITS ANCESTORS: A PUBLIC-SETTING SUBFORUM UNDER A PRIVATE PARENT STILL BROADCASTS FULL TOPIC BODIES TO THE PUBLIC ACTIVITY FEED, WHILE THE TOPIC'S OWN PERMALINK CORRECTLY 404s — THE CANONICAL READ PATH IS GATED AND THE AGGREGATE PATH IS NOT (bbPress + BuddyPress `hide_sitewide`, #4053546, Medium, 2026-10-10)

SOURCE: https://hackerone.com/reports/4053546 (WordPress — "Information Disclosure - Unauthen Leak Private Content", Medium, disclosed 2026-10-10, WordPress 7.1.2 / BuddyPress 14.5.2 / bbPress 2.6.18 / PHP 8.4.24 / MariaDB 11.8.8)  read 2026-11-27
ROUTE: HackerOne `.json` route — HTTP 200, `vulnerability_information` 2,013 B read IN FULL (affected-version table, the description, the three `curl` steps and the one-line code fix).
STATUS: UNVERIFIED (not reproduced — no WordPress/BuddyPress instance was stood up; the version table, the steps and the diff are the reporter's, quoted verbatim).
CLASS: broken access control / sensitive information disclosure without authentication — a DENORMALIZED visibility flag is computed at write time from the immediate object's own status, so a child of a restricted ancestor keeps a public-derived flag and is republished into an unrestricted aggregate surface (CWE-284 / CWE-200 / CWE-863, authorization data harmed by a derived value).
CORE METHOD (as the report states it):
  1. Map the inheritance model first: `private` forum (core status) and bbPress's `hidden` status (registered `'private' => true`) are the restricted CONTAINERS; topics and replies inside them are still stored with their own public status, so the container, not the child, carries the restriction.
  2. Find where the visibility decision is made and note its argument: "computes the hide_sitewide flag for new topic/reply activity by checking only the posting forum's own status, not its ancestors" — i.e. `! bbp_is_forum_public( $forum_id, false )`; that trailing `false` is the ancestor walk being switched off. Create the exact shape that defeats it: a **publish-status subforum nested under a private/hidden parent**.
  3. Post the topic as a member into the CHILD forum: `curl -s -b cookies.txt -L -d "bbp_topic_title=Test&bbp_topic_content=Secret&bbp_forum_id=6&action=bbp-new-topic&_wpnonce=$N" https://site/forums/forum/private/public-subforum/` → HTTP 200, redirect to `/forums/topic/test/`.
  4. Record the CONTROL that proves the app believes the content is restricted: the direct permalink returns `404` to the same viewer (`curl -s -o /dev/null -w "%{http_code}" https://site/forums/topic/test/` → `404`).
  5. Read it from the AGGREGATE surface with NO credentials: `curl -s https://site/wp-json/buddypress/v1/activity | grep -o '"rendered":"[^"]*Secret[^"]*"'` → `"rendered":"<p>Secret</p>"` — "full content disclosed", and the broadcast carries "title, forum name, permalink, and raw body".
  6. Fix stated by the reporter (the tell that this is a flag-computation bug, not a read-hook bug): drop the `false` argument so `bbp_is_forum_public()` walks parents — `'hide_sitewide' => ! bbp_is_forum_public( $forum_id ),`.
DETECTION SIGNAL: a hierarchical container model (forum → subforum, folder → subfolder, workspace → channel, category → collection, org → project) where the restriction is set on the CONTAINER; a derived/denormalized publication flag persisted on the CHILD at create/update time (`hide_sitewide`, `is_public`, `visibility`, `published`, `listed`, `broadcast`, `share_scope`); a helper whose ancestor check is an OPTIONAL argument (the `, false` pattern) or a single-level lookup; any AGGREGATE/feedsurface that re-publishes children independently of the canonical object: activity feed, `/activity`, notifications digest, "latest posts/items" list, search index, sitemap, RSS/Atom, public GraphQL `viewer`-free fields, webhook fan-out.
CHAIN: an ordinary member (primitive: the ability to post in a forum whose own status is public) -> the child is nested under a restricted ancestor, which is the normal shape of a permission hierarchy that has been re-parented or hardened at the top (primitive: the operator believes the container check carries the inheritance) -> the write-time flag is computed with the ancestor walk DISABLED, so the activity row is stored as sitewide-visible (primitive: the derived value is the authorization decision) -> the canonical permalink enforces the parent and returns 404, which is exactly why nobody audits the child (primitive: the control the tester checks is working) -> the unrestricted activity feed/API re-serves title + forum name + permalink + raw body to anonymous callers (escalation: the aggregate path is a second read path that never consults the same gate) -> every new topic/reply under every restricted ancestor is continuously republished, enumerable and indexable (terminal: unauthenticated mass disclosure of member-only content — the program rated it Medium because the content class was forum posts, and the report's own framing is "Access Control Bypass").
TRANSFERABLE TEST: in any product with nested containers, (1) create the hierarchy <restricted parent> → <child created with default/public settings>, post one unique marker in the child; (2) confirm the canonical object is denied (`404`/`403`) to a second, cookie-free client; (3) then read EVERY aggregate surface as that cookie-free client — `/activity`, `/feed`, `/notifications`, `/latest`, `/search?q=<marker>`, sitemap, RSS, the public API collection endpoint, the digest/preview worker — and grep for the marker; (4) if the marker appears, do not report the page: report the flag, and re-parent one more level (move the child under a restricted grandparent) to prove the ancestor walk is missing rather than the parent row simply being stale. Rule: **a publication flag derived from an object's own status is not an authorization decision — every aggregate, feed, digest and index is a second read path, so test the SAME restricted child through the aggregate with no cookies, having first confirmed the canonical path denies it.**
DEDUPE/DELTA: `hide_sitewide`, `bbp_is_forum_public`, `buddypress/v1/activity`, `activity stream`, `ancestor` + `derived` flag = 0 hits across the three write targets (`activity feed`/`activity API` hits are unrelated prose). Recorded neighbours REVIEWED and NOT conflated: the bbPress entry §INTAKE-2026-11-17/4 (#3801107, ledger 22265) is the SAME product family but a DIFFERENT mechanism — there the child rows stay `publish` and the ACL lives in a `pre_get_posts` QUERY FILTER that the core REST SINGLE-ITEM route never runs; here the ACL hook runs everywhere on the read side and the failure is upstream, in a stored flag computed without the ancestor; that entry's own transferable test enumerates READ PATHS, this one enumerates ANCESTRY and aggregate surfaces. The ledger's "visibility enforced only by a listing filter" family is likewise read-path-shaped. The ledger's WordPress REST-alias entry (#3892948) and the SCF `acf_get_posts` entry are missing/alias checks, not derived-flag arithmetic. NEW atoms: (a) the ancestor-optional argument (`$forum_id, false`) as the bug shape, (b) the derived publication flag persisted at write time as the authorization decision, (c) the aggregate/feed/digest surface as the second read path, (d) the canonical-permalink-404 as the control that hides the hole. PRIOR-PASS CORRECTION recorded so it is not repeated: the 2026-11-26 pass listed `#4053546` among WordPress items "same family as the recorded #4152553/#3893632" — that was wrong; #4053546 is this BuddyPress activity-stream disclosure and its mechanism had never been recorded.

### §INTAKE-2026-11-27/02 — A "RECENTLY VIEWED" SLOT THAT LEAKS **OTHER SESSIONS'** IDENTIFIERS IS AN AUTHORIZATION LEAK WHEN THE IDENTIFIER IS THE CAPABILITY: A COOKIE-FREE VISITOR RECEIVES A STRANGER'S PROJECT UUID, FETCHES A VALID CSRF TOKEN FROM THAT PROJECT'S OWN SETTINGS PAGE, AND PERSISTS A WRITE WITHOUT EVER AUTHENTICATING (creoline Marketplace, Bugcrowd P4, 2026-09-30)

SOURCE: https://bugcrowd.com/disclosures/81921e6f-7696-45f8-9ace-f9b8ba283623/unauthenticated-project-discovery-enables-cross-session-modification-of-marketplace-projects (creoline Vulnerability Disclosure Compliance Engagement — "Unauthenticated Project Discovery Enables Cross-Session Modification of Marketplace Projects", P4, disclosed 2026-09-30, resolved)  read 2026-11-27
ROUTE: CrowdStream `crowdstream.json?filter_by=disclosures` page 1–6 listings → the disclosure page fetched with `curl` + local HTML strip (HTTP 200); the researcher's summary is the full public text.
STATUS: VERIFIED-BY-REPORT as the researcher states it (a disposable researcher-owned project, cross-session validation with a cookie-free client, write persisted and confirmed fixed by the vendor); NOT reproduced by us.
CLASS: broken access control — an unauthenticated cross-session OBJECT-IDOR where the object's UUID doubles as its authorization capability, reachable because a personalization/telemetry widget renders identifiers from a shared pool instead of from the caller's own state (CWE-639 / CWE-284 / CWE-488 exposure of session data across sessions).
CORE METHOD (as the report states it):
  1. Do not log in. Open a FRESH anonymous session and read the page as a first-time visitor: "Fresh unauthenticated sessions on the creoline Marketplace received project UUIDs belonging to unrelated sessions through the 'Recently viewed projects' section."
  2. Treat the leak as an authorization primitive only if the id is also the capability: "Because the stable UUID also functioned as an authorization capability, an anonymous user could access another project's management and settings pages without authentication."
  3. Walk the leaked id into the highest-value surface, not just the read view: the project's MANAGEMENT and SETTINGS pages (those pages are where a per-session secret lives) — "a separate cookie-free session could obtain a valid CSRF token".
  4. Persist a write in that other session's project to convert a read into an integrity finding: "modify the project's name and description, and persist those changes."
  5. Contain the blast radius the way the researcher did (this is what made it P4 rather than a live customer incident): "Cross-session validation using a disposable researcher-owned project … No customer project or server was modified."
DETECTION SIGNAL: any widget that shows objects the CURRENT caller has not interacted with — "recently viewed", "recent", "continue where you left off", "recommended for you", "trending", "popular", "people also viewed", "your drafts" on an anonymous page; a personalization/recommendation store keyed by something other than the session (a global last-N list, a shared cache key, a device id, a cookie that is set but ignored on read); resource ids that are UUIDs but are used AS the authorization token (`/projects/<uuid>/settings` accepting the uuid alone); a settings page that renders a CSRF token to a caller who never authenticated for that object; a 200 on a management page where the create/list endpoints require auth.
CHAIN: an anonymous visitor (primitive: no account at all) -> a personalization widget hands them a UUID that belongs to a different, authenticated session (primitive: cross-session identifier disclosure — normally merely P4/P5 on its own) -> that UUID is the object's only authorization capability, so the management/settings routes render for the anonymous caller (escalation 1: identification becomes access) -> the settings page mints a CSRF token for that object, which the caller captures, so the app's own anti-CSRF control now vouches for the forged request (escalation 2: the token is issued to the wrong principal) -> name/description mutated and persisted in another session's project (terminal: unauthenticated cross-tenant write — integrity loss plus the ability to poison anything rendered from that project name/description, e.g. a title that lands in an admin list or a customer-facing page). The program rated it P4 on blast radius ("No customer project or server was modified"); with a populated widget the same chain is cross-tenant write at scale.
TRANSFERABLE TEST: with a cookie-less client, (1) hit the app's landing/marketplace/list pages and diff the object ids rendered against the ids your own session ever touched — any id you never created is a leak; (2) for each leaked id, request the object's EDIT/SETTINGS/ADMIN route, not the public view, and record status + whether a CSRF/nonce value is returned; (3) if a token comes back, use it to perform the cheapest reversible write (`name`/`description`/`notes` on an object you own, created for the test) and confirm persistence from a third clean session; (4) repeat on the SECOND and THIRD fresh session to prove the leak is a shared pool rather than a single stale cookie. Rule: **an identifier is a capability whenever the object's management route accepts it without a membership check — so every "recently viewed / recommended / trending" widget is an identifier-distribution channel, and the test is to take a leaked id straight to the settings page and see whether that page hands you a CSRF token.**
DEDUPE/DELTA: `recently viewed`, `recently-viewed`, `Recently viewed projects`, `creoline`, `81921e6f` = 0 hits across the three write targets; the ledger's `UUID`-as-capability material is the Opera Pinboards pub/sub wildcard entry (§INTAKE-2026-11-26C/06) which enumerates ids over MQTT, and the "UUID is one integer away" IDOR family which guesses ids — neither records a widget that DISTRIBUTES live ids from other sessions. Recorded neighbours REVIEWED and NOT conflated: the ledger's cross-session entries are session/packet mixing (KCP forensics) and per-user cache leakage — infrastructure-level; this is an application widget. The ledger's cache-key/per-user-cache family keys on a missing `Vary`, this keys on a global list. NEW atoms: (a) the personalization slot as an identifier-distribution channel, (b) identifier-equals-capability at the MANAGEMENT route, (c) the settings-page CSRF token handed to a stranger as the link that turns a read leak into a write, (d) one disposable object as the safe blast-radius control.
HONESTY: not reproduced by us; the widget name, the UUID-as-capability statement, the CSRF-token step, the name/description write and the "no customer project modified" scope control are the researcher's; the P4 rating is the program's and is recorded as-is rather than argued upward, because the demonstrated blast radius was one researcher-owned project.

### §INTAKE-2026-11-27/03 — THE ROUTER ACCEPTS A METHOD THE HANDLER DOES NOT KNOW: `HEAD` IS DISPATCHED TO THE `GET` HANDLER BY THE FRAMEWORK, BUT THE HANDLER ASKS "IS THIS A GET?" — SO `HEAD` FALLS INTO THE **GRANT** BRANCH, AND BECAUSE `HEAD` IS "SAFE" THE CSRF CHECK IS SKIPPED TOO, WHICH TURNS AN OAUTH CONSENT SCREEN INTO A ZERO-CLICK APP-AUTHORIZATION PRIMITIVE (GitHub `oauth/authorize`, Teddy Katz, $25,000, 2019 — case study read 2026-11-27)

SOURCE: https://masimshahzad.medium.com/github-oauth-bypass-the-25k-head-request-e9a666059615 (Muhammad Asim Shahzad, "GitHub OAuth Bypass: The $25K HEAD Request", published 2026-11-27, an AI-assisted analytical case study of Teddy Katz's public 2019 disclosure; original fix shipped on github.com June 2019 and in GitHub Enterprise Server 2.17.3, where the release notes list an "OAuth app authorization bypass" as CRITICAL; $25,000 via HackerOne)  read 2026-11-27
ROUTE: `web_extract` on the article URL — HTTP 200, body returned (the mechanism, the quotes and the consequence all present); the author's own disclaimer states no PoC is reproduced. `freedium.cfd` and `r.jina.ai` both failed from this host (000 / 401).
STATUS: UNVERIFIED (not reproduced by us, and the writeup deliberately carries no PoC; the mechanism statement is the case study's summary of Katz's disclosure). FRESHNESS CAVEAT: the original flaw is 2019 and the fix is long shipped on github.com — recorded as a GENERAL METHOD with its date, not as a live bug; re-test on any target that still branches on the request method.
CLASS: authentication/authorization bypass by HTTP-method confusion — a route registered for two methods whose body branches on "is this a GET" instead of on "is this the POST that carries consent", combined with a CSRF exemption for methods the framework classifies as safe (CWE-650 trusting HTTP permission methods server-side + CWE-352).
CORE METHOD (as the case study states it):
  1. Read the consent endpoint as TWO jobs on ONE path: "The OAuth authorize URL … does two jobs: a GET shows the consent page, and a POST from the 'Authorize' button, carrying a CSRF token, grants the app access."
  2. Check the router's method list for that path, then check what the HANDLER branches on: "The router accepted both methods for that path. Inside, the code asked one question: 'is this a GET?' If yes, show the page. Otherwise, grant access." Any verb that reaches the handler but is not `GET` inherits the grant branch.
  3. Reach the branch with a verb the framework maps to the GET handler: "Rails routes HEAD requests to GET handlers, so the router let them through. But the code's check still saw a request that was not a GET, so it took the grant branch."
  4. Note why the second control also disappears: "because HEAD is supposed to be side-effect free, CSRF protection did not ask for a token" — the grant therefore requires no token and no click.
  5. Deliver it as a page visit: "a malicious site could make a signed-in visitor's browser approve an attacker's OAuth app, which could then read or modify that user's private data." (Any auto-firing vector works — image/navigation/form; the state change is a "safe" method, so even `SameSite=Lax` top-level navigation suffices.)
  6. The fix direction the article gives is the general rule: branch on the SAFE case and deny everything else by default ("Branch on the safe case" first), not on "not-GET ⇒ grant".
DETECTION SIGNAL: a route documented or discoverable for two methods where one is read-only (`GET`/`HEAD`/`OPTIONS`) and the other grants (`POST`); handler code or behaviour that tests `method == 'GET'` / `req.method !== 'POST'` / `else { grant }` rather than whitelisting the granting verb; a framework that transparently maps `HEAD`→`GET` handlers (Rails, many routers) and a CSRF middleware that exempts `GET`/`HEAD`/`OPTIONS` (the near-universal default); any consent/approve/confirm/accept/authorize/token-mint endpoint whose GET renders a form and whose POST commits; an app that returns the same body for `curl -I` and `curl -X GET` on that path.
CHAIN: a victim with an active session on the identity/app provider (primitive: an ordinary logged-in browser) -> a page the attacker controls issues a `HEAD` (or any non-GET verb the router maps to GET) to the authorize path (primitive: the route accepts the verb) -> the handler's "is this a GET?" test answers NO and falls into the else/grant branch (escalation 1: consent display logic is inverted into consent grant) -> the CSRF/anti-forgery layer treats `HEAD` as safe and requires no token (escalation 2: the second, independent control is skipped by construction, not bypassed) -> the attacker's OAuth application is now authorized against the victim's account with the scopes in the request (terminal: third-party app holds read/write on private repositories / mail / files — an account-level integration compromise with zero interaction, which the vendor scoped as CRITICAL and paid $25,000 for).
TRANSFERABLE TEST: on every consent/approve/mint endpoint (OAuth/SAML authorize, app install, device-code approval, payment confirm, invite accept, scope grant, API-key mint), (1) send the GRANT request with the method swapped one rung at a time — `HEAD`, `OPTIONS`, `PATCH`, `PUT`, and `POST` with `X-HTTP-Method-Override: GET` — with NO CSRF token and NO `Origin`; (2) compare side effects (does the grant list / consent table / token table now show the application?); (3) if `HEAD` is refused, try the reverse asymmetry (`GET` on the commit path) and the method-override header; (4) whenever a handler's only question is "is this a GET", assume every other method is a grant. Rule: **a handler that branches "not-GET ⇒ grant" plus a CSRF layer that exempts safe methods means `HEAD` is an authenticated state change with no token — so enumerate the granting endpoints and send the grant with `HEAD` first, before you spend a pass on the consent UI.**
DEDUPE/DELTA: `HEAD` + consent, `side-effect free`, `Rails routes HEAD`, `not-a-GET ⇒ grant` = 0 hits across the three write targets; the two `method confusion` hits are the curl/`READDATA` client-state-confusion entry (ledger 6072, §17.186-family) — a reused HANDLE sending a wrong verb, not a router/handler disagreement. `Teddy Katz` hits are his 2021 fork-collaboration entry (create-check vs edit-check, §17 recorded), a different bug on the same product. The ledger's CSRF corpus (V-02 GET-based CSRF, `V-05` method mutation, "middleware mounted on POST only") covers state change on safe methods from the CLIENT side; it does not record the SERVER-side inversion where the handler's negative test makes `HEAD` the granting verb on an OAuth consent path, nor the "safe ⇒ no token" exemption doing double duty. NEW atoms: (a) framework verb remapping (`HEAD`→GET handler) as the way in, (b) `else { grant }` as the inversion, (c) the safe-method CSRF exemption removing the second control, (d) the consent screen as the highest-value target for the trick.
HONESTY: not reproduced; every quote is the 2026-11-27 case study's, which itself credits Katz and states the flaw was fixed in 2019 (GHES 2.17.3 notes call it CRITICAL, and $25,000 was paid) — the entry is a METHOD record with an explicit freshness caveat, not a claim that any current target is vulnerable.

### §INTAKE-2026-11-27/04 — A LOW-VALUE TOOL SERVED FROM THE **SAME ORIGIN** (PATH) AS A SENSITIVE AUTHENTICATED APP LAUNDERS ITS XSS INTO THAT APP'S DATA: THE VULNERABLE PAGE HOLDS NOTHING, BUT ITS JAVASCRIPT IS SAME-ORIGIN WITH THE PROPOSAL/ACCOUNT SYSTEM, SO IT READS THE VICTIM'S PII WITH THE VICTIM'S COOKIES (NASA HEASARC VOTable Viewer → ARK, Bugcrowd P3, 2026-06-17)

SOURCE: https://bugcrowd.com/disclosures/00cb5011-6768-4b68-a4a2-6b48a9ae35b3/reflected-dom-xss-in-votable-viewer-leads-to-authenticated-ark-user-pii-exfiltration-via-same-origin-xhr (NASA Vulnerability Disclosure Program — "Reflected DOM XSS in VOTable Viewer leads to authenticated ARK user PII exfiltration via same-origin XHR", P3, disclosed 2026-06-17, resolved)  read 2026-11-27
ROUTE: CrowdStream listing → disclosure page via `curl` + local HTML strip (HTTP 200); the researcher's summary is the published text (the program validated and resolved it).
STATUS: VERIFIED-BY-REPORT (program-validated, resolved); NOT reproduced by us.
CLASS: reflected/DOM XSS with demonstrated impact — impact is created by ORIGIN SHARING, not by the vulnerable page's own data: an unrelated utility mounted on the same scheme+host (different path) grants the injected script the credentials and API reach of the co-hosted sensitive application (CWE-79; the escalation is CWE-668 exposure of resources to the wrong sphere / missing origin isolation between tenants-in-paths).
CORE METHOD (as the report states it):
  1. Accept that the XSS page itself is worthless and that is not the point: "Although the vulnerable application itself did not contain sensitive information, it shared the same origin as the ARK proposal management platform used by NASA researchers and astronomers."
  2. Build the inventory of what shares that origin: other path-mounted apps on the same host (VOTable viewer, ARK, catalog tools, docs) — enumerate paths from the site's own navigation, `robots.txt`, JS bundles and `sitemap.xml`, not from DNS (they are the same host).
  3. Confirm the sharing is a true same origin (same scheme+host+port, path-based routing), because that is the whole primitive: cookies marked host-only for that host ride every path, and `document.domain`/relative XHR inherit it.
  4. Aim the injected JavaScript at the SENSITIVE app's endpoints with the victim's session: "By abusing the same-origin relationship, JavaScript executed through the XSS could perform authenticated requests to ARK endpoints and access sensitive user information available to the victim's account." Same-origin `fetch`/`XHR` needs no CORS, no `credentials:'include'` negotiation and no custom headers — the session cookie is attached automatically.
  5. Rate it on the co-hosted app's data: the report's title is the finding — "authenticated ARK user PII exfiltration via same-origin XHR" — and the program accepted it at P3 with the vulnerable page contributing nothing but the injection.
DETECTION SIGNAL: one host serving MULTIPLE applications by path (`/`, `/tools/`, `/viewer/`, `/ark/`, `/reports/`, `/api/`, `/legacy/`) — the tell is a public science/tool/doc app next to an authenticated business app under the same hostname; different apps distinguishable by `Set-Cookie` path scoping, different CSP headers per path, different `X-Powered-By`/framework fingerprints per path, or one path's HTML loading a bundle from `/static/<app>/`; an authenticated app whose APIs are reachable at relative paths from a sibling path app (`/ark/api/...`); any DOM/reflected XSS on the low-value sibling with no impact on its own page; per-path auth that relies on a host-scoped cookie rather than a path-scoped one.
CHAIN: an unauthenticated attacker sends a crafted link to the low-value viewer path (primitive: reflected DOM XSS with no data of its own — normally P4/P5 or a "self-XSS" style dismissal) -> the victim, signed into the co-hosted sensitive app, opens it and the script runs on that host with the victim's cookies attached to every same-origin request (escalation 1: the injection inherits the sibling app's authority because "origin" is scheme+host, not app) -> the script calls the sensitive app's relative API paths and reads the JSON the victim's session is entitled to — names, emails, addresses, proposal/project membership (escalation 2: no CORS, no token theft, no CSRF needed) -> the results are POSTed off-origin (beacon/image/same-origin redirect then external) (terminal: authenticated PII exfiltration from an app that was never itself vulnerable; the program rated P3 on data class, and the same chain on a payment/admin app on one host is P2).
TRANSFERABLE TEST: for every host, (1) list the path-mounted applications and classify which ones carry authenticated data; (2) find ANY injection on the low-value one (reflected/DOM XSS, HTML injection, an open `postMessage` handler); (3) prove the authority transfer with a read-only same-origin call from the injected context — `fetch('/<sensitive-app>/api/me',{credentials:'same-origin'}).then(r=>r.text())` — and capture the response body, plus a `document.cookie` read to show which cookies ride; (4) if the sensitive app is on a SUBDOMAIN instead, this particular chain stops (different origin) — check `document.domain` relaxation and host-only vs `.parent.tld` cookie scope before declaring it closed. Rule: **an XSS is worth what its ORIGIN is worth — before dismissing a bug on a throwaway tool page, enumerate the other applications mounted on the same host and try a relative-path authenticated fetch from the injected script; site-per-path architectures silently give every sibling app the same authority.**
DEDUPE/DELTA: `00cb5011`, `VOTable`, `HEASARC`, `same-origin XHR`, `path-mounted`/`site-per-path` = 0 hits across the three write targets. Recorded neighbours REVIEWED and NOT conflated: the ledger's `same-origin` material is CSP `script-src 'self'` defeat by storing a JS file through the platform's own uploader (§GitLab Mermaid / raw `/raw` entries) and a same-origin JSON-fetch through a cache/key differential — both require the attacker to PLANT an asset on the origin; here nothing is planted, an existing sibling app's own injection supplies the script context. The ledger's CORS entries read cross-origin by design; this needs no CORS at all. NEW atoms: (a) origin sharing (path routing) as an authority amplifier, (b) the "vulnerable app holds nothing" excuse retired, (c) relative-path same-origin API access as the exfil step, (d) the subdomain-vs-path distinction as the boundary test.
HONESTY: not reproduced by us; the shared-origin statement, the ARK-read outcome and the P3 rating are the researcher's and the program's; no request shapes were published beyond "authenticated requests to ARK endpoints", and none are invented here.
