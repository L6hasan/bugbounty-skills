### §INTAKE-2026-11-24/01 — TWO LAYERS, TWO CANONICAL PATHS: `@fastify/express` WITH `ignoreDuplicateSlashes` MATCHES THE ROUTER'S VIEW BUT NOT THE EXPRESS MIDDLEWARE'S, SO AN ABSOLUTE-FORM REQUEST TARGET REACHES A SCOPED `/admin` HANDLER WITH THE AUTH MIDDLEWARE SKIPPED (CVE-2026-112362, CVSS 9.1)

SOURCE: https://github.com/fastify/fastify-express/security/advisories/GHSA-6h42-57hq-9746 (OpenJSF CNA advisory GHSA-6h42-57hq-9746; corroborated by https://nvd.nist.gov/vuln/detail/cve-2026-112362 and https://access.redhat.com/security/cve/cve-2026-112362)  read 2026-11-24
ROUTE: live pages read in full via web_extract — advisory text (affected/patched versions, Impact, Patches, Workarounds, CVSS vector) plus NVD description. No request PoC is published by the vendor; none is invented here beyond the request line the advisory itself names.
STATUS: UNVERIFIED here (not reproduced — no Fastify app stood up this pass); vendor-coordinated disclosure with a patch (4.0.9), reporter credit agent-killjoy, remediation mcollina.
CLASS: authentication/authorization middleware bypass via an INTERPRETATION CONFLICT between two in-process routing layers (CWE-436) -> unauthenticated execution of path-scoped handlers (admin/internal/rate-limited routes).
CORE METHOD (as the advisory states it):
  1. Preconditions, both required: `@fastify/express` `>= 4.0.5, < 4.0.9` AND Fastify started with the NON-DEFAULT `routerOptions.ignoreDuplicateSlashes: true`. With the default (off) the bug is not reachable.
  2. Understand the two parsers. Fastify's router is find-my-way, which resolves an absolute-form request target to its PATH and dispatches the handler. The Express layer's duplicate-slash normalization also collapses the `//` after an absolute-form target's SCHEME (`http://host/admin/dashboard` effectively seen as `http:/host/admin/dashboard`), so the Express mount `app.use('/admin', authMiddleware)` no longer matches the scoped path. The advisory: "the plugin matches path-scoped Express middleware against a URL whose duplicate-slash normalization has also collapsed the separator after an absolute-form request target's scheme ... Fastify's router resolves the absolute-form target to its path and dispatches the handler, while the Express layer no longer sees the scoped path".
  3. Fire the request with an absolute-form target: `GET http://host/admin/dashboard` (absolute URL in the request line). The handler runs; the middleware chain for authentication, authorization or rate limiting never executes.
  4. Note the vendor's own workaround, which is the design lesson: "Enforce auth in a Fastify hook (such as `preHandler`) that runs after the router has resolved the request". Middleware that is mounted by the SECOND layer is only as strong as that layer's path view.
  5. Related upstream/downstream atoms (same advisory references): GHSA-6hw5-45gm-fj88 (CVE-2026-33808), the earlier `@fastify/express` middleware bypass whose fix INTRODUCED this normalization; GHSA-hx87-8wv7-pjv8 (CVE-2026-85184), the same absolute-form bypass in `@fastify/middie`. So this class recurs across the Fastify middleware plugins — check every one.
DETECTION SIGNAL: a Node stack with `@fastify/express`/`@fastify/middie` in the dependency tree (package-lock/npm ls) or `require('@fastify/express')` in bundled server code; `ignoreDuplicateSlashes` present in Fastify router options (config file, bootstrap code, leaked source, error text); Express middleware mounted on a path prefix (`app.use('/admin', ...)`, `app.use('/api', ...)`) that performs authn/authz/rate limiting rather than a Fastify `preHandler`/hook; version headers or package metadata pinning `@fastify/express` 4.0.5–4.0.8.
CHAIN: unauthenticated network caller (primitive: no credentials needed, CVSS PR:N) + the non-default `ignoreDuplicateSlashes: true` configuration (primitive: a hardening/UX option that changes normalization) -> send the request with an absolute-form target so the router and the Express middleware compute DIFFERENT canonical paths (escalation: the security middleware is silently not in the call path) -> the scoped handler executes as if no auth/ACL/rate-limit gate existed (terminal: unauthenticated access to admin/internal routes and their data/actions; CVSS 3.1 AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N = 9.1 Critical).
TRANSFERABLE TEST: on the next Node/proxy target, (1) fingerprint for `@fastify/express`/`@fastify/middie` and for `ignoreDuplicateSlashes`/`ignoreTrailingSlash`/`strictRouting` in router options; (2) for EVERY path-scoped middleware that enforces auth, ACL or rate limiting, send the SAME path twice — once origin-form (`GET /<scoped>/x HTTP/1.1`) and once absolute-form (`GET http://<host>/<scoped>/x HTTP/1.1`) — and diff status/body/latency; (3) extend the ladder with `//<scoped>`, `/\<scoped>`, `%2f`, and a `https://` scheme variant, plus a `Host` header that disagrees with the absolute-form authority; (4) if any absolute-form variant returns 200 where the origin-form is 401/403/429, the gate is bypassed — record the exact request line as the PoC. Rule: **when two layers must agree on the request path (a router and a middleware framework, or a front proxy and an app), any encoding that makes them compute different canonical paths is an authorization bypass — so always diff each layer's parsed path for the same raw request target, and put auth in the hook that runs LAST.**
DEDUPE/DELTA: `ignoreDuplicateSlashes`, `CVE-2026-112362`, `GHSA-6h42`, `find-my-way` = 0 hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: `/root/Bugbountyskills.md` R5 lists the "absolute-form request line" only as a generic desync/header-smuggling candidate, and ledger 1489/2810 list it among `X-Forwarded-*` variants — neither records the router-vs-middleware path disagreement. The ledger's HTTP-request-smuggling and path-normalisation-differential entries (front-end vs back-end proxies, Apache decode-after-check, `//-/admin` double-slash) are about TWO SERVERS disagreeing; here it is TWO IN-PROCESS LAYERS of one Node app, and the trigger is an ordinary absolute-form target plus a normalization option. HONESTY: not reproduced; the version ranges, the option name, the collapsed-separator mechanism, the `preHandler` workaround sentence and the two related-GHSA references are verbatim from the advisory; severity is the vendor/CNA figure (9.1), not ours.

### §INTAKE-2026-11-24/02 — A FEATURE FLAG SWITCHES WHICH RENDERER SEES THE DISPLAY NAME: ON >10K-USER WORDPRESS SITES QUICK EDIT READS THE AUTHOR CELL WITH `.text()` (DECODES ENTITIES) AND FEEDS IT TO `.prepend()` (REPARSES AS HTML) — A CONTRIBUTOR'S ENTITY-ENCODED DISPLAY NAME BECOMES ADMIN-SESSION JAVASCRIPT, AND THE URL FRAGMENT CARRIES STAGE TWO

SOURCE: https://hackerone.com/reports/3878399 (WordPress Core 7.0.2, "Large-site Quick Edit reparses a Contributor display name into active HTML", DOM XSS, Medium, disclosed 2026-10-21)  read 2026-11-24
ROUTE: live `.json` report route, HTTP 200, `visibility: full`, `vulnerability_information` ~9 KB read IN FULL (preconditions, docker lab, numbered repro, second-stage payload, root cause, confirmed result, file/line references).
STATUS: UNVERIFIED here (not reproduced — no WordPress instance stood up this pass); the reporter ran a self-contained Docker lab and attached the transcript; the report carries a collaborator and was triaged Medium by the program.
CLASS: stored DOM XSS via a decode-then-reparse sink PAIR inside an admin UI, gated by a site-size feature flag -> contributor-to-administrator privilege escalation.
CORE METHOD (as the report states it):
  1. Find the flag that changes the rendering path: "On sites with more than 10,000 users, a Contributor can save entity-encoded HTML in their display name. When an administrator opens the attacker's crafted Posts-page URL and clicks Quick Edit ... WordPress decodes the stored name with `.text()` and reparses it through jQuery `.prepend()`." Root cause bullets: "WordPress preserves valid entities such as `&lt;` in the saved display name"; "In large-site mode, Quick Edit omits the normal author options"; "The fallback reads the author cell through `.text()` and concatenates it into HTML passed to `.prepend()`."
  2. Store the entity-encoded payload where the display name lives, over the REST route the UI itself uses (fetch `/wp-admin/admin-ajax.php?action=rest-nonce`, then `POST /index.php?rest_route=/wp/v2/users/<me.id>` with header `X-WP-Nonce` and body `{"name":"&lt;img src=x onerror=eval(atob(location.hash.slice(1)))&gt;"}`). Confirmed HTTP 200.
  3. Make the value surface on a page the admin will open: create any post, submit it for review (HTTP 201), then hand the administrator a URL whose FRAGMENT is harmless-looking: `http://<host>/wp-admin/edit.php?post_status=pending&post_type=post#ZG9jdW1lbnQudGl0bGU9J1F1aWNrLUVkaXQtWFNTLTcyMSc=` (stage one only marks the tab title).
  4. The admin clicks Quick Edit on the contributor's post. Confirmed: "Before Quick Edit: zero active elements / After Quick Edit: tab title `Quick-Edit-XSS-721`, one active element" — the decoded `<img onerror>` became a live element and the hash payload ran in the ADMIN origin.
  5. Stage two (persistent): a second crafted URL's fragment is a base64 script that fetches `/wp-admin/user-new.php`, scrapes `#_wpnonce_create-user`, then POSTs `action=createuser&_wpnonce_create-user=<n>&user_login=h1-quick-edit-admin&email=...&pass1=...&pass2=...&role=administrator`. Confirmed: "Users contains Username: h1-quick-edit-admin / Role: Administrator".
  6. Note the exact boundary the reporter measured: "At exactly 10,000 users, the normal populated author dropdown prevents this branch" — the vulnerable renderer is selected by the flag, not available on small sites.
DETECTION SIGNAL: client bundles containing jQuery `.text()` (or `textContent`) whose result is concatenated into a string passed to `.prepend(`/`.append(`/`.html(`/`.after(`; any user-controlled field (display name, nickname, org name, filename) rendered by a DIFFERENT component under a feature flag (large-site count, mobile, legacy, print, preview, `?view=`); payload smuggled in the URL FRAGMENT (never sent to the server, so server-side encoding logs stay clean); a site whose display-name signup/validation accepts entity references.
CHAIN: a Contributor account (primitive: lowest content role, owns a pending post) -> store entity-encoded HTML in the display name, which the server preserves verbatim (primitive: a value that survives storage because it is only dangerous after a later decode) -> the admin opens a crafted link and performs ONE ordinary UI gesture (Quick Edit) (interaction) -> `.text()` decodes the entities and `.prepend()` parses them as markup (escalation: attribute-safe storage becomes live DOM in the admin origin) -> the fragment payload steals a nonce and creates an Administrator (terminal: full, persistent site takeover; the report's own words "The confirmed chain creates a persistent Administrator account").
TRANSFERABLE TEST: on any admin/console UI, (1) grep the JS for `.text()`/`textContent` immediately feeding `.prepend/.append/.html/.after` and for `innerHTML` assignments built by string concatenation; (2) enumerate user-controlled strings that are rendered by MORE THAN ONE component depending on a flag (user count, device, role, `?view=`, A-B bucket) and test the field on EVERY branch; (3) store `&lt;img src=x onerror=<marker>&gt;`-style entity-encoded HTML in each such field and look for a live element rather than text; (4) where the payload must survive a server round-trip, carry stage two in `location.hash` and read it with `atob(location.hash.slice(1))`; (5) prove admin impact with an observable side effect (new user row, changed title, network call) — never with `alert()` alone. Rule: **`.text()` is a DECODER and `.prepend()`/`html()`/`after()` is a PARSER — a decode immediately followed by a reparse is an XSS sink even when the stored bytes are correctly entity-encoded, so treat every `decode()-then-string-build()-then-DOM-insert()` triple as a sink and test each feature-flag-selected renderer separately.**
DEDUPE/DELTA: `3878399`, `inline-edit-post`, `wp_is_large_user_count`, `.prepend()` = 0 hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: §17.805 (Pontoon #3988961) is the sibling atom "server escapes into `data-*`, browser decodes, jQuery `.after()` reparses" — same decode-then-reparse FAMILY, but there the decoder is `.data()` reading an attribute and there is no feature-flag-selected renderer, no fragment-carried second stage and no privilege escalation; this entry's NEW atoms are (a) `.text()` as the decoder, (b) a rendering branch chosen by `wp_is_large_user_count()`, (c) the URL-fragment as the second-stage carrier, (d) the demonstrated contributor->administrator terminal. Also distinct from the ledger's GraphQL-autosave/"quick edit" detection signal (a typed-input partial-update atom) and from the WordPress media/sub-size filename XSS entries (#3931771/#3931777). HONESTY: not reproduced by us; the payload strings, the REST route, the fragment values, the confirmed outputs ("Quick-Edit-XSS-721", the created administrator), the 10,000-user boundary and all file/line references are verbatim from the report body; severity is the program's Medium (DOM XSS) — the ESCALATION to administrator is the reporter's confirmed chain and is recorded as such.

### §INTAKE-2026-11-24/03 — THE CANONICAL ROUTE ENFORCES THE OWNER-ONLY RULE, THE GEM-TRANSFER ROUTE DOES NOT: RUBYGEMS.ORG LETS AN ORGANIZATION ADMIN SUBMIT `role=Owner` FOR AN INVITEE THROUGH THE TRANSFER FLOW AND CREATE AN OWNER MEMBERSHIP THE DIRECT ENDPOINTS REFUSE

SOURCE: https://hackerone.com/reports/3938927 (RubyGems.org, "An organization admin can create an attacker-controlled organization owner via the gem transfer flow", Improper Access Control, High 7.0, disclosed 2026-10-15)  read 2026-11-24
ROUTE: live `.json` report route, HTTP 200; `visibility: no-content` (reporter body withheld at disclosure) but the program's own team summary is published and was read in full, plus the report metadata (severity, CVSS v4.0 metrics, asset rubygems.org, vote count).
STATUS: UNVERIFIED here (not reproduced — no RubyGems.org account or organization touched this pass); the mechanism is the program's own description of the fixed defect.
CLASS: vertical privilege escalation / broken function-level authorization — a role restriction applied on the primary membership route is absent on a SECONDARY object-transfer flow that writes the same membership table.
CORE METHOD (as the team summary states it):
  1. Establish that the rule EXISTS and is enforced on the canonical routes: "a direct owner invite returns 404, and adding a direct gem owner returns 403". Two independent negative controls — the restriction is real, so the finding is not a missing rule.
  2. Enumerate the OTHER flows that can create an organization membership. The gem transfer flow is one: "The transfer flow only checks that the user is an admin of the Organization. It then accepts whatever role is submitted for each invitee, including Owner, and creates the Organization membership without applying the owner-only rule."
  3. Note the regression shape: "A previous fix enforced this rule on the direct membership route but did not extend it to gem transfers." A partial fix on one route is an invitation to enumerate sibling writers.
  4. Impact: an Organization ADMIN (not an owner) grants themselves — or an attacker they name — the Owner role, i.e. full control of the organization's gems, members and settings; the program rated High 7.0 with `privileges_required: high` and integrity/availability high.
DETECTION SIGNAL: any system where a role/ownership/plan/pricing field can be set from a request body or hidden form field; MORE THAN ONE flow that writes the same membership/entitlement table (invite, transfer, import, merge, linking, SCIM, API, admin console); a restriction that returns 403/404 on the well-known route but is not mentioned in the sibling flow's docs; a recent security fix touching only one of those routes.
CHAIN: authenticated organization admin (primitive: a high-but-not-top role) -> issue a gem transfer (or any secondary assignment flow) naming an invitee and submitting `role=Owner` (primitive: the flow validates the ACTOR's org-admin rights but not the SUBMITTED role) -> an Owner membership row is created that the canonical invite route refuses with 404/403 (escalation: vertical privilege escalation to owner) -> control of the organization's gems, members, integrations and settings (terminal: full org compromise; program-rated High).
TRANSFERABLE TEST: on the next target with roles/entitlements, (1) pick a role ABOVE your own (Owner, Admin, Superadmin, Owner-tier plan) and try to assign it to yourself or an accomplice through EVERY endpoint that writes that field — canonical invite, transfer/import/migrate, bulk CSV, API/SCIM, account-link, admin-console edit; (2) record the status of each: a 200/302 where the canonical route 403s is the win; (3) also try the legacy/alias parameter spellings (`role`, `type`, `member_type`, `roles[]`, `is_owner`) and a JSON-vs-form content-type switch, since the sibling writer often has a looser schema; (4) confirm the gain from the TARGET account (log in as the newly-created owner, or read an owner-only resource). Rule: **a role restriction enforced on the canonical route is a per-route check, not a property of the object — enumerate every flow that writes the role/ownership column, and test each with a role above your own.**
DEDUPE/DELTA: `3938927`, `gem transfer`, `transfer flow` (in the role-writer sense) = 0 hits across all three write targets. Recorded RubyGems material REVIEWED and NOT conflated: the registry source-priority inversion/dependency-confusion entry (`okra`) and the `Gem::Package#install_location` symlink traversal #270072 — both are supply-chain/package-installer bugs, not authorization. ### §INTAKE-2026-11-24/04 — A MANAGEMENT API CHECKS THE CALLER'S API-LEVEL PRIVILEGE BUT NOT THE OBJECT: NEXTCLOUD GROUPFOLDERS' `POST /folders/{id}/groups` TAKES ANY AUTO-INCREMENT FOLDER ID, SO AN "API/REST ONLY" DELEGATED ADMIN SELF-GRANTS THEIR OWN GROUP INTO EVERY TEAM FOLDER

SOURCE: https://hackerone.com/reports/3674940 (Nextcloud groupfolders, "Critical broken access control: API-only delegated admin can enumerate all Team Folders and grant access to arbitrary groups", CVE-2026-77169, disclosed 2026-09-17)  read 2026-11-24
ROUTE: live `.json` report route, HTTP 200, `visibility: full`, `vulnerability_information` read IN FULL (endpoint table, preconditions, curl PoC, verbatim JSON response, mass-enumeration steps, impact).
STATUS: UNVERIFIED here (not reproduced — no Nextcloud instance stood up this pass); the reporter's own lab (Nextcloud Hub 26 Winter 33.0.2, Docker) and the program's advisory GHSA-9mjh-89xm-hcqw back the mechanism; program-rated Medium 5.7.
CLASS: broken object-level authorization (BAC/IDOR-with-write) on an access-control-mutating endpoint -> cross-team data exposure and group-access manipulation.
CORE METHOD (as the report states it):
  1. Locate a WRITE endpoint whose job is to change who may access an object: `POST /index.php/apps/groupfolders/folders/{id}/groups` with body `{"group": "Product_Dev"}`, authenticated by session cookie + `requesttoken` (CSRF token), `Content-Type: application/json`, `X-Requested-With: XMLHttpRequest`.

CHAIN: a low-scope `API/REST only` delegated admin holding one group (primitive: legitimate but narrow privilege) -> POST to the folder-group route with a FOREIGN, enumerable folder id (primitive: object-level authz absent on a writer that only checks API-level privilege) -> the attacker's group is granted permission 31 on someone else's Team Folder (escalation: authorization state mutated across tenants/teams) -> read/download the Finance/HR/Legal/Engineering folder contents, and repeat for every id (terminal: organization-wide data exposure from one low-privilege account).

Rule: **an endpoint that writes an ACL must authorize on the CONTAINER object, not just on the caller's role — a 200 that echoes an empty `manage`/owner field while mutating a foreign id is the signature, and the gain must be confirmed by reading the object as the beneficiary.**
DEDUPE/DELTA: `3674940`, `groupfolders`, `folders/{id}/groups`, `Team Folder` = 0 hits across all three write targets. No §17 slot this entry (see pass note). SOURCE: https://hackerone.com/reports/3772818 (Nextcloud Desktop Client 33.0.5 for macOS, "Code injection allows unprivileged local attacker to execute arbitrary code in Nextcloud's OAuth/web renderer process", CWE-94, Low 3.6, disclosed 2026-10-24)  read 2026-11-24

STATUS: UNVERIFIED here (not reproduced — no macOS host used this pass); the reporter supplied codesign/otool transcripts and screenshots; program-rated Low (local attack vector, user interaction).
CLASS: client-side code injection into an unsandboxed embedded-browser renderer -> credential/OAuth-token theft and local code execution at standard-user level (a sandbox-escape-adjacent, client-misconfiguration finding).
CORE METHOD (as the report states it):
  1. Pick the helper binary that handles embedded web content and OAuth: `Nextcloud.app/Contents/Frameworks/QtWebEngineCore.framework/Versions/A/Helpers/QtWebEngineProcess.app/Contents/MacOS/QtWebEngineProcess` (Team ID NKUJUXUJ3B, version 33.0.5).

  5. Plant a RE-EXPORT SHIM at the exact expected path (the report stresses a plain dylib fails at symbol resolution before any constructor): build with `clang -dynamiclib -arch arm64 -install_name nc_inject.dylib -Wl,-reexport_library,"$REAL_QtWebEngineCore" -Wl,-rpath,"<Frameworks dir>" -o nc_payload.dylib payload.c`, where `payload.c` carries `__attribute__((constructor(101)))` code that writes a proof file, dumps the Nextcloud keychain item with `security find-generic-password -wa 'Nextcloud'` and launches Calculator.
