Find the operation that still touches the object: "Sort by → Card name (alphabetically) … you can see that even the unauthorized mirrored card is sorted correctly, allowing an attacker to construct its full name." The comparator had to read the title to place it, and nothing checked authorization on that path.
  3. Turn the ordering into a comparator oracle: create your OWN probe cards in the same list with known names (`aaa…`, `zzz…`) and observe whether the hidden card sorts before or after each — "inserting probe cards and observing whether the target sorts before or after each, an attacker can binary-search the alphabet and reconstruct the hidden title without reading it."
  4. Respect the collation, don't fight it: "Now I use ASCII alphabet, but the alphabet could be extended with caution (because the sort is collation sort in mongodb)" — MongoDB collation folds case and punctuation, so an ASCII probe set recovers the string case-insensitively; at the end "extraction is case-insensitive (MongoDB collation)" is stated as a known limitation, not a bug.
  5. Batch the oracle: "GraphQL aliasing on `updateCardName` batches ~50 probes per request" — one request carries fifty aliased mutations, so the binary search costs requests/50.
  6. Get ids at scale from the existence oracle: "Short URLs use only 8 chars of [A-Za-z0-9]. Unauthenticated requests distinguish real cards ('unauthorized') from fake ('not found'), aren't rate-limited, and `/batch` accepts ~350 sub-requests vs its documented 10 — so valid IDs can be harvested at scale by guessing."
  7. Combine: "Chained, these enable mass enumeration of private card titles, privilege escalation, revocation bypass, and real-time title monitoring."
DETECTION SIGNAL: a list/board/collection UI with "sort by <field>" over fields the caller may not read (name, title, label, contact, price); a "mirror"/"linked"/"shared-with-me" rendering that shows a placeholder row for objects you cannot open; a Mongo/Elasticsearch/SQL backend where sort happens server-side after a partial permission filter; an unauthenticated error split between "unauthorized" and "not found" on the same route (the oracle); a `batch`/`multi`/`aliased GraphQL` endpoint whose documented limit is not enforced; short ids (8 chars base62) on shareable resources.
CHAIN: a non-privileged account that knows an object id (primitive) -> the read path refuses the content but the ORDER path still compares it (primitive: authorization attached to one operation, not to the object) -> probe objects make the comparator answer before/after questions, i.e. one bit of the hidden string per request, 50 bits per aliased request (escalation 1) -> 8-char unauthenticated existence oracle plus an unenforced batch limit supplies unlimited ids (escalation 2) -> mass reconstruction and ongoing monitoring of private titles, with downstream privilege escalation / revocation bypass wherever a title is a secret or a status (terminal; the program rated it P4 only because "severity depends on what users store in titles" — the mechanism itself is P2-capable wherever titles carry amounts, names, tokens or unreleased plans).
TRANSFERABLE TEST: for every sortable list, place two of your own objects named to bracket the target and read the resulting ORDER of the placeholder row; then binary-search with a probe set and repeat through the batch/alias endpoint. Separately, request one real and one fabricated id unauthenticated and compare the two error strings; if they differ, script the id harvest. Rule: **an object you cannot READ is still comparable — so audit every ORDER BY / sort / rank / filter feature as a separate authorization surface, and treat "unauthorized" vs "not found" plus an unenforced batch limit as a free id supply.**
