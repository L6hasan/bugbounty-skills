CLASS: XSS (client-side) enabled by a query-string PARSER DIFFERENTIAL between the server framework (`qs`, Express `'extended'`) and the browser (`URLSearchParams`) — "validate server-side, consume client-side".
CORE METHOD (as the post states it):
  1. Look for the anti-pattern, not a payload: server middleware reads a query parameter, validates it, then emits a page whose INLINE SCRIPT re-reads the same parameter from `window.location.search`. Two parsers now decide what "the value" is.
  2. Enumerate the backend parser's deviations from a naive split. With Express `'extended'` you get `qs.parse(str, {allowPrototypes:true})` and the defaults that matter: `depth 5`, `arrayLimit 20`, `delimiter '&'`, **`parameterLimit 1000`**, plus bracket notation and duplicate-key merging into arrays.
  3. Exploit path A — the `]=` priority: `qs` finds the separator with `bracketEqualsPos = part.indexOf(']=')` and, if found, splits at the `=` AFTER the `]`; otherwise at the first `=`. So `?redirect_uri=javascript:alert(origin)//?x]=x&redirect_uri=https://pwnbox.xyz/docs` makes `qs` treat the whole first part as one meaningless KEY (containing `]=`), leaving `req.query.redirect_uri` = the second, safe value → the `!==` check passes. `URLSearchParams` has no `]=` rule, splits at the first `=` of each part, and `.get()` returns the FIRST match → the browser gets `javascript:alert(origin)//?x]=x` and `location=` executes it.
  4. Exploit path B — bracket stripping + the parameter cap: `[redirect_uri]=<safe>` sets `req.query.redirect_uri` in `qs` (brackets stripped) but is the literal key `[redirect_uri]` to `URLSearchParams` (ignored). Then hide the malicious copy past the backend's budget: `?[redirect_uri]=https://pwnbox.xyz/docs&p&p&…(×1000)&p&redirect_uri=javascript:alert(origin)`. `qs` stops after 1000 parts, never sees the second `redirect_uri`; `URLSearchParams` has no cap and `.get("redirect_uri")` returns it.

CHAIN: attacker crafts one link (primitive) → the two parsers disagree on which of two same-named parameters is "the value" (primitive: validator sees the allow-listed string) → the page assigns the attacker's `javascript:` URL to `location`, or renders/redirects from it (escalation: script in the origin) → with origin JS the attacker reaches whatever the page's own token/session surface allows, or uses it as the first hop of a redirect_uri/token-leak chain (terminal: XSS with session/PII impact; the post's own extension is that the same differential defeats the server-side allow-list that was supposed to make the redirect safe).
TRANSFERABLE TEST: on any endpoint where a parameter is (a) validated server-side and (b) re-read by inline JS, send it TWICE and make the copies read differently: `?p=<safe>&p=<payload>`; `?p=<payload>//?x]=x&p=<safe>` (for `qs`); `?[p]=<safe>&p&p&…×1000&…&p=<payload>` (cap evasion). Then read the served HTML in a browser and confirm which value the page's own `.get()` returns — and whether it reaches `location`, `innerHTML`, `eval`. Generalize: for each parser pair, the differences worth fuzzing are separator selection (`]`), key rewriting (brackets, dots→nesting), duplicate handling (first vs last vs array), and LENGTH/BUDGET CAPS (`parameterLimit`, `arrayLimit`, `depth`).   1. Separate the two questions the receiver answers: (a) is this blob authentic, (b) is what the blob CLAIMS about my own account true. ### §INTAKE-2026-11-23/09 — TWIG'S COMPILER ESCAPES THE DOUBLE-QUOTED LITERAL BUT NOT THE SINGLE-QUOTED ONE: A `{% use %}` TEMPLATE NAME CONTAINING `'` TERMINATES THE SURROUNDING PHP STRING AND INJECTS ARBITRARY PHP INTO THE COMPILED CACHE FILE, EXECUTING WHEN THE CACHE IS FIRST LOADED AND BYPASSING THE SANDBOX (`SecurityPolicy` ALLOWS `{% use %}` UNCONDITIONALLY)

SOURCE: https://symfony.com/blog/cve-2026-46633-php-code-injection-via-use-template-name (Twig/Symfony security advisory CVE-2026-46633, published 2026-05-20; affects Twig <3.26.0, fixed in 3.26.0)  read 2026-11-23
ROUTE: live page via `web_extract` — HTTP 200, full advisory text read (affected versions, description, resolution, credits). Advisory-only source: no request shapes are published, and none are invented here.
STATUS: UNVERIFIED here (not reproduced — no Twig build stood up this pass); vendor-coordinated disclosure with a patch, credited to Anvil Secure + Claude/Anthropic Research.
CLASS: server-side template-engine code injection -> RCE. The primitive is an INCOMPLETE ESCAPER at a compiler boundary, not SSTI: the attacker does not need the template engine's expression language to be reachable, only a value that reaches a `{% use %}` tag's TEMPLATE NAME (CWE-94 / CWE-95 adjacent).
CORE METHOD (as the advisory states it):
  1. Read what the escaper escapes. `Compiler::string()` "escapes `"`, `$`, `\`, NUL and TAB when generating PHP double-quoted string literals, but does not escape single quotes." Every character class it covers is one that would break out of a DOUBLE-quoted PHP literal — which is exactly why the omission is invisible on the paths where it is used correctly.
  2. Find the call site whose SURROUNDING literal uses the other quote character. In `ModuleNode::compileConstructor()`, "the template name from a `{% use %}` tag is compiled via `subcompile()` -> `string()` and placed inside a surrounding PHP single-quoted string literal." The generated cache file therefore contains something like `... '<?php ... ' . $name . ' ...' ...` where `$name` was escaped for a double-quoted context.
  3. Break out with the un-escaped quote. A template name containing a single quote terminates the surrounding PHP string early, and whatever follows is parsed as PHP code inside the compiled template class.
  4. Note the reachability, which is what makes this more than a developer-error report: "`SecurityPolicy` unconditionally allows `{% use %}` regardless of the configured `allowedTags`, so this primitive is reachable from sandboxed templates as well." A deployment that believes it has locked templates down with a strict security policy is still exposed.
  5. Note the execution moment: "The injected code executes within the PHP process when the cache file is first loaded, bypassing the Twig sandbox entirely and achieving remote code execution." So the payload need not survive rendering semantics — it is plain PHP in a file the app includes.
DETECTION SIGNAL: a template engine/compiler that ESCAPES FOR ONE QUOTE CONTEXT and emits into the OTHER (grep the compiler for the escape set `" $ \ NUL TAB` and check whether any interpolation target is single-quoted PHP, single-quoted SQL, or a shell single-quoted argument); a templating feature whose name/identifier argument is caller-controlled and lands in the generated source rather than in data; a feature the framework's own sandbox/policy whitelists unconditionally (`{% use %}`, layout/inheritance names, parent-template names, include paths); any target running a Twig/PHP stack pre-3.26.0 (composer.lock, `SYMFONY_DEPRECATIONS_HELPER`/version headers, error text naming Twig).
CHAIN: an attacker who can influence a template name or `{% use %}` argument (a CMS page/template identifier, a theme name, a multi-tenant "template" field, a plugin-supplied layout name) → the value reaches `ModuleNode::compileConstructor()` with its single quote intact because `Compiler::string()` does not escape `'` → the compiled cache PHP file now contains attacker PHP (escalation: source-level injection into a file the app will `include`) → the first request that loads/regenerates that cache executes the injected code as the PHP-FPM/web user (terminal: RCE, sandbox policy bypassed; one report of this class chains further into the host/CI secrets that the web account can read).
TRANSFERABLE TEST: on any PHP target whose pages are server-rendered, (1) enumerate every parameter that NAMES a template/layout/theme/include/parent (a `?tpl=`, `?theme=`, `?layout=`, `template_id`, `parent`, `use`), (2) inject a value whose syntax is a valid identifier prefix plus a single quote plus a marker: `x';<?php system('id'); ?> //` / `x'; phpinfo();//` / `x';${system('id')}//`, (3) trigger a render (or a cache warm/clear if the app exposes one) and look for the marker in output OR for a newly created file under the template cache directory (`/var/cache/*/twig`, `templates_c`, `cache/twig`) whose bytes contain your marker, (4) read the generated file back through any template-source/local-file-read primitive or watch for command side effects. Rule: **an escaper is only defined by the CONTEXT it is emitted into — diff the escape set against the quote character of the destination literal, and treat any framework feature whose name argument is caller-controlled and whose tag is sandbox-whitelisted as a source-injection sink.**
DEDUPE/DELTA: `CVE-2026-46633`, `Compiler::string`, `ModuleNode::compileConstructor`, `use_template_name`, `SecurityPolicy` = 0 hits across all three write targets. Recorded neighbours REVIEWED and NOT conflated: the ledger's SSTI material (Jinja2/Twig `{{7*'7'}}` fingerprints, the old-Twig `_self.env.registerCallbackListenerCallbackAdd('id','class_exists',…)` gadget, sandbox-policy entries) is EXPRESSION injection inside a template — here there is no expression and no SSTI test needed, the injected bytes land in the generated PHP file itself, and the recorded Tricks-of-the-trade "engine fingerprint" line is unrelated. The recorded "single-quote closes the shell string" and "quote-asymmetry sanitizer bypass" entries (§17.439, §17.445, the `.twig` Live `|replace({'{{':…})` fix entry) are XSS/shell/path-traversal quote asymmetries — DELTA recorded so they are not conflated: same shape (escape one quote, emit into the other), different host language and different sink. NEW atoms: (a) a compiler-level escaper whose escape set matches the wrong destination quote, (b) `{% use %}`/template-NAME as the carrier, (c) the sandbox whitelist making it reachable from hardened deployments.

### §INTAKE-2026-11-23/10 — PRIME AN AUTHENTICATION CACHE WITH ONE GOOD LOGIN AND THE CREDENTIAL CHECK STOPS RUNNING: APACHE SHIRO'S `DefaultLdapRealm`/`JndiLdapRealm` SKIP THE LDAP BIND ON A CACHE HIT WHILE `AllowAllCredentialsMatcher` ACCEPTS ANY PASSWORD (CVE-2026-129349)

SOURCE: https://www.wiz.io/vulnerability-database/cve/cve-2026-129349 (CVE-2026-129349 analysis; disclosed 2026-11-14 by Joshua Rogers, patched same day; CVSS v4.0 9.1 Critical; public Python PoC on GitHub/OSS-Security)  read 2026-11-23
ROUTE: live page via `web_extract` — HTTP 200, overview/technical details/exploitability read in full. Secondary source: the Apache Shiro advisory / GitHub advisory referenced there.
STATUS: UNVERIFIED here (not reproduced — no Shiro/LDAP lab stood up this pass); a public PoC exists and is cited, not executed by us.
CLASS: authentication bypass / improper authentication (CWE-287) → session as ANY cached user, including administrative accounts.
CORE METHOD (as the analysis states it):
  1. Find the config that makes the bug real: "`authenticationCachingEnabled=true` is set on `DefaultLdapRealm` or `JndiLdapRealm`" — a NON-default configuration, which is the precondition to check before claiming anything.
  2. Understand what the cache replaces. "When `authenticationCachingEnabled=true` is set … a successful login populates the authentication cache with the user's credentials. On subsequent login attempts, Shiro retrieves the cached `AuthenticationInfo` and skips the LDAP bind (the actual credential verification against the directory server)."
  3. Find the comparator that is installed by default. "`AllowAllCredentialsMatcher`, which is installed by default in `DefaultLdapRealm`, then accepts any supplied password against the cached info without verification, completing the bypass." The dangerous default matcher is the second half of the chain; caching alone would not be enough if the password were re-compared.
  4. Prime, then reuse. "Exploitation requires network access to the application, knowledge of a valid username, and the target configuration having `authenticationCachingEnabled=true`" — and the PoC's method is exactly "priming the cache with one valid login and then authenticating with arbitrary passwords". One legitimate login (any low-priv account, or a self-registered one) warms the entry; thereafter the SAME username authenticates with any password.
  5. Read the ceiling honestly: the bypass covers users whose credentials are CACHED — i.e. accounts that have logged in since cache enablement/restart. It is not "any username with no prior login", and it is not a signature forgery: the attacker still needs a valid username and, for the first prime, a valid credential.
DETECTION SIGNAL: a Java EE/Spring/Shiro stack (`shiro-core` in the dependency tree; `/WEB-INF/shiro.ini`, `shiro.loginUrl`, JSESSIONID + `rememberMe` cookie shape); a security config exposing `authenticationCachingEnabled`, `cacheManager`, `credentialsMatcher`, `ldapRealm`/`jndiLdapRealm` bean definitions; an auth endpoint whose failure latency collapses for a username after that username has logged in once (cache hit short-circuits a directory round trip); a program asset list naming Apache Shiro or an IdP/portal built on it.
CHAIN: attacker with network reach to the app and one valid (possibly self-registered/lowest-privilege) account (primitive: a real credential exists for SOME principal) → perform ONE legitimate login so the realm caches that principal's `AuthenticationInfo` (primitive: cache priming — the same atom recorded for the MariaDB `acl_get` collision and for web-cache deception, here applied to an AUTHENTICATION decision) → authenticate as a TARGET username that also has a cached entry (an admin or any employee who has signed in since restart) with an arbitrary/wrong password; the LDAP bind is skipped and `AllowAllCredentialsMatcher` accepts it (escalation: authentication with no credential check) → a full authenticated session in that identity (terminal: confidential + integrity impact over everything that account can reach, "potentially including administrative interfaces"; availability not directly impacted).
TRANSFERABLE TEST: on the next target whose auth stack caches credentials (Shiro LDAP/JDBC realms, Spring Security `RequestCache`-adjacent auth caches, any "authentication cache" flag, a reverse-proxy authentication cache, a JWT-with-cached-principal design), (1) fingerprint for `shiro-core`/`authenticationCachingEnabled` in the JS bundle, error text, `/shiro.*` routes or a `shiro.`-prefixed config leak; (2) pick a username you legitimately control, log in successfully, then replay the SAME login with a WRONG password — success on the second attempt is the bypass; (3) do the same for an ADMIN username harvested from a password-reset/enumeration vector (wrong password accepted = win, right password = already win); (4) if caching is keyed per-principal, test whether a SHARED cache slot exists (same realm, same DN pattern) so that one warm principal satisfies another's lookup; (5) time both requests: a large latency drop on the second attempt is the cache-hit signal to look for in logs. Rule: **when authentication is cached, "cached" must mean "the credential was checked once", not "the credential check is skipped" — for every realm/authentication cache, verify that a cache hit still runs the credentials matcher, and that the comparator installed by default is not an allow-all.**
DEDUPE/DELTA: `Apache Shiro`, `DefaultLdapRealm`, `AllowAllCredentialsMatcher`, `authenticationCachingEnabled`, `129349` = 0 hits across all three write targets; `shiro` = 0 hits anywhere. Recorded neighbours REVIEWED and NOT conflated: §INTAKE-2026-11-23/08 (MariaDB `acl_get` AUTHORIZATION-cache key collision — same "warm the cache as one principal, read as another" atom, but there the DECISION is an ACL lookup with no credentials involved; here the cache short-circuits a CREDENTIAL CHECK and the comparator is allow-all) and the ledger's cache-priming entries (web cache deception, authorization-decision caches) — DELTA documented in-entry so the shared atom is not mistaken for a duplicate. Also distinct from the recorded "stale/revoked token regains access" family (there the credential is DELETED, here it is never re-verified). NEW atoms: (a) an authentication cache that skips the credential-verification step rather than re-running it, (b) `AllowAllCredentialsMatcher` as a shipped default, (c) cache-priming as the enabler.
